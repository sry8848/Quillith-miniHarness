# 后台记忆兜底与评测收尾执行

## 1. 最小必要修改

本次只增加一个生产触发源和一条评测同步链：

```text
生产：MemoryBackgroundProcessor 每 5 分钟再次执行现有 runPendingAndThreshold()

评测：WAIT_MEMORY_IDLE
   → 单线程队列中等待此前 Memory 工作
   → 额外执行一次 runPendingAndThreshold()
   → 返回当前 pending 数
   → 仅在 MEMORY_READY 后进入最终问题
```

不复制 extraction/consolidation 流程，不让普通 Turn 等待后台，不增加任务状态机或新配置项。

现有的新 Turn 唤醒、Anthropic Client `maxRetries(2)` 和最后一次 `WAIT_MEMORY_IDLE` 已覆盖正常网络波动。本次不实现跨 Harbor Trial 恢复；极端情况下收尾后仍有 pending，只保留错误与既有 Memory 归档作为诊断证据，待真实发生并确认价值后另立需求。

## 2. 从当前代码推导修改点

### 2.1 生产定时入口

当前问题：失败 task 由 `drainPendingTasks()` 保留，但之后没有新 Turn 时，只能等两小时 maintenance。

代码事实：`MemoryBackgroundProcessor.start()` 先调用 `wake()`，然后只注册两小时 `runTimedMaintenance()`；`wake()` 已经执行 `runPendingAndThreshold()`。

推导与决定：在 `start()` 中增加 5 分钟 `scheduleWithFixedDelay(this::runPendingAndThreshold, ...)`。继续保留：

```java
private void runPendingAndThreshold() {
    if (!memoryEnabled.getAsBoolean()) {
        return;
    }
    drainPendingTasks();
    consolidateWhenThresholdReached();
}
```

不得把 `consolidateWhenThresholdReached()` 移入 `drainPendingTasks()` 的 `for` 循环。两小时 `runTimedMaintenance()` 的 `> 0` 条件保持不变。

### 2.2 有界同步屏障

当前问题：`RECORDED_TURN` 的 `OK` 只证明 `MemoryRuntime.enqueue(...)` 已完成，不能证明后台 extraction 已完成。

代码事实：`MemoryBackgroundProcessor` 使用唯一的单线程 `ScheduledExecutorService`。最后一个 recorded Turn 已经 durable enqueue 并调用 `wake()`，所以随后向同一 executor 提交工作，天然排在此前 wake 之后。

推导与决定：在 `MemoryBackgroundProcessor` 增加同步入口，例如：

```java
/** 执行一次正常 Memory 批次，等待完成后返回仍待处理的任务数。 */
public int runPendingAndWait() {
    Future<Integer> batch = executor.submit(() -> {
        runPendingAndThreshold();
        return workStore.pendingTaskCount();
    });
    try {
        return batch.get();
    } catch (InterruptedException exception) {
        Thread.currentThread().interrupt();
        throw new IllegalStateException("等待后台记忆处理时被中断", exception);
    } catch (ExecutionException exception) {
        throw new IllegalStateException("后台记忆处理批次失败", exception.getCause());
    }
}
```

这里是“一次额外批次后检查”，不是循环到成功。单线程 FIFO 同时保证：

```text
此前正在执行或已排队的 wake
→ 本次显式 runPendingAndThreshold
→ 同一执行器内查询 pending 数
```

不要另写 `retryFailedMemoryTasks()` 或单独的 threshold 检查。

### 2.3 pending 计数归 Memory 存储边界

当前问题：`pendingTasks().size()` 会反序列化全部冻结上下文，只为计数没有必要。

代码事实：`MemoryWorkStore` 已经是 `memory_tasks` 的唯一持久化边界。

推导与决定：在 `MemoryWorkStore.java` 增加 `pendingTaskCount()`，只执行：

```sql
SELECT COUNT(*) FROM memory_tasks
```

沿用现有 `synchronized + inTransaction(...)` 风格，返回 `int`，不修改表结构。

### 2.4 向 Harbor 暴露，不进入普通 Turn

代码事实：`MemoryRuntime` 持有 processor，`AgentSession` 持有 runtime，`HarborRunner` 只持有 session。这正好是现有职责链，不需要新服务或让 Harbor 读取 SQLite。

按顺序增加最薄转发：

```text
MemoryRuntime.runPendingAndWait()
→ MemoryBackgroundProcessor.runPendingAndWait()

AgentSession.waitForMemoryIdle()
→ MemoryRuntime.runPendingAndWait()
```

返回值均为 pending task 数。不要在 `submitInternal()`、`submitRecorded()` 或普通 Harbor `TURN` 中调用它。

### 2.5 扩展 Harbor 单行协议

修改 `HarborRunner.java`：

1. 增加无载荷请求常量 `WAIT_MEMORY_IDLE` 和 `RequestType.WAIT_MEMORY_IDLE`；
2. `decodeRequest()` 像 `NEW_SESSION` 一样直接解析该完整字符串；
3. 在 Turn 计数与 switch 之前处理它；
4. 调用 `agentSession.waitForMemoryIdle()`；
5. pending 为 0 时写 `MEMORY_READY`，否则写 `MEMORY_PENDING <count>`；
6. 在写响应前打印包含 pending 数的完成日志，供归档日志证明最终问题发生在 ready 之后。

伪代码：

```java
if (decodedRequest.type() == RequestType.WAIT_MEMORY_IDLE) {
    int pendingCount = agentSession.waitForMemoryIdle();
    System.out.println("[Harbor Memory Wait Complete, pending=" + pendingCount + "]");
    writeResponse(pendingCount == 0
            ? "MEMORY_READY"
            : "MEMORY_PENDING " + pendingCount);
    continue;
}
```

该命令不是用户 Turn，不增加 `turnNumber`，不触发 recall，不创建 Session。

### 2.6 在 Memory Adapter 中固定调用顺序

修改 `harbor_adapter.py`，在父类协议 helper 附近增加 `_wait_memory_idle()`：

```python
response = await self._exchange(environment, "WAIT_MEMORY_IDLE")
if response == "MEMORY_READY":
    return
if response.startswith("MEMORY_PENDING "):
    pending_count = int(response.removeprefix("MEMORY_PENDING "))
    raise RuntimeError(
        f"memory processing incomplete: {pending_count} pending task(s)"
    )
raise RuntimeError("Quillith Harbor Memory wait 返回未知状态")
```

不在这里重试，不读取数据库，不捕获后继续答题。

在 `QuillithMemoryAgent.run()` 中，把调用放在所有 `sessions` 回放完成之后、cross-session 最终 `NEW_SESSION` 之前：

```python
for session in case["sessions"]:
    ...  # 原有 replay 与 session 间 NEW_SESSION

await self._wait_memory_idle(environment)

if case["memory_scope"] == "cross_session":
    await self._new_session(environment)

answer = await self._answer(environment, case["question"])
```

`QuillithHarborAgent.run()` 和普通用户交互路径不变。

## 3. 测试修改

### 3.1 `MemoryBackgroundProcessorTest.java`

当前没有该测试文件，也没有调度 seam。新增测试文件，并做最小 seam：把 processor 当前内联创建的 executor 移到生产构造函数中；增加一个包内构造函数允许测试传入 `ScheduledExecutorService`。5 分钟和两小时间隔仍是生产常量，不做 CLI/配置项。

使用记录型 `ScheduledThreadPoolExecutor` 子类捕获 `execute` 与 `scheduleWithFixedDelay`，手工运行捕获的任务，不真实等待 5 分钟。至少验证：

1. `start()` 立即提交一次恢复工作；
2. 注册 5 分钟 `runPendingAndThreshold`；
3. 注册两小时 `runTimedMaintenance`；
4. 普通批次先处理完整 pending 快照，批次结束后才以 `>= 5` 判断 consolidation；
5. 两小时 maintenance 在 `unconsolidated_count > 0` 时整理；
6. `runPendingAndWait()` 等待此前排队工作，并在显式批次后返回 0；
7. extraction 再次失败时方法结束并返回非零 pending，而不是循环重试。

涉及模型返回时复用项目已有的 JDK `HttpServer + AnthropicOkHttpClient(baseUrl=本地地址, maxRetries=0)` 测试模式，避免真实网络。
