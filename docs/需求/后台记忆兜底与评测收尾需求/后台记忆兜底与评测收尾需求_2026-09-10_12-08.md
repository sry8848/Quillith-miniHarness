# 后台记忆兜底与评测收尾需求

## 需求目的

在不改变正常 Turn 后台化语义的前提下，补齐两处触发边界：

1. 后台 extraction 失败且此后没有新 Turn 时，每 5 分钟仍有一次自动重试机会；
2. Harbor Memory Eval 回放完历史后，必须确认 extraction 队列已经稳定，再创建最终问题 Session 并答题。

## 已确认行为

### 生产侧

- 新 Turn 继续执行 `enqueue → wake → 后台处理`，用户不等待 Memory。
- 应用启动后继续立即唤醒一次，恢复持久化的 pending task。
- 新增每 5 分钟一次的兜底唤醒，直接复用正常处理入口：

```text
drain 当前批次 pending extraction
→ 当前批次结束
→ unconsolidated_count >= 5 时 consolidate
```

- consolidation 阈值检查必须保留在整批 extraction 结束后，不能移入逐 task 循环。extraction 是高频增量写入，consolidation 是全量模型调用和文件重写，批次边界可以减少重复整理和文件状态冲突。
- 两小时 maintenance 保持原语义：先处理 pending extraction，再在 `unconsolidated_count > 0` 时整理，用于收尾不足 5 条的低增长记忆。

最终触发模型为：

```text
新 Turn                  → 立即 wake
无新 Turn 的失败任务      → 每 5 分钟 wake
批次结束且新增数 >= 5     → consolidate
每 2 小时且新增数 > 0     → consolidate
```

### Harbor Memory Eval 侧

- 增加评测/诊断专用机器命令 `WAIT_MEMORY_IDLE`。
- 该命令排在同一后台单线程中此前已提交的工作之后，再显式执行一次 `runPendingAndThreshold()`，等待本批次结束并检查 pending task 数量。
- pending 为 0 时返回 `MEMORY_READY`；仍有失败任务时返回 `MEMORY_PENDING <count>`。
- `MEMORY_PENDING` 必须终止本次 Trial，记录 `memory processing incomplete`，不得继续最终问题、不得记为 Memory 能力 0 分，也不得在该命令内无限重试。
- 新 Turn 唤醒、单次模型请求的 SDK 重试和本次显式收尾批次已经构成足够的恢复机会；极端情况下仍失败，再根据真实发生频率单独评审，不为假设场景增加恢复框架。
- `MEMORY_READY` 只证明 extraction 队列已经清空。达到 5 条时仍按生产规则尝试 consolidation；不足 5 条不强制整理。consolidation 失败继续保留既有计数和诊断，不伪装成 extraction pending。
- Python 不直接读取 `.memory/memory-work.db` 决定运行时状态；pending 状态由 Java Memory 模块返回。

评测顺序固定为：

```text
单 Session：历史 replay → WAIT_MEMORY_IDLE → ANSWER → Judge

跨 Session：逐 Session replay
          → WAIT_MEMORY_IDLE
          → NEW_SESSION
          → ANSWER
          → Judge
```

## 正式评测验收

实现与便宜验证全部通过后，重新运行已有官方 Case：

- `question_id`：`edced276`
- 类型：`multi-session`
- 问题：`How many days did I spend in total traveling in Hawaii and in New York City?`
- 参考答案：`15 days`

必须保留并报告真实 Agent answer、Judge reward、失败阶段、Trial 结束时 pending task 数，以及日志中 `MEMORY_READY` 先于最终 `ANSWER` 的证据。成功但答错时正常记录 0 分；flush 后仍有 pending 时记录基础设施/后台处理错误。

## 控制边界

- 不修改普通 `AgentSession.submit()` 的异步返回语义。
- 不修改 `MemoryExtractor`、`MemoryConsolidator` 的 streaming 调用和 Anthropic Client `maxRetries(2)`。
- 不新增手写 SDK retry、任务级退避、`attempt_count`、`next_attempt_at`、并发 extraction、模型 fallback、失败状态机、dead letter queue 或新任务框架。
- 不强制 consolidation，不修改 Memory schema。
- 不修改官方题目、历史、参考答案或 Judge，不新增 Case 内断点恢复、跨 Harbor Trial 的 `.memory` 恢复入口或完整 Dataset 批量导入。
