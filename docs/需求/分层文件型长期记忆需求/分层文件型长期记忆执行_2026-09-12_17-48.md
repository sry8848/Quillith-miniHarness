## 4. 最小数据和文件契约

### 4.1 `MemoryDraft`

将 DTO 改为：

```java
public record MemoryDraft(
        String name,
        String description,
        String body
) {
}
```

字段职责：

- `name`：只用于生成近期候选文件名，必须是 kebab-case；
- `description`：单行 canonical description，直接进入文件 frontmatter 和临时根索引；
- `body`：完整 Markdown 正文。

不再保留 `type`。目录结构由整理 Agent 根据实际内容形成，固定 type 会重新引入预设分类。

### 4.2 近期候选文件

文件格式固定为：

```markdown
---
description: 这份文件包含什么
created_at: 2026-09-12T09:48:00Z
updated_at: 2026-09-12T09:48:00Z
---

# 标题

正文
```

frontmatter 固定写 `description`、`created_at` 和 `updated_at`，不写 `name`、`type`、priority 或评分。时间统一使用带时区的 ISO-8601；程序创建近期候选时使用 UTC `Z`。

时间语义固定为：

- 新建文件时，`created_at` 和 `updated_at` 使用同一时刻；
- 修改正文或 canonical description 时保留 `created_at`，把 `updated_at` 改为本次修改时间；
- 仅移动或重命名文件时两个时间都不变；
- 合并多个文件时使用来源中最早的 `created_at`，并把 `updated_at` 改为合并时间；
- 拆分既有文件时，新文件继承来源 `created_at`，并把 `updated_at` 改为拆分时间；
- 新增一份没有既有来源的记忆时，两个时间都使用新建时间。

`index.md` 是派生导航视图，不保存上述 frontmatter；它的变化已经由 Git 记录，不需要因为更新时间产生额外 diff。

### 4.3 目录 description 与 index

- 目录 canonical description 使用该目录内的 `.description.md` 保存；该文件使用与普通记忆相同的 `description/created_at/updated_at` frontmatter 和时间更新规则；
- 根目录始终存在 `index.md`；
- 不是每一级目录都固定创建 `index.md`；
- 当上级 index 折叠某个目录时，被折叠目录必须有自己的 `index.md`，以替代上级省略的子树；
- 当上级 index 已把该目录所需内容完整展开时，不为同一内容保留重复子 index；
- 文件节点在 index 中直接使用该文件 frontmatter 的 canonical description，不在 index 中维护第二份不同摘要。

`recent-unorganized/` 不是特殊旁路，而是普通目录树中的一个天然反例：它通常是少量、近期、异构且尚不能仅凭目录判断用途的内容，不满足“应折叠”的条件，因此整理 Prompt 应明确要求它保持较深曝光。

    List<MessageParam> messages = new ArrayList<>(List.of(
            MessageParam.builder()
                    .role(MessageParam.Role.USER)
                    .content("整理当前 llmwiki；检查近期候选、目录结构、canonical description 和各级 index，完成后用 git diff 自检。")
                    .build()

    agentLoop.run(messages, "");

完整删除 `recall(String query)`。

## 9. 验收标准

完成后必须同时满足：

- `rg "MemoryEntry|MemoryType|MemoryFileParser|MemoryRepository|MemorySelector|MemoryRecallService|MemoryConsolidator" src/main src/test` 无旧实现引用；
- 提取最终 HTTP 请求仍显式包含 `JSON`，并要求 description/body 使用简体中文；
- 新增的提取、整理和记忆导航 Prompt 使用中文，协议标识保持原名；
- 新建记忆文件包含 description、created_at、updated_at，两个时间初始相同且可按 ISO-8601 解析；
- 新候选直接进入 `.memory/llmwiki/recent-unorganized/`，无需等待整理即可从根 index 发现；
- 普通用户回答前没有额外 Selector 模型请求；
- 主 Agent 能使用现有 `read_file/glob` 沿 index 进入正文；
- 整理使用现有 AgentLoop，不存在第二套 loop 或通用 Agent 工厂；
- 整理 Agent 能直接修改整个 llmwiki，程序不复制目录语义；
- AgentLoop 正常结束后由 Java 提交 llmwiki，提交失败不会清零计数；
- `.memory/llmwiki/.git` 不包含外部的 `sessions.db` 和 `memory-work.db`；
- memory off、durable extraction、五分钟重试、五条阈值、两小时维护和等待屏障的既有测试通过；
- 不存在旧记忆自动迁移、索引校验器、自动回滚、Bash 沙盒或其他后置能力。

## 10. 最终自检

执行 AI 提交代码前逐项确认：

1. 是否可以删除某个新增抽象而不损失当前行为？如果可以，删除。
2. 是否复用了现有 AgentLoop、工具、YAML mapper 模式、原子写和调度器？
3. 是否只在固定机械边界写 Java 代码，没有把整理语义复制成程序规则？
4. 是否保留了当前用户已经修改的 JSON/简体中文提示词与对应请求体测试？
5. 是否没有读取、迁移或依赖当前本地旧记忆？
6. 是否没有顺手修改无关代码、文档、SOP 或用户未提交文件？
7. 是否所有异常都在能处理的边界处理，不能处理时直接抛出，没有静默兜底或重复日志？
8. 是否按项目规范为新增/修改方法补充职责、输入、输出注释，并为主要代码块使用有序 what 注释、单独写必要的 why 注释？

如果存在同样正确但更短、更直接的实现，应在不改变本文已确认边界的前提下选择更简单的实现。
