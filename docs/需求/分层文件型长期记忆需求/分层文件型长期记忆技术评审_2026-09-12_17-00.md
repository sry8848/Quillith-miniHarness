## 1. 本次修正

v2 已经确定“提取由程序控制，整理 Agent 直接维护 llmwiki”。在这个前提下继续检查代码后发现，v2 仍然保留了三处旧架构惯性：

1. `MemoryEntry` 只剩从提取 DTO 到文件写入之间的一次转换，不再承担长期领域对象职责；
2. `MemoryRepository` 只剩写近期候选和读根索引，却仍暗示 Java 层管理完整 Memory Domain；
3. Git commit 是确定性动作，却被分给整理 Agent，导致“文件整理完成但模型忘记提交”也会被误判成成功。

本版最终修正为：

- 删除 `MemoryEntry` 和 `MemoryFileParser`；
- `MemoryDraft` 直接交给 `LlmwikiStore.writeRecent()` 落盘；
- 删除 `MemoryRepository`，由极薄的 `LlmwikiStore` 只承担固定机械 I/O；
- 整理 Agent 负责语义整理和使用 Git diff 自检；
- Java 在 AgentLoop 正常结束后统一执行 `git add -A` 和 `git commit`；
- commit 成功才把本次整理视为成功并允许清零整理计数。

除此之外不扩大首期边界。

## 2. 最终架构结论

```text
MemoryRuntime
│
├─ MemoryExtractor
│    当前 Turn
│      ↓
│    必要时补冻结的完整 modelContext
│      ↓
│    List<MemoryDraft>
│
├─ LlmwikiStore
│    ├─ writeRecent(drafts)
│    └─ readRootIndex()
│
├─ MemoryBackgroundProcessor
│    ├─ durable extraction task
│    ├─ 五分钟失败重试
│    ├─ 新增 5 条触发整理
│    └─ 每两小时低频整理
│
└─ MemoryOrganizer
     ├─ 组装现有 AgentLoop
     ├─ Agent 直接整理 llmwiki
     ├─ Agent 使用 git diff 自检
     └─ 程序统一 git add/commit
```

文件系统本身是长期记忆领域模型：

```text
.memory/
├─ sessions.db
├─ memory-work.db（agentHome 与 workspace 相同时）
└─ llmwiki/
   ├─ .git/
   ├─ index.md
   ├─ recent-unorganized/
   └─ 整理 Agent 形成的目录和 Markdown
```

Java 不再建立一套与 llmwiki 平行的完整记忆对象树。

## 3. 从需求到代码的评审过程

### 3.1 主 Agent 如何使用记忆

**当前问题**

partial index 和渐进读取是否需要新的召回服务？

**查看代码**

- `AgentSession.submitInternal()`；
- `MemoryRuntime`；
- `MemorySystemPromptProvider`；
- 父 Agent 的 ToolRegistry 和 `ReadFileTool`。

**代码事实**

1. `AgentSession` 已经在每个 Turn 开始时刷新 SESSION System Prompt。
2. `MemorySystemPromptProvider` 已经能够把根索引常驻注入父 Agent。
3. 父 Agent 已有 `read_file` 和 `glob`，可以根据索引路径继续读取。
4. 当前 `MemorySelector` 和 `MemoryRecallService` 会在主 Agent 运行前额外调用一次模型，并一次性注入最多五条正文。

**推导**

主 Agent 本身已经具备读取和继续推理能力。保留 selector 会重复相关性判断，并无法表达逐层展开。

**当前决定**

- 删除 `MemorySelector` 和 `MemoryRecallService`。
- 删除 `MemoryRuntime.recall()` 和 `AgentSession` 中对应调用。
- 根 `index.md` 仍由 System Prompt Provider 每 Turn 注入。
- 主 Agent 使用现有 `read_file` 按需进入子 index 或正文。
- 不新增记忆专用读取工具。
- 不删除 AgentLoop 通用 `turnContext` 参数；主 Session 在这里传空字符串。

**下一步**

确认规范记忆为什么必须从 `.memory` 运行数据中分离。

### 3.2 原始证据与 llmwiki 的生命周期

**当前问题**

整理 Agent 可以直接操作整个 `.memory` 吗？

**查看代码和工作区**

- `SessionStore`；
- `MemoryWorkStore`；
- 当前 `.memory` 内容；
- 外层 Workspace Git 状态。

**代码事实**

1. `sessions.db` 保存 Session 原始事实。
2. `memory-work.db` 保存后台任务和整理计数。
3. 两者都可能位于 `<agentHome>/.memory/`。
4. 当前 `.memory` 同时混有数据库、`MEMORY.md` 和普通记忆文件。
5. Workspace 本身已经是另一个 Git 仓库。

**推导**

数据库是不可由整理 Agent 改写的运行证据；Markdown 记忆是允许移动、合并和删除的派生知识。两者需要不同的操作边界和 Git 生命周期。

**当前决定**

- `.memory/llmwiki/` 成为规范记忆根和独立 Git 仓库。
- `sessions.db`、`memory-work.db` 等原始证据继续留在 llmwiki 外。
- 整理 Agent 的 workspace 和 gitRoot 都设为 llmwiki。
- 外层 Workspace Git 不负责 llmwiki 内部版本历史。

**下一步**

确认提取阶段需要保留哪些 Java 数据结构。

### 3.3 提取为什么只需要 `MemoryDraft`

**当前问题**

`MemoryEntry` 是否还有独立生命周期？

**查看代码**

- `MemoryDraft`、`MemoryEntry`、`MemoryType`；
- `MemoryExtractor`；
- `MemoryRepository`；
- `MemorySelector`、`MemoryRecallService`、`MemoryConsolidator`；
- 全部生产代码和测试引用。

**代码事实**

1. 当前 `MemoryEntry` 被 Repository、Selector、RecallService 和 Consolidator 共同使用，因此原本是 Java 记忆领域模型。
2. 新方案会删除 Selector、RecallService 和结构化 Consolidator。
3. 整理 Agent 落盘后直接操作文件，不再把规范记忆解析回 `MemoryEntry`。
4. 剩余流程只有 `MemoryExtractor → MemoryDraft → 近期文件`。
5. 现有其他引用只属于即将随旧链路删除或改写的测试与 consolidation probe。

**推导**

继续把 `MemoryDraft` 转成 `MemoryEntry` 不会增加新的可信边界，只会保留一个已经失去领域生命周期的中间对象。以后如果出现明确的程序侧全树读取需求，应针对当时需求建立模型，而不是现在预留。

**当前决定**

- 删除 `MemoryEntry.java`。
- 删除 `MemoryType.java`。
- `MemoryDraft` 字段固定为 `name/description/body`。
- `MemoryExtractor.extract()` 直接返回 `List<MemoryDraft>`。
- 提取响应的数量、空值、重复 name 和文本约束直接在提取器中完成最小校验。
- `LlmwikiStore.writeRecent()` 只检查把 name 映射为安全文件名所必需的规则。

**下一步**

确认 `MemoryFileParser` 是否仍有调用价值。

### 3.4 文件系统成为领域模型后是否还需要 Parser

**当前问题**

程序不再读取规范记忆正文时，是否仍需要通用 Markdown Parser？

**代码事实**

当前 `MemoryFileParser` 只服务 `MemoryRepository.list/read`，用于把 Markdown 重新构造成 `MemoryEntry`。新方案中：

- 主 Agent 用 `read_file` 读取文本；
- 整理 Agent 用文件工具读取文本；
- Java 只读取根 `index.md` 原文；
- Java 写近期候选时已经持有结构化 `MemoryDraft`。

**推导**

没有任何生产链路需要把任意 llmwiki 文件解析成 Java 领域对象。保留 Parser 只会暗示程序仍负责验证整个 wiki。

**当前决定**

- 删除 `MemoryFileParser.java`。
- 写近期候选时直接由 `LlmwikiStore` 序列化固定 frontmatter。
- 根索引直接作为 UTF-8 文本读取，不解析树结构。
- 首期不扫描或验证整理 Agent 生成的其他 Markdown。

**下一步**

把旧 Repository 收缩到真正存在的机械职责。

### 3.5 `MemoryRepository` 为什么应改为 `LlmwikiStore`

**当前问题**

写近期候选和读根索引是否值得继续称为 Memory Repository？

**代码事实**

旧 Repository 负责完整主题的 save/list/read/delete 和索引重建。新方案中，全树修改全部由整理 Agent 使用文件工具完成。Java 只剩：

1. 写入刚提取出的近期候选；
2. 让根 index 立即出现候选；
3. 为 System Prompt 读取根 index。

**推导**

这三个动作是 llmwiki 边界上的少量机械 I/O，不构成完整 Repository 抽象。继续沿用旧名会让后续代码误以为 Java 拥有整个 Memory Domain。

**当前决定**

删除 `MemoryRepository.java`，新增一个极薄的 `LlmwikiStore`：

```java
final class LlmwikiStore {
    List<Path> writeRecent(List<MemoryDraft> drafts);
    Optional<String> readRootIndex();
}
```

不为两个方法再拆分 Writer、Reader、Repository 接口或 Factory。

**下一步**

明确 `writeRecent()` 的最小行为。

### 3.6 候选落盘和立即可见

**当前问题**

整理 Agent 只在达到 5 条或两小时后运行，候选怎样在这之前进入主 Agent 视野？

**需求事实**

1. `recent-unorganized/` 是正式记忆树的一部分。
2. 未整理不等于不可召回。
3. 用户已确认提取程序可以执行一次最小根索引追加。
4. 完整索引结构仍由整理 Agent 负责。

**当前决定**

`writeRecent()` 对每批候选只执行：

1. 确保 `.memory/llmwiki/` 和 `recent-unorganized/` 存在；
2. 使用候选 name 生成不覆盖的 Markdown 文件名；
3. 写入 description frontmatter 和 body；
4. 向根 `index.md` 追加实际路径与 canonical description；
5. 返回实际创建路径，供新增计数和 telemetry 使用。

追加示例：

```markdown
- [recent-unorganized/example.md](recent-unorganized/example.md) — 候选的 canonical description
```

这里不扫描整棵树、不寻找最佳插入位置、不判断折叠、不改子索引，也不修复旧格式。临时追加只保证可发现；下一次整理 Agent 负责恢复完整树形表达。

文件或索引追加失败时直接抛出，原 extraction task 不删除，继续沿用至少一次重放语义。

**下一步**

确认整理是否需要新的 AgentLoop。

### 3.7 整理复用现有 AgentLoop

**当前问题**

整理需要开放式文件操作，现有 AgentLoop 是否可以配置？

**查看代码**

- `AgentLoop` 构造函数；
- `ToolRegistry`；
- `SessionState`；
- `BashTool`；
- `AgentRuntime` 中父 Agent 和 Subagent 的组装。

**代码事实**

1. AgentLoop 构造函数已经注入 SystemPromptManager、SessionState、ToolRegistry、HookRegistry、ContextManager、OutputPrinter、BackgroundTaskScheduler、TurnJournal 和压缩器。
2. ToolRegistry 可以为不同 Agent 注册不同工具集合。
3. SessionState 可以使用独立 workspace、allowedRoots 和 gitRoot。
4. AgentLoop 已支持 NoOpTurnJournal 和不提供 ConversationCompactor。
5. BashTool 的 workspace 只是初始工作目录，并非文件系统沙盒。

**推导**

现有 AgentLoop 已经是可组装的模型工具循环。为了“轻量”复制一个 MemoryAgentLoop 反而会重复流式解析、工具执行和模型轮次控制。

**当前决定**

新增 `MemoryOrganizer` 直接组装现有 AgentLoop，使用：

- llmwiki 专用 SessionState；
- llmwiki 专用 System Prompt；
- 独立 ToolRegistry；
- 已有 `read_file/write_file/edit_file/glob/bash`；
- 空 HookRegistry；
- 静默 StreamOutputPrinter；
- NoOpTurnJournal；
- 不启用 ConversationCompactor；
- 不注册 Task、Skill、MCP 或其他业务工具。

不新增 AgentConfig、AgentProfile、AgentFactory 或 MemoryAgentBase。当前只有一个新增组装点，直接代码最容易理解。

首期接受 Bash 不是硬沙盒，依靠 workspace 和整理 Prompt 约束。硬隔离留待真实失败证明必要后再做。

**下一步**

区分整理 Agent 的语义动作和程序的 Git 动作。

### 3.8 Git commit 为什么由程序执行

**当前问题**

整理 Agent 是否还应执行 `git add` 和 `git commit`？

**代码事实**

1. Agent 必须根据内容判断怎样合并、移动、删除和展开索引。
2. `git add -A` 与固定格式 commit 不需要语义判断。
3. 如果模型忘记 commit，但 AgentLoop 正常结束，BackgroundProcessor 会把整理计数清零。
4. 若再增加“检查是否 commit、工作树是否 dirty、commit 是否完整”的模型行为约束，只会把确定性步骤变成新的概率性失败。

**推导**

文件怎么改由 Agent 决定，正常完成后怎样把所有变化记录为一个版本由程序决定。这符合“模型负责非确定性语义，程序负责确定性动作”。

**当前决定**

整理 Agent 负责：

- 查看根 index 和目录树；
- 按需读取正文；
- 创建、修改、移动、合并、拆分和删除文件；
- 更新目录 description；
- 决定展开深度并维护所有 `index.md`；
- 使用 `git status` 和 `git diff` 检查自己的修改；
- 正常结束并说明整理完成。

`MemoryOrganizer` 在 AgentLoop 正常结束后负责：

```text
git add -A
git commit -m <固定整理提交信息>
```

- commit 成功：`organize()` 返回，BackgroundProcessor 清零整理计数；
- commit 失败：`organize()` 抛出，BackgroundProcessor 记录 WARN 并保留整理计数；
- 首期不自动 reset、clean 或恢复脏工作树。

Git 初始化同样是程序启动 llmwiki 时的确定性动作，不让整理 Agent 每次判断。不要为此单独增加 Initializer 类；放在 `LlmwikiStore` 初始化或 `MemoryOrganizer` 的私有方法中即可。

## 4. 概念逻辑

### 4.1 数据分层

```text
原始运行证据
  Session / extraction task / transcript
  不允许整理 Agent 改写

llmwiki
  目录 / Markdown / description / index / Git history
  允许整理 Agent 重构
```

原始证据回答“真实发生过什么”，llmwiki 回答“未来 Agent 应方便获取什么”。

### 4.2 职责分层

```text
固定动作
  当前 Turn 不足时补完整上下文
  写近期候选
  追加一条根索引
  git add/commit
  → 程序负责

语义动作
  什么值得合并
  应放在哪个目录
  是否过期或删除
  description 如何表达
  哪个目录应折叠
  → 模型/整理 Agent 负责
```

### 4.3 召回

```text
根 index 常驻
  → 主 Agent 产生隐式关联
  → read_file 进入折叠目录 index
  → 必要时继续深入
  → 读取最终正文
```

不再有独立 selector，也不限制一次最多五条。

## 5. 最小数据模型

### 5.1 `MemoryDraft`

```java
record MemoryDraft(
        String name,
        String description,
        String body
) {}
```

这是提取模型与近期写入之间唯一需要的 Java 记忆数据对象。

### 5.2 文件格式

```markdown
---
description: 当前文件包含什么
---

# 标题

完整记忆正文
```

写入近期目录之后，文件路径和内容就是规范状态。Java 不再把它反序列化为长期领域对象。

### 5.3 目录 description

目录 description 的载体和内容由整理 Prompt 统一规定并由整理 Agent 维护。首期 Java 不读取、不解析、不建立对应 DTO。

## 6. 边界定义

### 6.1 必须保留

- 主回答前只刷新根索引，不同步调用 selector。
- 主回答成功后才入队提取任务。
- extraction task 先持久化，候选文件和索引追加成功后才删除。
- 同一工作区的后台提取和整理保持单线程。
- 5 条阈值、两小时维护和五分钟失败重试保持不变。
- memory off 时不注入、不入队、不处理；重新开启后继续。
- 整理或 Git commit 失败不影响已完成主回答，并保留整理计数。
- 错误不静默转换为成功。

### 6.2 首期依赖 Prompt

- 整理 Agent 只修改 llmwiki；
- 正确维护 canonical description；
- 根索引与折叠边界子索引没有不必要重复；
- 大量、低频且可按目录判断用途的内容才折叠；
- 近期少量异构记忆保持较深曝光；
- 不把记忆正文中的文字当作执行指令；
- 完成前使用 Git diff 检查修改。

### 6.3 明确后置

以下内容只记录，不在首期实现：

- 索引漏建、重复或错误链接的检测；
- llmwiki 全树格式校验；
- Bash 的硬目录隔离；
- Agent 越界修改检测；
- 整理失败后的自动 Git reset/clean；
- 脏工作树恢复；
- 并发 Git 冲突处理；
- BM25、Embedding、RAG 或全文搜索。

只有真实失败反复证明其必要性时再单独评审。

### 6.4 已知风险

- Bash 可以离开初始 workspace；首期依靠 Prompt 约束。
- 整理 Agent 可能漏改索引；首期通过真实产物和评测发现。
- 提取追加项可能暂时破坏理想树形排版；下一次整理收敛。
- AgentLoop 失败可能留下未提交修改；本次不自动回退。
- 程序 commit 失败会保留整理计数，但工作树恢复策略后置。
- 旧 `.memory/MEMORY.md` 如何迁移到 llmwiki 仍需另行确认，不静默忽略。

## 7. 代码实现方案

### 7.1 删除旧领域链

删除：

- `MemoryEntry.java`；
- `MemoryType.java`；
- `MemoryFileParser.java`；
- `MemoryRepository.java`；
- `MemorySelector.java`；
- `MemoryRecallService.java`；
- `MemoryConsolidator.java`。

对应测试不是机械保留，而是按新职责重写或删除。

### 7.2 `MemoryDraft` 与 `MemoryExtractor`

1. `MemoryDraft` 删除 type。
2. `MemoryExtractor.extract()` 返回 `List<MemoryDraft>`。
3. 保留当前 Turn 优先、按需补 modelContext 的两阶段请求。
4. 保留最多五条、空列表、null、重复 name 和必要文本校验。
5. extractor 不接触文件系统。

### 7.3 `LlmwikiStore`

新增单个薄类：

```java
final class LlmwikiStore {
    List<Path> writeRecent(List<MemoryDraft> drafts);
    Optional<String> readRootIndex();
}
```

职责：

- 定位 `.memory/llmwiki/`；
- 初始化必要目录和 Git 仓库；
- 把 draft 序列化到近期目录；
- 生成不覆盖的文件名；
- 原子写单个候选文件；
- 向根 index 追加一条直接链接；
- 读取根 index 原始文本。

不负责：

- 枚举完整记忆树；
- 解析整理 Agent 的 Markdown；
- 移动、合并或删除正式记忆；
- 重建 partial tree；
- 校验各级 index；
- 自动修复或回退。

### 7.4 `MemoryOrganizer`

新增：

```java
final class MemoryOrganizer {
    void organize();
}
```

方法内部直接：

1. 使用 llmwiki 路径创建专用 SessionState；
2. 创建专用 ToolRegistry；
3. 注册 `read_file/write_file/edit_file/glob/bash`；
4. 创建专用 SystemPromptManager；
5. 使用空 Hook、静默输出、NoOpTurnJournal 和无压缩器的现有 AgentLoop；
6. 运行一次整理任务；
7. AgentLoop 正常结束后，由 Java 执行 `git add -A`；
8. 由 Java 执行固定信息的 `git commit`；
9. 任一步失败直接抛出。

不新增通用 Agent 工厂或 Git 服务类。只有实际出现第二个相同调用点时再判断是否抽取。

### 7.5 `MemoryBackgroundProcessor`

将：

```java
repository.createNew(extractor.extract(task))
```

改为：

```java
List<Path> createdPaths = llmwikiStore.writeRecent(extractor.extract(task));
```

使用 `createdPaths.size()` 更新计数，并用相对路径记录 telemetry。

整理分支改为：

```java
organizer.organize();
workStore.clearUnconsolidatedCount();
```

`organize()` 包含程序 commit；因此只有 Agent 整理和 Git 提交都成功后才清零。

### 7.6 `MemoryRuntime` 与入口

1. 用 `LlmwikiStore` 替代 `MemoryRepository`。
2. 用 `MemoryOrganizer` 替代 `MemoryConsolidator`。
3. 删除 Selector、RecallService 和 `recall()`。
4. `loadIndex()` 调用 `llmwikiStore.readRootIndex()`。
5. `AgentSession` 不再同步召回，向 AgentLoop 传空 turnContext。
6. `MemorySystemPromptProvider` 指向 llmwiki 根 index，并说明渐进读取方式。
7. 删除 selector 专属 telemetry，保留 extraction 和 organization telemetry。

## 8. 验证方案

### 8.1 提取和近期写入

- 当前 Turn 足够时只请求一次。
- 信息不足时只追加一次冻结 modelContext 请求。
- 提取响应和 Markdown 不再包含 type。
- draft 直接写入近期目录，不经过 MemoryEntry。
- 同名候选不覆盖。
- 根 index 立即追加实际路径和 description。
- 文件或索引追加失败时 extraction task 保留。

### 8.2 主 Agent 召回

- 根 index 每 Turn 注入。
- 普通回答不再出现 selector 模型请求。
- 主 Agent 可以通过 read_file 进入子 index 和正文。
- memory off 时根索引不出现。

### 8.3 整理 Agent

- 使用现有 AgentLoop，没有第二套循环。
- workspace 和 gitRoot 指向 llmwiki。
- 不加载 Task、Skill 或 MCP 工具。
- 能直接移动、合并、删除记忆并维护各级 index。
- 能根据典型正反例正确决定展开深度。
- 不写主 Session history。

### 8.4 Git 边界

- llmwiki 是独立 Git 仓库，数据库不进入其历史。
- Agent 可以查看 status/diff，但不负责 commit。
- AgentLoop 正常结束后程序提交全部 llmwiki 变化。
- commit 成功后才清零整理计数。
- commit 失败时错误可见且计数保留，不执行自动回退。

### 8.5 既有后台语义

- 启动恢复、五分钟重试、整批后阈值整理继续通过。
- 两小时维护在存在未整理记忆时运行 organizer。
- `WAIT_MEMORY_IDLE` 仍只判断 extraction pending。
- 整理失败不破坏已完成的用户回答。

## 10. 最终自检

- `MemoryEntry` 没有真实生命周期，删除。
- `MemoryFileParser` 没有生产读取者，删除。
- `MemoryRepository` 不再假装管理完整领域，替换为两个方法的薄 Store。
- Git commit 是固定动作，由程序执行。
- AgentLoop 已可配置，不复制。
- 没有新增 AgentFactory、配置体系、索引校验器、自动恢复或全树 DTO。
- 每个保留组件都能直接映射到三条必要链路之一：候选立即可见、整理 Agent 自由操作、主 Agent 渐进读取。
