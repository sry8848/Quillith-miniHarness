## 1. 本次评审修正

上一版评审原本计划让整理模型返回完整目标树，再由 `MemoryRepository` 校验并发布目录、文件和索引。继续讨论后发现，这会让程序重新实现一套文件变更协议：模型需要表达创建、移动、合并、删除和折叠，程序还要负责动作顺序、冲突和索引生成。这与“整理模型负责维护整个长期记忆知识库”的需求不一致，也扩大了首期程序边界。

本版改为：

- 提取继续使用受程序控制的两阶段结构化模型调用，不使用 AgentLoop；
- 整理复用现有 AgentLoop，由整理 Agent 直接操作独立的 llmwiki Git 仓库；
- 整理 Agent 自己维护目录、记忆正文、目录 description 和各级 `index.md`；
- 程序不重新生成或语义校验整理 Agent 的索引；
- 提取后只执行一次最小根索引追加，保证候选在整理前已经可见；
- 首期优先验证整理 Prompt 和 Agent 行为，不增加索引修复、自动 Git 回退、Bash 沙盒或脏工作树恢复。

## 2. 评审结论

现有记忆系统的外层生命周期继续保留：

```text
用户 Turn 开始
  → 刷新 SESSION System Prompt
  → 注入 llmwiki 根 index.md
  → 主 Agent 使用已有工具按需读取子 index 或正文

用户 Turn 成功结束
  → 持久化 extraction task
  → 后台提取候选
  → 写入 recent-unorganized/
  → 最小追加根 index.md
  → 达到 5 条或两小时条件后运行整理 Agent
  → 整理 Agent 直接修改 llmwiki 并提交 Git
```

保留现有：

- `AgentSession` 回答成功后异步入队；
- `MemoryWorkStore` 的 durable task 和至少一次执行；
- 单线程后台串行；
- 5 个新增文件触发整理；
- 每两小时存在未整理记忆时整理；
- 每五分钟重试失败 extraction task；
- `WAIT_MEMORY_IDLE` 只等待 extraction 队列清空；
- 记忆开关和主回答不等待后台处理的语义。

删除现有：

- 扁平 `.memory/*.md` 记忆布局；
- `MEMORY.md`；
- 四种固定 `MemoryType`；
- 主回答前的 `MemorySelector` side-query；
- `MemoryRecallService` 一次性正文注入；
- 整理模型的全量 `MemoryBatch` 返回和程序侧全量替换。

## 3. 从需求到代码的推导

### 3.1 主 Agent 的召回入口

**当前问题**

根索引和渐进召回应当接入现有哪条调用链？

**查看代码**

- `AgentSession.submitInternal()`；
- `MemoryRuntime`；
- `MemorySystemPromptProvider`；
- `ReadFileTool` 与父 Agent ToolRegistry。

**代码事实**

1. `AgentSession` 每轮已经刷新 SESSION 级 System Prompt。
2. `MemorySystemPromptProvider` 已经负责把根记忆索引放入父 Agent 的 System Prompt。
3. 父 Agent 已注册 `read_file`、`glob` 和 Bash 等通用工具。
4. 当前额外调用 `memoryRuntime.recall(query)`，通过 selector 预选最多五条正文后才进入 AgentLoop。

**推导**

新需求要求主 Agent 根据常驻 partial tree 自行决定是否深入。继续保留 selector 会形成另一套独立推理链，并阻止主 Agent根据工具读取结果继续导航。

**当前决定**

- 根索引仍由 `MemorySystemPromptProvider` 注入。
- 删除同步 `memoryRuntime.recall(query)`。
- 主 Agent 使用已有 `read_file` 读取子 `index.md` 或正文。
- 不新增记忆专用读取工具。
- `AgentLoop.turnContext` 是通用能力，其他调用仍可能使用，不因本需求删除；主 Session 传空字符串。

**下一步**

确认 llmwiki 为什么必须与现有 `.memory` 运行数据分开。

### 3.2 原始运行证据与 llmwiki 分离

**当前问题**

可以直接把现有 `.memory` 初始化成 Git 仓库吗？

**查看代码与工作区状态**

- `SessionStore`；
- `MemoryWorkStore`；
- 当前工作区 `.memory`；
- 外层 Git 仓库状态。

**代码事实**

1. `SessionStore` 把 `sessions.db` 放在 `<agentHome>/.memory/`。
2. `MemoryWorkStore` 把 `memory-work.db` 放在 `<agentHome>/.memory/`。
3. 当前 `.memory` 同时存在索引、记忆正文和 `sessions.db`。
4. 当前 Workspace 本身已经是 Git 仓库。

**推导**

Session 数据库和后台任务数据库是原始运行证据及运行状态，不属于整理 Agent 可以合并、移动和删除的 llmwiki。直接让整个 `.memory` 成为整理仓库会混淆两种数据职责，也会让 Git diff 持续包含数据库变化。

**当前决定**

规范记忆根目录改为：

```text
.memory/
├─ sessions.db
├─ memory-work.db（agentHome 与 workspace 相同时）
└─ llmwiki/
   ├─ .git/
   ├─ index.md
   ├─ recent-unorganized/
   └─ 整理 Agent 形成的其他目录和 Markdown
```

`.memory/llmwiki/` 是独立 Git 仓库，也是整理 Agent 的 workspace 和 gitRoot。外层 `.memory` 数据不进入整理 Agent 的工作范围。

**下一步**

确认提取阶段为何不需要 AgentLoop。

### 3.3 提取仍由程序控制

**当前问题**

提取模型只看当前 Turn，但有时需要完整上下文，是否需要为此建立 AgentLoop？

**查看代码**

- `MemoryExtractor.extract()`；
- `MemoryExtractionDecision`；
- `MemoryExtractionTask`；
- `MemoryBackgroundProcessor.drainPendingTasks()`。

**代码事实**

1. 当前第一轮请求只提交 `turnContext`。
2. 模型可以通过 `needModelContext` 表示信息不足。
3. 需要时程序用同一任务冻结的 `modelContext` 发起第二次结构化请求。
4. 提取器只返回候选，真正写文件发生在 BackgroundProcessor 调用 Repository 时。

**推导**

提取阶段只有两个固定动作：“请求完整上下文”和“新增近期候选”。它不需要自由探索文件系统，也没有多轮开放式决策。现有结构化选择已经等价于一个由程序执行的受限工具，不需要引入 AgentLoop。

**当前决定**

- 保留现有两阶段提取结构。
- 第一阶段只看当前 Turn；需要时第二阶段读取冻结 modelContext。
- 模型输出只包含 `name/description/body`，删除固定 type。
- 程序把通过基本字段校验的候选写入 `llmwiki/recent-unorganized/`。
- 重名继续追加 `-2`、`-3`，保留现有至少一次重放语义。

**下一步**

解决整理前新候选如何进入主 Agent 可见索引。

### 3.4 提取程序只做最小索引追加

**当前问题**

整理 Agent 仍按 5 条或两小时触发，在它运行前如何避免新候选失忆？

**需求事实**

1. `recent-unorganized/` 是规范记忆树的一部分，不是召回之外的暂存区。
2. 新候选落盘后必须立即可见。
3. 整理 Agent 才负责完整目录树和索引结构。
4. 用户已确认允许提取程序执行一次最小的近期目录索引追加。

**推导**

提取程序无需理解完整树，也不应重新判断展开深度。它只需把刚创建文件的直接路径和 canonical description 追加到根 `index.md`，保证主 Agent可以发现该候选。这个临时条目允许不处在整理后的最佳树形位置；下一次整理 Agent 会统一修正。

**当前决定**

每个成功创建的候选执行一次简单追加：

```markdown
- [recent-unorganized/example.md](recent-unorganized/example.md) — 候选的 canonical description
```

具体规则：

- 根 `index.md` 不存在时，创建后再追加；
- 只追加本次实际创建的文件，不扫描或重建其他索引；
- 不移动已有索引内容；
- 不判断 `recent-unorganized/` 是否应该折叠；
- 不解析和修复整理 Agent 已有的树形结构；
- 同名重放生成了新文件时，按新路径追加新条目；
- 文件写入或索引追加失败时，沿用现有 extraction task 保留重试语义。

该追加的职责是“让新文件可发现”，不是“完成整理”。

**下一步**

确认整理阶段是否需要重写 AgentLoop。

### 3.5 整理直接复用现有 AgentLoop

**当前问题**

整理 Agent 需要自由读取和修改目录，现有 AgentLoop 能否配置，还是必须重写？

**查看代码**

- `AgentLoop` 构造函数；
- `ToolRegistry`；
- `SessionState`；
- `AgentRuntime` 中父 Agent/Subagent 的组装方式；
- `BashTool`。

**代码事实**

1. `AgentLoop` 构造函数接收独立的 `SystemPromptManager`、`SessionState`、`ToolRegistry`、HookRegistry、ContextManager、OutputPrinter、BackgroundTaskScheduler 和最大轮次。
2. `ToolRegistry` 可以按 Agent 实例注册不同工具。
3. `SessionState` 可以指定独立 workspace、allowedRoots 和 gitRoot。
4. AgentLoop 已提供使用 `NoOpTurnJournal`、不启用 ConversationCompactor 的构造方式。
5. `BashTool.workspace` 只是进程初始工作目录，代码明确说明它不是文件系统沙盒。

**推导**

现有 AgentLoop 已经具备依赖注入边界，可以装配第三种 Agent；不需要复制或重写模型工具循环。首期只需新增一个整理 Agent 的组装入口和专用 System Prompt。

**当前决定**

整理 Agent 使用：

- 现有 `AgentLoop`；
- workspace：`.memory/llmwiki/`；
- gitRoot：`.memory/llmwiki/`；
- 独立的 `SessionState`；
- 独立 `ToolRegistry`；
- 已有 `read_file`、`write_file`、`edit_file`、`glob` 和 `bash`；
- 空 HookRegistry；
- 静默 StreamOutputPrinter；
- NoOpTurnJournal；
- 不启用 ConversationCompactor；
- 不注册 Task、Skill、MCP、后台 Bash 等与整理无关的能力。

首期 Bash 仅通过 workspace 和整理 Prompt 约束，不新增硬沙盒。这个限制明确记录为已知边界，不伪装成 allowedRoots 已经能够限制 Bash。

**下一步**

确认整理 Agent 的实际工作和 Git 职责。

### 3.6 整理 Agent 直接维护 llmwiki

**当前问题**

模型与程序分别负责哪些动作？

**代码事实**

当前 `MemoryConsolidator` 把全部正文放进一次模型请求，并要求模型返回完整 `MemoryBatch`；程序再逐条 save/delete。它不能让模型根据局部读取结果继续判断，也不能自然表达目录整理。

**推导**

整理本身是一个文件工作任务。AgentLoop 已经能够在每轮工具结果后继续推理，Git 又能展示最终文件差异，因此最直接的方案是让 Agent 完成实际编辑，而不是把编辑重新编码成 DTO。

**当前决定**

整理 Agent 负责：

- 查看根 `index.md` 和当前目录树；
- 按需读取近期候选和既有记忆正文；
- 创建、重命名、移动或删除目录；
- 创建、更新、合并、拆分、移动或删除记忆文件；
- 更新文件 frontmatter 的 canonical description；
- 维护目录 description；
- 决定目录展开深度；
- 创建、修改或删除折叠边界的子 `index.md`；
- 维护根 `index.md`；
- 使用 Git 查看 diff；
- 完成整理后提交本次 llmwiki 变更。

程序只负责：

- 按原有阈值启动整理 Agent；
- 为它创建独立运行上下文和工具集合；
- 将 Agent 正常返回视为本次整理完成；
- 成功后清零 `unconsolidatedCount`；
- AgentLoop 抛出异常时沿用后台 WARN 和下次重试语义。

首期不增加程序侧的最终索引检查、文件树检查、Git clean 检查或自动恢复。整理质量由 Prompt、真实产物和评测验证。

## 4. 概念逻辑

### 4.1 两种长期数据

```text
原始运行证据
  sessions.db / memory-work.db / transcript
  用于恢复、审计和重新分析
  不允许整理 Agent 修改

llmwiki
  Markdown、目录、description、index.md、Git 历史
  是主 Agent 使用的长期记忆层
  允许整理 Agent 重构
```

原始证据解决“过去真实发生过什么”，llmwiki 解决“哪些信息值得让未来 Agent 方便使用”。两者不能混在同一个可整理仓库中。

### 4.2 提取与整理的不同执行形态

```text
提取：固定选择
  当前 Turn 是否足够？
  → 必要时补完整上下文
  → 输出候选

整理：开放式文件任务
  读取 → 判断 → 修改 → 再读取 → 再判断
  → Git diff → 提交
```

提取不使用 AgentLoop是因为动作集合固定；整理使用 AgentLoop是因为后续动作取决于刚读取的文件和当前目录状态。

### 4.3 索引责任

- 提取程序只追加刚生成候选的直接链接，保证即时可见。
- 整理 Agent 对索引的完整结构和正确性负责。
- 主 Agent 始终只常驻看到根 `index.md`。
- 折叠后通过子 `index.md` 渐进披露。
- 首期不增加第二套程序逻辑去证明整理 Agent 是否正确完成索引维护。

## 5. 模型设计

### 5.1 候选 DTO

```java
record MemoryDraft(
        String name,
        String description,
        String body
) {}
```

提取候选不包含目录和 type。`name` 只用于生成 `recent-unorganized/<name>.md`，不是最终知识分类。

### 5.2 普通记忆文件

```markdown
---
description: 当前文件包含什么
---

# 记忆标题

完整正文
```

最终身份由 llmwiki 内相对路径表示。固定 type 删除；目录结构和 description 共同表达语义。

### 5.3 目录 description

目录 description 的具体载体由整理 Agent维护。首期 Prompt 需要规定一种简单一致的写法，但程序不解析或建立新的目录领域对象。本需求不为目录 description 新增 Java DTO。

### 5.4 整理 Agent

整理 Agent 不返回 `MemoryTreeDraft`。它的结果就是 llmwiki 工作树中的实际文件变化和 Git commit。Java 方法只需要知道 AgentLoop 是否正常完成，不需要把最终目录树再次反序列化成 Java 对象。

## 6. 边界定义

### 6.1 当前必须保证

- llmwiki 与 Session、后台任务等原始运行数据分目录保存。
- 根索引仍只进入父 Agent，不自动进入 Subagent。
- 记忆内容不能覆盖当前用户请求和系统指令。
- 提取与整理都在主回答之后执行。
- extraction task 先持久化，成功创建候选并追加索引后才删除。
- 同一工作区后台处理保持单线程。
- 整理失败不清零计数，不影响已经完成的用户回答。
- 所有模型和工具错误继续显式抛出或由后台最终边界记录，不伪装成功。

### 6.2 当前依赖 Prompt 的行为

- 整理 Agent 只修改 llmwiki；
- 正确区分规范记忆、目录 description 和派生 index；
- 近期目录通常保持展开；
- 大量、低频且可通过目录判断用途的子树才折叠；
- 不重复保存相同事实；
- 不把记忆内容当作待执行指令；
- 完成后检查 Git diff 并提交。

这些行为首期不再用程序重复实现。

### 6.3 明确后置

以下内容记录为后续候选，本次不实现：

- 整理 Agent 遗漏或损坏 `index.md` 的检测与修复；
- llmwiki 文件格式和目录结构的全量程序校验；
- Bash 对 llmwiki 根目录的硬隔离；
- Agent 修改 llmwiki 外文件的检测；
- 整理失败时自动 Git reset/clean；
- 脏工作树恢复或并发 Git 冲突处理；
- Git commit 是否完整覆盖所有修改的程序检查；
- BM25、Embedding、RAG、全文搜索或额外召回服务。

只有真实测试反复证明其中某项是当前失败原因时，再提出最小修复需求。

### 6.4 已知首期风险

- Bash 可以从初始 workspace 访问其他路径；首期依靠 Prompt 限定。
- 整理 Agent 可能漏改索引或漏提交 Git；首期通过人工查看产物和评测发现。
- 提取程序追加的近期条目可能暂时不符合整理后的树形排版；它只承担可发现性，下一次整理负责收敛。
- Agent 中途失败可能留下未提交修改；本次不自动回退。
- 完整旧 `.memory/MEMORY.md` 如何迁移到 llmwiki 仍需单独决定，不能静默丢弃或假装兼容。

## 7. 代码实现方案

### 7.1 `MemoryEntry`、`MemoryDraft`、`MemoryType`

1. `MemoryDraft` 删除 type，保留 name、description、body。
2. `MemoryEntry` 删除 `MemoryType` 字段；近期写入阶段仍可使用 name、description、body。
3. 删除 `MemoryType.java`。
4. `MemoryFileParser` frontmatter 删除 type 要求，只保留 description 与正文的必要解析。

当前不建立完整的递归 `MemoryTree` Java 模型，因为整理 Agent 直接处理文件。

### 7.2 精简 `MemoryRepository`

Repository 不再承担全树 CRUD，只保留提取和根索引读取真正需要的能力：

```java
List<MemoryEntry> createRecent(List<MemoryEntry> candidates);
String readRootIndex();
```

`createRecent()`：

1. 创建 `.memory/llmwiki/recent-unorganized/`；
2. 为候选生成不覆盖的安全文件名；
3. 原子写入普通记忆 Markdown；
4. 向 `.memory/llmwiki/index.md` 追加实际文件路径和 description；
5. 全部成功后返回实际创建条目。

删除现有 `list/read/save/delete/rebuildIndex` 作为整理协议的用途。整理 Agent 通过文件工具直接操作，不绕回 Repository。

### 7.3 `MemoryExtractor`

1. 保留现有 `needModelContext` 两阶段请求。
2. 删除 type Prompt 和 DTO 字段。
3. 保留最多五条、空列表、重复 name 和结构化响应检查。
4. 返回候选后不访问 llmwiki。

### 7.4 新增整理 Agent 组装

新增 `MemoryOrganizer`，职责仅为创建并运行现有 AgentLoop：

```java
final class MemoryOrganizer {
    void organize();
}
```

它负责：

1. 确保 `.memory/llmwiki/` 和内部 Git 仓库已经初始化；
2. 创建 llmwiki 专用 SessionState；
3. 创建只包含当前所需工具的 ToolRegistry；
4. 创建专用 SystemPromptManager；
5. 使用静默输出、空 Hook、NoOpTurnJournal 和独立 BackgroundTaskScheduler 组装 AgentLoop；
6. 以一次明确的整理任务运行 AgentLoop；
7. 正常结束后返回；异常直接抛给 BackgroundProcessor。

不要复制 AgentLoop，不抽象新的通用 AgentFactory。当前只有一个新增调用点，直接组装更容易看清真实依赖。

### 7.5 替换 `MemoryConsolidator`

现有 `MemoryConsolidator` 的“读取全量记忆 → 结构化模型返回 → Repository 全量替换”全部删除。

可以直接删除该类并由 `MemoryOrganizer` 替代，也可以保留 `consolidate()` 名称作为后台调用适配；优先直接改名，避免类名继续暗示它只是一次无工具模型归纳。

### 7.6 `MemoryBackgroundProcessor`

- extraction 分支改为调用 `repository.createRecent(extractor.extract(task))`；
- consolidation 分支改为调用 `organizer.organize()`；
- 成功后仍清零 `unconsolidatedCount`；
- 异常仍在后台边界记录 WARN 并保留计数；
- 队列、五分钟重试、5 条阈值和两小时维护不修改。

### 7.7 删除同步召回

1. 删除 `MemorySelector.java`。
2. 删除 `MemoryRecallService.java`。
3. `MemoryRuntime` 删除 selector、recall service 和 `recall()`。
4. `AgentSession` 不再调用 memory recall，向 AgentLoop 传空 turnContext。
5. `MemorySystemPromptProvider` 改读 `.memory/llmwiki/index.md`，说明可用 `read_file` 逐层进入。
6. 删除 selector 的 `recordMemorySearch()`；提取和整理 telemetry 保留。

## 8. 验证方案

### 8.1 提取

- 当前 Turn 足够时只调用一次模型。
- 当前 Turn 不足时只追加一次冻结 modelContext 请求。
- type 不再出现在请求或响应中。
- 候选写入 `recent-unorganized/`，重名不覆盖。
- 新文件成功后，根 `index.md` 立即出现直接路径和 canonical description。
- 文件或索引追加失败时 task 不删除。

### 8.2 整理 Agent 组装

- 使用的类仍是现有 `AgentLoop`，不存在复制的模型工具循环。
- SessionState.workspace 和 gitRoot 指向 llmwiki。
- ToolRegistry 只包含确定提供给整理 Agent 的工具。
- System Prompt 是整理专用内容，不加载父 Agent 身份、Skill 或 MCP。
- 整理运行不写主 Session history。

### 8.3 整理行为

首期使用小型真实目录验证 Prompt，而不是编写程序语义校验器：

- 近期文件被移动到自然目录；
- 重复事实被合并；
- 过期事实可以删除或下沉；
- 大量可按目录识别的内容被折叠；
- 近期少量异构内容保持展开；
- 折叠目录生成子 `index.md`；
- 展开目录不保留重复子索引；
- 根 index 使用文件 canonical description；
- Git diff 能完整展示整理变更；
- Agent 完成后产生整理 commit。

这些是 Prompt/Agent 验收，不在首期转换成另一套 Java 规则。

### 8.4 现有生命周期

- 主回答不再产生 selector 模型请求。
- 根索引每 Turn 仍刷新。
- memory off 不注入、不入队、不处理。
- 5 条阈值、两小时维护、五分钟重试和 WAIT_MEMORY_IDLE 继续通过。
- 整理 Agent 失败不影响已完成主回答，并保留整理计数。

## 10. 最终回看

```text
需求
  → 主 Agent 对增长的长期记忆保持分层感知

入口
  → 每轮只注入 llmwiki/index.md

形成
  → 两阶段提取模型 + 程序写近期文件 + 最小索引追加

  → 复用现有 AgentLoop，直接编辑 llmwiki

版本
```
