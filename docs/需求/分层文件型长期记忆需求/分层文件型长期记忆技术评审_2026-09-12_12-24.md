# 分层文件型长期记忆技术评审

- 文档类型：技术评审
- 编写时间：2026-09-12 12:24
- 当前状态：评审完成，待执行文档
- 对应需求：`分层文件型长期记忆需求_2026-09-11_14-11.md`
- 评审范围：现有 Quillith 记忆代码到分层文件树、partial index 和渐进召回的最小改造

## 1. 评审结论

现有记忆系统的外层生命周期可以保留：`AgentSession` 仍在主回答前刷新 Session System Prompt，在主回答成功后将提取工作持久化并交给单线程后台处理；`MemoryWorkStore` 的至少一次任务、5 个新增文件触发整理、两小时低频整理以及五分钟失败任务重试都不需要重做。

需要替换的是 memory 模块内部的四个假设：

1. 记忆身份由根目录下的唯一 `name` 表示；
2. 每条记忆必须属于四种固定 `MemoryType`；
3. `MEMORY.md` 必须列出全部根级主题；
4. 主回答前必须由独立 `MemorySelector` 从扁平目录中最多选择五条正文。

目标实现采用下面的最小链路：

```text
Session 开始
  → System Prompt 只注入 .memory/index.md
  → 主 Agent 根据 partial tree 自行判断
  → 必要时使用已有 read_file 读取子 index.md 或正文

Session 成功结束
  → 持久化 extraction task
  → 提取模型只产生 name、description、body 候选
  → 仓库写入 .memory/recent-unorganized/
  → 沿现有折叠边界重新渲染 index.md，使候选立即可见
  → 达到既有阈值后，整理模型返回完整目标树和折叠目录集合
  → 仓库发布规范文件树，并从 canonical description 重新渲染索引
```

整理模型负责目录语义、记忆去留和折叠判断。程序不重新判断“什么重要”，也不引入评分器、索引状态机或语义校验器；程序只负责模型输出的基本结构、路径安全、文件发布和 canonical description 的机械复制。

## 2. 从需求到代码的评审过程

### 2.1 先找一轮请求的记忆入口

**当前问题**

新需求是否要求改变主 Agent 的 Turn 生命周期，还是可以只替换记忆模块内部实现？

**查看代码**

- `AgentSession.submitInternal()`；
- `AgentRuntime` 中父 Agent 和 MemoryRuntime 的装配；
- `MemoryRuntime`；
- `MemorySystemPromptProvider`。

**代码事实**

1. `AgentSession` 在接受用户输入后先刷新 SESSION System Prompt，再调用 `memoryRuntime.recall(query)`，最后进入 `AgentLoop`。
2. 主回答成功后，`AgentSession` 调用 `memoryRuntime.enqueue(turnContext, modelContext)`；入队或后台处理失败不会撤销主回答。
3. `MemorySystemPromptProvider` 是父 Agent 的 SESSION 级 Provider，每轮读取一次根索引；Subagent 没有注册该 Provider。
4. `MemoryRuntime` 已经是记忆开关、索引读取、同步召回和后台处理的统一入口。

**推导**

新需求仍要求“每轮看到根索引”和“回答后后台提取”，因此现有刷新、入队和后台时序已经满足需求。真正不再需要的是进入 `AgentLoop` 前的同步 selector 召回。

**当前决定**

- 保留 `AgentSession → MemoryRuntime → MemoryBackgroundProcessor` 外层依赖。
- 删除 `AgentSession` 对 `memoryRuntime.recall(query)` 的调用。
- `AgentLoop` 现有 `turnContext` 是通用临时上下文能力，TaskTool 也在复用，不因本需求删除；主 Session 暂时传空字符串。
- `MemoryRuntime` 删除 selector 和 recall service 的装配及 `recall()` 方法，只保留索引、入队、开关和后台屏障。

**下一步**

确认当前领域模型和仓库把扁平结构固化到了什么程度。

### 2.2 确认扁平存储的真实约束

**当前问题**

分层目录是否只需让仓库递归扫描，还是会改变领域身份和文件协议？

**查看代码**

- `MemoryEntry`；
- `MemoryType`；
- `MemoryFileParser`；
- `MemoryRepository`。

**代码事实**

1. `MemoryEntry.name` 同时承担领域身份、根目录文件名和召回键，不能表达两个目录下的同名文件。
2. `MemoryType` 封闭为 `user/feedback/project/reference`，解析和模型输出都强制提供。
3. `MemoryFileParser` 只允许 `name/description/type` 三个 frontmatter 字段，并要求文件名等于 `name + ".md"`。
4. `MemoryRepository.list()` 只扫描 `.memory` 第一层的 `*.md`。
5. 每次 `save()` 或 `delete()` 都扫描全部根级主题并重建单个 `MEMORY.md`。

**推导**

目录层级已经成为记忆身份的一部分，继续以 `name` 作为唯一键会丢失路径信息。固定类型也与“目录结构自然表达分类”的需求冲突。因此不能只增加递归扫描；必须把领域身份改为记忆根目录内的相对路径，并移除 `MemoryType`。

**当前决定**

- `MemoryEntry` 改为 `relativePath + description + body`。
- frontmatter 只保存 canonical `description`；文件名和父目录共同构成身份，不在 frontmatter 重复保存 name。
- 删除 `MemoryType`。
- 路径的每个目录段和文件 basename 继续采用现有安全名称约束，禁止绝对路径、`..`、索引保留名和 Windows 设备名。
- 仓库递归管理记忆 Markdown，但明确排除 `index.md` 和目录元数据文件。

**下一步**

确认现有召回协议能否承担逐层导航。

### 2.3 确认渐进召回的执行者

**当前问题**

应该把 `MemorySelector` 改造成递归选择器，还是让主 Agent 使用已有工具自行导航？

**查看代码**

- `MemorySelector`；
- `MemoryRecallService`；
- `ReadFileTool`；
- `AgentRuntime` 的父 Agent ToolRegistry。

**代码事实**

1. `MemorySelector` 只接收一次扁平 catalog，并返回最多五个整数下标。
2. `MemoryRecallService` 在主循环开始前一次性读取全部选中正文，无法根据正文或子索引继续推理。
3. 父 Agent 已经注册通用 `read_file`，可以读取工作区内的 `.memory/...` 文本文件，且只读操作不需要审批。
4. 根索引已经由 System Prompt Provider 常驻注入父 Agent。

**推导**

如果继续使用 selector，就必须额外构造多轮“选择子索引—读取—再选择”的第二套 Agent 循环。这既重复主 Agent 已有推理能力，也会让每轮回答继续支付同步 side-query 延迟。已有 `read_file` 已经提供需求所需的渐进读取能力。

**当前决定**

- 删除 `MemorySelector` 和 `MemoryRecallService`。
- 根 `index.md` 使用工作区相对路径指向子索引和记忆文件。
- `MemorySystemPromptProvider` 只说明索引是历史信息、折叠目录可以通过 `read_file` 按需深入；不预先加载正文。
- 主 Agent 读取记忆正文时产生普通 `tool.execute read_file` 轨迹，不再保留虚构的 `memory.recall/search_memory` 模型调用。

**下一步**

确认新候选的首次落点和既有后台调度能否复用。

### 2.4 确认提取和后台调度边界

**当前问题**

“近期未整理记忆”是否需要新的任务系统，候选写入后如何保持现有至少一次语义？

**查看代码**

- `MemoryExtractor`、`MemoryDraft`、`MemoryBatch`；
- `MemoryBackgroundProcessor`；
- `MemoryWorkStore` 及其测试。

**代码事实**

1. `MemoryExtractor` 已经只返回候选，不直接读取或修改文件。
2. `MemoryBackgroundProcessor.drainPendingTasks()` 在提取成功后调用 `repository.createNew()`，随后才删除任务并累计新增数。
3. 文件写入与 SQLite 完成标记不是跨资源事务；中断后允许重放并产生短期重复。
4. 5 个新增文件阈值、两小时维护和五分钟失败任务重试都围绕 `unconsolidatedCount` 工作，与文件是否位于根目录无关。

**推导**

新需求不需要新的候选表或第二套暂存机制。只要把 `createNew()` 的固定目标改成 `recent-unorganized/`，原有任务恢复和计数语义就能继续成立。

**当前决定**

- `MemoryDraft` 删除 `type`，继续保留提取模型给出的安全 `name`、description 和 body。
- `repository.createRecent()` 在 `.memory/recent-unorganized/` 下创建不覆盖同名文件的新候选。
- 重放时继续使用 `-2`、`-3` 后缀保留至少一次语义，后续整理负责合并。
- `recent-unorganized` 是固定写入入口，不是固定业务分类；其内容从落盘开始就是规范记忆。
- `MemoryWorkStore` 表结构和调度计数不修改。

**下一步**

解决“候选立即可见，但整理模型低频运行”的索引同步问题。

### 2.5 推导索引维护方式

**当前问题**

候选文件写入后，如果不立即调用整理模型，如何让它马上出现在 partial index 中，同时避免程序重新判断展开优先级？

**查看代码**

- `MemoryRepository.save/createNew/rebuildIndex/readIndex()`；
- 需求确定的折叠边界索引规则。

**代码事实**

1. 当前仓库已经在每次文件保存后机械重建派生索引。
2. 新需求要求整理模型决定折叠边界，但 canonical description 不能由索引另行总结。
3. 一个目录是否拥有自己的 `index.md`，本身已经能够表示它是否在父级被折叠：存在表示折叠，不存在表示由最近的上级索引继续展开。

**推导**

程序不需要解析旧索引文本，也不需要重算重要性。它只需保留现有子 `index.md` 的位置作为当前折叠边界，然后从规范文件和目录 description 重新渲染所有派生索引。新候选加入近期目录后，现有边界保持不变，但新文件会自然出现在负责展示该目录的索引中。

**当前决定**

索引采用“模型决策、程序渲染”的分工：

- 整理模型输出完整的 `foldedDirectories` 集合；
- 仓库根据该集合创建或删除对应目录的 `index.md`；
- 根 `.memory/index.md` 永远存在；
- 候选增量写入时，仓库从当前已经存在的子 `index.md` 读取折叠边界集合，并重渲染索引，不改变边界；
- 渲染时只复制文件 frontmatter 和目录元数据中的 canonical description；
- 不对模型的折叠判断打分、复核或自动改写。

这不是复杂格式校验。它只是把“哪些目录折叠”的语义判断与“把相同 description 写进 Markdown 树”的机械工作分开，直接解决候选立即可见和描述不漂移两个已确认需求。

**下一步**

确认整理器如何表达完整目录树，而不引入第二套模型工具循环。

### 2.6 确认整理模型的输出边界

**当前问题**

现有 `MemoryConsolidator` 的全量扁平替换如何最小演化为目录树整理？

**查看代码**

- `MemoryConsolidator.consolidate()`；
- `AgentLoop` 的工具循环及其 Session、审批、日志和恢复依赖。

**代码事实**

1. 整理器当前读取所有记忆正文，发起一次结构化模型请求，并把模型返回的完整集合写入后删除旧集合。
2. 当前硬编码 16,000 字符输入和 3,000 Token 输出限制，超限直接失败。
3. 项目没有独立可复用的后台模型工具循环；唯一工具循环是承担主 Agent 完整运行语义的 `AgentLoop`。
4. 把 `AgentLoop` 复用到后台整理会引入 ConversationState、Session、审批、TurnJournal、输出打印和恢复管理等无关依赖。

**推导**

当前需求的核心是限制主 Agent 常驻上下文，并没有要求本阶段建设大规模后台检索或第二个 Agent Runtime。在没有真实整理规模失败前，为整理器新增工具循环属于提前设计。最小方案应延续现有“一次完整结构化结果”的模式，只把结果从扁平列表扩展为完整目标树。

**当前决定**

新增整理结果模型：

```java
record MemoryTreeDraft(
        List<MemoryDirectoryDraft> directories,
        List<MemoryFileDraft> files,
        List<String> foldedDirectories
) {}

record MemoryDirectoryDraft(
        String relativePath,
        String description
) {}

record MemoryFileDraft(
        String relativePath,
        String description,
        String body
) {}
```

整理输入继续提供当前完整规范树，包括目录路径与 description、文件路径与 description/body、当前折叠边界。整理输出描述整理后的完整目标树：路径变化自然表达移动，缺失旧路径自然表达删除，多个旧文件变成一个新文件自然表达合并。

程序仅执行必要校验：响应完整、路径安全且唯一、文件和目录不冲突、folded directory 必须存在。程序不检查分类是否“合理”、某条记忆是否“足够重要”或模型为何折叠某个目录。

当前 16,000 字符业务硬限制不再作为需求规则保留；具体请求预算由实现时根据实际模型上下文设置。若真实记忆规模证明完整树整理不可持续，再以评测证据单独评审按需读取，不在本次先造后台 Agent 框架。

**下一步**

确认嵌套路径安全、`.memory` 中非长期记忆文件以及发布失败语义。

### 2.7 确认路径和发布边界

**当前问题**

仓库能否直接替换整个 `.memory` 目录，失败时应如何处理？

**查看代码**

- `WorkspacePathResolver`；
- `SessionStore` 和 `MemoryWorkStore` 的数据库位置；
- 当前 `MemoryRepository.writeAtomically()`；
- 当前后台异常处理。

**代码事实**

1. `WorkspacePathResolver` 支持嵌套相对路径，但允许范围是全部 allowed roots，不会自动限定在 `.memory`。
2. `.memory` 还可能包含 `sessions.db`；测试环境下 `memory-work.db` 也可能位于同名目录。
3. 当前仓库使用同目录临时文件和原子移动发布单个文件，没有跨文件事务。
4. 整理失败由 `MemoryBackgroundProcessor` 记录一次 WARN，并保留 `unconsolidatedCount`，不会影响已完成主回答。

**推导**

整理器不能通过删除并替换整个 `.memory` 目录发布结果，否则会误删 Session 和后台任务数据库。新仓库只能管理它能够明确识别的记忆 Markdown、目录元数据和 index 文件。现有单文件原子发布与“失败可见、下次重试”的语义已经足够，不需要引入目录快照事务。

**当前决定**

- 每个模型返回路径都先解析为 `.memory` 内部规范相对路径，再进行真实路径检查。
- 禁止模型操作 `.memory` 根之外、`sessions.db`、`memory-work.db` 或未知文件。
- 发布顺序为：完整校验模型结果 → 写入/更新目标记忆与目录元数据 → 删除不再保留的已管理记忆文件 → 删除已经为空的旧记忆目录 → 调整折叠边界文件 → 重渲染所有索引。
- 删除目录使用非递归 `Files.delete()`；未知文件阻止目录删除并使整理失败，不能静默吞掉。
- 单文件继续原子发布；跨文件中途失败允许短期新旧并存或索引过期，异常向上抛出，整理计数不清零。

**下一步**

确认测试和可观测性需要随依赖链如何变化。

哪些现有验证仍然有效，移除 selector 后哪些观测不能继续伪装存在？

**查看代码与历史证据**

- `MemoryBackgroundProcessorTest`；
- `MemorySystemPromptProviderTest`；
- `AgentSessionTest`；
- `GenAiSpanAttributes`；
- 对话记忆评测错误记录和后台评测收尾需求。

**代码事实**

1. 测试已覆盖启动恢复、五分钟重试、整批后阈值整理、两小时维护和失败任务保留。
2. 索引测试要求：只有数据库时为空仓库；已有主题但缺根索引时明确失败；索引只注入 description，不注入正文；开关关闭后移除索引。

- 保留提取、整理和后台 span；record ID 使用 `.memory` 内相对路径。
- `WAIT_MEMORY_IDLE`、MemoryWorkStore 和后台失败语义不修改。
- 新增仓库级 partial index、候选立即可见、目录移动/删除和 canonical description 测试。

## 3. 概念逻辑

### 3.1 唯一事实来源

```text
目录元数据 + 记忆文件 frontmatter/body
                 ↓
       规范记忆文件系统
                 ↓ 机械渲染
   root/折叠边界 index.md
```

索引永远不反向覆盖记忆文件或目录 description。模型决定目录结构和折叠位置，但索引中出现的 description 直接来自规范文件。

### 3.2 折叠状态

根 `index.md` 固定存在。其他目录的 `index.md` 是否存在，就是当前 partial tree 的折叠边界状态：

```text
父索引展开 customers/
  → customers/ 不存在 index.md
  → 父索引继续展示 customers/ 下级节点

父索引折叠 customers/
  → customers/index.md 存在
  → 父索引只展示 customers/ description 和该入口
  → customers/index.md 从本目录继续展开，直到下一个折叠边界
```

同一子树不会同时完整出现在父索引和子索引中。

### 3.3 新候选即时可见

`recent-unorganized/` 通常处于展开状态，但程序不强制这一判断。新增候选时，仓库不请求模型重新评估折叠，只保留现有边界并重渲染：

```text
写入 recent-unorganized/new-memory.md
  → 收集当前子 index.md 所表示的边界
  → 从 canonical tree 重新渲染
  → new-memory 出现在负责该目录的现有索引中
```

如果整理模型将该目录折叠，则新候选出现在其子 `index.md`；如果没有折叠，则出现在根索引。两种情况下都可召回。

## 4. 模型设计

### 4.1 记忆文件

```java
record MemoryEntry(
        String relativePath,
        String description,
        String body
) {}
```

- `relativePath` 相对于 `.memory`，例如 `projects/quillith/memory-design.md`。
- `description` 是索引使用的单行 canonical description。
- `body` 是完整 Markdown 正文。
- 文件 frontmatter 只保存 `description`，路径不在正文中重复保存。

### 4.2 目录

```java
record MemoryDirectory(
        String relativePath,
        String description
) {}
```

目录 description 使用该目录内固定的 `.description.md` 保存。选择独立元数据文件是因为展开目录按需求不存在自己的 `index.md`，不能把 canonical description 放在一个可能被删除的派生索引里。

`.description.md` 只保存一条 description，不承载记忆正文，也不参与主 Agent 的普通记忆文件枚举。

### 4.3 整理结果

`MemoryTreeDraft` 是整理模型返回的完整目标状态。它不是新的持久化数据库；通过校验后立即发布成目录和 Markdown 文件。

完整目标状态比“任意文件操作列表”更直接：模型不需要处理 move/write/delete 的执行顺序，应用也能在开始写入前检查路径冲突。当前实现本来就是全量集合替换，因此这是沿现有结构演化，而不是新增通用变更协议。

## 5. 边界定义

### 5.1 必须保留的边界

- 记忆仍然是工作区级数据，只进入父 Agent 的 System Prompt。
- 记忆内容属于历史数据，不能覆盖当前用户请求、系统规则或工具审批。
- 主回答不等待提取或整理。
- 提取任务仍采用 durable queue 和至少一次执行。
- 记忆关闭时不注入索引、不入队、不消费遗留任务；重新开启后继续。
- Provider 或文件处理失败不能伪装成成功；未知异常继续由后台边界记录完整堆栈。
- 同一工作区的提取写入和整理继续由单后台线程串行执行。

### 5.2 必须变化的边界

- `MEMORY.md` 改为小写根 `index.md`。
- 记忆 ID 从根级 name 改为相对路径。
- 固定 MemoryType 删除。
- 同步 selector 召回删除。
- 仓库从根级文件 CRUD 改为受控的递归记忆树发布。
- 整理从扁平列表归纳改为目录、文件和折叠边界的完整树归纳。

### 5.3 本次不增加

- 向量数据库、BM25、grep 或全文索引；
- 新的记忆专用读取工具；
- 后台 AgentLoop 或模型工具调用循环；
- 重要性数值、固定展开层数或 Token 评分公式；
- 索引语义评分器、自动纠错状态机或静默 fallback；
- 多进程锁和跨文件事务；
- 对 `.memory` 中未知文件的递归删除。

### 5.4 旧格式迁移

对应需求已把旧记忆迁移步骤列为非目标，本次实现不应未经确认自动重写用户已有 `.memory/MEMORY.md` 和旧 frontmatter。技术执行前需要单独决定是接受一次破坏性格式升级，还是补一项显式迁移需求；不能在仓库读取失败时静默忽略旧文件。

## 6. 代码实现方案

### 6.1 `MemoryEntry`、`MemoryDraft` 和 `MemoryType`

1. 将 `MemoryEntry` 字段改成 `relativePath/description/body`。
2. 把现有名称校验拆成路径段校验：每一段都必须是安全的 kebab-case，文件必须以 `.md` 结尾且不能使用 `index.md`、`.description.md` 等保留名。
3. `MemoryDraft` 保留候选 `name/description/body`，删除 type。
4. 删除 `MemoryType.java` 及所有 `type` 序列化、解析、Prompt 和上下文格式化逻辑。

### 6.2 `MemoryFileParser`

1. frontmatter 允许字段收缩为 `description`。
2. 解析方法接收规范记忆根与目标文件，从文件相对位置构造 `MemoryEntry.relativePath`。
3. 继续拒绝缺失 frontmatter、重复字段、未知字段、空 description、空正文和非普通文件。
4. `index.md` 与 `.description.md` 在进入解析器前由仓库排除。

### 6.3 新增目录和树结果模型

新增最小 DTO：

- `MemoryDirectory`：可信目录路径与 description；
- `MemoryTreeDraft`：整理模型的完整结构化结果；
- `MemoryDirectoryDraft`、`MemoryFileDraft`：模型响应 DTO。

不要为单次使用增加 Repository 接口、Factory 或通用文件树框架。这些类型只服务记忆整理的真实协议。

### 6.4 `MemoryRepository`

将现有根级 CRUD 收敛为下列职责：

```java
String readRootIndex();
List<MemoryEntry> listMemories();
List<MemoryDirectory> listDirectories();
List<MemoryEntry> createRecent(List<MemoryDraft> candidates);
void replaceTree(MemoryTreeDraft targetTree);
```

仓库内部增加两个私有机械步骤：

```java
Set<String> currentFoldedDirectories();
void rebuildIndexes(Set<String> foldedDirectories);
```

`rebuildIndexes()` 的规则：

1. 根索引固定从 `.memory` 开始渲染；
2. 遇到 folded directory 时，只输出目录名、canonical description 和子 index 路径；
3. 遇到展开目录时，继续递归输出其子节点；
4. 每个文件只输出相对路径或文件名及 canonical description，不输出 body；
5. 每个边界索引从自己的目录继续应用相同规则；
6. 所有 index 使用现有 `writeAtomically()` 发布。

### 6.5 `MemoryExtractor`

1. 结构化输出删除 type。
2. 仍只分析当前 Turn，必要时读取冻结 modelContext。
3. 仍限制单轮最多五条，并整批校验后返回。
4. telemetry 使用最终创建后的相对路径记录 ID；提取器本身尚不知道重名后缀，因此记录动作移到 `MemoryBackgroundProcessor` 写入成功之后。

### 6.6 `MemoryBackgroundProcessor`

将：

```java
repository.createNew(extractor.extract(task))
```

改为：

```java
repository.createRecent(extractor.extract(task))
```

其余队列、批次、阈值、定时维护和异常处理不修改。创建成功数量仍用于 `completeTaskAndIncrement()`。

### 6.7 `MemoryConsolidator`

1. 输入从 `List<MemoryEntry>` 改为完整目录树快照。
2. 整理请求包含目录描述、文件 description/body、当前 folded directories 和 recent-unorganized 的职责说明。
3. 输出从 `MemoryBatch` 改为 `MemoryTreeDraft`。
4. 在任何磁盘修改前完成整批结构和路径校验。
5. 调用一次 `repository.replaceTree(targetTree)` 发布，不再自己逐条 save/delete。
6. 整理后允许结果为空记忆集合；用户已确认整理模型有权删除，不保留现有“禁止清空全部记忆”的额外业务规则。

### 6.8 `MemoryRuntime` 与 `MemorySystemPromptProvider`

1. 删除 `MemorySelector`、`MemoryRecallService` 字段和装配。
2. 删除 `MemoryRuntime.recall()`。
3. `loadIndex()` 改读 `.memory/index.md`，错误信息同步更新。
4. Provider 说明根索引是 partial tree；折叠入口和文件链接可通过现有 `read_file` 按需读取。
5. 保留 SESSION 级刷新、memoryEnabled 开关和只注入索引不注入正文的行为。

### 6.9 `AgentSession`、Telemetry 和删除文件

1. `AgentSession` 不再同步召回，进入 `AgentLoop` 时传空 turnContext。
2. 删除 `MemorySelector.java`、`MemoryRecallService.java` 和对应测试。
3. 删除 `GenAiSpanAttributes.recordMemorySearch()` 及 selector 专属候选指标。
4. 提取和整理的 memory record ID 统一改为 `.memory` 内相对路径。
5. 不修改 AgentLoop 的通用 turnContext 能力。

## 7. 验证方案

### 7.1 领域与解析

- 同名文件位于不同目录时拥有不同相对路径 ID。
- type 不再是必填字段，未知 frontmatter 字段仍失败。
- 绝对路径、`..`、保留文件名、Windows 设备名和目录逃逸全部失败。
- `.description.md`、`index.md` 和数据库不会被解析为普通记忆。

### 7.2 partial index

- 根索引始终存在；空记忆库只含数据库时返回空 section。
- 少量目录未折叠时，根索引递归展示文件及 canonical description。
- 目录进入 folded set 后，父索引停止展开并指向子 index。
- 子目录取消折叠后，子 index 删除且内容回到上级索引。
- 多层折叠时每段子树只出现一次。
- 修改文件 frontmatter description 后，重建索引使用新值，不保留旧摘要。

### 7.3 近期未整理记忆

- 第一条候选创建 `recent-unorganized/` 并立即出现在根索引。
- 当前近期目录已经折叠时，新候选立即出现在其子 index。
- 同名候选追加后缀，不覆盖旧候选。
- 整理后候选移动或合并，近期目录不再保留重复文件。

### 7.4 整理和失败语义

- 完整目标树可以创建、移动、合并和删除文件及目录。
- 模型返回重复路径、文件目录冲突或越界路径时，任何文件都不修改。
- 未知文件阻止旧目录删除，错误向上传播。
- 发布中途失败保留已完成文件动作，后台计数不清零，下一次仍可重试。
- 整理模型返回零条记忆时可以清空受管理的记忆文件，但数据库和未知文件保留。

### 7.5 Session 与后台

- 普通回答不再产生 selector 请求，Provider 请求数量相应减少。
- 根 index 仍随每个 Session Turn 刷新。
- memory off 时不注入索引、不入队、不处理任务。
- 五分钟重试、5 文件阈值、两小时维护和 WAIT_MEMORY_IDLE 原测试继续通过。
- 整理失败不影响已完成主回答，也不伪装成 pending extraction。

## 8. 按依赖顺序的执行安排

技术讲解从入口向内部追踪；真正实现应按被依赖者优先，顺序如下：

1. 修改 `MemoryEntry`、`MemoryDraft`，新增目录与完整树 DTO，删除 `MemoryType`。
2. 修改 `MemoryFileParser`，先稳定新的单文件可信边界。
3. 重写 `MemoryRepository` 的递归扫描、近期写入、目标树发布和 partial index 渲染，并补齐仓库单元测试。
4. 修改 `MemoryExtractor` 的结构化协议和候选转换。
5. 修改 `MemoryConsolidator`，让它依赖新的树快照与 `replaceTree()`。
6. 修改 `MemoryBackgroundProcessor`，接入 `createRecent()`，保留原调度语义。
7. 删除 `MemorySelector/MemoryRecallService`，收缩 `MemoryRuntime`。
8. 修改 `MemorySystemPromptProvider` 与 `AgentSession`，完成根索引加主 Agent 渐进读取链路。
9. 调整 telemetry、现有 Session/SystemPrompt/后台测试和 consolidation probe。
10. 运行单元测试后，再执行一次真实多 Session 记忆评测，核对请求数、最终目录树、各级 index、pending task 和回答结果。

## 9. 最终回看

```text
需求：有限上下文下保持对增长记忆树的全局感知
  → 入口：每轮 SESSION System Prompt 已有根索引注入点
  → 核心状态：规范目录/文件 + canonical description + 折叠边界
  → 召回：父 Agent 使用现有 read_file 渐进导航
  → 形成：候选先进入 recent-unorganized 并立即重渲染索引
  → 整理：模型返回完整目标树和 folded directories
  → 发布：仓库只做安全路径、文件变更和确定性索引渲染
  → 验证：目录展开/折叠、候选即时可见、后台语义和跨 Session 回答
```

最终方案没有新增向量库、专用搜索工具、后台 AgentLoop、重要性评分器或复杂恢复系统。新增的数据结构和仓库逻辑都可以直接追溯到当前需求中无法由现有扁平实现表达的三个事实：记忆身份包含路径、目录需要 canonical description、索引只存在于根和折叠边界。
