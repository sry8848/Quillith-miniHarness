# 分层文件型长期记忆需求

## 1. 需求描述

长期记忆系统需要在有限的模型上下文中，对持续增长的文件型记忆库保持足够的全局感知，同时避免把全部记忆正文或完整目录树常驻上下文。

记忆库使用 Markdown 文件和目录保存。目录结构不预设固定业务分类，而是随着记忆积累，由整理模型根据实际内容逐渐形成和调整。主 Agent 每轮看到的不是黑盒检索结果，而是一份经过上下文预算裁剪的目录树视图；它可以根据当前任务继续进入被折叠的子树，按需读取更具体的索引或记忆正文。

本需求改变现有扁平主题文件和全量主题索引的目标形态。现有设计文档继续作为历史设计保留，后续通过独立技术评审确定迁移和代码修改方案。

## 2. 需要解决的问题

1. 记忆数量不断增长后，如何让主 Agent 仍然知道自己大致拥有哪些记忆。
2. 如何控制常驻索引的上下文成本，而不把记忆库变成无法感知内容范围的黑盒。
3. 如何让重要、近期或遗漏代价高的信息得到更多曝光，让大量、低频且容易按目录定位的信息按需披露。
4. 如何让记忆目录随实际内容演化，而不是被固定的类型或目录结构限制。
5. 如何区分记忆提取、结构整理和任务召回，避免让单个阶段同时承担所有判断。
6. 如何避免多级索引重复展示同一子树，并保持渐进导航入口。

## 3. 核心概念

### 3.1 规范记忆文件系统

规范记忆文件系统是长期记忆的唯一事实来源，包含：

- 目录及其稳定 description；
- 普通 Markdown 记忆文件；
- 记忆文件 frontmatter 中的稳定 description；
- 记忆正文。

目录结构不规定必须存在 `user/`、`project/`、`customer/` 等分类，也不保留现有 `user`、`feedback`、`project`、`reference` 四种固定记忆类型。整理模型应根据真实记忆内容形成必要的目录层级，并可在后续整理中移动、合并、拆分或删除内容。

目录与文件的 description 用于说明其内容范围。Agent 在尚未读取正文时，应能通过目录名、文件名和 description 判断其中是否可能存在当前任务需要的信息。

目录 description 必须有稳定的唯一真源。其具体存储格式不在本需求中规定，留待技术评审决定。

### 3.2 `index.md`

`index.md` 不是记忆正文，也不是独立摘要库，而是规范记忆文件系统的一张部分展开目录树视图。

索引展示哪些目录、继续展开到哪一级，由该子树的当前价值、信息密度、遗漏代价和上下文成本共同决定。展开深度本身就是信息曝光程度的表达，不额外要求 `priority`、`importance` 或类似评分字段。

本需求不规定统一展开层数、固定评分公式或精确 Token 上限。不同子树可以拥有不同的展开深度。

文件节点在索引中直接使用文件 frontmatter 中的 canonical description。目录节点直接使用目录的 canonical description。索引不得另外维护一份独立改写的描述，避免同一内容出现多个相互漂移的版本。

### 3.3 折叠边界索引

根记忆目录始终存在 `index.md`。其他目录只在成为上级索引的折叠边界时存在自己的 `index.md`：

- 目录在父级索引中展开时，其下级结构直接展示在父级索引中，该目录不再保留自己的 `index.md`；
- 目录在父级索引中折叠时，父级只展示该目录的名称、description 和子级 `index.md` 入口；
- 折叠前展示在父级索引中的子树内容，转移到该目录的 `index.md`；
- 同一段子树只由一个索引展示，避免多级索引重复呈现同一内容；
- Agent 只有在当前任务需要更多信息时，才继续读取折叠目录的 `index.md`。

索引文件是规范记忆文件系统的派生视图，不是第二事实来源。

## 4. 目录树裁剪要求

### 4.1 判断原则

整理模型决定是否继续展开某个目录时，需要判断：

> 继续展开这一层能够为主 Agent 增加多少有价值的信息，以及需要占用多少常驻上下文。

适合较早折叠的目录通常同时具有以下性质：

- 内容数量很大；
- 大部分内容使用频率较低；
- 仅通过目录名称和 description 就能判断何时需要进入；
- 展开后增加的大量信息对多数任务没有帮助。

例如，包含数百个客户资料的目录可以在根索引中折叠。用户提到具体客户时，Agent 再通过子级索引逐层导航。

适合继续展开的目录或文件通常具有以下性质：

- 当前时效性强；
- 遗漏后果较大；
- 后续任务可能不会直接出现可检索关键词；
- 少量 description 就能带来较高判断价值。

例如，未来七天有效的术后饮食限制应在有效期内获得较深曝光。即使用户询问的是一道菜且没有提到“术后”或“忌口”，主 Agent 仍有机会从索引中意识到当前存在饮食限制并读取正文。

### 4.2 时效变化

记忆重要性的变化可以通过索引曝光深度的变化体现。短期内重要的信息可以展开到文件级；失去时效性后，可以从根索引的详细展示中下沉到更深层历史目录。

下沉不等于必须删除。整理模型有权根据事实是否仍有保留价值决定移动、合并或删除记忆。系统不要求为短期记忆建立独立数据库。

### 4.3 “近期未整理记忆”是统一原则的典型反例

规范记忆树中存在一个“近期未整理记忆”目录，作为新候选记忆的固定首次落点。该目录不是树外暂存区，其中的文件从写入开始就是可见、可召回的正式记忆。

“近期未整理记忆”不采用硬编码的特殊展开规则，而是与其他目录遵循相同的裁剪原则。它通常不应被折叠，因为它天然具有：

- 内容较新；
- 数量尚未大到必须折叠；
- 尚未形成可仅凭目录判断用途的稳定分类；
- 过早隐藏容易使主 Agent遗漏刚形成的记忆。

因此，该目录是帮助整理模型理解“不应折叠什么”的典型反例，而不是独立于统一判断原则之外的特例。

## 5. 记忆生命周期

### 5.1 提取

每轮对话结束后，后台提取模型识别未来可能值得保留的候选记忆。

提取阶段只判断哪些内容值得留下，不决定最终目录结构，不负责长期分类，也不决定索引展开深度。候选记忆首先写入“近期未整理记忆”目录，使其能够立即进入后续召回。

### 5.2 整理

整理模型读取现有规范记忆树和近期未整理记忆，负责：

- 判断已有文件是否应更新；
- 创建必要的新文件或目录；
- 合并或拆分记忆；
- 移动记忆到更合适的位置；
- 删除不再需要保留的记忆；
- 更新文件和目录 description；
- 根据完整记忆树重新决定各子树的展开深度；
- 创建、移动或删除折叠边界上的 `index.md`。

候选记忆完成迁移或合并后，应从“近期未整理记忆”目录移除，最终事实只在整理后的规范位置保留。

整理继续沿用已经确认的触发要求：每累计新增 5 个记忆文件时整理一次；每 2 小时检查一次，只要仍存在未整理记忆就执行整理。

本需求不要求增加复杂的程序格式校验、索引状态机或自动恢复协议。整理模型负责维护目录与索引的一致性；是否需要增加确定性校验，应在出现可重复的真实失败后根据证据另行评审。

### 5.3 召回

主 Agent 每轮始终看到根 `index.md`，从而保持对长期记忆库的大致全局感知。

召回遵循渐进披露：

1. 主 Agent 根据当前任务和根索引判断是否存在潜在相关记忆；
2. 如果目标目录已展开，则直接利用暴露的文件 description 判断是否读取正文；
3. 如果目标目录处于折叠状态，则按需读取该目录的 `index.md`；
4. 必要时继续沿折叠边界深入；
5. 最终只读取当前任务真正需要的记忆正文。

主 Agent 可以利用自身的世界知识建立用户问题与索引信息之间的隐式关联，召回不依赖用户问题必须包含与记忆相同的关键词。

## 6. 已确认边界

- 记忆存储仍然采用可读、可编辑的 Markdown 文件和目录。
- 规范记忆文件系统是唯一事实来源，所有 `index.md` 都是派生视图。
- `index.md` 替代现有扁平 `MEMORY.md` 的目标形态。
- 目录结构由整理模型根据实际内容演化，不预设固定业务分类。
- 取消现有四种固定记忆类型。
- 展开深度表达信息曝光程度，不新增独立的重要性评分体系。
- 不规定统一展开层数、评分公式或精确 Token 上限。
- 整理模型有权更新、移动、合并、拆分和删除记忆。
- 不因索引一致性的低概率错误预先增加复杂程序规则或兜底逻辑。
- 全文搜索、grep、BM25、Embedding 和 RAG 都可以作为未来补充能力存在，但本需求不要求实现。

## 7. 非目标

本需求不包含：

- 具体 Prompt；
- 代码实现方案；
- 领域类、接口或数据结构设计；
- 目录 description 的具体存储格式；
- 固定的索引裁剪算法；
- 程序侧索引格式校验或自动修复机制；
- 全文搜索、BM25、向量数据库或 RAG；
- 对现有记忆文件的迁移步骤。

以上内容需要在需求确认后，通过技术评审沿现有代码事实逐步确定。

## 8. 之前的思考路径总结

最初的关注点是如何准确搜索长期记忆，但继续拆解后发现，核心问题不是单次搜索算法，而是主 Agent 在有限上下文中如何持续知道“自己大致拥有哪些记忆”。

如果把全部文件目录和 description 常驻上下文，成本会随记忆规模持续增长；如果只保留黑盒检索入口，主 Agent 又无法利用自身推理发现没有直接关键词关联的重要记忆。因此形成了“规范文件树加部分展开索引”的结构：正文继续保存在文件系统中，主 Agent 常驻看到经过预算裁剪的目录树，并在需要时逐层深入。

进一步讨论发现，所有目录都保存自己的索引会导致重复内容和额外维护。因此索引被收敛为折叠边界上的派生视图：父级展开目录时直接展示内容，父级折叠目录时才由子级 `index.md` 承接被隐藏的内容。

对于新提取但尚未完成结构整理的记忆，最初考虑过将其放在召回之外的暂存区，但这会导致模型在整理前无法使用刚形成的记忆。因此最终确定：“近期未整理记忆”本身就是规范目录树的一部分。它不需要特殊的强制展开规则；其近期、少量、难以按稳定目录判断用途的自然属性，已经使它成为统一裁剪原则下不应折叠的典型例子。

最终形成的需求重点不是构建更复杂的检索基础设施，而是让目录结构、description 和动态展开深度共同承担全局感知与上下文控制，并将提取、整理和召回的职责清晰分开。

## 9. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 记忆库只有少量当前重要文件 | 根 `index.md` 展开到文件及其 canonical description，主 Agent 无需先进行黑盒搜索 |
| 客户目录包含大量低频客户资料 | 根索引折叠客户目录并提供 description 和子级 `index.md` 入口 |
| 用户提到某个具体客户 | 主 Agent 进入客户目录的 `index.md`，继续导航到相关文件并按需读取正文 |
| 当前存在短期有效且遗漏代价高的饮食限制 | 相关文件在当前阶段获得较深曝光，即使问题没有直接关键词也能被主 Agent意识到 |
| 短期限制失效但仍有历史价值 | 整理模型可以将其下沉到历史目录，减少根索引曝光，而不必自动删除 |
| 提取模型产生新候选记忆 | 文件进入“近期未整理记忆”目录，并立即参与索引展示和召回 |
| 近期未整理记忆数量少且内容各异 | 按统一裁剪原则保持展开，而不是仅因它是暂存目录就折叠 |
| 整理模型完成候选归档 | 候选从近期目录移除，在最终目录中保留、合并或按事实需要删除 |
| 某目录从展开调整为折叠 | 父级索引以目录节点和入口替换原子树内容，该目录生成承接内容的 `index.md` |
| 某目录从折叠调整为展开 | 子级内容进入父级索引，该目录不再保留重复的 `index.md` |
| 记忆文件正文或 description 更新 | 后续索引使用文件的 canonical description，不产生独立摘要版本 |

## 10. 最终需求原则

长期记忆系统需要同时满足：

1. 正文只有一个规范事实来源；
2. 主 Agent 始终知道自己大致拥有哪些记忆；
3. 上下文只常驻当前值得暴露的目录层级和 description；
4. 目录结构能够随真实记忆自然演化；
5. 新记忆在等待整理期间不会失忆；
6. 大量、低频且容易定位的内容逐层折叠；
7. 近期、重要或容易被隐式关联遗漏的内容得到更深曝光；
8. 没有真实失败证据时，不为低概率一致性问题增加复杂程序设计。
