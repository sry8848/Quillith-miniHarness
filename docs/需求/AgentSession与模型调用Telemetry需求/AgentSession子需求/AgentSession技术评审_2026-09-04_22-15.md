# AgentSession 技术评审

## 一、评审结论

当前 `ManualAgent` 已经承担一段连续会话的核心职责：持有主对话历史，并接收多次用户提交。该对象在业务语义上就是 `AgentSession`，不需要再增加一层 Session 包装。

本需求采用以下最小方案：

1. 将现有 `ManualAgent` 的业务名称统一为 `AgentSession`；
2. 在现有 Session 状态中增加一个创建后不再变化的 `sessionId`；
3. 每次有效 `submit` 建立一个覆盖完整 Turn 的 OpenTelemetry Span；
4. 该 Span 在当前没有父 Span 的 CLI 入口下成为本 Turn 的 Trace 根节点；
5. 父 Agent、Sub-Agent 和现有业务 Span 从同一份 Session 状态读取并记录相同的 `sessionId`；
6. 不新增 `SessionContext`、Identity Provider、ThreadLocal、Baggage、Session Repository 或其他中间层。

该方案直接复用现有对象和 OpenTelemetry 能力，没有第二份 Session 状态，也没有第二套执行上下文。

---

## 二、最小运行链路

完整链路只保留以下对象关系：

```text
ManualAgentApplication
        │
        │ 创建一次 Session 状态
        ▼
AgentState
        │
        │ 包含唯一且不可变的 sessionId
        │ 被父 Agent 和 Sub-Agent 共享
        ▼
AgentRuntime
        │
        │ 装配并返回唯一的 AgentSession
        ▼
AgentSession
        │
        │ 持有一份主 conversation history
        │
        ├── submit(query) ── Turn Trace
        │                       └── AgentLoop
        │                           ├── Model Call
        │                           ├── Tool Call
        │                           └── Sub-Agent
        │
        └── submit(query) ── 新的 Turn Trace
```

其中只有一份业务 Session Identity：

```text
AgentState.sessionId
```

`AgentSession`、父 AgentLoop 和 Sub-Agent AgentLoop 不生成自己的 Session ID，只读取这一个值。

## 三、现有代码边界判断

### 3.1 ManualAgent 已经是 Session

现有 `ManualAgent` 同时具备以下特征：

- 内部持有唯一的主对话历史；
- 同一实例连续处理多次 `submit`；
- 编排一次用户 Turn 的 Hook、Memory 和 AgentLoop；
- 失败时按本次用户消息回滚对话历史；
- 读写当前会话的动态状态。

这些职责共同构成 Agent Session。保留 `ManualAgent`，再新增一个持有它的 `AgentSession`，只会产生两个生命周期相同、职责边界无法区分的对象。

因此本次应直接统一名称，不增加包装层。

### 3.2 AgentState 是 Session 内部状态

现有 `AgentState` 已经由应用入口创建一次，并同时传给：

- 父 AgentLoop；
- Sub-Agent AgentLoop；
- MemoryRuntime；
- System Prompt；
- 工具审批及其他会话级组件。

它已经是当前执行链共享的 Session 状态载体。在这里增加不可变的 `sessionId`，可以让现有父子执行链读取同一个值，不需要额外建设传播对象。

`AgentState` 仍然只是 AgentSession 持有和共享的内部状态，不与 `AgentSession` 形成第二个业务会话概念。

### 3.3 AgentRuntime 不是 Session

现有 `AgentRuntime` 负责创建和关闭模型客户端、调度器、Bash 工具及 MCP 客户端等运行资源。

这些资源当前与 AgentSession 同时创建和关闭，但资源生命周期与对话语义不是同一种职责。AgentSession 不需要因为当前生命周期重合而承担资源关闭行为。

因此保留 `AgentRuntime`：

```text
AgentRuntime
= 资源装配和关闭

AgentSession
= 会话历史、状态和 Turn 入口
```

本次只把 Runtime 对外持有和返回的 `ManualAgent` 改为 `AgentSession`，不合并两个对象。

## 四、Session Identity 设计

### 4.1 数据归属

`sessionId` 属于 AgentSession，并保存在 AgentSession 已经共享的 `AgentState` 中。

该字段满足以下不变量：

```text
一个 AgentState 对应一个 AgentSession
一个 AgentSession 只有一个 sessionId
sessionId 创建后不再改变
不同 AgentState 创建不同 sessionId
```

AgentSession 对外可以读取该 ID，但不能修改它。

### 4.2 创建规则

`AgentState` 创建时同步生成 `sessionId`，使用 Java 标准库提供的随机 UUID 字符串。

当前需求只要求进程内创建新 Session，不支持恢复指定 Session，因此不增加：

- ID 生成接口；
- 可替换 ID Provider；
- 外部传入 ID 的构造分支；
- ID 格式配置；
- Session ID 持久化。

生成 ID 失败时不进行降级或伪造，异常保持向上抛出。

### 4.3 名称映射

Java 业务字段统一称为：

```text
sessionId
```

写入 OpenTelemetry 时使用标准属性：

```text
gen_ai.conversation.id
```

不在业务模型中同时增加 `conversationId`，避免两个字段表示同一个值。

## 五、Turn Trace 边界

### 5.1 Span 起点

一次 Turn 必须在 `submit` 的输入契约校验通过后开始。

Turn Span 随后覆盖：

```text
UserPromptSubmit Hook
Session Prompt 刷新
Memory recall
主历史写入
AgentLoop
Memory complete
失败诊断与历史回滚
```

这样可以同时满足：

- 非法方法参数不产生 Turn；
- Hook BLOCK 仍有完整 Turn；
- AgentLoop 之前和之后的会话工作属于同一 Trace；
- Provider 失败和历史回滚不会删除已经发生的执行事实。

现有 `agent.run` Span 位于 AgentLoop 内部。增加 Turn Span 后，它自然成为 Turn Span 的子节点，不再承担根 Trace 和完整 Turn 两种职责。

### 5.2 Span 结束

Turn Span 在本次 `submit` 正常返回或抛出异常时结束。

本阶段 Sub-Agent 是同步执行，会在 `submit` 返回前结束，因此自然属于同一 Turn Trace。

后台 Bash 任务可能晚于当前模型轮次完成，但它不创建新的业务 Session。它已经登记在当前 AgentRuntime 持有的后台调度器中，继续使用同一份 `AgentState`。本需求不为后台任务增加新的 Session Identity。

### 5.3 一次 Turn 一条 Trace

当前 CLI Runner 调用 `submit` 时不存在上层业务 Span，因此 Turn Span 会成为新 Trace 的根节点。

本阶段不支持把 AgentSession 嵌入另一个已经存在的业务 Trace，也不为假设中的外部调用模式增加强制新建根 Trace 的自定义 Tracer 逻辑。

如果未来出现嵌入式调用入口，应在对应需求中重新决定“继承外部 Trace”还是“强制新建 Turn Trace”，不能在当前 CLI 需求中提前假设。

## 六、sessionId 的 Span 记录范围

当前手工声明的业务 Span 包括：

```text
Turn
Agent Run
Agent Iteration
Model Call
Tool Call
```

这些 Span 记录同一个：

```text
gen_ai.conversation.id = AgentState.sessionId
```

父 Agent 和 Sub-Agent AgentLoop 已经共享同一个 `AgentState`，因此不需要通过方法参数逐层传递 `sessionId`。

OpenTelemetry 自动生成的 HTTP、线程或其他底层基础设施 Span 不重复写入该业务属性。它们已经通过 Trace 父子关系归属于对应业务 Span；把 Session 属性复制到所有底层 Span 会增加数据量，但不会增加新的关联能力。

Context 和 Memory 的专用 Model Call Span 尚属于后续 Telemetry 子需求。本次保证它们在同步执行时处于 Turn Trace 内，并能够从现有会话状态取得 `sessionId`；后续新增对应业务 Span 时必须写入相同的 `gen_ai.conversation.id`。

---

## 七、异步传播边界

当前前台 Tool 执行已经捕获并恢复所属 Agent Iteration 的 OpenTelemetry Context，Sub-Agent 又在 Tool 执行中同步运行，因此现有 Trace 父子关系可以继续使用，不需要新增传播机制。

Session Identity 本身保存在父子组件共享的 `AgentState` 中，不依赖执行线程，也不会因为切换虚拟线程而变化。

后台任务当前执行的是工具工作，不会在后台命令线程中创建新的 AgentSession 或模型调用。本次不增加通用异步 Session Context。

如果未来允许后台任务独立发起模型调用或跨进程继续执行，应由该异步能力的需求明确任务归属和 Context 传播方式，不能为了尚不存在的链路提前建设通用框架。

---

## 八、代码实现范围

本需求需要完成以下有限改造：

1. 将 `ManualAgent` 及其直接调用方使用的业务名称统一为 `AgentSession`；
2. 保持主对话历史继续由 AgentSession 唯一持有；
3. 在 `AgentState` 中增加只读 `sessionId`，创建 AgentState 时自动生成；
4. 在有效 `submit` 的完整执行流程外建立 Turn Span；
5. 在现有手工业务 Span 上记录同一个 `gen_ai.conversation.id`；
6. 更新受类名变化直接影响的测试和注释。

本次不改变：

- AgentLoop 的模型与工具循环；
- conversation history 的内容和更新顺序；
- Hook 的触发顺序和 BLOCK 行为；
- Memory recall、capture 和 complete 的顺序；
- Provider Error 诊断与历史回滚；
- 父 Agent 与 Sub-Agent 的上下文隔离；
- 后台任务调度行为；
- Runtime 资源关闭顺序。

## 九、不采用的额外设计

### 9.1 不新增 AgentSession 包装 ManualAgent

两个对象会共享相同生命周期，AgentSession 除了转发 `submit` 和读取 ID 外没有独立职责。该包装只增加命名层级和构造依赖，因此直接重命名现有对象。

### 9.2 不把 AgentState 合并进 AgentSession

AgentState 已经是多个工具、Prompt、Memory 和父子 AgentLoop 的窄状态依赖。如果把整个 AgentSession 传给这些组件，它们会同时依赖对话历史和 Turn 编排能力，扩大可见职责并增加循环装配风险。

保留 AgentState 可以让下游只读取所需的共享状态，同时 AgentSession 继续拥有会话编排职责。

### 9.3 不新增 SessionIdentity 或 SessionContext

当前 Identity 只有一个不可变字符串，现有 AgentState 已能唯一承载。为单个字段增加 record、context holder 或 service 不会解决新的问题。

只有未来出现多个彼此独立、需要整体传递的 Session 字段，且现有 AgentState 无法作为依赖时，才重新评估独立值对象。

### 9.4 不使用 ThreadLocal

Session 已经具有明确的对象归属，ThreadLocal 会隐藏依赖，并在虚拟线程、异步调度和测试中增加额外传播规则。当前没有只能通过线程局部变量解决的调用边界。

### 9.5 不使用 OpenTelemetry Baggage 作为业务事实来源

Baggage 适合跨进程传播观测上下文，但本需求中的 AgentSession 必须在 OpenTelemetry 未启用时仍然存在。把 Baggage 作为唯一存储会让业务 Identity 依赖观测设施，而且 Baggage 不会自动变成所有 Span 的 Attribute。

当前直接从 AgentState 向手工业务 Span 写入属性更短、更明确。

### 9.6 不新增 ID Provider

当前只有一种新建 Session 的方式，没有恢复、导入、分布式发号或可预测 ID 的需求。Java 标准 UUID 已满足唯一性，抽象 ID Provider 没有第二个真实实现。

### 9.7 不让 AgentSession 实现 AutoCloseable

AgentSession 当前拥有的是 Java 对象中的历史和状态，没有需要单独关闭的资源。真实资源继续由 AgentRuntime 关闭。增加空的 `close` 或把 Runtime 资源转移进 Session 都不能改善业务语义。

### 9.8 不增加 turnId

当前一次有效 `submit` 对应一条 Trace，Trace 已经拥有唯一 `traceId`。额外的 `turnId` 不提供新的关联能力，只会让调用方在两个 ID 之间选择。

## 十、边界条件

### 10.1 非法输入

没有通过 `submit` 方法契约校验的调用不创建 Turn Span，也不影响 AgentSession 的历史和状态。

### 10.2 Hook BLOCK

输入通过契约校验后，Turn 已经开始。Hook BLOCK 结束本次 Turn，但不创建模型调用，也不撤销 Trace 或 Session Identity。

### 10.3 Provider 失败

Provider 失败仍属于当前 Turn。现有异常传播、诊断和 history rollback 保持不变，Session ID 和 Trace 不因业务历史回滚而撤销。

### 10.4 多次提交

同一个 AgentSession 的多次有效提交使用相同 `sessionId`，每次提交产生不同的 Trace。

### 10.5 Sub-Agent

Sub-Agent 使用隔离的局部消息历史，但属于发起它的 AgentSession，使用相同 `sessionId`，并处于当前 Turn Trace 内。

### 10.6 Tracing 未启用

OpenTelemetry 退化为 no-op 时，AgentSession 和 `sessionId` 仍然正常创建和使用。此时没有可导出的 Trace，但业务对象不依赖 Trace 反向生成 Identity。

---

## 十一、验证范围

自动化测试至少验证：

- 一个 AgentSession 在多次读取和多次提交之间保持同一个 `sessionId`；
- 两个分别创建的 AgentSession 使用不同 `sessionId`；
- 现有多轮 history 行为在名称调整后保持不变；
- Hook BLOCK、Provider 失败和 history rollback 行为保持不变；
- 父 Agent 与 Sub-Agent 使用同一份 Session 状态；
- 输入契约校验失败不进入 Turn 执行；
- 启用现有 OpenTelemetry Java Agent 时，同一 Turn 的业务 Span 使用相同 `gen_ai.conversation.id`；
- 同一 AgentSession 的两次 Turn 使用相同 conversation ID 和不同 traceId。

不为了测试本需求而引入新的 Observability 后端或独立 OpenTelemetry SDK 装配。Trace 验证继续使用项目现有 Java Agent 路径。

---

## 十二、性价比评估

本方案新增的长期业务状态只有一个不可变 `sessionId`，新增的运行边界只有一个 Turn Span。其余工作主要是现有类名和 Span 属性的直接调整。

它解决了以下当前问题：

- `ManualAgent` 与 Session 的概念重复；
- 多个 Turn 无法通过稳定业务 ID 识别为同一段对话；
- Agent、Model 和 Tool Span 缺少统一 conversation 关联；
- 现有 `agent.run` Span 无法覆盖 Hook 和 Memory 等完整 Turn 生命周期。

同时没有引入新的生命周期对象、传播框架、持久化层或可配置扩展点，符合当前单进程、单 AgentSession、串行 Turn 的真实运行方式。
