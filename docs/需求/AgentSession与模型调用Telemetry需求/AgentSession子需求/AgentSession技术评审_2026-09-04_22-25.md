# AgentSession 技术评审

## 一、评审结论

当前 `ManualAgent` 已经持有主对话历史并连续接收用户提交，在业务语义上就是 AgentSession。当前 `AgentState` 每次 CLI 会话只创建一份，并由父 Agent、Sub-Agent、Memory、Prompt 和工具相关组件共享，在业务语义上就是 SessionState。

本需求采用直接改名和补充唯一 ID 的最小方案：

1. `ManualAgent` 统一为 `AgentSession`；
2. `AgentState` 统一为 `SessionState`；
3. SessionState 增加一个创建后不再变化的 `sessionId`；
4. AgentSession 继续唯一持有现有主对话历史；
5. 现有父子执行链继续共享同一份 SessionState；
6. 不改变用户提交、模型调用、工具调用和资源关闭流程。

本次不设计 Turn 和 Telemetry，不新增任何 Session 包装层或传播框架。

---

## 二、最小链路

```text
ManualAgentApplication
        │
        │ 创建一份
        ▼
SessionState
├── sessionId
├── memoryEnabled
├── approvalMode
└── 路径上下文
        │
        │ 交给现有 Runtime 装配链
        ▼
AgentRuntime
        │
        ├── 父 AgentLoop ─────┐
        ├── Sub-AgentLoop ────┤ 共享同一份 SessionState
        ├── Memory/Prompt ────┤
        └── AgentSession ─────┘
                │
                ├── 主 conversation history
                └── submit(...)
```

链路中不增加新的 Session 对象、Identity 对象或 Context 对象。

---

## 三、对象职责

### 3.1 AgentSession

AgentSession 保留现有 ManualAgent 的职责：

- 唯一持有主对话历史；
- 接收并编排用户提交；
- 调用 Hook、Memory 和父 AgentLoop；
- 在 Provider 最终失败时执行现有诊断与历史回滚；
- 提供当前会话允许对外操作的状态入口。

名称变化用于让类名与已经存在的真实职责一致，不新增行为层。

### 3.2 SessionState

SessionState 保留现有 AgentState 的职责：

- 保存当前会话的记忆开关；
- 保存当前会话的工具审批模式；
- 保存本次会话使用的路径上下文；
- 作为父 Agent、Sub-Agent 和相关组件共享的窄状态对象。

在此基础上增加不可变的 `sessionId`。

SessionState 不持有主对话历史，也不提供 `submit`。这样下游组件可以读取必要的共享状态，而不需要依赖完整的 AgentSession 编排能力。

### 3.3 AgentRuntime

AgentRuntime 继续负责模型客户端、后台调度器、Bash 工具和 MCP 客户端等资源的装配与关闭。

当前 AgentRuntime 和 AgentSession 的生命周期相同，但职责不同：

```text
AgentRuntime
= 运行资源

AgentSession
= 会话历史和用户提交
```

本次不合并二者，也不让 AgentSession 接管资源关闭。

## 四、sessionId 设计

### 4.1 保存位置

`sessionId` 保存在 SessionState 中。

选择该位置的原因是：SessionState 已经在一段新会话开始时创建，并被现有父子执行链共享。把 ID 放在这里可以直接复用当前对象关系，不需要再增加 Identity 容器。

AgentSession 通过自己持有的 SessionState 对外返回 `sessionId`，不保存第二份字段。

### 4.2 创建规则

SessionState 创建时使用 Java 标准库生成随机 UUID 字符串，并在整个对象生命周期内保持不变。

当前没有恢复旧 Session、外部导入 ID 或分布式发号需求，因此不增加：

- ID Provider；
- ID Factory；
- 可配置 ID 格式；
- 外部传入 ID 的构造分支；
- Session ID 持久化。

如果 ID 创建过程出现异常，保持异常向上抛出，不生成替代值，也不把失败降级成无 ID Session。

### 4.3 唯一事实来源

SessionState 中的 `sessionId` 是唯一事实来源。

AgentSession、父 Agent、Sub-Agent 和其他会话级组件不得缓存或重新生成第二份 Session ID。

本次不建立 `conversationId`、`turnId` 或其他业务 Identity。

---

## 五、装配与生命周期

应用入口继续按当前方式为一次 CLI 会话创建一份状态，只把类型从 AgentState 统一为 SessionState。

AgentRuntime 继续接收这一份状态，并将同一个实例交给现有需要会话状态的组件。

AgentRuntime 最终创建一个 AgentSession。该 AgentSession 持有相同的 SessionState 和唯一的主对话历史。

交互模式继续在同一个 AgentSession 上执行多次用户提交；单次执行模式继续只提交一次。

退出命令、本地命令、Hook、模型循环和异常处理行为不因 Session 命名调整而改变。

AgentRuntime 关闭时继续按照现有顺序释放资源。AgentSession 不实现无实际资源可关闭的 `AutoCloseable`。

---

## 六、代码影响范围

本需求只需要以下直接修改：

1. 将 `ManualAgent` 类及直接引用统一命名为 `AgentSession`；
2. 将 `AgentState` 类及直接引用统一命名为 `SessionState`；
3. 在 SessionState 中增加不可变 `sessionId` 和只读访问入口；
4. 在 AgentSession 中提供当前 Session ID 的只读访问入口；
5. 更新 AgentRuntime 对 AgentSession 的持有和返回命名；
6. 更新 CLI Runner、相关测试及注释中的旧名称。

本次不修改：

- `submit` 的执行步骤和返回语义；
- 主对话历史的数据结构；
- Hook 顺序和 BLOCK 行为；
- Memory 调用顺序；
- AgentLoop 的模型与工具循环；
- 父 Agent 与 Sub-Agent 的消息历史隔离；
- Provider Error 诊断和历史回滚；
- 后台任务调度；
- Trace、Span 和 Telemetry；
- Runtime 资源关闭顺序。

## 七、不采用的额外设计

### 7.1 不新增 AgentSession 包装 ManualAgent

现有 ManualAgent 已经拥有 AgentSession 的全部核心职责。新增包装对象只能转发 `submit` 和状态读取，无法形成独立职责，因此直接改名。

### 7.2 不把 SessionState 合并进 AgentSession

SessionState 是父子 AgentLoop、Memory、Prompt 和工具组件已经使用的窄共享依赖。合并后，下游组件必须依赖同时拥有主历史和 `submit` 能力的完整 AgentSession，扩大依赖范围。

保留 SessionState 可以继续让下游只接触会话状态，而 AgentSession 独占会话历史和编排能力。

### 7.3 不新增 SessionIdentity 值对象

当前 Session Identity 只有一个不可变字符串。SessionState 已经能够直接承载它，单独增加只包装一个字符串的对象没有额外约束或行为价值。

### 7.4 不新增 SessionContext 或 ThreadLocal

当前所有需要共享会话状态的组件都通过构造关系取得同一个 SessionState，不存在只能依靠隐式线程上下文跨越的边界。

引入 SessionContext 或 ThreadLocal 会隐藏依赖，并额外制造虚拟线程和异步任务的传播问题。

### 7.5 不使用 OpenTelemetry Baggage

本子需求不负责 Telemetry。SessionState 已经能够在 OpenTelemetry 未启用时保存业务 Identity，没有必要让业务对象依赖观测上下文。

后续 Telemetry 需求可以读取 SessionState 中的 `sessionId`，但不能反过来把 Baggage 或 Span 作为 Session Identity 的事实来源。

### 7.6 不新增 Session Repository

当前不支持保存、查询或恢复旧 Session。没有持久化用例时新增 Repository 只会形成没有消费者的接口和存储决策。

### 7.7 不引入 Turn

Session 子需求只关心多次用户提交共享同一份会话历史、状态和 ID。

一次提交如何形成 Trace、Span 在哪里开始、失败提交如何观测，均属于后续 Turn 或 Telemetry 需求，本次不提前决定。

---

## 八、边界条件

### 8.1 多次提交

同一个 AgentSession 的多次提交始终读取同一个 `sessionId` 和同一份 SessionState，并继续使用同一份主对话历史。

### 8.2 不同 Session

分别创建的 SessionState 和 AgentSession 必须具有不同的 `sessionId`，且不得共享主对话历史。

### 8.3 Sub-Agent

Sub-Agent 使用自己的局部消息历史，但继续使用父 Agent 所属的 SessionState，因此属于同一个 AgentSession。

### 8.4 Tracing 未启用

Session 创建和 `sessionId` 不依赖 OpenTelemetry。是否启用 tracing 不影响 AgentSession 的业务行为。

---

## 九、验证范围

自动化测试至少验证：

- 一个 SessionState 的 `sessionId` 非空且多次读取保持不变；
- 两个 SessionState 生成不同的 `sessionId`；
- AgentSession 返回其持有的 SessionState 对应的 `sessionId`；
- AgentSession 多次提交继续共享原有主对话历史；
- 父 Agent 与 Sub-Agent 继续共享同一个 SessionState；
- 名称调整后 Hook、Memory、Provider Error 和 history rollback 测试保持通过；
- 当前完整测试集不因纯名称和 Identity 增加而产生行为变化。

不为本需求新增 OpenTelemetry 测试依赖或外部存储测试。

---

## 十、性价比评估

该方案只增加一个不可变字符串字段和必要的只读入口，其余修改主要是现有类及引用的直接改名。

它解决了以下当前问题：

- ManualAgent 与 Session 的业务语义重复；
- AgentState 名称无法表达其实例属于一次具体 Session；
- 同一会话缺少稳定且明确的业务 Identity；
- 父 Agent、Sub-Agent 和其他组件的共享状态缺少统一的 Session 名称。

同时不改变现有执行链，不新增抽象层、传播机制、持久化接口或观测设计，是完成当前 Session 需求所需的最小改造。
