# AgentState 统一代理状态需求

## 需求描述

当前 CLI Session 中，记忆开关、权限模式、启动目录、默认工作目录、Agent 自身目录、可操作目录范围以及 Git 仓库上下文分别由不同组件保存。各个功能虽然能够独立运行，但系统没有一份统一对象表达“这个 Session 当前采用什么状态”，组件也可能长期持有创建时取得的值，导致运行中的真实状态与组件内部副本产生分歧。

本需求引入一份 CLI Session 级别的 `AgentState`，统一保存当前 Session 的语义状态、策略状态和路径上下文。一次 CLI 启动目前只创建一个 Session，因此也只创建一份 `AgentState`；后续所有用户 Turn、父 Agent 和 SubAgent 都复用这同一份状态。

`AgentState` 与 `AgentRuntime` 是由应用启动层或 Session 组装层共同创建和注入的两类并列对象：`AgentState` 表达当前 Session 的状态，`AgentRuntime` 持有执行所需的运行资源。`AgentRuntime` 不拥有 `AgentState`，其他组件按需持有 `AgentState` 的引用并读取当前值。

第一版 `AgentState` 纳入管理的状态包括：

```text
memoryEnabled
approvalMode
agentHome
workspace
allowedRoots
gitRoot
```

`memoryEnabled` 表示当前 Session 是否启用记忆能力。它由父 Agent 的 MemoryRuntime 消费，继续控制记忆提示、召回和回合结束处理；本需求不改变 SubAgent 当前不使用 MemoryRuntime 的行为。

`approvalMode` 表示当前 Session 的工具审批模式，是运行期间可修改的状态。Interactive 默认使用 `ASK`，Exec 默认使用 `BYPASS`。未来可以通过 `/permission` 或等价的受控入口修改；修改后，父 Agent 和 SubAgent 的后续工具调用必须立即按照新模式判断，任何组件都不能永久缓存创建时的审批模式。

`agentHome` 表示 Agent 自身拥有的数据和资源目录，用于区分 Agent 的内部运行数据与用户工作区中的交付物。它可以承载 `skills/`、日志、Trace、缓存和配置等 Agent 自身内容。

`workspace` 表示 Agent 的默认工作位置，是CLI 启动时进程所在的当前目录。它是 Session 组装阶段的输入，也是相对路径的解析基准和 Bash 的默认初始目录。当前实现可以使用启动时的 `cwd` 初始化 `workspace`；

`allowedRoots` 表示 Agent 被允许访问和修改的目录集合，而不是单个目录。`workspace` 可以是其中一个默认工作位置，但不应被直接当作完整权限边界。

`gitRoot` 表示当前 Git MCP 所需的启动配置。它在 CLI Session 启动时以启动 `cwd` 作为 Git 仓库发现的起点；未发现 Git 仓库时允许为空。第一版不要求运行期间切换 `gitRoot`，也不要求 Git MCP 随 `workspace` 变化自动重建。


系统职责按以下方式理解：

```text
AgentState
= 当前 CLI Session 的语义状态、策略状态和路径上下文

AgentRuntime
= Session 和 Agent 执行依赖的运行资源

ManualAgent
= 长期存在的主 Agent 和会话编排对象

ManualAgent.submit()
= 一次用户 Turn 的编排

AgentLoop
= Model / Tool 循环
```

“唯一状态”只约束 `AgentState` 管理的 Session 级状态：这些状态只能有一份权威来源。其他组件可以读取状态或持有 `AgentState` 引用，但不能再维护一份可能与之分歧的可变副本。

后台任务队列、线程池、正在执行的 Bash Process、会话 history、System Prompt 缓存、工具调度状态、AgentLoop 当前迭代状态和模型本轮返回值，仍由 `AgentRuntime`、`ManualAgent`、`AgentLoop` 或具体组件管理，不属于本需求要求统一进 `AgentState` 的范围。

当前一个 CLI Session 只对应一份 Agent 语义状态，因此第一版不再额外设计独立的 `SessionState`。


## 问题拆解

## 一、`AgentState` 尚不存在

当前 `AgentRuntime.create()` 接收的是多个分散参数：

[AgentRuntime.java:109](D:/learn_claudecode/learn-claude-code/demo/manual-agent/src/main/java/dev/learn/agent/manual/AgentRuntime.java:109)

```java
Path cwd,
boolean memoryEnabled,
ToolApprovalMode approvalMode,
Scanner scanner
```

应用层也分别创建工作目录、权限模式和记忆开关：

[ManualAgentApplication.java:42](D:/learn_claudecode/learn-claude-code/demo/manual-agent/src/main/java/dev/learn/agent/manual/ManualAgentApplication.java:42)

[ManualAgentApplication.java:143](D:/learn_claudecode/learn-claude-code/demo/manual-agent/src/main/java/dev/learn/agent/manual/ManualAgentApplication.java:143)

因此当前没有：

- CLI Session 级别唯一的 `AgentState`
- 明确的 Session 状态创建位置
- 父 Agent 和 SubAgent 对同一个状态对象的显式依赖

## 二、各字段仍由不同组件分别持有

| 需求字段 | 当前代码中的持有者 | 当前问题 |
| --- | --- | --- |
| `memoryEnabled` | `MemoryRuntime.enabled`、`ApplicationOptions` | 状态由 `MemoryRuntime` 持有，不在 `AgentState` |
| `approvalMode` | `ToolApprovalGate.mode` | Gate 保存创建时的固定副本 |
| `workspace` | `RuntimeContext.cwd`、`WorkspacePathResolver.workspace`、`BashTool.workspace` | 同一个语义被多个类分别保存 |
| `allowedRoots` | 不存在 | 当前只有单一 `workspace` |
| `agentHome` | 不存在 | Agent 内部资源仍直接从 workspace 推导 |
| `gitRoot` | `AgentRuntime` 局部变量、`RuntimeContext.gitRoot`、`GitMcpClient` | 启动发现行为正确，但没有统一状态来源 |

这正是需求中“唯一权威状态”尚未落地的主要表现。

`ToolApprovalGate` 中的模式是 `final`：

- 运行期间无法修改权限模式
- 没有 `/permission` 或等价入口

- 父 Agent 和 SubAgent 虽然共享同一个 Gate，但共享的是固定快照

## 五、`workspace` 仍被旧的 `cwd` 语义包裹

## 六、`agentHome` 尚未接入

当前尚未通过 `agentHome` 表达的 Agent 自身资源只有：

- Skills：`cwd/skills`

  [AgentRuntime.java:169](D:/learn_claudecode/learn-claude-code/demo/manual-agent/src/main/java/dev/learn/agent/manual/AgentRuntime.java:169)

- Terminal transcript：`workspace/.task_outputs/transcripts`

  [ManualAgentApplication.java:83](D:/learn_claudecode/learn-claude-code/demo/manual-agent/src/main/java/dev/learn/agent/manual/ManualAgentApplication.java:83)

以下数据本来就属于当前 workspace，不应迁移到 `agentHome`：

- ContextManager 工具结果：`workspace/.task_outputs/tool-results`
- Context 压缩前历史：`workspace/.transcripts`
- TaskStore：`workspace/.tasks`
- 项目记忆：`workspace/.memory`

因此，`agentHome` 接入只需要改变 Skills 和 Terminal transcript 的路径来源。TaskStore、ContextManager 和 MemoryRepository 继续从 `workspace` 派生存储路径。

## 七、`allowedRoots` 完全缺失

当前 `WorkspacePathResolver` 只有一个 `workspace`：

[WorkspacePathResolver.java:25](D:/learn_claudecode/learn-claude-code/demo/manual-agent/src/main/java/dev/learn/agent/manual/utils/WorkspacePathResolver.java:25)

不存在目录集合，也没有统一的 allowed roots 判断。

具体表现：

- 文件工具通过 `resolveExistingAnywhere()`、`resolveForWriteAnywhere()` 允许 workspace 外路径
- workspace 外写入只是触发审批，并不会被 allowed roots 拒绝
- `read_file` 可以读取 workspace 外路径
- `BashTool` 明确不是文件系统沙盒，可以通过命令访问任意位置
- `GlobTool` 只能搜索单个 workspace，无法处理多个允许目录

[WorkspacePathResolver.java:67](D:/learn/claude-code/demo/manual-agent/src/main/java/dev/learn/agent/manual/utils/WorkspacePathResolver.java:67)

[WorkspacePathResolver.java:123](D:/learn/claude-code/demo/manual-agent/src/main/java/dev/learn/agent/manual/utils/WorkspacePathResolver.java:123)

这是路径模型和权限模型都需要拆开的独立问题。

## 八、`gitRoot` 的行为基本符合，但状态归属不符合

当前代码确实：

1. 使用启动时的目录发现 Git root；
2. 未发现时允许为空；
3. 只在启动时创建 Git MCP；
4. 不在运行中动态切换 Git MCP。

这部分行为与当前需求一致。

但 `gitRoot` 目前只是：

```text
AgentRuntime 局部变量
    -> RuntimeContext.gitRoot
    -> GitMcpClient 固定参数
```

它没有进入 `AgentState`，因此仍然缺少统一权威来源。

## 九、需要补充的测试问题

现有测试主要覆盖旧模型，尚未覆盖：

- 一个 Session 只创建一份 `AgentState`
- 父 Agent 和 SubAgent 共享同一个 `AgentState`
- 修改权限模式后后续工具调用立即生效
- `agentHome`、`workspace`、`allowedRoots`、`gitRoot` 的初始化
- 多个 `allowedRoots` 的路径解析和符号链接边界
- Skills、Terminal transcript 与 workspace 所属的 Task、Context、Memory 数据之间的目录归属
