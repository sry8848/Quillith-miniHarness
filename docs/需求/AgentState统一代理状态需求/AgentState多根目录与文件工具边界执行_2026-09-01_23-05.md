# AgentState 多根目录与文件工具边界执行

## 1. 文档定位

本执行文档把 `allowedRoots` 落到 Java 文件工具的真实路径边界，并保留 `workspace` 只作为相对路径基准和默认搜索位置。

本轮能直接覆盖：

```text
read_file
write_file
edit_file
路径解析器
写入审批分类
```

`glob` 和 Bash 存在尚未确认的产品/安全契约，必须先完成第 2 节决策，不能由执行 AI 自行猜测。

## 2. 执行前必须确认的边界

### 2.1 `allowedRoots` 的启动值（已确认）

第一版由应用层创建：

```java
List<Path> allowedRoots = List.of(workspace);
```

这只是初始配置，不是单根限制。实现必须保留集合语义，不能校验集合长度、拒绝第二个目录或为未来追加目录增加特殊分支。

`tool-results` 继续位于 workspace，已经由初始的 workspace allowed root 覆盖，不需要为它追加 `agentHome` 或其他允许目录。

### 2.2 `glob` 的多根协议（已确认，A）

当前工具只有 `pattern`，结果始终是 workspace 相对路径。多个根目录后必须先选择并记录一种契约：

```text
方案 A：增加 root 参数，一次只搜索一个 allowed root
方案 B：一次搜索全部 allowed roots，结果返回绝对路径或带根标识的路径
方案 C：glob 第一版仍只搜索 workspace，并明确它不是 allowedRoots 全量浏览工具
```

执行 AI 不得自行选择。相同相对路径在两个根中可能冲突，继续只返回相对字符串会产生歧义。

### 2.3 Bash 边界

当前 `BashTool` 启动的是普通宿主进程。`ProcessBuilder.directory(workspace)` 只设置初始目录，不能阻止命令访问其他路径。

禁止通过字符串黑名单或解析 shell 命令伪装成 allowed-roots 沙盒。若需求要求 Bash 也受强边界约束，必须另行确定 OS sandbox、容器或受限执行环境。本执行文档只能声明并验证 Java 文件工具边界，不能宣称整个 Agent 已被文件系统隔离。

## 4. 本轮明确不做

- 不增加 OS sandbox。
- 不解析 Bash 命令中的路径。
- 不把审批等同于 allowed-roots 授权。
- 不允许用户通过一次 ASK 审批越过 allowed roots。
- 不把 `agentHome` 整体自动加入 `allowedRoots`。
- 不引入通用 VFS、Mount、PathPolicy 或规则引擎。
- 不修改 Git MCP 的仓库根目录。

## 5. 先写路径解析测试

扩展：

```text
src/test/java/dev/learn/agent/manual/utils/WorkspacePathResolverTest.java
```

使用两个临时目录作为 allowed roots，另建第三个禁止目录，至少覆盖：

1. 相对路径仍以 `workspace` 解析。
2. workspace 内已存在文件允许读取。
3. 第二个 allowed root 中的绝对路径允许读取和写入。
4. 第三个目录中的绝对路径被拒绝。
5. `..` 逃逸到未允许目录被拒绝。
6. allowed root 内符号链接指向未允许目录时被拒绝。
7. allowed root 外符号链接指回允许目录时，按真实目标位于允许目录处理。
8. 新文件通过最近已存在父目录解析，父目录链接逃逸时被拒绝。
9. 多个 roots 有父子重叠时不改变结果，不需要额外最小化集合算法。
10. `isInsideWorkspace()` 只分类 workspace，不把第二个 allowed root 当作 workspace。

Windows 创建符号链接可能受权限限制。沿用当前测试已有的条件跳过方式，不为测试引入平台模拟层。

## 6. 修改 `WorkspacePathResolver`

保留类名，避免只为命名产生全仓库重命名。修改它的职责注释为：

```text
workspace = 相对路径解析基准
allowedRoots = 文件工具可访问边界
```

构造器改为接收共享状态：

```java
public WorkspacePathResolver(AgentState agentState) throws IOException
```

路径解析器持有 `AgentState` 引用，不再保存自己的 workspace 字段。每次通过 `agentState.workspace()` 和 `agentState.allowedRoots()` 取得路径；第一版路径不可变，因此不需要动态更新集合或缓存。

### 6.1 统一公共方法

最终保留：

```java
public Path workspace()
public List<Path> allowedRoots()
public Path resolveExisting(String userPath) throws IOException
public Path resolveForWrite(String userPath) throws IOException
public boolean isInsideWorkspace(Path target)
public boolean isInsideAllowedRoots(Path target)
```

删除：

```java
resolveExistingAnywhere(...)
resolveForWriteAnywhere(...)
```

“Anywhere” 与新权限模型冲突，不能保留成旁路。

### 6.2 解析规则

`resolveExisting()`：

```text
1. workspace.resolve(userPath).normalize()
2. target.toRealPath() 解析目标和符号链接
3. 检查真实目标 startsWith 任一 allowed root
4. 不在集合内则抛 IOException
5. 返回真实目标
```

`resolveForWrite()`：

```text
1. 以 workspace 解析相对路径
2. 已存在目标直接 toRealPath()
3. 未存在目标向上寻找最近已存在父目录
4. 对真实父目录执行 allowedRoots 检查
5. 拼回尚不存在的后缀并 normalize
6. 对最终路径再次执行 allowedRoots 检查
7. 返回目标
```

`allowedRoots` 必须在 Session 创建阶段转为真实、绝对、已存在目录。解析器不要在每次工具调用中重复 `toRealPath()` 根目录，也不要吞掉无效 root。

边界判断使用一个直接循环或 stream `anyMatch` 即可，不新增 RootMatcher 抽象。

## 7. 修改文件工具

修改：

```text
ReadFileTool.java
WriteFileTool.java
EditFileTool.java
```

分别把：

```text
resolveExistingAnywhere -> resolveExisting
resolveForWriteAnywhere -> resolveForWrite
```

工具参数错误和 IO 错误继续沿用当前 `ToolExecutionResult.failure(...)` 形式。

边界拒绝发生在工具内部执行前。即使审批模式为 BYPASS，或者用户对一次调用选择 yes，也不能越过 `allowedRoots`。

## 8. 修改审批分类

修改：

```text
src/main/java/dev/learn/agent/manual/tool/approval/DefaultToolApprovalPolicy.java
```

写入分类保持现有语义，但只对 allowed roots 内的有效目标分类：

```text
workspace 内写入 -> NOT_REQUIRED
allowed root 内、workspace 外写入 -> REQUIRED
allowed roots 外 -> 解析失败，Policy 返回 NOT_REQUIRED，随后工具返回真实边界错误
```

Policy 解析失败时继续不替代工具错误。审批层只决定是否询问，不负责把非法路径包装成权限结果。

不要把 allowed roots 外路径分类为 `REQUIRED`，因为用户同意也不能使它合法。

## 9. 处理 `glob`

只有第 2.2 节协议确认后才修改 `GlobTool` 和测试。

无论选择哪种协议，都必须满足：

- 不跟随目录符号链接越过 allowed roots；
- 不把两个根中的同名相对路径合并成同一个结果；
- 继续保留 `MAX_RESULTS` 总上限和稳定排序；
- 工具描述准确说明搜索范围；
- 不把 agentHome 中未授权的配置、日志或凭证暴露给模型。

如果确认方案 C，本轮只需保持 `paths.workspace()` 搜索并更新验收说明，不要为“未来多根 glob”预留抽象。

## 10. Runtime 装配

`AgentRuntime` 只创建一个：

```java
WorkspacePathResolver paths = new WorkspacePathResolver(agentState);
```

父 Agent 和 SubAgent 的 read/write/edit/glob 工具、MemoryRepository（在其归属未调整前）以及审批 Policy 复用这个实例。

不要为每个 allowed root 创建一个 resolver，也不要为父子 Agent 复制集合。

## 13. 验收标准

- [ ] workspace 只承担相对路径基准，不再被当作完整权限边界。

- [ ] 多根目录和符号链接测试通过。
- [ ] “Anywhere” 解析旁路已经删除。
- [ ] 审批不能放行 allowed roots 外路径。
- [ ] workspace 外、allowed root 内的写入仍按现有规则询问。
- [ ] glob 行为符合用户已确认的协议。
- [ ] 没有用 Bash 字符串解析冒充沙盒。
- [ ] 文档和代码没有宣称 Bash 已受 allowed-roots 强隔离。
