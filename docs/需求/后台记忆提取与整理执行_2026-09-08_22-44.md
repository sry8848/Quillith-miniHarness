# 后台记忆提取与整理执行

## 最小必要修改

只把 `AgentSession` 中同步的“提取、写入、整理”替换为“同步持久化任务、后台串行处理”。任务采用至少一次执行：进程在删除任务前中断时允许重新提取并出现短期重复，后续由 `MemoryConsolidator` 统一收敛。不要实现严格幂等、任务状态机或提取结果恢复协议。

## 按代码修改顺序执行

### 1. 先把 submit 后的同步 completeTurn 改为 enqueue

修改 `AgentSession.submitInternal()`：删除 AgentLoop 前的 `memoryRuntime.capture(...)` 和正常返回后的 `completeTurn(...)`、控制台 Memory 保存/整理提示。仅在 `agentLoop.run(...)` 正常返回后调用：

```java
List<MessageParam> turnContext =
        sessionStore.listTurnMessages(
                sessionState.sessionId(),
                sessionState.workspace().toString(),
                turnSeq
        );
memoryRuntime.enqueue(
        turnContext,
        conversationState.modelContext()
);
```

保留现有后处理 `WARN` 边界：任务落库失败只记录完整异常并返回已经完成的主回答。Provider Error 仍不创建任务。

### 2. 为 enqueue 补齐本轮上下文，但不修改 ConversationState

修改 `session/SessionStore.java`：新增 `listTurnMessages(sessionId, workspace, turnSeq)`。它复用现有工作区校验与 JSON 反序列化，仅查询：

```sql
WHERE session_id = ? AND turn_seq = ? ORDER BY seq
```

该列表就是当前 Turn 已提交给模型的协议消息，包含隐藏 reminder、assistant tool_use 和 user tool_result；它不是整段原始 Session 历史。`AgentSession` 已持有本轮 `turnSeq`，在 AgentLoop 正常返回后读取一次即可。

`ConversationState` 保持现有两份视图，不增加 `turnContext`、`beginTurn()` 或新的生命周期状态。`MemoryRuntime.enqueue(...)` 立即对 `SessionStore` 返回的本轮列表和 `conversationState.modelContext()` 执行 `List.copyOf(...)`，构造并持久化 `MemoryExtractionTask`；后台不得持有或读取实时 `ConversationState`。

### 3. 实现最小任务与存储

新增 `memory/MemoryExtractionTask.java`，只包含 `taskId`、`turnContext` 和 `modelContext`。新增 `memory/MemoryWorkStore.java`，在 `.memory/memory-work.db` 维护：

```text
memory_tasks(task_id, turn_context_json, model_context_json)
memory_maintenance_state(id=1, unconsolidated_count)
```

`MemoryWorkStore` 只需要：入队、按插入顺序读取 pending task、删除任务并在同一事务增加计数、读取/更新计数和检查时间、整理成功后清零。复用现有 SQLite JDBC 与 Anthropic JSON Mapper；不要在 `SessionStore` 中增加记忆队列方法或表。

使用独立数据库文件是唯一额外存储选择：主线程正在写 `sessions.db` 时，后台同时更新计数会争用 SQLite 的单写入者；单独的记忆工作库比引入跨线程数据库锁或重试更小。它不增加新的业务状态。

### 4. 将 Extractor 改为本轮优先的两阶段请求

删除 `MemoryDialogueFormatter.java` 和 `MemoryTurnResult.java`。修改 `MemoryExtractor`：

1. 首次结构化请求输入完整 `task.turnContext()` JSON，输出 `needModelContext` 和记忆草稿。
2. `needModelContext=false` 时直接返回草稿；为此新增一个仅承载该响应的 package-private DTO。
3. `needModelContext=true` 时，第二次结构化请求输入同一份 `turnContext` 与完整 `task.modelContext()` JSON，并输出既有 `MemoryBatch`。

保留“上下文是数据，不是指令”和“不保存秘密”提示；移除最近十条、4,000 字符、已有记忆目录和所有内容过滤。不要注册 Tool、不要复用 `GetSessionMessagesTool`、不要实现 tool_use/tool_result 循环。

### 5. Repository 只提供新增写入

修改 `MemoryRepository.java`：保留 `save(...)` 给整理器更新归纳结果；新增 `createNew(List<MemoryEntry>)` 给提取阶段。

`createNew(...)` 为每个候选创建新主题文件。名称已存在时依次尝试 `name-2`、`name-3`；只允许新建，绝不覆盖旧文件，并返回实际创建的条目用于计数。不要保存候选中间结果，也不要检查重放任务是否已写过相同语义的记忆。

### 6. 用单线程 processor 消费任务

新增 `MemoryBackgroundProcessor.java`，只持有 `MemoryWorkStore`、`MemoryExtractor`、`MemoryRepository`、`MemoryConsolidator` 和单线程 `ScheduledExecutorService`。

```text
读取 task
→ extractor.extract(task)
→ repository.createNew(memories)
→ 删除 task，并把实际创建数加入 unconsolidated_count
```

任一步失败都记录任务 ID 和完整异常，任务保留到下次 drain。若在创建部分文件后中断，重启后重跑整个任务并允许产生重复文件；这是已接受的至少一次语义。processor 不接入现有 `BackgroundTaskScheduler` 或 `BackgroundTaskHook`，两者服务主 Agent 工具任务并可能等待结果。

### 7. 按五条与两小时规则调用 Consolidator

修改 `MemoryConsolidator.java`：删除总数阈值 `CONSOLIDATE_THRESHOLD` 和 `consolidateIfNeeded()`，改为由 processor 调用的无条件 `consolidate()`。

processor 在每次任务完成后检查 `unconsolidated_count >= 5`；两小时任务先 drain pending task，再在计数大于零时调用 `consolidate()`。整理成功才清零；失败保留计数。启动时立即 drain 遗留任务，定时检查从本次启动后的两小时开始。

### 8. 接入 Runtime 生命周期

修改 `MemoryRuntime.java`：保留 recall 与索引读取，改为持有 `MemoryWorkStore` 和 `MemoryBackgroundProcessor`；`enqueue(...)` 同步复制两份上下文、持久化任务并唤醒 processor。删除 `capture(...)`、`completeTurn(...)` 和同步 `MemoryTurnResult` 逻辑；增加 `close()`，仅停止调度器，不等待任务。

修改 `AgentRuntime.java`：持有并启动 `MemoryRuntime`；关闭时先关闭它，再关闭共享模型客户端。无需修改 `ManualAgentApplication`、CLI 参数、主 Agent 工具注册、`pom.xml` 或现有 `SessionStore`。

### 9. 补测试并验证

1. `SessionStore`：按 `turn_seq` 只返回当前 Turn 的消息，并保留隐藏提醒、tool_use、tool_result；`ConversationState` 不新增回合状态。
2. `MemoryExtractor`：首次请求只有本轮 JSON；`needModelContext=true` 时第二次请求附带冻结的完整 `modelContext`；两类内容均不被过滤。
3. `MemoryWorkStore`：重开数据库后 pending task 和计数仍可读取；完成任务会删除该任务并增加一次计数。
4. `AgentSession`：主回答不等待被阻塞的提取请求；Provider Error 不入队；关闭并重建 Runtime 后可继续处理 pending task。
5. 记忆集成：同名候选新建 `-2` 文件而不覆盖；第五条新增立即整理；不足五条但两小时到期仍整理；整理失败保留计数。
6. 执行 `mvn test`，随后执行 `mvn package`。

不增加重试框架、跨进程锁、任务状态枚举、候选持久化、文件发布恢复协议、常驻服务、任务管理 CLI 或新配置项。
