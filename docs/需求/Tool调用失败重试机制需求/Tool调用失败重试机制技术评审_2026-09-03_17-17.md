# Tool 调用失败重试机制技术评审

## 评审目标

本文评审“Tool 调用失败重试机制需求”的最小技术方案。

本阶段只分析并设计两个典型适配样本：

- 本地只读工具：`read_file`（`ReadFileTool`）；
- 远程只读 MCP 工具：GitHub MCP 经 `McpAgentTool` 包装后的一个工具。

不在本阶段逐个改造所有本地 Tool、Git MCP 或未来 MCP Server。本文建立公共 Harness 重试边界，并用两个样本证明异常分类和执行流程可行；其他 Tool 必须在后续按其副作用与错误语义单独适配，不能批量把现有异常一律标记为可重试。

## 当前代码逻辑

### 一、完整调用链

当前一次已完成的模型 `tool_use` 会经过以下链路：

```text
AgentLoop 接收并校验 JSON object
  → ToolCallDispatcher 按并发/后台模式调度
  → AgentLoop.executeTool
      → BeforeToolUse Hook
      → ToolApprovalGate
      → ToolRegistry.execute
          → AgentTool.execute
      → AfterToolUse Hook
  → ToolExecutionResult
  → AgentLoop.collectToolResults
  → Anthropic tool_result
```

`AgentLoop.executeTool()` 负责 Hook、审批和调用注册表；`ToolRegistry.execute()` 根据名称找到 `AgentTool` 并执行。当前 `ToolRegistry` 捕获所有 `RuntimeException`，记录完整堆栈后立即转换为文本失败结果：

```text
Error: tool execution failed unexpectedly: <message>
```

因此当前 Harness 没有机会识别“这次异常可重试”。所有未经 Tool 自行转换为 `ToolExecutionResult.failure(...)` 的运行时异常都会在注册表边界一次性结束。

工具结果按模型原始调用顺序回传；同一批明确并发安全的工具可并发运行，独占工具会形成前后顺序边界。调度器等待的是整个提交动作完成，因此如果在该动作内部实现重试，重试不会绕过既有的并发与副作用顺序约束。

### 二、ReadFileTool 当前逻辑

`ReadFileTool.execute(input)` 的当前行为为：

1. 校验 `path` 是字符串，`limit` 是正整数；参数不合法时直接返回 `ToolExecutionResult.failure`。
2. 用 `WorkspacePathResolver.resolveExisting` 解析路径和 allowed roots。
3. 若目标不是普通文件，直接返回失败结果。
4. 使用 `Files.newBufferedReader` 读取 UTF-8 内容；任何 `IOException` 都直接转换为 `Error: <message>` 的失败结果。

该实现安全且直观，但把“文件不存在、路径越界、权限不足”和“短暂共享锁、短暂 IO 故障”都折叠成了同一种 Tool Result。Harness 无法从结果中得知是否值得重新读取，也不会重试。

`ReadFileTool` 明确声明并发安全；这表示一次完整的读取尝试可以和同批只读工具并发，但不表示任何读取异常都可以安全重试。

### 三、McpAgentTool 当前逻辑

`McpAgentTool.execute(input)` 将模型 JSON 转为 `Map`，以 MCP Server 的原始名称调用 `McpToolClient.callTool`：

```text
模型侧 mcp__github__<tool>
  → McpAgentTool
  → McpToolClient.callTool(<remote tool>, arguments)
  → MCP CallToolResult
```

MCP 返回 `isError=true` 时，当前包装器把远端内容渲染成文本并返回 `ToolExecutionResult.failure`；正常结果则返回成功。MCP 客户端调用抛出的运行时异常会被 `ToolRegistry` 兜底成“unexpectedly”失败。

GitHub MCP 客户端已设置 30 秒初始化与请求 timeout，且以只读 Header 和只读工具集连接远端服务；但没有在本项目中实现按超时、连接失败、429 或 5xx 分类的 Tool 级重试。远端 `isError` 的内容当前只是文本，不能可靠推断为瞬时错误或参数错误。

### 四、当前边界及其影响

- `ToolExecutionResult` 当前只有 `content` 和 `error` 两个字段，最终失败没有 attempts 或 retry-exhausted 字段。
- `AgentLoop` 已将最大模型轮次限制在父 Agent 100 次、子 Agent 30 次；这不是单次 Tool Call 的重试预算。
- Anthropic 客户端的 `.maxRetries(2)` 属于模型 API 客户端配置，不能替代 Tool 调用重试。
- Provider 拒绝工具结果时已有最多两次的模型请求恢复；该恢复不重跑 Tool，不能复用为 Tool retry。

## 方案评估与决策过程

### 一、重试边界应放在 ToolRegistry，而不是 AgentLoop 或调度器

候选位置如下：

| 位置 | 结论 | 原因 |
| --- | --- | --- |
| `AgentLoop.executeTool` | 不选 | 这里同时管理 Hook 与审批。把重试循环放在此处容易重复触发审批、Before/After Hook，且会扩大 AgentLoop 职责。 |
| `ToolExecutionScheduler` / `ToolCallDispatcher` | 不选 | 它们解决并发、顺序和后台生命周期，不应了解 Tool 异常语义或等待退避。 |
| `AgentTool` 默认实现 | 不选 | 会把 Harness 的 attempts、backoff 和调度责任下沉给每个 Tool，导致重复实现和不一致。 |
| `ToolRegistry.execute` | 选择 | 它已经是“按名称定位具体 Tool 并调用”的唯一公共执行边界，天然可捕获 Tool 对外异常，并在不改变 Hook、审批和调度职责的前提下包住一次完整 Tool 执行。 |

因此重试循环放在 `ToolRegistry.execute(ToolCall)` 内。一次 Tool Call 的审批和 Hook 只执行一次；通过审批后，由注册表在同一个 `AgentTool.execute` 调用边界内重试。After Hook 只观察最终成功或最终失败结果，不会在中间失败时重复执行。

### 二、异常而不是 failure Result 作为重试信号

需求已经规定 Tool 使用异常类别向 Harness 表达可重试性。继续让 Tool 以 `ToolExecutionResult.failure` 表达“可重试失败”不可行：该 Result 只有文本和布尔值，Harness 只能猜测字符串含义，违反职责边界。

因此样本 Tool 的契约调整为：

```text
成功：返回 ToolExecutionResult.success(...)
可重试失败：抛 RetryableToolException
不可重试失败：抛 NonRetryableToolException
未分类 RuntimeException：由 Harness 默认按不可重试处理
```

现有 `ToolExecutionResult.failure` 不需要在本次全局删除。未迁移 Tool 可暂时维持现状，表示“已由 Tool 自己确定为最终失败”；但本需求覆盖的 Tool 失败路径必须改为抛出分类异常，才能由 Harness 实现重试。

### 三、异常类型保持最小

新增两个位于 `dev.learn.agent.manual.tool` 包的异常类：

```java
final class RetryableToolException extends RuntimeException
final class NonRetryableToolException extends RuntimeException
```

它们提供 `message` 和 `cause` 构造器即可。两者使用非受检异常，原因是当前 `AgentTool.execute` 不声明 checked exception；引入 checked exception 会迫使全部 Tool 和调用链改签名，但并不会增加本需求所需的信息。

不新增抽象异常父类、错误码体系、通用错误分类器或每个 Tool 的重试策略接口。Harness 只需要 `instanceof RetryableToolException`；其余 `RuntimeException` 都按未知异常处理。这正好满足“Tool 决定可重试性、Harness 不认识内部错误”的边界。

### 四、配置保持一个小值对象

需求要求 `initialDelay`、`maxDelay`、jitter 范围可配置。仅把这些散落为 `ToolRegistry` 常量将无法完成该要求。

建议新增不可变 `ToolRetryPolicy` 值对象，字段仅包括：

```text
maxAttempts
initialDelay
maxDelay
jitterRatio
```

`maxAttempts` 在默认策略中固定为 3。该对象在 `AgentRuntime` 创建一次并传入父、子 `ToolRegistry`；测试可构造更短的 delay。此处的“可配置”指可由装配点显式提供，不在本需求中新增 CLI 参数、环境变量约定或通用配置中心。

选择单一值对象而不是“重试框架”的原因是：当前系统只有一个 Tool 执行边界和一个统一预算，独立框架、注解或 Tool 级策略注册表都没有额外收益。

### 五、退避算法的选择

第 `n` 次可重试失败后的基础等待为：

```text
baseDelay = min(initialDelay × 2^(n - 1), maxDelay)
```

最终等待时间在 `baseDelay` 周围施加由 `jitterRatio` 定义的随机扰动，并在计算后限制到 `maxDelay`。算法应由 `ToolRegistry` 的私有方法完成；测试验证等待值处于预期范围，而不绑定某个随机数。

循环等待使用 `Thread.sleep`。若等待线程被中断，Harness 恢复中断标记、停止重试并返回最终失败；不能忽略中断后继续调用 Tool。

## 推荐架构

### 一、类与依赖关系

```text
AgentLoop
  └─ ToolRegistry.execute(toolCall)
       ├─ ToolRetryPolicy
       ├─ AgentTool.execute(input)
       │    ├─ ReadFileTool（样本）
       │    └─ McpAgentTool（样本）
       └─ ToolExecutionResult
```

新增类型仅为：

- `RetryableToolException`；
- `NonRetryableToolException`；
- `ToolRetryPolicy`。

不新增 `RetryExecutor`、全局异常分类器、Tool 重试注解或第二套调度器。重试逻辑作为 `ToolRegistry.execute` 的私有循环存在，避免一层只被此处使用的抽象。

### 二、核心伪代码

```java
ToolExecutionResult execute(ToolCall toolCall) {
    AgentTool tool = findToolOrReturnUnknownFailure(toolCall);

    for (int attempt = 1; attempt <= retryPolicy.maxAttempts(); attempt++) {
        try {
            return requireNonNull(tool.execute(toolCall.input()));
        } catch (RetryableToolException exception) {
            if (attempt == retryPolicy.maxAttempts()) {
                logFinalFailure(toolCall, exception, attempt);
                return retryFailure(toolCall, exception, attempt, true);
            }

            logRetry(toolCall, exception, attempt);
            sleep(calculateRetryDelay(attempt));
        } catch (NonRetryableToolException exception) {
            logFinalFailure(toolCall, exception, attempt);
            return retryFailure(toolCall, exception, attempt, false);
        } catch (RuntimeException exception) {
            logFinalFailure(toolCall, exception, attempt);
            return retryFailure(toolCall, exception, attempt, false);
        }
    }

    throw new IllegalStateException("unreachable");
}
```

这里捕获的未知异常限定为 `RuntimeException`，不捕获 `Error`。`OutOfMemoryError`、`StackOverflowError` 等 JVM 级故障不能伪装成普通 Tool 失败继续运行。

### 三、最终失败结果

为了避免本次为重试机制扩展整套结果层次，保留 `ToolExecutionResult(content, error)` 的现有形态。`ToolRegistry` 在最终失败时生成稳定、字段明确的文本内容，例如：

```text
Tool call failed
tool: read_file
exception_type: RetryableToolException
message: temporary file busy
attempts: 3
retry_exhausted: true
```

然后以 `ToolExecutionResult.failure(content)` 交回现有 `AgentLoop`。这样 Agent 能获得需求要求的全部字段，`tool_result.is_error` 仍为 `true`，且不需要让 Hook、输出打印器、上下文预算和 Anthropic 协议适配一并修改。

完整堆栈继续只写本地日志；模型侧不接收 stack trace、路径细节或下游敏感信息。未来若需要按错误码聚合指标，再独立设计结构化 `ToolExecutionResult`，不在本需求预先扩张。

## 两个典型 Tool 的适配方案

### 一、ReadFileTool

`ReadFileTool` 是只读工具，重新读取同一文件通常不会产生副作用，但仍需要由 Tool 精确判断何时安全、何时有意义。

建议分类：

| 当前失败点 | 适配后语义 | 理由 |
| --- | --- | --- |
| `path` 非字符串、`limit` 非正整数 | `NonRetryableToolException` | 重试不会修正模型参数。 |
| 路径不在 allowed roots、路径不存在、不是普通文件 | `NonRetryableToolException` | 当前调用前置条件不满足，重复读取没有价值。 |
| 明确可识别的临时文件占用或临时文件系统故障 | `RetryableToolException` | 工具确认再次完整读取安全，且短暂等待可能恢复。 |
| 权限不足、编码/内容处理失败 | `NonRetryableToolException` | 重试通常无意义或不是临时故障。 |
| 无法明确识别的 `IOException` | `NonRetryableToolException` | 遵守未知错误默认不重试的需求，不从异常文本猜测。 |

实现时不应把所有 `IOException` 标为可重试。特别是在 Windows 下，`AccessDeniedException` 既可能表示文件占用，也可能表示真实权限不足；只有能利用异常类型、平台错误码或可靠的内部上下文明确证明“临时占用”时才转换为 `RetryableToolException`。

### 二、GitHub MCP 的 McpAgentTool

本样本限定为 GitHub MCP 当前暴露的只读能力。对这类调用，重复发送相同查询在业务语义上通常安全；但“安全”不等于任何失败都应该重试。

建议分类：

| 当前失败点 | 适配后语义 | 理由 |
| --- | --- | --- |
| 模型参数已被 MCP Server 以 `isError=true` 拒绝 | `NonRetryableToolException` | 当前 MCP 返回只有文本，不能可靠从文本猜测临时性；默认不重试。 |
| 客户端明确识别的连接超时、临时连接失败、HTTP 429、HTTP 5xx | `RetryableToolException` | 由 GitHub MCP 客户端或其 Tool 包装层根据具体 SDK 异常转换；只读请求可安全重发。 |
| 认证失败、授权不足、参数错误、非瞬时 4xx | `NonRetryableToolException` | 重试相同请求没有价值。 |
| 未识别 SDK RuntimeException | 保持未知异常 | Harness 默认不重试。 |

必须注意：`McpAgentTool` 不能根据远端返回的自由文本含有“timeout”“busy”等词来决定重试。这会把 Harness 不应理解的下游语义换成脆弱的字符串匹配。正确做法是由 GitHub MCP 客户端在仍能获得 HTTP/SDK 异常类型的边界，将已确认的瞬时故障转换为 `RetryableToolException`；`McpAgentTool` 对普通 `isError` 结果保守地视为最终失败。

本结论不自动推广到 Git MCP 或未来 MCP Server。任何可能写入、创建资源或改变远端状态的 MCP Tool，必须先证明幂等或重复执行安全，才能抛出 `RetryableToolException`。

## 与现有并发、审批、Hook 的关系

- 调度器提交的 action 是整个 `AgentLoop.executeTool` 管线；注册表中的重试循环完成前，该 action 不会结束。因此重试不会使后续独占工具越过当前调用。
- `BeforeToolUse` 与审批只执行一次。用户批准的是同一 Tool Call 的有限重试，不会在每个 attempt 重复弹窗。
- `AfterToolUse` 只接收最终结果，不为中间失败重复触发；否则日志、工作区 Hook 或后置副作用会被放大。
- 工具调用终端展示保持一次；新增 retry 日志应记录 Tool 名称、attempt、异常类型和等待时间，但不得重复展示为多个独立模型 Tool Call。
- 当前 `tool.execute <tool-name>` span 覆盖完整重试流程；实现阶段应在 span 上记录 attempts、是否恢复成功、是否耗尽，并为每次 retry 添加事件，而不是为同一模型 Tool Call 创建平行的业务 span。

## 测试方案

### 公共 ToolRegistry 单元测试

使用一个可控 `AgentTool` 替身验证：

1. 第一次成功：调用一次，返回成功。
2. 第一次 `RetryableToolException`、第二次成功：调用两次。
3. 连续三次可重试异常：调用三次，结果含 `attempts: 3` 与 `retry_exhausted: true`。
4. 三次不同可重试异常：仍只调用三次。
5. 第一次不可重试异常：调用一次。
6. 第一次可重试、第二次不可重试：调用两次后停止。
7. 未知 `RuntimeException`：调用一次后停止。
8. 退避计算：各 attempt 的等待值在基础退避与 jitter 的允许范围内；测试策略使用极短 delay，避免慢测试。
9. 等待被中断：恢复中断标记，不再执行下一次 Tool。

### ReadFileTool 样本测试

覆盖参数错误、路径不存在、allowed root 外路径均被归类为不可重试；再通过可控制的文件访问替身或明确的可识别临时异常验证它能抛出可重试异常。不要依赖真实操作系统文件锁做核心测试，因为不同平台的锁语义不稳定。

### GitHub MCP 样本测试

使用 `McpToolClient` 替身验证：普通 `isError` 不重试；明确映射后的临时连接/限流异常可重试；认证或参数异常不重试；成功结果维持当前文本渲染逻辑。测试不访问真实 GitHub 网络。

## 复杂度与范围控制

本方案新增两个语义异常、一个策略值对象，并在既有 `ToolRegistry.execute` 中增加有限循环。它不改变 Tool 调度器、AgentLoop 的协议组装、Hook 顺序、审批模式或 Anthropic 消息格式。

刻意不做的事情：

- 不在 Harness 中建立 IOException、HTTP 或 MCP 文本错误分类表。
- 不把重试下沉到每一个 Tool。
- 不增加全局重试框架、注解或多级策略继承。
- 不在本阶段实现熔断、fallback、幂等、限流或 metrics 平台。
- 不批量修改所有 Tool；仅以 `read_file` 和 GitHub MCP 为首批样本。

因此该方案能完成需求的统一语义和有限重试，同时把适配成本限制在真正需要证明可重试性的 Tool 上。

## 实施前置条件

开始编码前需要确认：

1. `ToolRetryPolicy` 默认值中 `initialDelay`、`maxDelay` 与 `jitterRatio` 的具体数值；本需求只固定 `maxAttempts = 3`。
2. GitHub MCP SDK 在当前版本中可用于稳定识别 timeout、429 和 5xx 的异常类型或状态信息；若不能稳定识别，首版只能把未识别客户端异常保守地视为不可重试。
3. ReadFileTool 在目标操作系统中识别“临时文件占用”的可靠条件；无法可靠判断时，不将其列为可重试。
