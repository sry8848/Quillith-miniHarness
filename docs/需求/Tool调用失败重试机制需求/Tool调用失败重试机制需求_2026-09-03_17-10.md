# Tool 调用失败重试机制需求

## 需求描述

当前 Harness 执行 Tool Call 时，Tool 失败会直接结束本次调用并把错误交回 Agent。对于临时文件占用、短暂 IO 故障、连接超时或服务暂时不可用等问题，立即失败会降低任务成功率；但对参数错误、权限不足或已产生副作用的调用自动重试，又可能无效甚至造成重复操作。

本需求为 Harness 增加统一的 Tool 调用失败重试机制。Tool 负责把内部错误转换为“可重试”或“不可重试”的业务语义；Harness 不识别 Tool 内部错误类型，只根据 Tool 对外抛出的异常类型决定是否重试、何时重试和何时停止。

一句话概括：**Tool 决定“这个错误能不能重试”，Harness 决定“什么时候重试、最多重试多少次”；所有可重试错误共享一次 Tool Call 的统一重试预算。**

## 需求目标

- 为 Harness 中的 Tool 调用提供统一、有限、可观测的失败重试流程。
- 保持 Tool 对内部异常、协议和业务语义的所有权，Harness 不判断具体 IO、HTTP 或业务错误是否可重试。
- 同一 Tool Call 的全部可重试异常共享最多三次执行的 attempts 预算。
- 使用指数退避和随机抖动，避免多个失败调用同时集中重试。
- 最终失败必须把足以支持 Agent 决策的信息交回 Agent。
- 未明确分类的未知异常默认不重试，避免程序 Bug 或副作用不确定性导致重复执行。

## 概念模型与职责边界

### Tool 的职责

Tool 负责：

- 执行具体业务操作。
- 识别自身内部发生的错误。
- 将安全且可能因再次完整执行而成功的错误转换为 `RetryableToolException`。
- 将参数、权限、前置状态、业务校验或重复执行存在风险的错误转换为 `NonRetryableToolException`。
- 提供最终异常信息，供 Harness 和 Agent 记录、展示与后续处理。

Tool 不负责维护尝试次数、等待退避时间或调度下一次调用。

### Harness 的职责

Harness 负责：

- 捕获 Tool 对外抛出的异常。
- 仅根据异常是否为 `RetryableToolException` 判断是否进入重试。
- 维护当前 Tool Call 的 attempts 计数。
- 在相邻尝试之间执行指数退避和随机抖动。
- 在 attempts 耗尽时停止重试。
- 将最终成功结果或最终失败结果交回 Agent。

Harness 不负责判断 `IOException`、HTTP 状态码、文件错误码或某个 Tool 业务异常的可重试性；这些语义必须在 Tool 内部完成转换。

### Agent 的职责

Agent 不参与 Harness 的自动重试调度。它只接收最终结果，并根据最终错误决定是否修正参数、选择其他 Tool、向用户说明失败或结束任务。

## 异常分类

### RetryableToolException

`RetryableToolException` 表示当前调用失败，但重新**完整执行一次同一 Tool Call**是安全的，并且存在成功可能。

典型示例：

- 临时文件占用；
- 临时 IO 错误；
- 连接超时；
- 临时服务不可用。

抛出该异常隐含 Tool 的明确承诺：再次执行不会造成不可接受的重复副作用，且重试有实际成功可能。

### NonRetryableToolException

`NonRetryableToolException` 表示继续执行相同 Tool Call 没有意义，或重复执行存在风险。

典型示例：

- 参数错误；
- 文件不存在；
- 权限不足；
- 前置状态不满足；
- 业务校验失败。

Harness 收到此异常后必须立即停止当前 Tool Call，不能继续尝试。

### 未知异常

Tool 未明确转换的任何未知异常，默认按不可重试处理。

原因是未知异常可能代表程序 Bug、部分副作用已经发生，或当前状态不可判断；在没有 Tool 明确保证可安全重试前，Harness 不得为了提高成功率而重复调用。

## Attempts 预算

本需求固定采用：

```text
maxAttempts = 3
```

语义为：

```text
首次执行 1 次
+
最多额外重试 2 次
=
同一 Tool Call 最多执行 3 次
```

attempts 按一次完整 Tool Call 统一累计，而不是按异常类别分别累计。不同 `RetryableToolException` 之间不重置预算。

例如：

```text
Attempt 1 → Timeout
Attempt 2 → FileBusy
Attempt 3 → TemporaryIOException
```

三次异常即使类型都不同，仍已耗尽同一个 `maxAttempts`，Harness 必须停止并交回最终失败。

## 重试策略

仅在捕获到 `RetryableToolException` 且当前 attempts 尚未达到 `maxAttempts` 时重试。

两次尝试之间使用：

```text
指数退避 + 随机抖动（Jitter）
```

基础退避示例：

```text
第 1 次失败后：约 500 ms
第 2 次失败后：约 1000 ms
```

实际等待时间必须在基础退避时间上加入随机抖动，避免大量 Tool Call 因同类故障在相同时间再次冲击下游服务。

`initialDelay`、`maxDelay` 与 jitter 范围应作为可配置参数；具体默认值在技术评审和实现阶段确定。本需求只固定 `maxAttempts = 3` 的语义。

## 执行规则

```text
执行 Tool
  ↓
成功 → 返回 Tool Result

失败
  ↓
RetryableToolException？
  ├─ 否
  │   ├─ NonRetryableToolException → 立即返回最终错误
  │   └─ 未知异常 → 默认不重试，返回最终错误
  │
  └─ 是
      ↓
      attempts < maxAttempts？
      ├─ 是 → backoff + jitter → 再次完整执行 Tool
      └─ 否 → 返回“重试耗尽”的最终错误
```

“再次执行”必须是一次完整的同一 Tool Call，不允许 Harness 试图修改参数、猜测补偿动作或只重试 Tool 内部某一个未对外暴露的步骤。

## 最终失败处理

发生以下任一情况时，Harness 停止执行当前 Tool Call：

- 捕获 `NonRetryableToolException`；
- 捕获未知异常；
- 捕获 `RetryableToolException`，但 `maxAttempts` 已耗尽。

Harness 交回 Agent 的最终失败结果至少包含：

- Tool 名称；
- 最终异常类型；
- 异常信息；
- 实际执行 attempts；
- 是否因重试耗尽失败。

若为重试耗尽，结果必须明确表示“已执行多少次、可重试预算是否耗尽”，避免 Agent 将它误判为参数问题并无意义地重复同一调用。

## 场景与验收标准

| 场景 | 预期行为 |
| --- | --- |
| Tool 第一次成功 | 执行 1 次并正常返回 |
| 第一次 `RetryableToolException`，第二次成功 | 执行 2 次并正常返回 |
| 连续 3 次 `RetryableToolException` | 最多执行 3 次，随后返回最终错误，标识重试耗尽 |
| 三次可重试异常类型不同 | 仍共享 `maxAttempts = 3`，不因类型不同重置预算 |
| 第一次 `NonRetryableToolException` | 不重试，立即返回 Agent |
| 第一次可重试、第二次不可重试 | 第二次失败后立即停止，不执行第三次 |
| Tool 抛出未知异常 | 默认不重试，返回最终错误 |
| 发生重试 | 相邻两次调用之间存在指数退避和随机抖动 |
| 最终失败 | Agent 可获得 Tool 名称、最终异常类型、错误信息、实际 attempts 与耗尽标记 |

## 不在本次范围内

- Harness 根据 `IOException`、HTTP 状态码、文件错误码或业务错误文本自行推断可重试性。
- 自动修正 Tool 参数。
- 对失败 Tool 自动选择其他 Tool 或实现业务 fallback。
- 熔断、限流、健康检查或下游服务自动摘除。
- 对已有副作用进行补偿或回滚。
- 幂等机制的设计与实现。
- 修改 Agent 的最终决策逻辑；Agent 只消费最终结果。
- 修改 `maxAttempts = 3` 的统一语义。

## 调研与决策记录

### 已确认决策

1. 可重试性由 Tool 决定，Harness 只识别对外异常类别。
2. 未知异常默认不可重试。
3. 同一 Tool Call 的所有可重试错误共享同一 attempts 预算。
4. `maxAttempts` 表示总执行次数，不是“额外重试次数”；本需求固定为 3。
5. 重试之间必须使用指数退避和 jitter。
6. 最终失败必须回传 attempts 与是否耗尽，支持 Agent 做下一步决策。

### 后续技术评审需明确的问题

- `RetryableToolException` 与 `NonRetryableToolException` 的继承关系、字段和错误序列化形式。
- Harness 重试入口放在现有 Tool 调度与执行管线的具体位置。
- `initialDelay`、`maxDelay`、jitter 算法及配置来源。
- 等待期间的线程模型、取消语义与 Tool timeout 的关系。
- 最终失败如何映射到当前 `ToolExecutionResult`，以保留结构化字段而不破坏模型 Tool Result 协议。
- 哪些现有 Tool 能安全抛出 `RetryableToolException`；任何可能有副作用的 Tool 在未证明安全前应保持不可重试。
