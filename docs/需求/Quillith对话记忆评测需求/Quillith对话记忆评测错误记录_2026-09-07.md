# Quillith 对话记忆评测错误记录

## 1. 文档目的

本文只记录官方 LongMemEval Case `edced276` 首次接入过程中的真实错误、已采取的修复和仍然缺失的观测能力。

评测是否答对与执行链路是否可靠是两件事：

- 官方题答错可以作为能力基线保留，不为得到通过分数修改原题、参考答案或 Judge；
- 环境无法构建、进程退出后长期阻塞、正常 FIFO 被破坏等属于执行链路错误，需要修复后再继续；
- 性能慢但内部阶段无法定位时，只记录现象和观测缺口，不把推测写成根因。

## 3. 错误时间线

### 3.1 第一次运行：Ubuntu 软件源返回 502

Job：`quillith-memory-edced276-first-run`

实际错误：

```text
Failed to fetch ... libjpeg-turbo8 ... 502 Bad Gateway
```

判断：环境构建错误，Agent 尚未开始，不代表 Quillith 记忆能力失败。

处理：第一次出现时保留错误并重试，没有立即扩大 Dockerfile。

同时发现 Harbor CLI 在 Windows GBK 终端输出 Unicode 符号时触发 `UnicodeEncodeError`。后续运行进程显式使用 UTF-8，避免 CLI 展示错误掩盖 Trial 的原始错误。

### 3.2 第二次运行：Ubuntu 软件源再次返回 502

Job：`quillith-memory-edced276-second-run`

实际错误：

```text
Failed to fetch ... libldap2 ... 502 Bad Gateway
```

判断：不同软件包连续出现同类 502，说明不是单一包损坏，而是构建时网络波动。

根因修复：只在 Task Dockerfile 的 `apt-get` 上增加 `Acquire::Retries=5`。没有增加与运行无关的软件包，也没有更换官方基础镜像。

### 3.3 第三次运行：空 Memory 被误判为损坏

Job：`quillith-memory-edced276-third-run`

表面结果：

```text
Agent execution timed out after 600.0 seconds
```

JVM 的真实启动错误：

```text
java.nio.file.NoSuchFileException: /app/.memory/MEMORY.md
```

根因：`SessionStore` 会先创建 `.memory/sessions.db`。原来的 `MemoryRepository.readIndex()` 只要看到 `.memory` 目录存在，就要求 `MEMORY.md` 必须存在，因此一个只有 Session 数据库、尚未保存长期记忆的合法初始状态被当成损坏状态。

根因修复：

- `.memory` 不存在时视为空 Memory；
- `.memory` 中只有 `sessions.db`、没有任何 topic Markdown 时也视为空 Memory；
- 已有 topic Markdown 却缺少 `MEMORY.md` 时继续抛错，不能吞掉真实损坏。

验证：增加“只有 Session DB 时为空 Memory”和“已有 topic 但缺 index 时仍失败”两个测试。

伴生问题：JVM 启动后退出，但 Adapter 仍阻塞等待 response FIFO，因此 Harbor 只能等到 600 秒超时。Verifier 随后找不到 `final_answer.json`，这是 Agent 没有完成后的次生错误，不是独立根因。

### 3.4 第四次运行：执行链路可前进，但 600 秒不足

Job：`quillith-memory-edced276-fourth-run`

真实现象：

- 同一个 JVM PID 连续完成 recorded Turn；
- 运行推进到第 9 个 recorded Turn；
- 600 秒到达后触发 `AgentTimeoutError`；
- 最终问题尚未执行，因此没有 `final_answer.json`。

判断：这次不是死锁；日志证明 Quillith 一直在推进。当前每个 recorded Turn 仍执行 Memory recall、历史快照、Memory 提取/保存以及可能的 consolidation，整题包含 9 个 recorded Turn 和 1 个真实回答 Turn，600 秒不足以覆盖实际运行时间。

处理：仅把该 Task 的 Agent timeout 从 600 秒调整为 1200 秒。此调整不改变题目、模型输出或评分规则，因此不是强行让评测通过。

尚不能下的结论：没有阶段级耗时数据，不能断言主要耗时一定来自 recall、extract、consolidate 或 Provider 中的某一个。

### 3.5 第五次运行：Provider HTTP/2 流被取消后，Adapter 无法感知 JVM 退出

Job：`quillith-memory-edced276-fifth-run`

真实错误：

```text
okhttp3.internal.http2.StreamResetException: stream was reset: CANCEL
```

该异常发生在第 2 个 recorded Turn 的 Memory/Provider 调用路径，随后 JVM 退出。

根因：Adapter 的 FIFO 协议只有成功响应，没有进程退出响应。JVM 在请求处理中退出后，Python 继续等待 response FIFO，失败会被伪装成一个长达 1200 秒的超时。

根因修复目标：Java 进程退出时向 response FIFO 写入 `PROCESS_EXIT <code>`，Python 立即抛出包含退出码的 `RuntimeError`。这不重试 Provider，也不吞掉原始 JVM 日志。

本次运行由人工中断无意义的等待，所以 Job 元数据仍显示 running；它不是一条完成的 Harbor 结果。

### 3.6 第六次运行：第一次进程退出检测破坏了正常 FIFO 语义

Job：`quillith-memory-edced276-sixth-run`

实际结果：进程退出能在约 1 分钟内被报告为：

```text
Quillith Harbor 进程已退出：PROCESS_EXIT 1
```

但 JVM 的真实错误变成：

```text
Harbor 请求管道未收到完整请求
```

根因：为了同时处理“JVM 启动即失败”，第一次实现让 Python 用 `O_RDWR` 长期持有 request/response FIFO。request FIFO 的 writer 不再随每个命令关闭，Java 完成 Turn 1 后重新打开 reader 时读到了错误的 EOF/边界，正常协议被观测修复本身破坏。

根因修复：

- 恢复原来每个请求单独打开、写入并关闭 request FIFO 的行为；
- Java 退出包装器临时启动一个 request drainer，只用于解除“启动失败时还没有 Java reader”的写阻塞；
- 写出 `PROCESS_EXIT <code>` 后终止 drainer；
- 增加 Python 测试，确认退出被立即报告且不再使用 `O_RDWR`。

反思：错误检测不能改变被检测协议的正常生命周期。第一次修改只验证了异常路径，没有先验证一个正常 Turn，导致修复制造了新错误。

### 3.7 第七次运行：第 9 轮 Memory consolidation 遇到 Provider 流取消

Job：`quillith-memory-edced276-seventh-run`

最终结果：Harbor `RuntimeError`，没有进入 Verifier，未产生评测分数。

执行证据：

- 同一个 JVM PID `66` 连续完成了前 8 个 recorded Turn；
- 第 9 个 recorded Turn 已开始；
- 第 9 轮在 `MemoryRuntime.completeTurn()` 调用 `MemoryConsolidator.consolidateIfNeeded()` 时失败；
- Provider 抛出 `AnthropicIoException`，底层原因仍是 `StreamResetException: stream was reset: CANCEL`；
- Java 进程退出后，Adapter 收到 `PROCESS_EXIT 1` 并立即报告 `RuntimeError`；
- 总运行时间为 16 分 35 秒，没有等满 1200 秒；
- 最终问题没有执行，因而没有 `final_answer.json`，Judge 也没有运行。

关键调用栈：

```text
MemoryConsolidator.consolidateIfNeeded()
→ MemoryRuntime.completeTurn()
→ AgentSession.submitInternal()
→ AgentSession.submitRecorded()
→ AnthropicIoException
→ StreamResetException: stream was reset: CANCEL
```

结论：

- FIFO 正常 Turn 语义和新的进程退出检测已在长链路中共同得到验证；
- 本次失败点是 Memory consolidation 的真实 Provider I/O 错误，不是 Harbor timeout；
- 这也是第五次运行中同类 `StreamResetException` 的第二次真实出现，但这次调用栈把阶段明确定位到了 consolidation；
- 按“记录真实结果，不强制通过”的约定，本轮停止，不通过增加重试、跳过 consolidation、修改官方历史或重复运行来获得通过结果。

本次链路验证结果应记为“执行错误、未评分”，不能把 Harbor summary 中用于展示异常 Job 的 `Mean: 0.000` 解释成记忆问答得分 0。

### 3.8 第七次运行结束后：Memory 内容没有被 Harbor 归档

运行时的 Memory 确实写入了容器内的 `/app/.memory`，stdout 也记录了多轮保存和 consolidation 数量。但 Trial 结束后 Harbor 删除了容器，而当前 Job 只归档 `/logs`：

```text
Job 目录中没有 MEMORY.md
Job 目录中没有 topic Markdown
Job 目录中没有 sessions.db
第七次运行的容器已不存在
```

因此，目前只保留了“本轮保存了几条 Memory”等日志证据，没有保留模型实际生成的 Memory 内容，已经无法从第七次运行恢复。

这是执行产物设计遗漏。若“记录结果”包含 Memory 中间产物，不能只在整题成功结束后复制，因为 JVM 可能像本次一样在第 9 轮退出。最小修复方向是让该 Trial 的 `/app/.memory` 从启动时就落到 Harbor 会归档的 `/logs/agent/memory`；这样每一轮持久化完成后内容就已成为 Job 产物，不需要修改 Memory 业务逻辑。

这项修复尚未实施。它涉及是否长期保留完整对话衍生内容，正式实施前需要确认产物保留边界。

### 3.9 后台启动：下游参数被 PowerShell 位置绑定截获

Job：`memory-longmemeval-edced276-20260908-122907`

后台进程已经退出，Harbor 没有创建 Job。launcher stderr 为：

```text
OpenTelemetry Java Agent 不存在：--path
```

根因是 `start-job.ps1` 直接把 `--path` 等 Harbor 参数追加到 `quillith-harbor-run.ps1` 调用后面。PowerShell 在进入 Harbor 前先完成脚本参数绑定，将 `--path` 当成了可选位置参数 `OpenTelemetryAgentPath` 的值。

处理：

- 使用命名参数 `-HarborArguments @(...)` 显式传递全部 Harbor 参数；
- 后台启动时持久化进程 ID；
- 进程已退出且 Job 未创建时，状态改为 `LAUNCH_ERROR`，不再长期显示 `STARTING`。

本次失败发生在 Harbor 创建 Job 之前，没有调用题目模型，不产生能力评测结果。

### 3.10 修复后再次启动：worker 续行失效且 Docker 未运行

Job：`memory-longmemeval-edced276-20260908-124547`

状态脚本正确报告了 `LAUNCH_ERROR`。launcher 日志同时包含：

```text
Docker daemon is not running. Please start Docker and try again.
The term '-Agent' is not recognized
The term '-HarborArguments' is not recognized
```

这里有两个独立问题：

- Docker daemon 没有运行；
- 上一次参数修复在可展开 here-string 内使用了反引号续行。构造字符串时续行符被消费，worker 实际把 `-Agent` 和 `-HarborArguments` 当成了独立命令。

处理：worker 改用 splatting；创建后台进程前解析最终 worker 命令并同步检查 Docker。Docker 或脚本语法不可用时，`start-job.ps1` 必须在前台直接失败，不得再返回一个看似已启动的 Job 身份。

本次仍未进入 Harbor Job，也没有产生能力评测结果。

### 3.11 第三次后台启动：自动化遗漏 Judge 环境变量映射

Job：`memory-longmemeval-edced276-20260908-125313`

PowerShell 参数已经正确进入 Harbor，Docker 也已经可用，但 Harbor 在解析 Task verifier 配置时报告缺少：

```text
QUILLITH_JUDGE_API_KEY
QUILLITH_JUDGE_BASE_URL
QUILLITH_JUDGE_MODEL
```

这些变量不是新要求。既有执行设计已经规定从项目 Agent 配置派生 Judge 配置，但新的 `start-job.ps1` 漏掉了这一步；默认便宜验证只解析 Task schema，没有覆盖 Harbor 的运行时环境变量解析。

处理：

- API Key 按 `QUILLITH_API_KEY → ANTHROPIC_API_KEY → DASHSCOPE_API_KEY` 解析；
- Base URL 按 `QUILLITH_BASE_URL → ANTHROPIC_BASE_URL → Quillith 默认地址` 解析；
- Judge model 使用 Harbor `-Model` 去掉 `anthropic/` 前缀后的名称；
- 三项变量只在创建后台进程时临时注入并立即恢复，不进入命令行或日志；
- Job 目录存在但 `result.json` 不存在、launcher 又已退出时，状态改报 `LAUNCH_ERROR`。

本次在 Trial 创建前停止，没有调用模型，也没有能力评测结果。

### 3.12 正式运行：第 7 轮 consolidation 再次被 Provider 取消

Job：`memory-longmemeval-edced276-20260908-134640`

本次基础设施链路正常进入 Harbor Trial。环境初始化、Agent 安装、Session 切换、recorded Turn 注入、进程退出传播和失败时 Memory 归档均实际执行。

运行结果：

- Harbor 状态：`ERROR`；
- 已成功完成 6 个 recorded Turn，第 7 个 Turn 在 Memory consolidation 阶段失败；
- 没有执行最终问题，没有 `final_answer.json`；
- Verifier 未运行，没有 Judge 结果和 reward；
- Harbor 汇总中的 `Mean: 0.000` 仅用于异常 Job 展示，不是记忆能力得分。

第 7 轮 Trace `31bc634f439c9544319993239497f588` 的阶段耗时：

| 阶段 | 耗时 | 结果 |
| --- | ---: | --- |
| `memory.recall` | 4.638 秒 | 成功 |
| `agent.run.recorded` | 0.022 秒 | 成功 |
| `memory.extract` | 41.777 秒 | 成功 |
| `memory.consolidate` | 168.143 秒 | 失败 |
| `agent.turn` | 214.655 秒 | 失败 |

consolidation 内部连续三次 Anthropic-compatible 请求分别运行约 43.342、59.867、58.181 秒，最终都出现：

```text
AnthropicIoException: Request failed
Caused by: StreamResetException: stream was reset: CANCEL
```

Java 以退出码 1 结束后，Adapter 立即收到 `PROCESS_EXIT 1` 并将异常传播给 Harbor，没有等待外层 1200 秒 timeout。

失败时的 `/app/.memory` 已由 Harbor 成功归档，包含：

- `MEMORY.md`；
- 11 个 topic Markdown；
- `sessions.db`；
- artifact manifest 状态为 `ok`。

两条答题关键事实已经被保存：纽约单人旅行 5 天、夏威夷家庭旅行 10 天。数据库中有 2 个 Session 和 15 条已提交消息，第二个 Session 已包含第 7 轮的 user/assistant 消息。因此本次证明了跨 Session 历史和长期 Memory 能够持久化关键事实，但由于最终问题未执行，不能据此宣称系统答对了官方问题。

这与 3.7 的失败模式相同，说明 consolidation 的 Provider I/O 失败已经复现。当前证据支持的根因是外部请求在 HTTP/2 流层被取消；不支持把失败归因于 Harbor timeout、FIFO、Session 切换、Memory 未保存或模型不会回答。

后续网络调查得到以下证据：

- 当前 Anthropic Java SDK `2.49.0` 的单次 request/read 默认 timeout 是 10 分钟，本次单次失败约 43-60 秒，因此不是 SDK 默认 timeout 主动触发；
- Quillith 设置 `maxRetries(2)`，所以同一个 consolidation 共执行 3 次请求。重试使最终失败耗时增加，但不产生底层 `CANCEL`；
- Windows 用户代理启用，地址为 `127.0.0.1:7890`，监听进程是 `FlClashCore.exe`；
- 宿主机和 Docker 对 `dashscope.aliyuncs.com` 都解析为 `28.0.0.115`，即使显式查询 `223.5.5.5` 仍然得到相同地址；
- Trace 中失败连接的 `network.peer.address` 也是 `28.0.0.115`。

这些证据高度指向 FlClash 全局/TUN 模式的 DNS fake-IP 和代理链路重置了长时间无响应数据的 HTTP/2 请求。该判断仍需通过“关闭代理或为 DashScope 配置 DIRECT 后，用相同 consolidation 请求复现”的 A/B 实验最终确认。

## 4. 为什么这次定位显得很慢

直接原因有两类：

1. 前两次耗时消耗在 Docker 构建网络错误，Agent 根本没有运行；
2. JVM 退出后 Adapter 不知道进程已经死亡，只能等待 Harbor 的 600/1200 秒外层 timeout。

执行方式上的问题也很明确：已经有 Trace 基础设施，却先依赖粗粒度 stdout 推断性能阶段；直到用户提醒后才核查 Trace 是否真正接入 Harbor。这使“每轮为什么慢”无法及时得到证据化答案。

不过，现有 Trace 即使接入也不足以直接回答 Memory 耗时，因为当前业务 span 只有：

```text
agent.run
agent.run.recorded
agent.iteration
llm.call
tool.execute
```

`MemoryRuntime.recall()` 和 `MemoryRuntime.completeTurn()` 都由 `AgentSession.submitInternal()` 在 `agent.run.recorded` 外调用，Memory 类当前没有独立 span。Harbor 的启动命令又只有 `java -jar`，没有附加 OpenTelemetry Java Agent；本机 Jaeger 也处于停止状态。因此本次 Trial 没有可供事后查询的 Memory Trace。

## 5. 应补的最小观察指标

下面按“先能定位本次问题，再考虑长期分析”排序。不是要求一次全部实现。

### 5.1 第一优先级：一轮时间花在哪里

增加一个覆盖 `AgentSession.submitInternal()` 的 Turn span，并至少记录三个子阶段：

```text
agent.session.turn
├── memory.recall
├── agent.run / agent.run.recorded
└── memory.complete_turn
```

必要属性：

| Span | 属性 | 用途 |
| --- | --- | --- |
| `agent.session.turn` | `turn.mode=recorded/live`、`turn.index`、`session.index`、`error.type` | 判断慢在第几轮、是否只影响回放路径 |
| `memory.recall` | duration、候选数、选中数、是否调用模型 | 区分文件读取、候选增长和模型选择耗时 |
| `memory.complete_turn` | duration、输入消息数、输入 token 数、保存数、是否触发 consolidation | 判断全历史提取是否随 Turn 累积，以及整理是否造成尖峰 |

不应记录 user/assistant 原文，避免 Trace 泄露评测内容和用户数据。

### 5.2 第二优先级：Memory 内部的 Provider 调用

Memory 的 selector、extractor、consolidator 都可能调用模型。它们需要和主 Agent 的 `llm.call` 使用相同的基础耗时、token 和错误字段，同时增加低基数用途：

```text
gen_ai.operation.purpose = main | memory_select | memory_extract | memory_consolidate
```

至少记录：

- model；
- input/output token；
- 首 token 时间和总耗时；
- 请求是否重试；
- HTTP/stream 错误类型。

这样才能判断第 2 轮的 `StreamResetException` 发生在哪一种 Memory 调用，而不是只能从调用栈猜测。

### 5.3 第三优先级：上下文与压缩

只在压缩实际发生时记录：

- `compaction.triggered`；
- 压缩前后 message 数；
- 压缩前后 token 数；
- 压缩耗时；
- 保留的 checkpoint 数。

这些指标用于以后比较“压缩前后信息保真与成本”，本次不专门评测压缩，因此不应先扩展成完整 Dashboard。

### 5.4 Harbor 协议侧必须保留的运行指标

Java Trace 之外，Adapter 日志至少应能关联：

- Case ID；
- 命令类型：`RECORDED_TURN`、`NEW_SESSION`、`ANSWER`；
- Turn 序号；
- JVM PID；
- 命令开始、结束和耗时；
- JVM exit code；
- Agent、Verifier、Judge 各自耗时与状态。

其中 PID 和命令边界已经有部分文本日志；缺少的是可靠时间字段与统一关联标识。首版不需要引入新的指标平台，结构化日志即可补足 FIFO/进程层问题。

### 5.5 可复查的 Memory 产物

指标只能解释数量和耗时，不能用于检查模型究竟写入了什么。每个 Memory Case 还应按 Trial 保存：

- 最终 `MEMORY.md`；
- 实际生成的 topic Markdown；
- `sessions.db`；
- 若中途失败，保留失败前最后一次成功写入的状态。

公开 Benchmark 可以默认保存这些产物；真实用户对话则需要单独的数据保留与脱敏规则，不能沿用评测默认值。

## 6. 最小实施顺序建议

如果下一步专门处理可观测性，最小顺序应为：

1. 先让 Harbor 容器实际附加现有 OpenTelemetry Java Agent，并连到可用 OTLP Collector/Jaeger；
2. 给 `AgentSession.submitInternal()`、`MemoryRuntime.recall()` 和 `MemoryRuntime.completeTurn()` 增加 span；
3. 给 Memory 的模型调用标注 purpose，并复用现有 GenAI 属性；
4. 用同一条 `edced276` 再跑一次，对照 Turn 1 到 Turn 9 的耗时与 token 增长；
5. 只有 Trace 证明某一阶段存在主要瓶颈后，才设计性能修复。

当前不建议先做指标存储、Dashboard、告警、采样策略或跨 Case 聚合。这些都不是定位首条官方用例所必需的。
