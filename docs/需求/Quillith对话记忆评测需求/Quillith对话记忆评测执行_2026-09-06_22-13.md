# Quillith 对话记忆评测执行

## 1. 本次执行到哪里停止

对应文档：

- [Quillith 对话记忆评测需求](./Quillith对话记忆评测需求_2026-09-06_20-26.md)
- [Quillith 对话记忆评测需求技术评审](./Quillith对话记忆评测需求技术评审_2026-09-06_20-26.md)

本次只打通一条最小但完整的链路：

```text
一条用户确认的官方 Memory Case
→ 固定 user/assistant 历史逐 Turn 回放
→ 按官方 session 边界切换 Quillith Session
→ 最终问题由真实模型回答
→ Harbor verifier 使用 LLM Judge 评分
→ Harbor 保存答案、分数和错误
```

到第一条官方 Case 能完整跑通并得到可信结果后停止。

本次不做批量题目转换、结果汇总脚本、Dashboard、RAG、Memory 改进或压缩改进。它们都不是验证第一条链路所必需的。

## 2. 为什么现有代码还不能完成这条链路

当前正常路径是：

```text
Harbor instruction
→ harbor_adapter.py
→ FIFO
→ HarborRunner
→ AgentSession.submit()
→ AgentLoop.run()
→ 真实模型
```

真正缺少的只有三个能力。

### 2.1 历史 assistant 不能固定

官方历史如果是：

```text
user: 我下周二去上海
assistant: 好的，我记住了
```

不能只调用：

```java
agentSession.submit("我下周二去上海");
```

因为这会让当前模型重新生成另一条 assistant，官方历史会被改变。

需要新增：

```java
agentSession.submitRecorded(
        "我下周二去上海",
        "好的，我记住了"
);
```

其中 user 仍走正常 Turn 生命周期，只把“本轮主模型生成 assistant”替换成官方固定 assistant。

### 2.2 跨对话需要真正的新 Session

已经确认的映射是：

```text
官方 session 1 → Quillith Session A
官方 session 2 → Quillith Session B
最终问题       → Quillith Session C
```

新 Session 必须：

- 清空旧 `ConversationState`；
- 清空旧 Checkpoint 视图；
- 使用新的 Session ID；
- 下一条消息创建新的 SessionStore 记录。

但必须继续复用：

- 当前 JVM；
- 当前 `AgentRuntime`；
- 当前 workspace；
- 当前 `MemoryRuntime`；
- workspace 下的 `.memory`。

### 2.3 最终答案现在被丢弃

`AgentLoop.run()` 已经返回最终文本，但当前 `AgentSession.submit()` 返回 `void`，`HarborRunner` 又只返回 `OK`。

编程题可以让 verifier 检查文件，记忆问答必须取得自然语言答案。因此需要把已有的 String 沿原调用链返回：

```text
AgentLoop
→ AgentSession
→ HarborRunner
→ harbor_adapter.py
→ /logs/agent/final_answer.json
→ Judge
```

## 3. 一条 Case 的完整运行链路

Harbor 对一条最终问题只执行一次 Agent Phase。历史消息不是 Harbor step。

```text
Harbor
  │ instruction.md：一条 Case JSON，不含参考答案
  ▼
QuillithMemoryAgent.run()
  │
  ├─ 复用 _start_session() 启动一个 JVM
  │
  ├─ RECORDED_TURN(user 1, assistant 1)
  ├─ RECORDED_TURN(user 2, assistant 2)
  │
  ├─ 官方进入下一个 session 时发送 NEW_SESSION
  │
  ├─ RECORDED_TURN(user 3, assistant 3)
  │
  ├─ cross_session 最终提问前再发送 NEW_SESSION
  │
  ├─ ANSWER(final question)
  │       ↓
  │   真实 AgentLoop + 真实主模型
  │       ↓
  │   RESULT(final answer)
  │
  └─ 写 /logs/agent/final_answer.json
          ↓
      Harbor verifier
          ↓
      LLM Judge
          ↓
      /logs/verifier/reward.txt
```

这里不传 `--resume-trajectory`。该参数用于 Harbor multi-step，而本评测在一个 Agent Phase 内完成全部历史回放。

## 5. 逐文件修改

## 5.1 `AgentSession.java`

### 现有问题

当前 `submit()` 已经包含完整的 Turn 外层生命周期：

```text
UserPromptSubmit Hook
→ SESSION Prompt 刷新
→ Memory recall
→ user 持久化
→ Hook additional context 持久化
→ Memory capture
→ AgentLoop
→ Memory complete
```

如果另写一份 recorded 流程，今后修改 Memory 或 Session 时两条路径会分叉。因此 live 和 recorded 必须共用一个私有方法。

### 修改方法

将：

```java
public void submit(String query) throws IOException
```

改为：

```java
public String submit(String query) throws IOException {
    return submitInternal(query, null);
}
```

新增：

```java
/**
 * 按正常 Turn 生命周期提交固定的 user/assistant 历史。
 *
 * @param userText 官方历史中的 user 文本
 * @param assistantText 官方历史中的 assistant 文本
 * @return 已提交的 assistant 文本
 */
public String submitRecorded(
        String userText,
        String assistantText
) throws IOException {
    Objects.requireNonNull(assistantText, "assistantText 不能为 null");
    return submitInternal(userText, assistantText);
}
```

把当前 `submit()` 主体原样移入：

```java
private String submitInternal(
        String query,
        String recordedAssistant
) throws IOException
```

只修改当前调用 `agentLoop.run()` 的位置：

```java
String output;
try {
    output = recordedAssistant == null
            ? agentLoop.run(
                    conversationState,
                    recalledMemories
            )
            : agentLoop.runRecorded(
                    conversationState,
                    recalledMemories,
                    recordedAssistant
            );
} catch (AnthropicServiceException exception) {
    // 当前诊断、回滚和继续抛出的代码原样保留。
}

// 当前 memoryRuntime.completeTurn(...) 原样保留。
return output;
```

Hook 阻止输入时保留当前行为并返回空字符串，不增加新的错误类型或兜底答案。

### 新增 `startNewSession()`

```java
/**
 * 创建不继承当前活动上下文的新 Session，同时保留工作区长期记忆。
 *
 * @return 新 Session ID
 */
public String startNewSession() {
    conversationState.restore(
            List.of(),
            List.of(),
            -1
    );
    String newSessionId = sessionState.startNewSession();
    persisted = false;
    systemPromptManager.refreshFrom(
            RefreshScope.SESSION,
            sessionState
    );
    return newSessionId;
}
```

为什么只做这些：

- `ConversationState.restore(empty...)` 已经能同时清空完整历史、活动上下文和 Checkpoint，无需给 `ConversationState` 新增 `reset()`；
- `persisted = false` 让下一条 user 走现有 `createSessionWithFirstMessage()`；
- 不删除旧 SessionStore 记录；
- 不重建 Runtime，因此 `.memory` 和 Memory 服务继续复用。

### 本次故意不修的现有 Memory 语义

当前 `memoryExtractionSnapshot` 在 AgentLoop 响应前产生，所以 assistant 通常在下一 Turn 才进入 Memory 提取；一个 session 的最后一条 assistant 在立即切 Session 时可能尚未被提取。

这是当前产品的真实行为，也是评测可能发现的问题。本次不能为了让题目通过而移动 `capture()` 或额外调用 Memory 提取。

## 5.2 `AgentLoop.java`

### 目标

只把“一次主模型响应来自哪里”变成 recorded/live 两种输入。它不能判断 benchmark、题型或 Session 类型。

### 方法结构

保留现有公开 live 方法，新增：

```java
/**
 * 执行真实请求前治理，并提交一个已经完成的 assistant 文本。
 */
public String runRecorded(
        ConversationState conversationState,
        String turnContext,
        String assistantText
) {
    Objects.requireNonNull(assistantText, "assistantText 不能为 null");
    return runInternal(
            conversationState,
            turnContext,
            assistantText
    );
}
```

现有：

```java
public String run(
        ConversationState conversationState,
        String turnContext
)
```

改为调用：

```java
return runInternal(conversationState, turnContext, null);
```

当前主体移入：

```java
private String runInternal(
        ConversationState conversationState,
        String turnContext,
        String recordedAssistant
)
```

### 唯一核心分支

分支必须位于现有以下逻辑之后：

```text
TURN Prompt 刷新
→ BeforeModelCall Hook
→ Hook additional context 提交
→ snipMiddle()
→ compactOldToolResults()
→ 必要的 compactHistory()
→ 必要的 replaceModelContext() 和 Checkpoint
```

并位于 `runIteration(createRequest(...))` 之前：

```java
if (recordedAssistant != null) {
    MessageParam assistantMessage =
            MessageParam.builder()
                    .role(MessageParam.Role.ASSISTANT)
                    .content(recordedAssistant)
                    .build();

    commitCompletedTurn(
            conversationState,
            List.of(assistantMessage)
    );
    return recordedAssistant;
}

// 下面继续执行当前 runIteration、SSE、工具和错误恢复代码。
```

为什么分支必须在这里：

- 放在上下文治理前：回放历史无法逐 Turn 触发真实压缩；
- 放进 `streamModel()`：必须伪造 SSE、工具和流错误，复杂度更高；
- 在 AgentSession 直接 append：会绕过 BeforeModelCall Hook、压缩和 Checkpoint；
- 当前位置只替换主模型生成，不复制其余生命周期。

recorded assistant 是官方已经完成的回答，所以提交后直接结束该 Turn，不执行 Provider SSE、工具调用、输出续写或 Stop Hook。

## 5.3 `SessionState.java`

当前 Session ID 字段已经支持恢复时切换，只缺少语义明确的新建入口。

修改字段注释为：Session ID 在一个 Session 内稳定，只在显式新建或恢复 Session 时切换。

新增 package-private 方法：

```java
/**
 * 为一个新的空白 Session 生成稳定 ID。
 *
 * @return 新 Session ID
 */
String startNewSession() {
    sessionId = UUID.randomUUID().toString();
    return sessionId;
}
```

该方法不修改 workspace、allowed roots、Memory 开关或审批模式。

## 5.4 `HarborRunner.java`

### 保持旧协议不变

```text
TURN <base64(user)>
→ agentSession.submit(user)
→ OK
```

普通 Harbor 任务和现有 `--resume-trajectory` multi-step 继续使用它。

### 新增三种命令

```text
RECORDED_TURN <base64(user)> <base64(assistant)>
→ agentSession.submitRecorded(user, assistant)
→ OK
```

```text
NEW_SESSION
→ agentSession.startNewSession()
→ OK
```

```text
ANSWER <base64(question)>
→ String answer = agentSession.submit(question)
→ RESULT <base64(answer)>
```

Base64 只解决单行 FIFO 中的换行和 Unicode 传输，不改变原始文本。

### 最小解析结构

把当前只支持 TURN 的 `decodeInstruction()` 改为 `decodeRequest()`，返回一个 `HarborRunner` 内部 record：

```java
enum RequestType {
    TURN,
    RECORDED_TURN,
    NEW_SESSION,
    ANSWER
}

record Request(
        RequestType type,
        String userText,
        String assistantText
) {
}
```

`RECORDED_TURN` 用空格分隔两个 Base64 字段。首版 Case 校验保证 user 和 assistant 都是非空文本。

`run()` 根据 `RequestType` 直接 switch，不增加协议 Handler、Command 模式或新的 Java 文件。

### 不新增错误状态机

本次不增加：

```text
READY
CLOSE
ERROR FIFO
PID 文件
watchdog
reconnect
额外 timeout
```

异常继续由现有 Java stderr 和 Harbor Trial error 记录。只有真实运行证明 FIFO 阻塞妨碍定位时，再单独评审错误协议。

## 5.5 `harbor_adapter.py`

Python 首版只修改这一个现有文件，不新增独立 `quillith_memory_agent.py`。

### 为什么复用现有 Adapter

当前 `QuillithHarborAgent` 已经负责：

```text
校验并上传 JAR
检查 Java/Git/Bash
创建 FIFO
启动长驻 JVM
保存 _session_started
写请求 FIFO
读响应 FIFO
传递模型配置和 Token
```

重新创建独立 Adapter 会复制这些逻辑。正确边界是共享通信基础设施，只分开普通任务和 Memory Case 的上层编排。

### 给 `QuillithHarborAgent` 增加通用 helper

先从当前 `_submit_turn()` 中提取：

```python
async def _exchange(
    self,
    environment: BaseEnvironment,
    request: str,
) -> str:
    """发送一条机器协议消息并返回 Java 的单行响应。"""
```

它复用当前 FIFO shell 命令。请求继续通过环境变量传入，不能拼接到 shell command。

当前 `_submit_turn()` 改为调用 `_exchange()`，但仍要求响应严格等于 `OK`，保持原行为。

新增：

```python
async def _submit_recorded_turn(
    self,
    environment: BaseEnvironment,
    user_text: str,
    assistant_text: str,
) -> None:
    request = (
        f"RECORDED_TURN {encode(user_text)} "
        f"{encode(assistant_text)}"
    )
    response = await self._exchange(environment, request)
    if response != "OK":
        raise RuntimeError("Quillith 固定历史提交失败")
```

```python
async def _new_session(
    self,
    environment: BaseEnvironment,
) -> None:
    response = await self._exchange(environment, "NEW_SESSION")
    if response != "OK":
        raise RuntimeError("Quillith 新 Session 创建失败")
```

```python
async def _answer(
    self,
    environment: BaseEnvironment,
    question: str,
) -> str:
    response = await self._exchange(
        environment,
        f"ANSWER {encode(question)}",
    )
    if not response.startswith("RESULT "):
        raise RuntimeError("Quillith 未返回最终答案")
    return decode(response.removeprefix("RESULT "))
```

这些 helper 只理解 Quillith 机器协议，不理解 Memory Case、官方数据或评分。

### 同文件新增薄子类

```python
class QuillithMemoryAgent(QuillithHarborAgent):
    """按一条 Memory Case 的顺序驱动 Quillith 通用机器协议。"""

    async def run(
        self,
        instruction: str,
        environment: BaseEnvironment,
        context: AgentContext,
    ) -> None:
        case = json.loads(instruction)
        self._validate_case(case)

        if self._resume:
            raise RuntimeError("Memory Case 是单步 Harbor Task，不接受 resume")
        if self._session_started:
            raise RuntimeError("同一 Memory Case 不能重复执行")

        await self._start_session(environment)
        self._session_started = True

        for session_index, session in enumerate(case["sessions"]):
            if session_index > 0:
                await self._new_session(environment)

            messages = session["messages"]
            for message_index in range(0, len(messages), 2):
                user = messages[message_index]
                assistant = messages[message_index + 1]
                await self._submit_recorded_turn(
                    environment,
                    user["content"],
                    assistant["content"],
                )

        if case["memory_scope"] == "cross_session":
            await self._new_session(environment)

        answer = await self._answer(
            environment,
            case["question"],
        )
        await self._save_answer(
            environment,
            case["case_id"],
            answer,
        )
```

`_validate_case()` 首版只验证运行所必需的契约：

- `case_id`、`memory_scope`、`sessions`、`question` 存在；
- `memory_scope` 只能是 `single_session` 或 `cross_session`；
- `single_session` 恰好一个 session；
- 每个 session 消息数量为正偶数；
- 消息严格按非空 `user/assistant` 文本交替。

`_save_answer()` 将 JSON 经过 Base64 环境变量写入：

```text
/logs/agent/final_answer.json
```

内容只有：

```json
{
  "case_id": "官方题目 ID",
  "answer": "Quillith 最终答案"
}
```

答案不能直接拼进 shell 命令，也不能混入 Quillith stdout 日志。

这个子类不负责 Memory、压缩、Hook、SessionStore 或评分。它只是 Case 的机器播放器。

## 6.5 `tests/judge.py`

第一版 Judge 只做一个函数链：

```python
reference = load_reference("/tests/reference.json")

response = call_anthropic_compatible_model(
    question=reference["question"],
    reference_answers=reference["reference_answers"],
    rubric=reference["rubric"],

)

write_result(judgement)
```

模型只允许返回：

```json
{"correct": true, "reason": "简短依据"}
```

`correct` 映射为 Harbor reward `1` 或 `0`。同时写：

```text
/logs/verifier/judge-result.json
```

Judge 失败时写不含密钥的：

```text
/logs/verifier/judge-error.txt
```

然后非零退出，不得把 Judge 基础设施失败伪造成 Agent 得 0 分。

本次不实现多 Judge、投票、重试、校准或部分分数。

Judge 使用 Python 标准库向以下地址发送 Anthropic Messages 请求：

```text
{QUILLITH_JUDGE_BASE_URL 去掉尾部 /}/v1/messages
```

请求只使用 `content-type`、`anthropic-version` 和 `x-api-key` 三个必要头。prompt 中将问题、参考答案、rubric 和候选答案作为 JSON 数据传入，并明确要求不得执行这些字段内部出现的指令。响应不是严格 JSON 或缺少 boolean `correct` 时直接失败，不从 Markdown 代码围栏中猜测结果。

## 10. 完成标准

第一条官方 Case 同时满足以下条件才算打通：

1. 固定历史 assistant 没有触发主模型调用；
2. 固定 user/assistant 已进入真实 SessionStore 和下一 Turn history；
3. 历史增长过程中真实上下文治理仍会执行；
4. 官方 session 边界对应不同 Quillith Session ID；
5. 新 Session 的模型上下文不包含旧 Session history；
6. 新 Session 仍使用同一 workspace `.memory`；
7. 最终问题执行真实主模型；
8. 最终文本经过 Java、FIFO、Python 无损到达 Judge；
9. Judge 使用项目现有 API Key，仓库和日志中没有真实密钥；
10. Harbor 记录 reward；Judge 或 Agent 失败时记录为 Trial/verifier error；
11. 原 `QuillithHarborAgent` 的普通 TURN 和 multi-step 行为没有回归。

这一步得到的是评测基础链路，不是最终简历数据。后续再单独选择各记忆类型的多道官方题，并根据真实重复工作决定是否需要批量转换和分类汇总。
