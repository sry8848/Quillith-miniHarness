未确认：无。下面把第一版交互语义直接定死。

第一性原理拆解：  
交互需求只需要回答四件事：怎么进入 Session、恢复时用户看到什么、用户下一条输入意味着什么、哪些旧执行绝不能偷偷继续。

事实校验：  
前面横向查看 Codex、nanobot、Pi 后，这种“会话恢复与新 Turn 分离”的产品语义是成立的。Codex 也明确区分长期 Thread 与单次 Turn，Interrupted Turn 后 Thread 仍可继续接收新的 Turn。

认知降维设计：  
不用任何实现术语，直接按“新会话 / 正常恢复 / 中断恢复 / 用户继续输入 / 异常工具”五种用户场景定义行为，并最后给出一句不可违背的总契约。  

# 一、核心产品定义

第一版“断点恢复”正式定义为：

> **恢复 Session，而不是恢复旧 Turn 的执行控制流。**

进程中断时：

```text
当前 Turn → INTERRUPTED
```

以后重新打开这个 Session：

```text
恢复已有对话与执行事实
↓
不自动继续旧 Turn
↓
进入正常可输入状态
↓
用户下一条消息创建一个新的 Turn
```

因此明确：

```text
不恢复旧 AgentLoop
不自动续跑模型
不自动重新执行工具
不恢复旧 Turn 的续写次数、模型轮次等运行现场
```

---

# 二、新建 Session

用户开始一段全新的对话：

```text
New Session
↓
获得唯一 sessionId
↓
进入聊天输入状态
```

之后：

```text
用户消息
→ Turn 1
→ Agent 完成

用户消息
→ Turn 2
→ Agent 完成
...
```

只要没有切换 Session，后续 Turn 都共享前面的会话历史。

---

# 三、恢复一个正常结束的 Session

假设：

```text
Session abc

Turn 1 COMPLETED
Turn 2 COMPLETED
Turn 3 COMPLETED
```

用户重新打开 `abc`。

行为固定为：

```text
加载 Session abc
↓
显示/恢复之前的对话
↓
直接进入正常输入状态
```

用户输入：

```text
继续刚才的问题
```

这是：

```text
Turn 4
```

用户输入：

```text
换个问题，看看 B.java
```

也是：

```text
Turn 4
```

Harness 不需要区分。

---

# 四、恢复一个中断的 Session

假设：

```text
Turn 3

User:
帮我修改 A.java

Assistant:
read_file ...

Tool:
成功

Assistant:
edit_file ...

💥 程序中断
```

此时：

```text
Turn 3 = INTERRUPTED
```

重新打开 Session 后，**禁止自动继续执行**。

用户看到的交互语义应该是：

```text
以前的对话仍然存在

[上一轮任务在执行过程中被中断]
```

然后直接进入：

```text
>
```

等待用户输入。

不用弹：

```text
是否继续？Y/N
```

也不用强制：

```text
/continue
```

---

# 五、中断之后，“继续”只是普通用户消息

用户输入：

```text
继续
```

创建：

```text
Turn 4
```

模型会获得：

```text
之前完整历史
+
中断事实
+
工具已经确定的执行结果
+
当前用户消息：“继续”
```

于是模型自己判断应该怎么接着做。

例如：

```text
先检查 A.java 当前状态
↓
确认上一次 edit_file 有没有实际发生
↓
再继续工作
```

---

用户也可以说：

```text
不用继续了，解释一下刚才读到的这个类
```

那么新 Turn 就执行这个新要求。

也可以：

```text
先检查刚才文件到底改成功没有
```

正常执行。

也就是说：

> **中断后的下一条用户消息拥有正常的新 Turn 语义，并且优先级高于旧任务。**

旧任务不是一个必须完成的后台 Job。

---

# 六、如果用户一句话都不说

恢复 Session 后：

```text
等待输入
```

什么都不发生。

禁止：

```text
自动请求模型
自动补完回答
自动执行工具
自动 retry
自动继续旧任务
```

这条需要定死。

因为：

> `open session` 是读取行为，不是执行行为。

---

# 七、工具状态的交互语义

这里第一版只需要三种最终恢复语义：

```text
SUCCEEDED
FAILED
UNKNOWN
```

## SUCCEEDED

意味着：

> 已经确定工具执行完成，并且结果可用。

恢复以后模型应知道：

```text
这个工具已经做过了
这是它的结果
不要因为 Session 恢复重新执行
```

---

## FAILED

意味着：

> 已经确定工具执行失败。

模型应该看到真实失败事实。

后续是否重试：

```text
由新的 Turn 根据用户要求和模型判断决定
```

不是恢复过程自动重试。

---

## UNKNOWN

意味着：

> 工具曾经开始执行，但进程中断导致无法确定最终副作用是否发生。

恢复以后必须明确告诉模型：

```text
这个工具结果未知。
不能假定成功。
不能假定失败。
不能直接重复执行。
应先检查当前现实状态。
```

之后如果用户说：

```text
继续
```

模型可以：

```text
read_file
git diff
查询任务状态
查询外部状态
...
```

来调查。

---

# 八、UNKNOWN 不是“继续执行中的工具”

这一点一定要定死。

程序重启以后：

```text
以前的 RUNNING
```

不能继续被理解为：

```text
现在还在 RUNNING
```

旧进程已经不存在。

所以产品语义应该是：

```text
旧进程中的 RUNNING
+
进程中断
=
UNKNOWN
```

不是：

```text
RUNNING → 重新执行
```

---

# 九、等待审批时中断

比如：

```text
Assistant:
edit_file(...)

系统：
是否允许执行？ [y/N]

💥
```

因为工具还没有真正执行：

```text
不存在未知副作用
```

旧 Turn：

```text
INTERRUPTED
```

恢复 Session 后：

```text
不会重新弹出旧审批框
```

直接回到普通聊天输入。

用户如果说：

```text
继续修改
```

新 Turn 由模型重新决定是否需要调用 edit_file。

如果再次调用：

```text
重新走正常审批流程
```

旧审批请求不恢复。

---

# 十、模型输出一半时中断

例如用户屏幕上曾经看到：

```text
这个问题主要是因为 Spring 在创建 Bean 的时候...
```

然后流断了 / 程序死了。

如果这个 block 没有形成系统认可的完整历史事实：

```text
恢复后不承诺保留
```

用户可能看到之前终端打印过的半截文字，但它不能成为后续模型可依赖的历史。

产品语义：

> **只保证恢复已经提交完成的内容；流式半成品可以丢失。**

之后用户：

```text
继续
```

模型基于最后一个稳定历史重新回答/继续。

允许一定程度重复。

第一版接受这个代价。

---

# 十一、压缩、摘要、Context 治理中断

统一规则：

> **不向用户暴露“压缩恢复”概念。**

假设：

```text
正在自动 compact
💥
```

重新打开 Session：

```text
恢复原始可用历史
↓
正常等待用户输入
```

下一 Turn 如果仍然需要压缩：

```text
重新执行压缩
```

用户不需要：

```text
继续压缩
```

也不应该看到：

```text
上一次压缩执行到 47%
```

这类状态不属于第一版产品语义。

---

# 十二、输出续写中断也是一样

比如模型因为 token 上限已经自动续写过两次：

```text
continuation 1
continuation 2
💥
```

恢复以后：

```text
旧 Turn = INTERRUPTED
```

不会继续恢复：

```text
continuationCount = 2
```

用户说：

```text
继续
```

这是新 Turn。

新 Turn 使用正常的新执行预算。

所以之前讨论的：

```text
outputContinuationCount
modelRoundCount
contentRejectionRecoveryCount
```

第一版**不属于跨进程恢复需求**。

---

# 十三、用户输入永远是新的 Turn

这一点建议作为最重要的 invariant。

无论之前：

```text
COMPLETED
INTERRUPTED
工具 UNKNOWN
模型流中断
审批中断
```

只要程序恢复完成并进入聊天框：

```text
用户发送消息
```

就意味着：

```text
创建新的 Turn
```

永远不是：

```text
把用户消息塞回旧 Turn
```

这可以大幅简化整个语义。

---

# 十四、Session 恢复本身不产生模型消息

例如不能：

```text
resume abc
↓
Harness 自动给模型：
“刚刚程序重启了，请继续”
↓
模型自动开始工作
```

不做。

应该是：

```text
resume abc
↓
修复 Session 成为一个一致、可继续对话的状态
↓
等待用户
```

只有用户真正发送消息以后：

```text
才产生新的模型请求
```

---

# 十五、Session 恢复后的状态只有两种用户可感知情况

其实产品层甚至可以非常简单：

### 正常恢复

```text
Session restored.
>
```

### 上一 Turn 中断

```text
Session restored.
[Previous turn was interrupted.]
>
```

如果存在 UNKNOWN 工具，可以进一步提示：

```text
[Previous turn was interrupted.
One or more tool executions have unknown outcomes.]
>
```

但不会自动要求用户做某个动作。

---

# 十六、第一版明确“不做”的东西

为了避免以后需求重新膨胀，建议明确写入非目标：

```text
不恢复 JVM 调用栈

不恢复旧 AgentLoop 控制流

不从旧 Turn 某个 phase 自动继续

不自动恢复模型 stream

不恢复半截 block

不恢复旧审批请求

不恢复旧输出续写次数

不恢复旧模型轮次

不恢复 compact/summary 的中间状态

不自动执行 UNKNOWN 工具

不要求用户必须输入“继续”

不把 Session 打开等价成任务继续
```

---

# 十七、最后可以压成一个完整交互例子

第一次：

```text
> 帮我修改登录 Bug

Agent:
我先检查代码。

Tool: read_file(...)
✓ success

Agent:
准备修改文件。

Tool: edit_file(...)

💥 Quillith unexpectedly stopped
```

重新打开：

```text
$ quillith <恢复 Session abc>

Session abc restored.
Previous turn was interrupted.
One tool execution has an unknown outcome.

>
```

用户选择 1：

```text
> 继续

Agent:
上一次文件修改的最终状态不确定。
我先检查当前文件内容。

Tool: read_file(...)
...
```

用户选择 2：

```text
> 先别改了，告诉我你刚才发现的问题

Agent:
...
```

用户选择 3：

```text
> 不管刚才那个了，帮我检查订单模块

Agent:
...
```

三个行为都完全合法。

没有额外的恢复模式。

---

## 最终可以把第一版需求定成这一句话

> **Quillith 的 Session Recovery 负责在进程重启后恢复完整、可继续使用的会话事实，并将未正常结束的 Turn 封口为 `INTERRUPTED`。恢复过程本身不执行模型或工具。Session 恢复完成后立即回到普通交互状态，用户的任意下一条消息创建新的 Turn；模型依据历史中的已完成工具结果、失败结果和未知执行事实，自主决定如何继续或转向新的用户目标。**
