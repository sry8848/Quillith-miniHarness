# Session 持久化与中断恢复设计

## 1. 目标

实现最小化的 Session 恢复能力：

> 打开已有 Session 时，加载完整历史消息；如果上一次 Turn 因进程中断未正常提交，则根据已持久化的流式内容和工具执行状态，将其统一封口为合法历史。恢复过程不自动调用模型或重新执行工具，完成后等待用户下一条输入。

不恢复旧 `AgentLoop` 控制流，不恢复模型轮次、续写次数、压缩进度等临时状态。

---

# 2. SQLite 表结构

## `sessions`

| 字段           | 说明            |
| ------------ | ------------- |
| `session_id` | Session 唯一 ID |
| `workspace`  | Session 所属工作区 |
| `created_at` | 创建时间          |
| `updated_at` | 最后更新时间        |

用途：

- 标识 Session。
- 恢复时校验 workspace。
- 提供 Session 列表和排序能力。

---

## `messages`

| 字段             | 说明                     |
| -------------- | ---------------------- |
| `session_id`   | 所属 Session             |
| `seq`          | 消息顺序                   |
| `message_json` | 完整 `MessageParam` JSON |

主键：

```
(session_id, seq)
```

约束：

> `messages` 只保存已经正式提交到 conversation history 的完整消息。

不保存半条流式 assistant message。

加载 Session 时：

```
SELECT message_json
FROM messages
WHERE session_id = ?
ORDER BY seq;
```

恢复成当前：

```
List<MessageParam> history
```

---

## `inflight_responses`

| 字段                       | 说明                                     |
| ------------------------ | -------------------------------------- |
| `response_id`            | 当前模型回复 ID                              |
| `session_id`             | 所属 Session                             |
| `assistant_content_json` | 已完整关闭但尚未正式提交的 assistant content blocks |

其中：

```
assistant_content_json
```

对应当前 `AgentLoop.streamModel()` 中：

```
List<ContentBlockParam> assistantContent
```

只保存已经收到：

```
content_block_stop
```

的完整 block。

例如：

```
thinking ✓text ✓tool_use ✓text 半截 ✗
```

只保存前三个。

半截 block 直接丢弃。

---

## `tool_executions`

| 字段            | 说明                          |
| ------------- | --------------------------- |
| `response_id` | 所属模型回复                      |
| `tool_use_id` | Claude tool_use ID          |
| `state`       | 工具执行状态                      |
| `result_json` | 已完成时的 `ToolExecutionResult` |

其中：

```
tool_use_id
```

关联 `assistant_content_json` 中对应的 `tool_use`。

工具名称和 input 不重复保存，因为完整 `tool_use` 已存在于 assistant content 中。

# 3. 工具状态

只定义三个状态：

```
NOT_STARTEDRUNNINGCOMPLETED
```

## `NOT_STARTED`

含义：

> `tool_use` 已经完整产生并持久化，但真实工具尚未开始执行。

包括：

```
等待审批等待调度
```

恢复时可以确定：

> 工具没有执行过。

---

## `RUNNING`

含义：

> 工具已经进入真实执行阶段。

此时副作用可能已经发生。

进程恢复后：

```
RUNNING→ outcome unknown
```

不能自动重新执行。

---

## `COMPLETED`

含义：

> 已经得到完整 `ToolExecutionResult` 并持久化。

成功或失败不由 state 区分，而由：

```
ToolExecutionResult
```

自身表示。

恢复时直接复用原结果。

---

# 4. 工具状态变更时机

结合当前代码，基本流程为：

```
content_block_stop(tool_use)↓保存完整 tool_use↓INSERT tool_execution = NOT_STARTED↓才允许提交 ToolCallDispatcher
```

这是“先记再做”的核心规则。

---

工具经过当前：

```
BeforeToolUse Hook↓ToolApprovalGate
```

审批通过、即将进入：

```
toolRegistry.execute(toolCall)
```

之前：

```
NOT_STARTED→ RUNNING
```

并先提交 SQLite transaction。

然后才真正执行工具。

---

`toolRegistry.execute()` 得到：

```
ToolExecutionResult
```

之后：

```
RUNNING→ COMPLETEDresult_json = result
```

立即持久化。

因此顺序固定为：

```
tool_use durable↓NOT_STARTED durable↓RUNNING durable↓真实 execute↓COMPLETED + result durable
```

---

# 5. 正常关闭策略

当前代码本来就会：

```
等待本轮所有已提交工具↓得到 ToolExecutionResult[]↓组装 assistant tool_use message↓组装 user tool_result message↓加入 history
```

持久化后沿用相同模式。

当一轮工具结果全部可以提交时，使用一个 SQLite transaction：

```
BEGININSERT assistant messageINSERT user tool_result messageDELETE inflight_responseDELETE 对应 tool_executionsCOMMIT
```

要求：

> 正式历史提交和 in-flight 清理必须原子完成。

避免出现：

```
messages 已经提交但 inflight 还存在
```

导致下次恢复重复封口。

---

# 6. 流中断关闭策略

当前 JVM 仍然存活时，已有代码会等待所有已经提交的工具 Future：

```
流中断↓保留完整 assistant blocks↓等待已提交 tools↓获得 ToolExecutionResult[]↓commitInterruptedTurn()
```

新的持久化逻辑不改变这个基本模式。

区别只是完整 blocks 和工具状态同步写入 SQLite。

最终仍然：

```
完整 assistant content+完整 tool results↓统一封口
```

---

# 7. 进程恢复关闭策略

重新打开 Session：

```
加载 sessions↓加载全部 messages↓检查 inflight_response
```

如果不存在：

```
直接进入正常用户输入
```

如果存在：

```
读取 assistant_content_json↓读取对应 tool_executions
```

每个工具转换为一个恢复用 `ToolExecutionResult`：

### NOT_STARTED

```
工具在上次中断前尚未执行
```

生成普通失败 `tool_result`。

### RUNNING

```
工具执行过程中进程中断，最终外部状态未知，重新执行前需要先检查现实状态
```

生成普通失败 `tool_result`。

### COMPLETED

直接使用：

```
result_json
```

---

然后复用正常/流中断已有的统一组装逻辑：

```
assistant_content+ToolExecutionResult[]↓assistant Message+user tool_result Message
```

使用 transaction：

```
INSERT repaired messagesDELETE inflight_responseDELETE tool_executions
```

旧 Turn 至此完成封口。

恢复过程：

```
不调用模型不重新执行工具
```

然后进入普通输入：

```
>
```

用户输入：

```
继续
```

或者：

```
不要继续，做另一件事
```

都只是新的普通 Turn。

---

# 8. Session 打开策略

用户打开已有 Session：

```
open session↓读取 workspace↓校验当前 workspace↓加载所有 messages↓如果存在 inflight：    执行一次恢复封口↓进入正常交互循环
```

Session 打开本身永远不意味着：

```
自动继续旧 AgentLoop自动请求模型自动重试工具
```

---

# 9. 总体模型

最终数据关系：

```
Session│├── Messages[]│     已正式提交的完整 conversation history│└── InflightResponse?          最多一个当前未提交模型回复      │      ├── AssistantContent[]      │     已完整关闭的 blocks      │      └── ToolExecutions[]            NOT_STARTED            RUNNING            COMPLETED + result
```

运行时统一遵循：

```
稳定事实先 durable↓再产生外部副作用
```

恢复统一遵循：

```
加载稳定事实↓为所有 tool_use 得到一个 ToolExecutionResult↓组装合法 assistant/tool_result 消息↓原子提交历史↓清理 inflight↓等待用户下一条消息
```

这就是当前需求下的最小模型。后台任务、模型续写计数、压缩状态、Provider recovery state、旧 `AgentLoop` phase 等暂不纳入这一版。
