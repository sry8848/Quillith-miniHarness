# Session 持久化与中断恢复执行

## 1. 执行目标和边界

实现 SQLite Session 持久化、`/session` 和 `/resume <sessionId>`。恢复只加载并封口上次未完成的模型响应；恢复过程不请求模型、不自动续写任务、不重跑工具。

本次只覆盖父 `AgentSession`。`TaskTool` 创建的子 Agent 历史本来就不进入父会话，仍只通过父层 `task` 工具结果进入持久化历史。

不实现自动恢复、Session picker、`/new`、`/continue`、重命名、fork，也不改变 `exec`、`harbor` 的输入协议。三种启动模式仍在第一次正常提交给模型的用户消息时创建持久化 Session；新命令仅由 Interactive Runner 识别。

## 2. 必须保持的会话模型

新增 `dev.learn.agent.manual.session.ConversationState`，替代 `AgentSession` 内部单独的 `List<MessageParam> history`：

```java
public final class ConversationState {
    private final List<MessageParam> messages;
    private final List<MessageParam> modelContext;
}
```

- `messages` 是展示、Session 列表首条用户消息摘要和持久化审计使用的完整 committed history。它只追加正式提交的消息，不因上下文治理而删除或替换。
- `modelContext` 是下一次 `createRequest()` 传给模型的活动历史。它初始与 `messages` 相同；`snipMiddle()`、`compactOldToolResults()` 和 `compactHistory()` 的结果只替换它。
- 一条新的正式消息必须同时追加到两份内存列表。持久化只追加完整 `messages`；每次模型上下文发生有损替换时，额外覆盖保存一个 Context Checkpoint。恢复时以 Checkpoint 加后续消息重建 `modelContext`，绝不重新压缩完整历史。
- 类中只提供直接的 `appendCommitted(MessageParam)`、`appendCommitted(List<MessageParam>)`、`replaceModelContext(List<MessageParam>)`、只读快照访问器和加载时一次性替换方法。不要引入事件总线、Repository 泛型层或额外状态机。

这使恢复后的模型输入精确等于进程中断前的活动上下文，同时 `/session` 等展示仍能看到完整的已提交历史，且不需要永久双写两张完整消息表。

## 3. 架构责任边界

- `InteractiveRunner` 只识别 `/session`、`/resume <sessionId>` 和普通输入；它不访问 SQLite，也不理解消息协议。
- `AgentSession` 是父会话编排边界：拥有 `ConversationState`，创建首个持久化 Session、追加正式用户消息、执行恢复、处理 Provider 失败后的回滚。
- `AgentLoop` 只负责模型流、工具调度和 Anthropic 协议消息组装。它通过窄的 `TurnJournal` 记录“完整 block / 工具状态 / 本轮原子封口”；不查询 Session 列表，也不决定恢复入口。
- `SessionStore` 是唯一 SQL 和 JSON 边界：持有 session metadata、完整 messages、context checkpoint 和 in-flight 工具事实，提供原子 transaction。
- 父 `AgentLoop` 使用 `SessionTurnJournal`；子 `AgentLoop` 使用 `NoOpTurnJournal`。这个区分是必要的：`TaskTool` 的子 Agent 中间 history 不属于父 Session，若它直接写父 Session 的 in-flight，会让恢复时生成父历史中不存在的 tool_result。

`TurnJournal` 只包含 AgentLoop 确实需要的流式事实写入方法，不做通用 Repository 抽象；`SessionTurnJournal` 只是把当前 `SessionState.sessionId()` 转交给 `SessionStore`，因此 `/resume` 改变当前 Session 后不需要重建 Runtime。

## 4. SQLite 存储实现

### 4.1 依赖、位置和类型

1. 在 `pom.xml` 添加 Xerial SQLite JDBC 依赖（`org.xerial:sqlite-jdbc`），只添加满足 SQLite 访问的一个运行期依赖；不引入 ORM、连接池或迁移框架。
2. 新增 `dev.learn.agent.manual.session.SessionStore`。数据库文件固定为 `sessionState.agentHome().resolve(".memory/sessions.db")`；在初始化 Store 时创建 `.memory` 目录和表。此时只创建数据库文件，不能插入空 Session 行。
3. `SessionStore` 的所有公开写方法使用同一个对象监视器串行化。当前工具能在多个虚拟线程中同时完成；串行化 SQLite 写入即可避免同一进程的 `database is locked`，不需要连接池或异步写队列。
4. 每个 Store 方法自行打开 JDBC Connection、使用 prepared statement 和显式 transaction；成功 `commit`，异常 `rollback` 后原样以 `UncheckedIOException` 包装并向上抛出。不要记录后吞掉数据库异常，也不要返回内存成功而落盘失败。
5. JSON 一律复用 `ObjectMappers.jsonMapper()`。`MessageParam`、`ContentBlockParam` 与 `ToolExecutionResult` 通过明确的 Jackson `TypeReference` 序列化/反序列化，避免手拼 JSON 丢失 tool_use、thinking signature 或 tool_result 字段。

### 4.2 表和约束

初始化时创建以下表与索引：

```sql
CREATE TABLE IF NOT EXISTS sessions (
    session_id TEXT PRIMARY KEY,
    workspace TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS messages (
    session_id TEXT NOT NULL,
    seq INTEGER NOT NULL,
    message_json TEXT NOT NULL,
    PRIMARY KEY (session_id, seq),
    FOREIGN KEY (session_id) REFERENCES sessions(session_id)
);

CREATE TABLE IF NOT EXISTS context_checkpoints (
    session_id TEXT PRIMARY KEY,
    through_seq INTEGER NOT NULL,
    context_json TEXT NOT NULL,
    FOREIGN KEY (session_id) REFERENCES sessions(session_id)
);

CREATE TABLE IF NOT EXISTS inflight_response (
    session_id TEXT PRIMARY KEY,
    assistant_content_json TEXT NOT NULL,
    FOREIGN KEY (session_id) REFERENCES sessions(session_id)
);

CREATE TABLE IF NOT EXISTS tool_executions (
    session_id TEXT NOT NULL,
    tool_use_id TEXT NOT NULL,
    state TEXT NOT NULL,
    result_json TEXT,
    PRIMARY KEY (session_id, tool_use_id),
    FOREIGN KEY (session_id) REFERENCES inflight_response(session_id)
);

CREATE INDEX IF NOT EXISTS sessions_updated_at_idx
    ON sessions(updated_at DESC);
```

`context_checkpoints` 是完整历史与活动上下文之间的唯一额外持久化事实。`through_seq` 表示 `context_json` 已经吸收并替代到哪条完整消息：恢复时严格执行 `context_json + messages(seq > through_seq)`。Checkpoint 不存在时，活动上下文就是全部 `messages`。所有时间使用 `Instant.now().toString()`；每次成功变更该 Session 的 transaction 都更新 `sessions.updated_at`。

### 4.3 Store 的确定方法

实现足够支撑调用点的直接方法，不实现通用 CRUD：

- `createSessionWithFirstMessage(sessionId, workspace, userMessage)`：在一个 transaction 中插入 `sessions`，再以 `seq = 0` 插入 `messages`。只由首条未被 Hook 阻止的用户输入调用。
- `appendCommitted(sessionId, message)` / `appendCommitted(sessionId, messages)`：按 `messages` 当前最大 `seq + 1` 追加消息，并更新 `updated_at`；绝不维护第二份消息表。
- `saveContextCheckpoint(sessionId, throughSeq, modelContext)`：upsert 当前 `through_seq` 与完整 `modelContext` JSON。调用方传入的 `throughSeq` 必须是当前完整 history 的最大 seq；这样 Checkpoint 已包含该序号之前所有历史的压缩表示，后续只需追加更大的 `messages.seq`。
- `clearContextCheckpoint(sessionId)`：仅在恢复后的活动上下文重新等于完整 `messages` 时删除 Checkpoint；本次代码不主动把已压缩上下文反向展开，因此正常路径不调用它。
- `recordClosedAssistantContent(sessionId, assistantContent)`：首次完整 `content_block_stop` 时创建 `inflight_response(session_id, "[]")`，再把最新完整 block 列表写回。普通 text/thinking block 使用此方法。
- `recordToolUse(sessionId, assistantContent, toolUseId)`：一个 transaction 同时确保存在 in-flight、写入最新完整 assistant content 与插入 `tool_executions(..., NOT_STARTED, NULL)`。这是 `tool_use` 在被提交给调度器前的唯一写入入口。
- `markToolRunning(sessionId, toolUseId)`：只把 `NOT_STARTED` 更新为 `RUNNING`；若受影响行数不是 1，直接抛出状态不变量错误。
- `completeTool(sessionId, toolUseId, result)`：把状态更新为 `COMPLETED` 并写入完整 `result_json`。被 Hook 拒绝、审批拒绝、非法参数导致的失败也必须持久化为 `COMPLETED`，但不能虚构 `RUNNING`。
- `commitCompletedTurn(sessionId, committedMessages, checkpointOrNull)`：一个 transaction 追加本次正式消息到 `messages`、按需 upsert Context Checkpoint、删除该 `inflight_response` 及其 `tool_executions`、更新 `updated_at`。正常无工具 assistant、正常工具对、运行期流中断封口和重启恢复封口都走它。
- `restoreAfterFailedTurn(sessionId, committedMessages, checkpointOrNull)`：按当前内存回滚后的完整历史替换 `messages`，恢复或删除 Checkpoint；若历史为空，删除这个 Session，确保首个 Provider 请求失败后不会在 `/session` 中出现没有首条用户消息的空记录。
- `loadSession(sessionId, workspace)`：先按 session ID 读取 `sessions.workspace` 并与当前 `workspace.toRealPath().toString()` 精确比较，不同则抛出清晰业务错误；随后按 `seq` 读取完整 `messages`、可选 Checkpoint 及可选 in-flight/tool execution，重建不可变 `LoadedSession`。
- `listSessions()`：按 `updated_at DESC` 返回 `SessionSummary`。首条用户摘要读取该 Session `messages` 的第一条 user message，压缩连续空白后截取 80 个字符；不为摘要额外保存字段。

加载时若数据库中一个 `tool_use` 没有对应 `tool_executions`，或 `COMPLETED` 没有 `result_json`，这是持久化不变量损坏：直接失败，不静默生成伪造 tool_result。

## 5. SessionState、Runtime 与启动路径

### 5.1 `SessionState.java`

1. 将 `sessionId` 从 `final` 改为仅在 `AgentSession` 包内调用的可变字段，并新增 `restoreSessionId(String sessionId)`；新进程构造时仍生成 UUID。
2. 不改变 `workspace`、`agentHome`、审批模式、允许路径和 Git 根目录。`/resume` 只会在 Store 完成同 workspace 校验后调用 `restoreSessionId`。

新进程先保有临时内存 ID 是需求要求的“新内存 Session”；用户输入 `/resume` 后临时 ID 被丢弃且从未入库。没有 `/new`，恢复后的 Session 继续作为当前 Session。

### 5.2 `AgentRuntime.java` 与 `ManualAgentApplication.java`

1. `ManualAgentApplication.main()` 在解析选项、解析 `cwd` 并创建 `SessionState` 后创建一个 `SessionStore`，再传给 `AgentRuntime.create(...)`。
2. `AgentRuntime.create(...)` 创建一个父层 `ConversationState`、绑定 Store 的 `SessionTurnJournal` 和 `AgentSession`；父 `AgentLoop` 接收该 Journal，子 `AgentLoop` 显式接收 `NoOpTurnJournal`。
3. `AgentRuntime` 持有 Store 并在其他运行资源之后关闭它。若 Store 没有长连接，`close()` 只保留可用的生命周期边界即可。
4. 不更改 `ApplicationOptions`、`exec` 或 `harbor` 参数。Interactive command 是运行期输入命令，不是新的启动参数。

## 6. `AgentSession.java` 的 Turn 与恢复编排

### 6.1 正常首条和后续用户输入

把当前 `history` 字段替换为 `ConversationState`，并在 `submit()` 中按以下顺序修改：

1. 先执行既有 `UserPromptSubmit` Hook。若为 `BLOCK`，保持现有终端提示并直接返回；不创建 Session 行。
2. 保持既有 SESSION Prompt 刷新和 memory recall。
3. 构造原始 user `MessageParam`。若当前 session 尚未持久化，调用 `createSessionWithFirstMessage()`，成功后把消息加入内存两份列表并标记 persisted；否则调用 `appendCommitted()` 后再加入两份列表。
4. Hook additional context 仍构造为独立的隐藏 user message。它是既有 history 的一部分，必须通过 `appendCommitted()` 写入完整历史后同时追加两份内存列表。
5. `memoryRuntime.capture()` 改读取 `conversationState.messages()`，保持“回合结束记忆提取看到完整历史”的语义；`agentLoop.run()` 改接收 `ConversationState`。
6. `AnthropicServiceException` 分支仍调用既有诊断与 `rollbackFailedTurn()`；回滚后调用 `restoreAfterFailedTurn()`，使数据库完整历史和 Checkpoint 恰好镜像回滚后的内存状态。不要把 Provider 失败降级为成功。
7. 正常返回后的 Memory complete 逻辑不改。

### 6.2 新增恢复方法

新增包内可见的 `resume(String sessionId)`，供 Interactive Runner 调用：

1. 调用 `sessionStore.loadSession(sessionId, sessionState.workspace())`；ID 不存在或 workspace 不匹配时抛出带用户可读信息的业务异常，内存状态不变。
2. 使用 `LoadedSession` 的 Checkpoint 按 `context_json + messages(seq > through_seq)` 重建 `modelContext`；无 Checkpoint 时使用完整 `messages`。随后将两份列表一次性装入 `ConversationState`，再调用 `sessionState.restoreSessionId(sessionId)`。
3. 若无 inflight，立即返回。此路径不调用 `AgentLoop.run()`。
4. 若有 inflight，读取持久化 assistant content，并按其中 `tool_use` 的顺序构造结果：`NOT_STARTED` 生成失败结果“工具在上次中断前尚未执行”；`RUNNING` 生成失败结果“工具执行过程中进程中断，最终外部状态未知，重新执行前需要先检查现实状态”；`COMPLETED` 反序列化其 `result_json`。
5. 复用 AgentLoop 的现有 assistant/tool_result 组装规则：有 assistant content 时构造 assistant message；构造一个 user message，先放全部 tool_result，最后追加既有 `STREAM_INTERRUPTION_PROMPT` text block。将准备好的消息以 `commitCompletedTurn()` 一次性追加到完整 history、按需保存当前 Context Checkpoint，并删除 in-flight 与 tool execution。
6. 返回后由 Interactive Runner 打印“Session 已恢复：<sessionId>”，回到普通提示符。此处绝不调用模型、工具、Hook 或 memory complete。

把 `commitInterruptedTurn()` 中的消息组装提取为一个只接收 assistant content、工具结果和中断提示的私有 helper；运行期中断和上述重启恢复共用它，避免两套 protocol 组装规则分叉。

## 7. `AgentLoop.java` 的双历史与 durable-before-effect 改动

### 7.1 历史更新

1. `run(List<MessageParam> messages, String turnContext)` 改为 `run(ConversationState conversationState, String turnContext)`；`createRequest()` 永远读取 `conversationState.modelContext()`。
2. `BeforeModelCall` additional context、普通 assistant 完成、输出上限 continuation、Stop Hook continuation、assistant tool_use/user tool_result 对、流中断封口，全部改成“先 Journal/Store 成功，再同时更新 `messages` 和 `modelContext`”。
3. 原第 382–415 行的上下文治理改为只以当前 `modelContext` 调用 `snipMiddle()`、`compactOldToolResults()`、`compactHistory()`；成功取得结果后，保存一个 `throughSeq = messages` 当前最大 seq 的 Checkpoint，再替换内存 `modelContext`。绝不 `clear()` 或重写 `messages`。
4. `ModelRequestRecoveryState` 继续接收并操作 `modelContext`，因为它修复的是下一次模型请求的活动输入。其替换完成后，立即以当前最大 committed seq 保存 Checkpoint；不重写完整 `messages`。

### 7.2 流与工具状态

在现有 `streamModel()` 的事件处理内按如下精确顺序接入 Store：

1. 不使用 Provider Message ID，也不在 `message_start` 创建记录。当前 Session 最多只能有一个未提交回复，`session_id` 已经是足够的关联键。
2. text 或 thinking 的第一个 `content_block_stop`：先创建 `inflight_response(session_id, "[]")` 并写入完整 block；之后每个完整 block 只更新同一行的 `assistant_content_json`。Store 成功后才加入局部 `assistantContent`。
3. tool_use 的 `content_block_stop`：先完成现有 JSON 解析和 `ToolUseBlock` 构造；再在单个 Store transaction 中创建/更新 in-flight、写入最新完整 assistant content 与插入 `(session_id, tool_use_id, NOT_STARTED)`；成功后才将它加入局部列表并调用 `ToolCallDispatcher.submit()`。无效工具 JSON 同样记录完整 tool_use 和 `NOT_STARTED`，再持久化其失败结果为 `COMPLETED`，不进入真实执行。
4. 给调度器的 action 保留当前 `executeInIteration()`/`executeTool()` 管线。仅当 `BeforeToolUse` 未阻止、审批通过且即将调用 `toolRegistry.execute()` 时，先 `markToolRunning(sessionId, toolUseId)` 并提交 transaction，再调用真实 registry。被 Hook 阻止或被用户拒绝的工具从 `NOT_STARTED` 直接写入 `COMPLETED` 失败结果。
5. 真实 Registry、AfterToolUse Hook、输出修改与现有 RuntimeException 收敛逻辑全部完成、得到最终 `ToolExecutionResult` 后，先 `completeTool(sessionId, toolUseId, result)`，再让 Future 正常完成。这样进程在完成结果落库前中断仍是 `RUNNING`，不会把未知副作用误报为完成。
6. `runIteration()` 现有 Dispatcher close 与 `collectToolResults()` 的等待顺序保持不变。当前 JVM 流中断时，等所有已调度 Future 后调用共用封口 helper，并使用 `commitCompletedTurn()` 原子追加 assistant/user 消息、按需保存 Checkpoint、删除 in-flight 和 tool execution。
7. 正常无工具 assistant 也必须调用 `commitCompletedTurn()` 写正式 assistant message 并删除 inflight；正常含工具批次也使用同一 transaction。禁止只把消息加到内存后延迟到下一个 Turn 才保存。

除 Store 持久化失败外，既有流中断、Provider Error、工具失败的业务语义保持不变。Store 失败属于未知系统故障，应中止当前执行链，而非伪造工具已完成或会话已保存。

## 8. `InteractiveRunner.java` 命令

在现有退出和 `/memory` 判断之前增加两个精确分支：

1. 输入恰为 `/session`：调用 `agentSession.listSessions()`，按 Store 返回的更新时间倒序打印 `sessionId`、`updatedAt` 和首条用户消息摘要；无记录打印明确空提示。随后 `continue`，不提交模型。
2. 输入以 `/resume` 开头：只有两个 token（`/resume` 和非空 sessionId）时调用 `agentSession.resume(sessionId)`，成功后打印恢复成功信息；缺少 ID 或额外 token 时打印 `用法：/resume <sessionId>`。失败时打印返回的用户可读错误。无论这些分支的结果如何都 `continue`，绝不调用 `submit()`。

不要实现其他 `/session ...` 子命令，也不要在启动 banner 后主动显示 Session 列表。

## 9. 测试清单

新增 `src/test/java/dev/learn/agent/manual/session/SessionStoreTest.java`，用 `@TempDir` 中的实际 SQLite 文件验证：

1. 新 Store 不产生 `sessions` 行；首次 `createSessionWithFirstMessage()` 后才出现 Session 和 `messages` 的 seq=0 消息。
2. `listSessions()` 按 `updated_at DESC` 排序，首条用户摘要来自完整 `messages`，而非 model context。
3. 完整 `messages` 有 55 条、Checkpoint 的 `context_json` 表示压缩后的前 55 条时，load 后可由 `context_json + messages(seq > through_seq)` 原样重建 model context。
4. `recordToolUse()` 原子保存 assistant block 与 `NOT_STARTED`；`RUNNING`、`COMPLETED + result_json` 可正确加载，且整个关系只使用 session ID。
5. `commitCompletedTurn()` 不留下 in-flight/tool execution，并在重开数据库后能读到 assistant/tool_result 对与正确的 Checkpoint；事务故意失败时不留下半对消息。
6. workspace 不匹配、丢失 tool state、`COMPLETED` 缺结果时明确失败。

扩展 `AgentSessionTest` 的 fixture 注入临时 `SessionStore` 和父 `SessionTurnJournal`，覆盖：

1. 被 `UserPromptSubmit` 阻止的首条消息不创建 Session。
2. 首条正常输入创建 Session，第二次 `submit()` 的模型请求仍包含上一轮恢复的 model context。
3. Provider 最终失败回滚后，首轮空 Session 不在列表中；已有 Session 恢复到失败 Turn 之前的两份历史。
4. `resume()` 只装载历史且不发送 HTTP 请求；调用后一条普通输入才发送请求，且请求体包含已存 model context。
5. `NOT_STARTED`、`RUNNING`、`COMPLETED` 三种 inflight 均封口为合法 assistant/user tool_result 协议；前两种 result 的 `isError` 为 true，完成结果复用原内容和错误标记。

扩展 `InteractiveRunner` 相关测试，验证 `/session`、有效 `/resume <id>`、缺参 `/resume`、未知 ID、workspace 不匹配均不调用 Provider；恢复成功后的下一普通文本才调用 Provider。

扩展 `AgentLoopModelRequestRecoveryIntegrationTest`，通过可控 SSE 和测试 Journal/Store 验证：第一个完整 block 在 `content_block_stop` 后才创建 in-flight、工具在真实 Registry 前为 `RUNNING`、结果在 Future 完成前为 `COMPLETED`，以及正常/流中断提交后 in-flight 记录被原子清除。另增加子 Agent 使用 `NoOpTurnJournal` 时不会创建父 Session in-flight 的测试。
