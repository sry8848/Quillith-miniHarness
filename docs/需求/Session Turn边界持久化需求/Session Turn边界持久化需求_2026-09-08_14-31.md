# Session Turn 边界持久化需求

## 目的

为同一 Session 内每次 `AgentSession.submit()` 产生的 canonical message 记录稳定的 Turn 归属。`turnSeq` 只表示“这条消息属于本 Session 的第几次 submit”，用于让后续上下文治理能够按完整 Turn 选择、摘要或保留消息，避免拆开 `tool_use` 与其 `tool_result`。

它不改变 `sessionId + seq`：`sessionId` 标识会话，`seq` 保持全会话顺序，`turnSeq` 仅增加分组维度。

## 已确认规则

1. 每次进入 `AgentSession.submit()` 或 `submitRecorded()` 的 `submitInternal()` 时，取该 Session 已持久化最大 `turn_seq + 1`；首个 Turn 为 `0`。
2. 本次调用产生并正式提交的全部 canonical message 使用该值：用户消息、Hook reminder、assistant 消息、tool_use、tool_result、输出续写及恢复提示消息。
3. `messages` 增加 `turn_seq`。同一 Session 内的新 Turn 序号递增；一个 Turn 内的消息保留原有连续 `seq`。
4. 进程中断后恢复未封口回复时，复用该 Session 最后一条 canonical message 的 `turn_seq`，使修复产生的 assistant、tool result 和恢复提示仍属于原 Turn。恢复完成后的下一次 `submit()` 必须取新的递增序号。

示例：

```text
session_id  turn_seq  seq  message
S1          0         0    user
S1          0         1    assistant tool_use
S1          0         2    user tool_result
S1          0         3    assistant
S1          1         4    user
```

## 控制边界

本需求只持久化并传递消息分组序号，不新增 Turn 表、Turn 生命周期状态机、in-flight `turn_seq` 字段或新的压缩策略。当前 in-flight 回复之前已经至少持久化本次用户消息，因此恢复时可从 `messages` 推导 Turn 序号，无须重复存储。

现有 Provider 失败语义保持不变：已接受并 durable 的用户输入仍保留在 Session 中；本需求不新增“Provider 失败删除当前 Turn”的回滚逻辑。当前源码不存在粘贴对话中提到的 `restoreAfterFailedTurn()`，并且测试已验证该保留语义。把这类失败改为删除整个 Turn 会使“用户输入后 Provider 立即返回 500”这一真实场景丢失用户刚刚提交的需求，属于独立的产品行为变更，不能作为本需求的顺带修改。

本需求不兼容旧数据库。开发阶段删除旧 `.memory/sessions.db` 后按新 schema 重建。

## 验收

1. 同一 `submit` 的所有 `messages.turn_seq` 相同；两次 `submit` 的序号连续递增。
2. 正常完成、工具调用、续写及中断恢复后产生的消息均不跨 Turn。
3. Provider 失败前已持久化的用户消息仍保留，现有失败语义测试继续通过。
