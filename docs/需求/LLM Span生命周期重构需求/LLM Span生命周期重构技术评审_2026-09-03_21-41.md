# LLM Span 生命周期重构技术评审

> 评审时间：2026-09-03 21:41  
> 关联需求：`LLM Span生命周期重构需求_2026-09-03_21-30.md`  
> 适用项目：`learn-claude-code/demo/manual-agent`

## 评审目标与边界

本评审解决的唯一问题是：让一次真实的模型流式调用、该响应触发的前台工具调用，以及它们所属的 Agent 内部轮次，在 Trace 中具有与运行时一致的生命周期和层级。

目标 Trace 为：

```text
agent.run
└─ agent.iteration
   ├─ llm.call
   │  └─ HTTP
   ├─ tool.execute <toolA>
   └─ tool.execute <toolB>
```

本次不扩展正式 Session / User Turn ID、Tool outcome 与 Approval outcome 治理、非法 Tool JSON 的 Span、后台 Bash 进程完整生命周期、Memory / Context / Recovery 独立 Span、MDC、Metrics、成本和正文采集。上述限制直接沿用关联需求，避免把一次 Span 生命周期修正扩大为可观测性平台重构。

## 当前代码逻辑

### 一、当前主链

`AgentLoop.run()` 带有 `@WithSpan("agent.run")`。每个外层模型业务轮次先完成 BeforeModelCall Hook、上下文治理和请求构造；随后在内部 `while` 中调用 `createStreamingTurn()`。输出续写和可恢复请求会回到这个内部循环，因此一个 `modelRoundCount` 不严格等于一次真实 Provider 请求。

```text
AgentLoop.run() [agent.run]
  → BeforeModelCall / ContextManager / createRequest
  → createStreamingTurn() [llm.call]
  → 根据 StreamTurn 决定续写、恢复、最终输出或 Tool Result 回填
```

当前 `createStreamingTurn()` 的职责同时包含：

1. 用 `client.messages().createStreaming(request)` 建立并消费 SSE；
2. 增量展示 text / thinking；
3. 在完整 `tool_use` 的 `content_block_stop` 处解析输入并提交 Tool；
4. 收到 `message_stop` 后形成 `StreamTurn`；
5. 在 `try (ToolCallDispatcher ...)` 退出时关闭前台调度器。

最后一点决定了现有问题。`ToolCallDispatcher.close()` 会调用 `ToolExecutionScheduler.close()`；调度器对当前响应的全部前台工具执行 `allOf(...).join()`。因此 Java 方法直到前台 Tool 完成才真正返回，方法注解创建的 `llm.call` 也一直不结束。

```text
createStreamingTurn() [llm.call]
  → createStreaming / 消费 SSE
  → tool_use content_block_stop
       → ToolCallDispatcher.submit()
            → ToolExecutionScheduler 虚拟线程执行 executeTool() [tool.execute]
  → message_stop / StreamResponse.close()
  → ToolCallDispatcher.close()
       → 等待全部前台 Tool
  → 方法返回，llm.call 结束
```

这解释了当前实际树：`tool.execute` 在 `llm.call` 方法仍活跃时被提交，执行器传播当前 Context 后成为 `llm.call` 的子 Span；而 `llm.call.duration` 同时包含模型流耗时和 Tool 等待。

### 二、不能改变的运行时契约

当前调度和协议行为是正确的，重构 Trace 时必须保持：

- Tool 必须在完整 `tool_use` 块关闭后立即提交，不能等待 `message_stop`；
- 连续并发安全 Tool 仍可并发，独占 Tool 仍服从已有 barrier；
- Tool Result 仍按模型 Tool Call 的顺序由 `collectToolResults()` 回填；
- `runIteration()` 返回前仍等待前台 Tool，以保证后续 assistant `tool_use` 与 user `tool_result` 能成对提交；
- 后台 Bash 的当前 Tool Span 仍只覆盖“任务启动成功并返回 `bg_xxxx`”，不延伸到后台命令结束；
- `ToolUseBlock.id()` 仍是 `tool_result.toolUseId` 的协议关联键。

换言之，本次只改变 Span 的创建与结束位置，不改变 Tool 的提交时机、Future、Scheduler、消息历史或错误恢复控制流。

### 三、当前流可获得但未消费的模型数据

项目使用 `anthropic-java 2.49.0`。流式 `message_start.message` 已携带实际 response model 和初始 `Usage`；`message_delta` 携带累计 output usage 与 stop reason。当前流消费代码只从 `message_delta` 读取 `MAX_TOKENS`，没有保存 input/output tokens、cache usage、完整 finish reason 或实际 response model。

SDK 的 `Usage` / `MessageDeltaUsage` 将 cache read 与 cache creation 定义为 optional。它们只有在 Provider 实际返回时才应写入 Span；不能写 0，更不能从请求文本长度估算。成功请求的 request id 不在当前 `StreamResponse` 调用路径中取得，但 SDK 的 raw response API 可读取 HTTP request id；现有代码仅在 Provider 异常路径中从 body / header 打印该值。

## 方案评估与决策过程

### 一、优先通过方法边界继续使用 `@WithSpan`

候选方案如下：

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 保留 `@WithSpan`，把 Tool 延后到 SSE 完成后执行 | 不选 | 会破坏 Tool 流内提前执行、并发和用户等待行为，直接违反需求。 |
| 保留 `@WithSpan`，让 `createStreamingTurn()` 不等待 Tool | 不选 | 破坏现有前台 Tool 完成和 `tool_use/tool_result` 成对回填契约；而且把行为变化伪装成观测改造。 |
| 把 Tool 等待移到另一个线程或另一个方法，继续依赖自动上下文传播 | 不选 | 生命周期可能变短，但 Tool 的父级仍取决于提交时当前 Scope 和 Java Agent executor instrumentation，不能满足“明确来自 iteration”的要求。 |
| 按真实运行阶段拆出 iteration 与 SSE 方法，并继续使用 `@WithSpan` | 选择 | Annotation 继续负责 start、end、Scope close 和逃逸异常的状态；LLM 方法只覆盖建流、消费和关闭 SSE，Tool 等待仍由外层 iteration 完成。 |

结论：不应为四类 Span 全部手写 `Span.start()/end()`。将当前过宽的 `createStreamingTurn()` 拆为真实生命周期方法后，`agent.run`、`agent.iteration`、`llm.call` 和既有 `tool.execute` 都继续使用 `@WithSpan`。

### 二、必须新增 `agent.iteration`，但不新增新的 Agent 业务执行框架

`modelRoundCount` 不能直接作为 iteration：输出续写和恢复会在同一个计数内再次发起真实模型请求。正确边界是“每次即将调用 `createStreaming` 的内部 while 迭代”，即每一次真实 Provider Streaming 请求都新建一个 `agent.iteration`。

Iteration 在请求执行前开始，在以下工作完成后结束：当前 SSE 已经结束、由该响应产生的前台 Tool 已完成、Tool Result 已完成预算处理。随后由既有主循环根据正常结束、流中断、SSE Provider Error 或续写分支决定如何写回 messages；这部分不应为 Span 边界而复制状态机。这样 `llm.call` 和 Tool Span 都有同一个稳定父级，且 iteration 覆盖一次 Provider 请求及其直接 Tool 结果准备。

建议抽取一个私有 `runIteration()` 方法并标注 `@WithSpan("agent.iteration")`。它一次只执行一个真实请求：拥有本次 `ToolCallDispatcher`、调用只负责 SSE 的 `streamModel()`、等待前台 Tool，并按现有顺序准备 Tool Result。原有 `AgentLoop.run()` 继续在现有分支中回填结果；输出续写和恢复再次调用 `runIteration()`，所以不会把多个 Provider 请求合并到同一个 iteration。

不新建 `IterationExecutor`、`AgentIteration` 领域对象、结果状态机或第二套循环。现有 `AgentLoop.run()` 仍决定续写、恢复、停止和下一业务轮次；`runIteration()` 只是从既有循环中收拢一轮已经连续存在的工作，避免方法注解与真实生命周期不一致。

### 三、Tool Parent 必须显式捕获 iteration Context

仅依赖 `CompletableFuture.supplyAsync` 与 Java Agent 的自动传播，在当前实测环境中能够形成父子关系，但它把业务正确性依赖于提交瞬间的当前 Span。LLM Span 提前结束后，这个前提更不能成立。

因此，`runIteration()` 在调用 `streamModel()` 前捕获自己的 `Context`，再把该 Context 作为参数传入。`streamModel()` 处理完整 `tool_use` 时，把一个恢复 iteration Context 的小闭包传给 Scheduler：闭包内以 `try (Scope ignored = iterationContext.makeCurrent())` 建立当前 Context，再调用 `executeTool(toolUse)`。虚拟线程真正调用既有 `@WithSpan("tool.execute") executeTool()` 时，当前 Context 已明确恢复为 iteration，Tool 的直接父 Span 因而固定是对应 iteration。

只在这一处显式处理 OTel Context；不在提交 Scheduler 的短暂调用期使用 `makeCurrent()` 并依赖执行器“恰好捕获”它，不把 Context 放进 ThreadLocal，也不维护自定义 parentSpanId 或全局 Map。`makeCurrent()` 位于实际执行的闭包内，因此 parent 与单次 Tool 提交绑定。

### 四、属性映射保留为小型静态助手，不接管 Span 生命周期

需求要求属性映射不散落在业务代码中。直接在 `AgentLoop` 多处写 `setAttribute("gen_ai...", ...)` 会使语义约定、缺失字段处理和测试难以统一；但为此建立事件总线、通用 tracing DSL 或多实现接口又明显过度。

需求要求属性映射不散落在业务代码中，但这不要求 Adapter 创建和管理所有 Span。选择一个 final 的小型 `GenAiSpanAttributes` 助手即可：

- 以 `Span.current()` 为目标，集中维护 GenAI 属性键；
- 记录 LLM requested / actual model、Usage、finish reason、request id 和 Tool Call ID；
- 对被当前代码转换为返回值的 LLM 失败设置 ERROR；
- 不创建 Span、不持有 `Tracer`、不返回 Scope、不保存业务状态，也不需要由 `AgentRuntime` 注入。

这样保留统一属性约定，同时让 Annotation 继续承担标准的 Span 生命周期管理。

## 推荐架构

### 一、组件关系

```text
AgentLoop.run()                         @WithSpan("agent.run")
  └─ runIteration()                     @WithSpan("agent.iteration")
       ├─ ToolCallDispatcher（本 iteration 持有并关闭）
       ├─ streamModel(...)              @WithSpan("llm.call")
       │    ├─ createStreaming / 消费 SSE / StreamResponse.close
       │    └─ tool_use → scheduler.submit(闭包内 iterationContext.makeCurrent())
       ├─ executeTool(...)               @WithSpan("tool.execute")
       │    └─ 现有 Hook → Approval → ToolRegistry → AgentTool
       └─ collect tool_result（既有主循环随后按分支回填）
```

生产运行继续依赖现有 OpenTelemetry Java Agent；未安装 Java Agent 时注解退化为无观测的正常业务调用，不需要新增生产 SDK 或注入对象。

### 二、四个 Span 的职责

| Span | 开始 | 结束 | Parent | 主要属性 |
| --- | --- | --- | --- | --- |
| `agent.run` | `AgentLoop.run()` 入口 | `run()` 返回或未恢复异常离开 | 当前 Context | 无新增正文属性；保持现有语义。 |
| `agent.iteration` | `runIteration()` 进入 | 当前响应的 Tool Result 已准备；或本次请求走向续写 / 恢复 / 失败分支时 | `agent.run` | 不新增正式 iteration ID。 |
| `llm.call <requested-model>` | `streamModel()` 进入 | SSE 正常消费完成且 `StreamResponse` 已关闭；或流 / 请求失败时 | 对应 iteration | requested / actual model、input/output tokens、finish reason、按需 cache usage、request id。 |
| `tool.execute <tool-name>` | 工具虚拟线程实际进入既有 `executeTool` | `executeTool` 公共管线返回 | 对应 iteration 的显式 Context | `gen_ai.tool.call.id = ToolUseBlock.id()`。 |

不把 Tool Span 的状态模型扩展为完整业务 outcome 治理。`ToolExecutionResult.error()` 的 span status 语义是独立需求；本次只确保 Tool 的父级、生命周期和 provider tool-call 因果关联正确。

### 三、核心时序

```text
runIteration() [agent.iteration] 开始
  → 捕获 iteration Context
  → createRequest()
  → streamModel() [llm.call] 开始
       → createStreaming()
       → 处理 SSE
            → 完整 tool_use
                 → scheduler 提交恢复 iteration Context 的 executeTool 闭包
                 → Tool 可与后续 SSE 重叠执行
       → message_stop / iterator 结束
       → StreamResponse.close()
  → streamModel() 返回，llm.call 自动结束
  → ToolCallDispatcher.close() 等待前台 Tool
  → collectToolResults()，按原顺序构造并预算 tool_result
  → 返回已准备的 Tool Result
runIteration() 返回，agent.iteration 自动结束
AgentLoop.run() 按既有分支回填 messages
```

Tool 运行时的逻辑为：

```text
被调度的 iteration Context 恢复闭包
  → executeTool(toolUse) [tool.execute]
       → BeforeToolUse Hook
       → Approval Gate
       → ToolRegistry
       → AfterToolUse Hook
  → 方法返回，tool.execute 自动结束
```

`executeTool` 继续是当前的公共 Tool 管线；不复制 Hook、审批或 Registry 逻辑。Tool 的父级也不从 Java Agent 的执行器自动传播猜测，而是由传给实际闭包的 iteration Context 建立。

### 四、LLM Usage 与属性映射

属性键都由 `GenAiSpanAttributes` 的私有常量集中定义，业务代码只传递 SDK 对象或已解析的低基数值。首版记录：

| 来源事件 | 读取字段 | 写入条件 |
| --- | --- | --- |
| 请求构造 | requested model | 每个 `llm.call` 必写。 |
| `message_start` | actual model、`inputTokens`、cache read、cache creation | model / input 必写于 SDK 成功解码；cache 字段仅 Optional 有值时写。 |
| `message_delta` | `outputTokens`、stop reason | 有事件字段时写；output 采用最后一个 delta 的累计值。 |
| 成功 HTTP raw response | request id | response/header 实际返回时写。 |
| 完整 `tool_use` | `ToolUseBlock.id()` | 每个 Tool Span 必写为 `gen_ai.tool.call.id`。 |

不写 prompt、completion、thinking、Tool 输入、Tool 输出、Provider 错误 body 或异常详情。cache 未返回时保持 attribute 缺失，而非 0；所有 Usage 均直接取 SDK 响应，不作字符数/token 估算。

### 五、错误与 Recovery 语义

从 `streamModel()` 逃出的异常继续由 `@WithSpan` 自动结束和标记。当前代码中有一部分流错误会被捕获并转换为 `StreamTurn`，以便外层 Recovery 使用；这些异常没有逃出标注方法，因此仅在这几个既有转换分支通过 `GenAiSpanAttributes` 对当前 `llm.call` 调用 `setStatus(ERROR)`：

- `createStreaming` 抛出未恢复的 Provider / 请求异常；
- SSE 收到 provider error；
- `AnthropicIoException`、`AnthropicInvalidDataException` 或流提前结束；
- `StreamResponse` 关闭或流处理抛出其他运行时异常且被转换为正常返回值。

异常详情继续由既有日志与 Provider 诊断承载，不写入 Span 属性。若外层 Recovery 后再次请求，失败请求的 `llm.call` 保持 ERROR；下一实际请求另开新的 iteration 与 `llm.call`。恢复成功不回写前一 Span。iteration 和 agent.run 是否标记失败仍按控制流最终是否成功离开决定：已完成恢复交接的 iteration 不因为内部已记录的 LLM 失败被改写为“模型成功”，也不把最终成功的 agent.run 错标为失败。

## 实施影响与测试设计

### 一、预期改动面

核心修改集中在：

- `AgentLoop`：抽取标注 `@WithSpan("agent.iteration")` 的单请求方法；把 SSE 处理抽取到标注 `@WithSpan("llm.call")` 的方法；由 iteration 持有 Dispatcher；提交 Tool 时用 iteration Context 包装既有 `executeTool`。
- 新增 `telemetry/GenAiSpanAttributes`：仅集中属性和 LLM 已捕获错误的状态写入。
- `AgentRuntime` 不增加 Telemetry 装配或注入。
- `pom.xml` 不需要为 in-memory tracing 增加生产或测试 SDK 依赖。

不改 `ToolExecutionScheduler` 的并发策略、`ToolCallDispatcher` 的调度分流、`ToolRegistry`、Hook、审批、MCP、BackgroundTaskScheduler 和 Anthropic 消息协议结构。

### 二、测试层次

1. **真实 Trace 验收**：在已加载 OpenTelemetry Java Agent 的应用进程中，使用 Jaeger 检查无 Tool、单 Tool、并发 Tool、`LLM → Tool → LLM → Final` 和可恢复 LLM 失败场景的实际 Span 树、时间重叠、Usage 与错误状态。
2. **真实行为验收**：单 Tool 场景确认 Tool 在 SSE 仍持续时已开始执行，且 `streamModel()` 返回后 iteration 才等待前台 Tool；这验证的是改动后的运行行为，而不是模拟 Telemetry 实现细节。
3. **既有行为回归**：继续运行 Streaming、Tool、exclusive barrier、Tool Result 顺序、MCP、task 子 Agent、Background Bash 启动、Recovery 和终止规则的已有测试。

不引入 in-memory exporter、Telemetry mock 或“仅验证手工 Span API 调用”的测试结构。Trace 层级、时间线和 annotation instrumentation 只在真实 Java Agent 运行时验收；普通单元测试继续验证 Agent 行为契约。

## 复杂度与范围控制

该方案只新增一个集中属性映射的小型助手；没有手工 Span scope、Tracer 注入、Span 生命周期封装、新调度器、事件总线、Trace 存储、ID 生成器或可配置 tracing 框架。`AgentLoop` 的业务决策仍保留在原处，局部整理只为让方法边界准确覆盖 iteration、SSE 与 Tool Result 回填。

最大的实现风险不是 API 调用，而是把 iteration 方法过早返回，重新造成 Tool 成为 root 或 LLM child。为此以“显式包装 iteration Context”和“Tool Result 回填仍位于 iteration 方法内”作为两个不可违反的不变量，并通过加载真实 Java Agent 的 Trace 验收直接验证。

这在满足需求的同时保留了现有 Agent 行为：模型调用耗时、Tool 耗时和并发关系可被独立解释；Tool 的 provider call id 提供跨兄弟 Span 的因果关联；但不提前引入需求明确排除的 outcome、Session、后台任务或指标体系。
