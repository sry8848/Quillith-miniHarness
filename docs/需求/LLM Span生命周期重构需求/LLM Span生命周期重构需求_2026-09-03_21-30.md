# LLM Span 生命周期重构需求

## 1. 需求概述

### 1.1 需求名称

LLM Span 生命周期重构

### 1.2 需求背景

当前 `AgentLoop.createStreamingTurn()` 使用 `@WithSpan("llm.call")` 创建 LLM Trace Span。由于该方法在关闭 `ToolCallDispatcher` 并等待全部前台 Tool 完成后才返回，`llm.call` 的持续时间不仅包含模型 Streaming 时间，还可能包含前台 Tool 的执行和等待时间。

当前 Trace 结构如下：

```text
agent.run
└─ llm.call
   ├─ HTTP
   └─ tool.execute
```

这会导致两个问题：

1. `llm.call.duration` 不能准确表示真实模型调用延迟；
2. `tool.execute` 被表示为 LLM Operation 的子操作，而不是 Agent 当前执行轮次中的独立操作。

### 1.3 需求价值

通过拆分 Agent 执行轮次、模型调用和 Tool 调用的 Span 生命周期，使 Trace 能够准确表达 Agent Runtime 的业务执行语义，并为模型延迟、Tool 延迟和并发关系提供可靠的观测基础。

## 2. 需求目标

将一次 Agent 模型执行轮次的 Trace 结构调整为：

```text
agent.run
└─ agent.iteration
   ├─ llm.call
   ├─ tool.execute <toolA>
   └─ tool.execute <toolB>
```

其中：

- `agent.iteration` 表示一次 Agent 内部执行轮次，覆盖模型请求、模型产生 Tool Call、当前轮 Tool 执行以及 Tool Result 准备完成；
- `llm.call` 只表示一次真实 Provider / Streaming Model 调用；
- `tool.execute` 表示当前 Agent Iteration 中的一次 Tool Invocation；
- `llm.call` 与由该模型响应产生的 `tool.execute` 是同一 `agent.iteration` 下的兄弟 Span，允许在时间线上重叠。

## 3. 需求范围

### 3.1 本次需求包含

- 新增每次模型执行轮次对应的 `agent.iteration` Span；
- 调整 `llm.call` 的创建、结束和错误生命周期；
- 调整 Tool Span 的 Parent Context，使其父 Span 为 `agent.iteration`；
- 保留 Provider Tool Call ID，表达模型响应与 Tool Invocation 之间的因果关联；
- 采集 Anthropic Streaming SSE 已提供的模型、Token、停止原因和 Cache Usage 数据；
- 增加覆盖 Span 层级、时间重叠、Usage 和行为回归的测试。

### 3.2 明确不包含

以下事项不属于本次需求：

- 完整 `ManualAgent.submit()` User Turn Root；
- 正式 Session ID / Turn ID；
- Tool Outcome / Approval Outcome 完整治理；
- 非法 Tool JSON 在 `executeTool()` 前缺少 Span 的问题；
- Background Bash 完整生命周期 Span；
- Memory Recall、Memory Extraction、Context Compaction Span；
- Recovery 独立业务 Span；
- SLF4J MDC；
- Metrics / Prometheus / Grafana；
- Cost 计算、Eval、Jaeger Dashboard 和 Trace Sampling；
- Prompt、Completion、Tool Result 正文采集。

除为本需求提供最小必要支持外，不应顺带实现上述能力。

## 4. 功能需求

### 4.1 `agent.run` 生命周期

当前 `AgentLoop.run()` 的 Agent Span 语义保持不变。本次不要求将 Memory Recall、`ManualAgent.submit()` 或 Memory Extraction 纳入 `agent.run`。

完整 User Turn Root Span 属于后续独立需求。

### 4.2 `agent.iteration` Span

每一次实际模型执行轮次必须创建一个独立的 `agent.iteration` Span。

其生命周期至少覆盖：

```text
当前请求前准备
→ 一次模型调用
→ 当前模型响应产生的前台 Tool 完成
→ 当前轮 Tool Result 准备完成
```

具体是否包含请求前 Context Governance，可结合现有 `AgentLoop.run()` 边界确定，但必须保证：

> `llm.call` 和由该模型轮次产生的 `tool.execute` 拥有共同且稳定的父 Context。

多轮模型调用必须分别创建 `agent.iteration`，不得将多个模型请求合并到同一个 `llm.call` Span。

### 4.3 `llm.call` Span

`llm.call` 必须在真实模型 Streaming Operation 开始前或紧邻其前创建，推荐位置为 `client.messages().createStreaming(...)` 之前。

正常结束条件为：

```text
SSE 消费正常结束
→ 收到 message_stop / 流正常结束
→ StreamResponse 正常关闭
```

`llm.call` 不得等待以下操作完成后才结束：

- 前台 Tool 完成；
- `foregroundScheduler.close()`；
- `allOf(...).join()`；
- Tool Result 收集与回填。

因此，`createStreamingTurn()` 的 Java 方法生命周期可以继续等待 Tool Scheduler，但 `llm.call` 必须能够提前结束。

### 4.4 `tool.execute` Span

每次 Tool Invocation 应创建对应的 `tool.execute` Span，并以 `agent.iteration` 为 Parent Context，不得继续自动继承 `llm.call` 作为 Parent。

目标结构为：

```text
agent.iteration
├─ llm.call
└─ tool.execute
```

Tool 在 SSE 尚未结束时仍应能够开始执行，`llm.call` 与 `tool.execute` 的时间区间允许重叠。

### 4.5 Tool 执行与结果语义

本次仅调整 Observability Span 生命周期，不得改变现有 Agent 行为：

- 收到完整 `tool_use` 后，仍立即提交 Tool 到 `ToolExecutionScheduler`；
- 禁止改为等待完整模型响应结束后再统一执行 Tool；
- `createStreamingTurn()` 返回前仍保证本轮前台 Tool 已完成；
- Tool 可并发执行，但 Tool Result 仍按现有模型 Tool Call 顺序回填；
- 不得修改 `PendingToolExecution` 语义、`tool_use / tool_result` 对应关系、Scheduler Barrier 或 Exclusive Tool 行为；
- Background Bash 的 `tool.execute` 仍只表示后台任务已启动，不扩展为后台 Process 生命周期 Span。

### 4.6 OpenTelemetry Context 传播

Tool Scheduler 捕获的 Parent Context 必须明确来自对应的 `agent.iteration`，不能依赖提交 Tool 时线程上恰好处于哪个 Span。

实现可采用保存 Iteration Context、显式传入 Context、`Context.wrap(...)`、`context.makeCurrent()` 或与当前 OTel Java Agent / Executor instrumentation 兼容的等价方式。

必须满足：

> Tool Parent Context 来自明确的 Agent Iteration，而不是偶然继承当前 LLM Scope。

### 4.7 Tool Call 因果关联

调整为兄弟 Span 后，不再通过父子关系表达 Tool 由哪次模型响应产生。`tool.execute` 必须至少保留已有 Provider Tool Call ID：

```text
gen_ai.tool.call.id = <provider tool call id>
```

该 ID 来自 `ToolUseBlock.id()`，并继续用于 `tool_result.toolUseId`。

如果当前 OpenTelemetry GenAI Semantic Convention 版本不便直接使用该字段，应通过统一 Telemetry Adapter 映射，不得在业务代码中散落硬编码字符串。本次不要求额外生成新的 Tool Invocation UUID。

### 4.8 LLM Usage 数据

应消费 Anthropic SDK 已提供的低成本 Usage 数据，并记录到当前 `llm.call` Span。

从 `message_start` 读取：

- `input_tokens`；
- Provider 实际返回时的 `cache_read_input_tokens`；
- Provider 实际返回时的 `cache_creation_input_tokens`；
- 实际响应模型。

从 `message_delta` 读取：

- `output_tokens`；
- `stop / finish reason`。

至少应记录以下信息：

- requested model；
- actual response model；
- input tokens；
- output tokens；
- finish reason。

Cache Usage 仅在 Provider 返回时记录；未返回时属性保持缺失，不得自行填写为 0，也不得通过字符串长度估算 Provider Usage。

### 4.9 错误处理

以下情况发生时，`llm.call` Span 必须正确结束并反映失败：

- Streaming API Exception；
- SSE 异常中断；
- Provider 请求失败；
- Stream 无法正常关闭；
- 其他未恢复的模型请求异常。

如果 Provider Error 经外层 Recovery 最终恢复成功，则必须保留真实失败状态：

```text
第一次 llm.call = failed
后续 llm.call = success
Agent iteration / Agent run = 根据最终结果决定
```

不得因为最终 Recovery 成功而将第一次失败的 `llm.call` 修改为成功。

## 5. 验收标准

### 5.1 无 Tool 场景

Jaeger 应看到：

```text
agent.run
└─ agent.iteration
   └─ llm.call
      └─ HTTP
```

### 5.2 单 Tool 场景

应看到：

```text
agent.run
└─ agent.iteration
   ├─ llm.call
   │  └─ HTTP
   └─ tool.execute read_file
```

不得出现 `llm.call` 包含 `tool.execute read_file` 的父子结构。

### 5.3 并发 Tool 场景

应看到同一 `agent.iteration` 下的兄弟 Span：

```text
agent.iteration
├─ llm.call
├─ tool.execute toolA
└─ tool.execute toolB
```

如果 Tool 执行存在并发，Jaeger 时间轴中的 Tool Span 应能够重叠，并保持当前真实 Tool 并发行为。

### 5.4 Tool 与 SSE 重叠场景

构造 SSE 持续输出、前部产生完整 Tool Call 且 Tool 执行时间较长的测试，验证：

- `llm.call` 与 `tool.execute` 的时间区间可以重叠；
- `llm.call.duration` 不因等待 Tool 完成而被拉长。

### 5.5 多模型轮次

对于 `LLM → Tool → LLM → Final`，应形成：

```text
agent.run
├─ agent.iteration #1
│  ├─ llm.call
│  └─ tool.execute
└─ agent.iteration #2
   └─ llm.call
```

### 5.6 Usage

对包含 `input_tokens`、`output_tokens`、`finish reason` 和 `model` 的测试 SSE，验证对应 `llm.call` Span 能正确获得数据。

没有返回 Cache Usage 时，对应属性必须缺失，而不是填写推测值。

### 5.7 行为回归

以下现有行为必须继续通过：

- Streaming 输出；
- Tool Calling；
- 前台 Tool 并发；
- Exclusive Tool Barrier；
- Tool Result 顺序；
- MCP；
- Subagent；
- Background Bash 启动；
- Model Recovery；
- 当前 AgentLoop 终止规则。

## 6. 最终完成定义

本需求完成后，必须同时满足：

1. `llm.call` 可以可靠解释为真实模型 Streaming 调用耗时，不再包含前台 Tool 等待时间；
2. Tool 仍能在模型 SSE 尚未完全结束时提前执行；
3. Trace 结构表达 Agent Runtime 业务语义：

   ```text
   Agent Iteration
   ├─ Model Operation
   └─ Tool Operations
   ```

4. Provider Tool Call ID 作为模型决策与 Tool Invocation 之间的稳定因果关联被保留；
5. 现有 Agent 行为和 Tool 调度语义无回归。

## 7. 评审关注点

需求评审和实现前应重点确认：

- `agent.iteration` 的准确创建边界及结束时机；
- LLM Span 提前结束后，`createStreamingTurn()` 如何继续等待前台 Tool 且不影响 Span 归属；
- 当前 Executor / Java Agent Context Propagation 与显式 Iteration Context 的兼容方式；
- Usage 字段在当前 Telemetry Adapter 中的统一映射方式；
- 失败的 `llm.call`、Recovery 结果与 Iteration / Run 最终状态之间的状态表达。
