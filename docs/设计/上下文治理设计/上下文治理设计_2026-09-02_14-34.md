# Manual Agent 上下文治理设计

> 文档时间：2026-09-02 14:34  
> 适用项目：`learn-claude-code/demo/manual-agent`  
> 文档性质：当前实现设计说明，不代表未来功能承诺

## 1. 文档目的

本文说明 Manual Agent 如何在有限的模型上下文中组织信息、控制增长、执行有损压缩，并在压缩后保留可恢复入口。

这里的“上下文治理”不是单独的摘要算法，也不等同于长期记忆。它覆盖从用户输入进入系统，到模型请求组装、工具结果回写、历史压缩、失败恢复和子 Agent 隔离的完整链路。

本文重点回答以下问题：

1. 哪些信息会进入模型请求，它们分别存活多久；
2. 为什么需要多层治理，而不是只在超限时做一次摘要；
3. 四层上下文治理分别处理什么问题，按什么顺序生效；
4. 有损压缩如何保留恢复入口，失败时如何避免提交半成品；
5. 会话上下文、长期记忆、Hook 上下文和子 Agent 上下文之间是什么关系；
6. 当前设计有哪些明确边界和已知风险。

## 2. 首先区分：上下文不等于会话历史

模型一次实际请求看到的信息由多个来源组合而成：

```text
模型请求上下文
├─ System Prompt
│  ├─ Agent 身份
│  ├─ Workspace 状态
│  ├─ Memory 索引
│  └─ Skills 等动态提示
├─ 活跃会话历史 messages
│  ├─ 用户消息
│  ├─ Assistant 回复
│  ├─ tool_use / tool_result 协议消息
│  ├─ Hook 写入的隐藏提醒
│  └─ 压缩摘要或裁剪占位消息
├─ 本轮临时上下文 turnContext
│  └─ 根据当前问题召回的长期记忆正文
└─ 工具定义 tools
```

这些信息虽然最终共同进入请求，但生命周期和治理方式不同。如果把它们都当作同一个 `history` 处理，会产生两个问题：一是临时信息被错误固化，二是压缩预算无法反映各类信息的真实语义。

当前设计因此采用“请求时组装、按生命周期分别管理”的方式。

### 2.1 各类上下文的生命周期

| 上下文类型                     | 所有者                      | 是否写入 `history` | 生效范围               | 主要治理方式                  |
| ------------------------- | ------------------------ | --------------:| ------------------ | ----------------------- |
| System Prompt             | `SystemPromptManager`    | 否              | 每次模型请求             | 按刷新作用域重新生成              |
| 原始用户消息                    | `ManualAgent.history`    | 是              | 当前会话               | 中段裁剪、旧结果压缩、摘要           |
| Assistant 消息              | `ManualAgent.history`    | 是              | 当前会话               | 中段裁剪、摘要                 |
| Tool Use / Tool Result    | `AgentLoop` 写入 `history` | 是              | 当前会话               | 协议成对保护、结果预算、旧结果压缩       |
| UserPromptSubmit Hook 上下文 | `ManualAgent` 写入         | 是              | 当前及后续会话历史          | 作为隐藏 user reminder 参与压缩 |
| BeforeModelCall Hook 上下文  | `AgentLoop` 写入           | 是              | 当前及后续模型轮次          | 作为隐藏 user reminder 参与压缩 |
| 召回记忆 `turnContext`        | `MemoryRuntime`          | 否              | 当前用户 Turn 内的每次模型请求 | 请求时临时追加，不进入压缩和记忆提取      |
| 工具定义                      | `ToolRegistry`           | 否              | 每次模型请求             | 当前版本不纳入本地字符预算           |
| 压缩前 Transcript            | `ContextManager`         | 文件存储           | 持久化恢复入口            | JSONL 归档，按需读取           |
| 长期记忆                      | `MemoryRuntime`          | 否              | 跨会话                | 选择、召回、提取、整理             |

## 3. 治理目标与核心不变量

### 3.1 治理目标

上下文治理同时追求四个目标：

1. **可继续工作**：压缩后仍保留当前目标、已完成工作、关键决定和下一步；
2. **协议正确**：不能把 `tool_use` 和对应的 `tool_result` 从裁剪边界处拆开；
3. **损失可见且可恢复**：被移除的信息必须留下明确标记；重要完整内容应有文件入口或可重新执行路径；
4. **成本逐级增加**：优先使用本地、确定性的低成本治理，最后才调用模型生成摘要。

### 3.2 核心不变量

当前实现依赖以下不变量：

- `ManualAgent` 是父 Agent 会话历史的唯一长期持有者；`ContextManager` 不持有 `history`；
- `ContextManager` 的压缩方法返回新列表，不直接修改调用方输入；
- `AgentLoop` 只有在一整条请求前治理管线成功后，才统一替换真实历史；
- 任何有损摘要之前必须先保存当次活跃历史快照；
- 工具结果压缩只替换 `content`，保留 `toolUseId`、错误标记和其他协议属性；
- 临时召回记忆不写入会话历史，避免被后续压缩、重复召回或再次提取；
- 子 Agent 使用全新消息列表，不复制父 Agent 历史；
- 本地字符阈值是教学版软预算，不宣称等于真实 Token 或 Provider 上下文上限。

## 4. 一次用户 Turn 的上下文生命周期

### 4.1 Turn 外层：`ManualAgent.submit`

一次用户输入按以下顺序进入系统：

```text
用户输入
  ↓
UserPromptSubmit Hook
  ├─ BLOCK：本 Turn 结束，不写入历史
  └─ CONTINUE：可产生附加上下文
  ↓
刷新 SESSION 级 System Prompt
  ↓
根据当前 query 召回长期记忆 → recalledMemories
  ↓
原始用户消息写入 history
  ↓
Hook 附加上下文作为 <system-reminder> 写入 history
  ↓
在 AgentLoop 可能压缩前捕获 Memory 提取快照
  ↓
AgentLoop.run(history, recalledMemories)
  ↓
成功：基于预先捕获的快照执行长期记忆提取
失败：按本 Turn 的 userMessage 尝试回滚
```

这里有一个重要区分：`recalledMemories` 被作为 `turnContext` 传给 `AgentLoop`，但不会加入 `history`；Hook 附加上下文则会加入 `history`。前者是本轮临时知识，后者是 Agent 行为链的一部分。

当前 Memory 快照在进入 `AgentLoop` 前捕获。因此它保留压缩前的既有对话、当前用户消息和 UserPromptSubmit Hook 提醒，但不包含本轮之后产生的 Assistant 回复和工具协议。

### 4.2 模型轮次内：`AgentLoop.run`

每个业务模型轮次在真正调用 Provider 前都会重新执行请求前治理：

```text
当前真实 history
  ↓
BeforeModelCall Hook 追加隐藏提醒
  ↓
L1：按消息数量裁剪中段
  ↓
L2：压缩活跃历史中的旧 Tool Result
  ↓
是否超过自动摘要字符阈值？
  ├─ 否：继续
  └─ 是：L4 保存 Transcript 并生成摘要
  ↓
整条管线成功后统一替换真实 history
  ↓
刷新 MODEL_CALL 级 System Prompt
  ↓
组装 messages + turnContext + tools
  ↓
请求模型
```

模型返回工具调用后，工具结果在写入历史前还会经过 L3：

```text
执行本轮全部工具
  ↓
Tool Hook 处理最终结果
  ↓
L3：限制本轮 Tool Result 总字符数，必要时落盘
  ↓
assistant tool_use 与 user tool_result 成对写入 history
  ↓
下一模型轮次再经过 L1 → L2 → L4
```

因此，“L1 → L2 → L4”是每次请求前的执行顺序；L3 位于工具结果产生时。层号表达治理职责，不代表四层一定在同一时刻连续调用。

## 5. 四层上下文治理

### 5.1 L1：中段消息裁剪

#### 处理的问题

长任务中消息数量会持续增加。只保留最近消息虽然简单，但可能丢失用户最初目标；只保留开头又会丢失当前进度。L1 因此采用“保留头部 + 删除中段 + 保留尾部”的结构。

#### 当前规则

- 软目标消息数：`50`；
- 固定保留头部：`3` 条；
- 中间插入：`1` 条裁剪说明；
- 其余配额用于保留最近尾部消息；
- 如果裁剪切口落在 `tool_use` 与紧随其后的 `tool_result` 之间，边界会向外移动；
- 边界调整后可能比 50 条多一条，也可能因为没有安全裁剪区间而保持原历史。

#### 裁剪结果

裁掉中段前，系统先把当前活跃历史保存到 `.transcripts/context-<UUID>.jsonl`。随后中段被替换为一条 user 角色占位消息，说明：

- 多少条中间消息被移除；
- 当次 Transcript 的工作区相对路径；
- 缺少细节时可以读取 Transcript、重新读取文件或重新执行工具。

#### 设计取舍

L1 是确定性、本地、零模型调用成本的治理方式，适合先快速缩小扫描范围。但它只理解消息位置和工具协议边界，不理解语义重要性。因此它保留“开头目标”和“最近状态”，却不能保证中段的某个关键决定一定留在活跃上下文中。

### 5.2 L2：旧 Tool Result 微压缩

#### 处理的问题

工具结果往往比普通对话更大，而且同一结果在刚产生时价值最高，随着后续步骤推进，其完整正文通常不再需要持续占用上下文。

#### 当前规则

- 按 `tool_result` 内容块计数，而不是按消息计数；
- 最近 `3` 个工具结果保留完整内容；
- 更旧结果只有在正文超过 `120` 个字符时才替换；
- 已经由 L3 落盘、以 `[[agent:persisted-tool-result]]` 开头的引用继续保留；
- 被压缩的普通旧结果替换为统一说明，提示模型在需要时重新运行工具。

同一条 user 消息可以包含多个 `tool_result`，L2 会逐块判断并只重建真正发生变化的消息。

#### 设计取舍

L2 不额外为每个旧结果写文件。这样可以避免持续产生大量小文件，但意味着一个未经过 L3 落盘的旧结果在被替换后，恢复方式主要是重新执行工具，或者读取此前 L1/L4 生成且覆盖该结果的 Transcript。

短结果保留原文，因为用同样长度的占位符替换并不能获得有意义的空间收益。

### 5.3 L3：单轮 Tool Result 预算与落盘

#### 处理的问题

单次工具调用批次可能立刻返回超大内容。如果先把完整结果写入历史，再等待下一轮治理，当前批次就可能已经远超合理输入规模。因此 L3 在工具结果进入历史之前执行。

#### 当前规则

- 同一轮全部工具结果总预算：`200,000` 个 Java 字符；
- 预算只计算字符串形式的 `tool_result.content`；
- 超限时按结果从大到小选择落盘候选；
- 完整结果写入 `.task_outputs/tool-results/<session-UUID>/<result-UUID>.txt`；
- 模型上下文中用“文件路径 + 原字符数 + 最多 2,000 字符预览”替换完整结果；
- 只有引用确实比原文短时才允许替换；
- 如果所有有效替换仍不能把预计字符数降到预算内，直接抛出异常。

#### 四阶段提交

L3 使用先规划后写入的方式：

1. 扫描并校验本批结果，计算总字符数；
2. 在内存中选择候选并模拟替换后的大小；
3. 确认整批方案能够满足预算后，保存全部计划文件；
4. 在新列表中按原位置替换内容块。

这避免了“写了部分文件，最后才发现预算仍然无法满足”的正常控制流。文件写入中途发生 I/O 异常仍可能留下已写文件，但原始工具结果列表不会被部分修改，错误会直接暴露给调用方。

#### 协议与路径安全

- 结果文件名使用应用生成的 UUID，不使用模型提供的 `toolUseId`；
- 路径通过 `WorkspacePathResolver` 解析，不能绕过工作区写入边界；
- 文件使用 `CREATE_NEW`，不覆盖已有结果；
- 替换通过原 `ToolResultBlockParam.toBuilder()` 完成，保留工具协议元数据；
- 预览切口会避免截断 UTF-16 代理对，防止留下半个 Unicode 字符。

### 5.4 L4：模型摘要压缩

#### 触发条件

L1 和 L2 完成后，系统使用 Anthropic SDK 的 JSON 序列化器序列化 `messages`。当序列化字符数超过 `50,000` 时触发自动摘要。

这个阈值只覆盖 Messages API 的 `messages` 部分，不包含：

- System Prompt；
- 工具定义；
- 本轮临时 `turnContext`；
- Provider 内部的协议开销。

因此它是便于教学和稳定复现的本地软阈值，不是精确 Token 预检。

#### 压缩过程

正常 L4 压缩执行以下步骤：

1. 建立不可变的消息快照；
2. 把同一快照保存为 JSONL Transcript；
3. 使用独立摘要请求总结该快照；
4. 构造一条 `[[agent:conversation-compacted]]` user 消息；
5. 摘要成功后，由 `AgentLoop` 用这一条消息替换真实活跃历史。

摘要消息同时包含 Transcript 相对路径，明确说明它替代了哪些旧消息，以及缺少细节时可以使用 `read_file` 恢复。

#### 摘要职责

摘要模型只负责压缩，不继续执行原任务。固定 System Prompt 要求保留：

1. 用户当前目标和明确约束；
2. 已完成工作；
3. 已确认事实、关键决定及原因；
4. 读取、创建或修改过的文件；
5. 尚未完成的工作和建议下一步；
6. 未解决错误、风险和不确定信息；
7. 重要路径、类名、方法名、命令和错误信息。

会话记录被放在明确的数据边界中，并明确规定其中的命令和提示只是待总结数据，不能成为摘要器的新指令。

摘要请求不携带工具定义。否则一个纯信息压缩动作会重新变成可产生副作用的 Agent 循环，并引入新的工具执行和终止问题。

#### 摘要输入预算

摘要请求本身也可能因为输入太长失败。当前采用字符级软预算：

- 摘要输入上限：`80,000` 字符；
- 固定保留序列化历史头部：`20,000` 字符；
- 剩余预算用于保留尾部；
- 中间插入省略标记，声明内容不连续且完整快照已存档。

这个分配偏向尾部，因为摘要的首要目标是让 Agent 继续当前工作；头部主要保存原始目标，尾部保存最新状态。

#### 摘要输出完整性检查

摘要输出上限为 `2,000` Token。以下结果都不能替换真实历史：

- Stop Reason 为 `MAX_TOKENS`；
- Stop Reason 为 `REFUSAL`；
- 没有任何非空文本摘要；
- 历史无法可靠序列化；
- Transcript 无法写入。

此时异常直接向上抛出。系统不把截断摘要或空摘要伪装成成功压缩。

## 6. 为什么采用分层治理

四层并非四种可互换方案，而是分别控制不同增长来源：

| 层级  | 控制对象        | 主要触发维度          | 是否调用模型 | 是否持久化完整内容            |
| --- | ----------- | --------------- | ------:| --------------------:|
| L1  | 历史消息结构      | 消息数 > 50        | 否      | 是，保存当次活跃历史           |
| L2  | 活跃历史中的旧工具结果 | 结果新旧、长度         | 否      | 通常否，提示重跑；已有 L3 引用则保留 |
| L3  | 新产生的单轮工具结果  | 批次字符数 > 200,000 | 否      | 是，只保存被选中的大结果         |
| L4  | 低成本治理后的整体消息 | 序列化字符数 > 50,000 | 是      | 是，保存当次活跃历史           |

只使用消息条数无法处理“一条消息含几十万字符”；只使用字符数无法保护原始目标和最近进度；只做摘要会在每次增长时引入费用、延迟和语义损失；只做工具结果落盘又无法处理普通对话增长。因此需要组合使用。

## 7. 提交模型：先生成副本，再统一替换

请求前治理使用类似事务的提交边界：

```text
真实 history
  │
  ├─ snipMiddle(history)            → 新列表 A
  ├─ compactOldToolResults(A)       → 新列表 B
  └─ compactHistory(B)（必要时）    → 新列表 C
                                      │
                           全部成功后统一提交
                                      ↓
                              history = C 的内容
```

实际实现通过 `messages.clear()` 和 `messages.addAll(requestMessages)` 保持 `ManualAgent` 持有的列表对象不变，只替换其内容。

这个设计的价值在于：

- 任一压缩方法失败时，真实列表仍保留管线开始前的内容；
- `ContextManager` 不需要持有 Session，也不需要知道谁拥有历史；
- 父 Agent 和子 Agent 可以共享压缩策略及文件目录配置，但各自维护独立消息列表；
- 调用方明确决定何时把有损结果变成新的会话事实。

需要注意，“列表提交原子性”不等于“文件系统事务”。L1/L4 可能已生成 Transcript，L3 也可能已写出部分计划文件，然后后续步骤失败。这些文件会成为未被活跃历史引用的孤立文件，当前版本没有自动清理机制。

## 8. Transcript 的恢复语义

### 8.1 文件格式与位置

压缩快照保存在工作区：

```text
.transcripts/context-<UUID>.jsonl
```

每一行是一条通过 Anthropic SDK 序列化的 `MessageParam`。逐行写入避免在历史已经很大时额外拼接一个同等大小的完整字符串。

### 8.2 Transcript 是哪一层“完整”

Transcript 保存的是某次有损操作前的**当次活跃消息快照**，不保证单个文件包含从 Session 开始以来的全部原始消息。

例如，L1 先把早期完整历史存为 Transcript A，并生成带 A 路径的裁剪占位消息；之后 L4 对已经裁剪过的活跃历史生成 Transcript B。B 中会保存指向 A 的占位消息，但不会重新复制 A 已归档的全部正文。

因此恢复可能形成一条链：

```text
当前摘要
  ↓ 读取 Transcript B
发现更早的裁剪占位与 Transcript A 路径
  ↓ 按需继续读取 Transcript A
获得更早的原始消息
```

这是一种分层归档，而不是每次压缩都复制整个 Session 的全量日志。

### 8.3 当前恢复方式

恢复由模型按需执行，而不是系统自动把 Transcript 全量重新注入上下文。模型可以：

- 使用 `read_file` 读取指定 Transcript；
- 重新读取工作区中的业务文件；
- 重新执行产生旧结果的工具；
- 根据 L3 引用读取完整工具输出文件。

按需恢复避免压缩后立即把全部内容重新塞回上下文，但也意味着恢复质量依赖摘要是否保留了正确线索，以及模型是否意识到需要读取归档。

## 9. Provider 错误恢复与上下文治理的关系

Provider 错误恢复会修改模型可见上下文，但它不是 L4 摘要压缩。

当前请求级 `ContentRejectionRecoveryHandler` 维护最近一批尚未被后续请求接受的 Tool Result ID。当 Provider 返回明确的 `DataInspectionFailed` 时：

1. 从历史尾部定位最近的 user 工具结果消息；
2. 在副本中确认待处理 ID 能够整批匹配；
3. 保留 `toolUseId`，把这些结果正文替换为安全错误说明并标记 `isError=true`；
4. 只有整批替换成功后才提交并消耗一次恢复次数；
5. 在同一业务轮次重试模型请求。

模型请求一旦被 Provider 接受，旧恢复链结束并创建新的 `ModelRequestRecoveryState`。这样恢复次数不会跨越已经成功的请求累积。

流式响应中断时，系统只提交已经完整关闭的内容块，丢弃未完成块，追加恢复说明，并从外层循环重新执行 Hook 和上下文治理。它不重发原始请求，也不把不完整协议块写入历史。

### 9.1 Turn 回滚边界

`ManualAgent` 在不可恢复的 Provider Error 后，使用当前 Turn 原始 `userMessage` 的对象身份定位回滚起点，并删除它及其后的消息。

当前存在一个已知边界：如果 Provider Error 发生前 L4 已经把包含该对象的历史替换为摘要，原 `userMessage` 可能已经不在列表中，回滚就无法找到边界。当前版本没有为“自动压缩后 Provider 最终失败”建立稳定 Turn ID 或显式检查点。

## 10. 长期记忆与会话压缩的边界

会话压缩和长期记忆都在减少当前上下文压力，但职责不同：

| 维度       | 会话压缩               | 长期记忆                   |
| -------- | ------------------ | ---------------------- |
| 核心问题     | 当前会话太长，如何继续工作      | 跨会话事实如何保存和召回           |
| 输入       | 活跃消息历史             | 可见用户/Assistant 文本与已有记忆 |
| 输出       | 摘要消息、占位消息、文件引用     | 结构化记忆文件和按需召回正文         |
| 生命周期     | 当前 Session         | 跨 Session              |
| 选择依据     | 数量、字符数、新旧位置、固定摘要清单 | 当前 query 相关性和记忆整理规则    |
| 是否保留工具协议 | 是                  | 否，提取时过滤工具协议            |

### 10.1 召回不写入历史

`MemoryRuntime.recall(query)` 返回的正文通过 `turnContext` 注入每次主模型请求。`createRequest` 在构造 API 参数时追加一条 `<system-reminder>`，不修改调用方 `messages`。

这样可以避免：

- 召回内容被 L1/L2/L4 当成真实会话再次压缩；
- 同一记忆在后续 Turn 未经重新选择仍长期残留；
- 召回内容在 Turn 完成后被记忆提取器再次保存，形成自我复制。

### 10.2 记忆提取使用压缩前快照

`ManualAgent` 在进入 `AgentLoop` 前调用 `memoryRuntime.capture(history)`。这样即使 AgentLoop 在后续请求中压缩真实历史，记忆提取仍基于捕获时的不可变消息快照。

`MemoryDialogueFormatter` 只保留 user 和 assistant 普通文本，过滤工具块及 `<system-reminder>`，再选择最近 10 条可见消息。它不会把工具输出、隐藏提醒和召回记忆直接固化为长期事实。

## 11. 子 Agent 上下文隔离

`TaskTool` 创建全新的 `subagentMessages`，只写入父模型明确提供的子任务描述，不复制父 Agent 的历史消息。

```text
父 Agent history
  │
  ├─ task(description)
  │      ↓
  │   新建 [user: description]
  │      ↓
  │   子 Agent 独立 Model/Tool 循环
  │      ↓
  └─ 仅最终文本结论作为 task tool_result 返回父 history
```

因此子 Agent 的文件读取、工具结果和中间推理不会直接膨胀父 Agent 上下文。父 Agent必须在 `description` 中显式提供子任务需要的信息，这是隔离带来的责任转移。

父子 Agent 在当前运行时装配中共享同一个 `ContextManager`，因此复用同一模型配置、工作区路径边界和工具结果 Session 目录；但它们传入不同消息列表，压缩不会把两段对话混合。共享的是治理能力和存储命名空间，不是会话历史。

## 12. 角色与职责边界

### `ManualAgent`

- 持有父会话 `history`；
- 编排一个用户 Turn；
- 决定原始用户消息和 UserPromptSubmit Hook 上下文何时入历史；
- 在压缩前捕获长期记忆提取视图；
- 处理 Turn 级失败回滚。

### `AgentLoop`

- 编排每个模型轮次；
- 在请求前调用 L1、L2、L4；
- 在工具结果写入历史前调用 L3；
- 保证 tool_use/tool_result 成对提交；
- 组装 System Prompt、活跃历史、临时上下文和工具定义；
- 处理流中断、输出续写和请求错误恢复。

### `ContextManager`

- 提供无直接历史所有权的上下文治理操作；
- 保存压缩前 Transcript 和超大工具结果；
- 执行本地字符预算计算；
- 发起职责受限的摘要模型调用；
- 返回不可变治理结果，由调用方决定是否提交。

### `MemoryRuntime`

- 管理长期记忆开关、召回、提取和整理；
- 只把召回结果作为本轮临时上下文；
- 不参与 tool_use/tool_result 协议压缩。

### `SystemPromptManager`

- 按 APPLICATION、SESSION、TURN、MODEL_CALL 生命周期刷新提示词；
- 让动态系统状态在每次真实请求前重新取得；
- 不通过不断向 `history` 追加系统消息来表达状态变化。

## 13. 当前设计的失败语义

上下文治理遵循“不能证明安全，就明确失败”的原则：

- Transcript 写入失败：阻止有损裁剪或摘要；
- Tool Result 类型超出当前字符串契约：抛出异常，不静默忽略；
- L3 无法通过有效引用满足预算：抛出异常，不返回已知超限结果；
- 摘要序列化失败：不发起基于残缺数据的摘要；
- 摘要达到输出上限、被拒绝或为空：不替换完整历史；
- Provider 错误无法精确匹配最近待确认结果：不盲目修改历史；
- 不认识的 Provider 错误：保留原异常交给外层处理。

当前实现没有通过兜底摘要吞掉这些错误，因为错误压缩的后果通常不是一次请求失败，而是把错误或不完整状态永久写成后续会话事实。

## 14. 当前边界与已知限制

### 14.1 预算不是 Token 预算

当前所有本地阈值主要使用 Java 字符数或消息数。字符数与 Token 数没有固定换算关系，中文、代码、JSON、路径和不同模型分词都会产生差异。

自动摘要判断还没有计算 System Prompt、工具定义和临时召回记忆，因此无法保证治理后请求一定低于 Provider 限制。

### 14.2 L3 只治理当前工具批次

`200,000` 字符预算限制同一轮新产生的 Tool Result 总量，不是整个历史中全部工具结果的总预算。历史累积由下一轮的 L1、L2、L4 继续治理。

### 14.3 摘要仍然是有损且可能漂移的

固定清单只能降低遗漏概率，不能保证语义无损。多次“摘要的摘要”可能逐步丢失因果关系、否定条件或未解决风险。Transcript 是恢复入口，但当前没有自动验证摘要覆盖率，也没有自动回读校验。

### 14.4 Transcript 没有索引和保留策略

当前文件使用 UUID 命名，没有 Session 元数据、压缩原因、父子归档关系索引、过期时间或自动清理。长期运行会积累 Transcript 和工具结果文件。

### 14.5 没有对话恢复 Session

Transcript 用于压缩后的按需信息恢复，不等于可重启、可恢复的持久化会话。应用重启后不会自动读取这些文件并重建 `ManualAgent.history`。

### 14.6 没有对外暴露手动压缩入口

`compactHistory(messages, focus)` 的接口允许提供关注点，但当前主调用链只在自动触发时传空字符串。现有 CLI 没有把用户的手动压缩命令接入该能力。

### 14.7 Turn 回滚缺少稳定身份

当前失败回滚依赖 `userMessage` 对象身份。历史一旦在失败前被摘要替换，原对象可能消失。更稳定的设计需要显式 Turn 边界或压缩前检查点，但当前尚未实现。

### 14.8 本地治理无法代替 Provider 真实校验

模型支持的上下文窗口、供应商网关附加内容、缓存策略和服务端检查不由本地代码完全掌握。当前设计负责降低风险和控制常见增长来源，不承诺消除所有 Prompt Too Long 或内容检查错误。

## 15. 关键设计取舍

### 15.1 为什么先做本地压缩，再做模型摘要

本地裁剪和替换具有低延迟、零额外模型费用、结果确定的优势。摘要具有语义选择能力，但增加网络调用、费用、失败点和信息漂移。因此只有低成本治理后仍超过阈值才进入 L4。

### 15.2 为什么保留头部和尾部，而不是只保留最近消息

头部通常包含原始目标和限制，尾部包含当前执行状态。编码任务如果只剩尾部，模型可能继续完成局部动作，却偏离用户最初要求。

### 15.3 为什么不自动把 Transcript 重新注入

压缩的目的就是减少活跃输入。自动回填完整 Transcript 会立即抵消压缩收益。当前设计选择暴露恢复路径，让模型在发现信息不足时按需读取。

### 15.4 为什么工具结果优先落盘而不是先摘要

工具输出通常已经是可重复获取或可文件化的原始数据。保存原文并给出预览比用模型改写更可验证，也不会把编译错误、代码片段或结构化结果摘要错。

### 15.5 为什么 ContextManager 不持有 history

历史所有权保留在 `ManualAgent` 和各自的 AgentLoop 调用方，可以让父子 Agent 复用同一治理组件而不共享对话，也让有损结果的提交时机保持显式。

## 16. 演进触发条件

以下内容是出现明确问题后的演进方向，不是当前实现：

| 触发信号                 | 候选演进方向                                                        |
| -------------------- | ------------------------------------------------------------- |
| 字符阈值频繁低估 Provider 输入 | 使用供应商 Token 计数或经过校准的分类型估算，并纳入 System Prompt、tools、turnContext |
| 摘要遗漏导致重复返工           | 为摘要增加结构化字段、覆盖率检查或压缩后验证请求                                      |
| 多次嵌套 Transcript 难以恢复 | 增加归档元数据和父归档引用索引，而不是每次复制全量历史                                   |
| 文件持续增长影响工作区          | 增加可解释的 Session 保留策略和显式清理命令                                    |
| 自动压缩后失败回滚出现真实故障      | 引入稳定 Turn ID、历史检查点或以索引为基础的回滚协议                                |
| 用户需要主动控制保留重点         | 接入手动压缩命令，并把用户 focus 传给 `compactHistory`                       |
| 需要应用重启后继续原会话         | 单独设计 Session 持久化与恢复，不复用 Transcript 归档冒充 Session Store         |
| 子 Agent 输出仍过度膨胀父上下文  | 对 task 最终结论增加独立预算或结构化交付协议                                     |

演进时应优先解决已经观测到的失败模式，不为了追求理论完整性一次性引入 Token 计数、向量检索、归档数据库和复杂压缩图。

## 17. 验证重点

上下文治理的测试和评审应优先验证不变量，而不是只验证“消息变短了”：

1. L1 不在裁剪边界拆开相邻的 tool_use/tool_result；
2. L1/L4 在有损替换前能够生成可解析 JSONL；
3. L2 保留最近三个结果、短结果和 L3 文件引用；
4. L3 按大结果优先落盘，替换后确实低于预算；
5. L3 保留 Tool Result 的 ID、错误状态和原始顺序；
6. L4 截断、拒绝、空摘要和 I/O 失败都不会提交摘要；
7. `turnContext` 出现在真实请求中，但不进入 `history`；
8. 父子 Agent 历史相互隔离，只交付子 Agent 最终结论；
9. Content Rejection 恢复只修改最近待确认的完整结果批次；
10. 自动压缩后 Provider 最终失败的回滚边界应作为已知风险持续观察。

## 18. 总结

Manual Agent 的上下文治理可以概括为：

> 用不同生命周期隔离不同类型的信息，用低成本确定性规则控制常见增长，用模型摘要处理剩余语义压缩问题，并在每次有损操作前保存可追溯入口。

它不是“尽量把所有内容永远塞给模型”，而是在有限上下文中维护一份足以继续工作的活跃状态，同时承认压缩一定可能丢失信息，并为重要信息留下重新读取、重新执行或逐层回溯的路径。
