> 记录时间：2026-09-02 14:34  
> 适用项目：`D:\learn_claudecode\learn-claude-code\demo\manual-agent`

## 1. 设计目的与结论

manual-agent 的可观测性不是把所有运行数据塞进一个 Trace 系统，而是让不同类型的问题由适合的载体回答，并通过 `traceId` 建立必要关联：

| 要回答的问题 | 当前事实来源 | 主要内容 | 是否保存模型/工具正文 |
| --- | --- | --- | --- |
| 一次 Agent 调用经历了哪些步骤、每一步花了多久、谁触发了谁？ | OpenTelemetry Trace，使用 Jaeger 查询 | Span 树、父子关系、时间范围、传输层 Span | 不保存业务正文 |
| 用户在交互终端实际看到了什么？ | 终端 transcript | thinking、正文、工具调用、工具结果预览、本地提示、Trace ID | 是，但工具结果只保留终端预览 |
| 被上下文压缩前的完整会话是什么？ | 会话 JSONL 存档 | 模型协议消息、完整 tool result、摘要前历史 | 是，仅在触发压缩时保存 |
| 为什么出现异常、恢复或边界判断？ | SLF4J 诊断日志 | 异常栈、恢复次数、Hook 与运行时诊断 | 视日志调用而定，不作为查询主链路 |

因此，本设计的核心决定如下：

1. **调用拓扑和耗时使用 OpenTelemetry 标准 Trace。** 项目不自建 Trace ID、Span 树、事件总线、JSONL Trace 格式或 Exporter。
2. **面向人工排障的完整可读过程使用本地终端 transcript。** Trace 只负责定位和时间线，不承担敏感内容归档。
3. **上下文治理产生的持久化文件是模型工作记忆的恢复入口，不是 Trace 的副本。** 它们由 `ContextManager` 按需生成，语义与终端 transcript 不同。
4. **三类记录只做必要关联，不强行统一。** 当前唯一跨载体主键是交互终端中的 `[Trace ID]`；日志尚未统一注入 MDC，ContextManager 的文件也不写 Trace ID。

这组边界让“模型慢、工具慢、工具是否由某次模型回合触发”可以在 Jaeger 中快速定位，同时避免把提示词、thinking、工具参数和工具结果复制到外部 Trace 存储。

## 2. 范围、术语与非目标

### 2.1 范围

本文描述当前代码已经实现并已验证的运行时可观测性。它覆盖：

- 父 Agent 和 `task` 子 Agent 的 Agent 生命周期；
- 每一次流式模型请求及其底层 HTTP 自动埋点；
- 本地工具、MCP 工具、`task` 工具的执行边界；
- 同一模型响应内前台工具的并发调度与结果交付；
- 交互模式下的终端显示和 transcript；
- 上下文压缩时的会话/大工具结果落盘；
- 现有 SLF4J 日志可提供的诊断信息。

### 2.2 核心术语

| 术语 | 含义 | 生成者 |
| --- | --- | --- |
| Trace | 一次相关调用组成的有向调用树，由同一个 `traceId` 标识 | OpenTelemetry Java Agent |
| Span | Trace 中有开始/结束时间的操作区间 | `@WithSpan` 业务注解或 Java Agent 自动埋点 |
| 父 Agent Turn | `ManualAgent.submit()` 接收一条用户输入后，调用父 `AgentLoop.run()` 完成的处理 | `ManualAgent` / `AgentLoop` |
| 子 Agent | `task` 工具同步调用的、拥有隔离消息历史和工具白名单的 `AgentLoop` | `TaskTool` |
| 终端 transcript | 交互会话期间写入 stdout 副本的可读 `.log` 文件 | `ManualAgentApplication` |
| 会话 transcript | 上下文有损压缩前，将完整协议消息逐行保存的 JSONL 文件 | `ContextManager` |
| 大工具结果持久化 | 为降低模型上下文占用，把完整工具结果写入工作区的 `.txt` 文件并以预览替换 | `ContextManager` |

### 2.3 明确非目标

当前设计**不**包含以下能力：

- OpenTelemetry Metrics、Logs exporter 或自定义 Dashboard；
- 业务指标，例如 token 数、成功率、P95、工具成功率、成本统计；
- 为每个 Hook、审批、上下文压缩、记忆召回、后台任务生命周期建立业务 Span；
- 将用户原始输入、完整提示词、模型正文、thinking、工具参数、工具结果或异常正文写入 Span 属性；
- 日志自动携带 `traceId` / `spanId`，或从日志反查 Trace；
- Trace 的本地持久化、回放、审计检索、自动保留期限或删除策略；
- `exec` 模式的终端 transcript；
- 后台 Bash 命令从启动到真实结束的完整 Trace 生命周期。

上述缺口并不表示数据不存在：例如完整大工具结果和压缩前会话会在满足相应上下文治理条件时落盘；它们只是刻意不被视为 Trace 数据。

## 3. 总体架构与数据流

```text
交互用户输入
    │
    ▼
ManualAgent.submit() ────── 记忆召回、Session Hook、历史维护（当前无业务 Span）
    │
    ▼
AgentLoop.run()  @WithSpan("agent.run")
    │  ├── 打印 [Trace ID]（仅有效 Trace） ──────────────► 终端 / transcript
    │  ├── 多次 Agent 业务轮次
    │  │     └── createStreamingTurn() @WithSpan("llm.call")
    │  │           ├── SDK 发起 HTTP 流请求 ──────────────► 自动 HTTP Span
    │  │           ├── 增量正文/Thinking ────────────────► 终端 / transcript
    │  │           └── 完整工具调用
    │  │                 └── executeTool() @WithSpan("tool.execute")
    │  │                       ├── Hook、审批、ToolRegistry
    │  │                       ├── task ──► 子 AgentLoop.run()（子 Span）
    │  │                       └── MCP / 本地工具
    │  └── 工具结果按模型顺序回填下一次模型请求
    │
    ├──────────────────────► Jaeger（OTLP Trace，仅结构与时间）
    └──────────────────────► SLF4J（异常与运行诊断）

ContextManager 在上下文需要降载时独立写入：
    workspace/.task_outputs/tool-results/<session-uuid>/<uuid>.txt
    workspace/.transcripts/context-<uuid>.jsonl
```

图中两个“transcript”名称相近但用途不同：第一个是交互显示的 `.log`，第二个是供模型通过 `read_file` 恢复上下文的协议级 JSONL。二者不能互相替代。

## 4. Trace 设计

### 4.1 技术选型与运行前提

业务代码仅引入 OpenTelemetry API（`1.64.0`）和 `@WithSpan` 注解（`2.30.0`）。真正创建 Span、维护上下文、自动传播到已支持的 HTTP/执行器边界、OTLP 导出，均由外置的 OpenTelemetry Java Agent 完成。

也就是说，代码直接运行时 `Span.current()` 可能是无效上下文，应用必须照常工作；只有附加 Java Agent 且配置可用 exporter 时，三类业务 Span 才会被导出。`AgentLoop.run()` 会先检查 `SpanContext.isValid()`，无效时不打印全零的 Trace ID。

本地 Jaeger 验证使用 OTLP/HTTP 接收端，典型启动配置如下（路径应替换为本机 Java Agent JAR 的真实位置）：

```text
VM options:
-javaagent:<opentelemetry-javaagent.jar 的绝对路径>

Environment:
OTEL_SERVICE_NAME=manual-agent
OTEL_TRACES_EXPORTER=otlp
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
OTEL_METRICS_EXPORTER=none
OTEL_LOGS_EXPORTER=none
```

Jaeger 本地接收端需要暴露 `4318`，查询页面默认使用 `16686`。没有运行接收端时，业务调用仍可完成；导出失败只意味着该次 Trace 不可查询，不能据此判定 Agent 逻辑失败。

### 4.2 三个业务 Span

项目固定保留三个最高层次的业务 Span。Span 名称仅使用稳定的操作名和低基数业务标识，避免把内容数据作为名称或属性传播。

| Span 模板 | 创建位置 | 一个 Span 代表什么 | 覆盖范围 | 动态名称 |
| --- | --- | --- | --- | --- |
| `agent.run` | `AgentLoop.run()` | 一次父 Agent 处理或一次同步子 Agent 子任务 | 动态提示词刷新、业务轮次、模型调用、工具结果回填、自动压缩与恢复控制流 | 固定为 `agent.run` |
| `llm.call <model>` | `AgentLoop.createStreamingTurn()` | 一次完整的流式模型请求 | SDK 建连、整个 SSE 事件消费、流内提交的前台工具调度器关闭与等待 | 例如 `llm.call qwen3.5-flash` |
| `tool.execute <toolName>` | `AgentLoop.executeTool()` | 一个完整关闭的 `tool_use` 的公共工具管线 | Before Hook、审批、ToolRegistry 执行、After Hook、结果修改和运行时异常转换 | 例如 `tool.execute read_file`、`tool.execute task`、`tool.execute mcp__git__git_status` |

没有在 `ManualAgent.submit()` 上创建 Span。因此 Agent Trace 从 `AgentLoop.run()` 开始，并不包含该方法之前的用户输入 Hook、记忆召回和在成功完成后的记忆提取/持久化。这是当前的精确边界，不应把 `agent.run` 误解为完整 CLI Turn。

### 4.3 正常父子关系

无工具的最小调用树为：

```text
agent.run
└── llm.call <model>
    └── POST                 （OpenTelemetry HTTP 自动埋点；存在与否取决于运行时 instrumentation）
```

模型请求工具后的第一轮通常为：

```text
agent.run
├── llm.call <model>
│   ├── POST
│   └── tool.execute read_file
└── llm.call <model>         （接收 tool_result 后的下一次请求）
```

这里的 `tool.execute` 是 `llm.call` 的子 Span，而不是同级 Span。这不是展示错误：工具调用在 `createStreamingTurn()` 消费模型 SSE 流期间，收到 `content_block_stop` 后立刻提交到调度器；该方法返回前又会关闭前台调度器并等待已经提交的前台工具结束。真实调用栈和上下文仍位于该次 `llm.call` 内，因此该树准确表达了“由哪一次模型回合提出了此工具调用”。

### 4.4 子 Agent、MCP 与并发工具

#### `task` 子 Agent

`TaskTool` 同步调用一个拥有新消息历史的 `subagentLoop.run()`。子 Agent 的思考和正文被静默 `StreamOutputPrinter` 接收，但其 Trace 不会静默：

```text
agent.run                         （父 Agent）
└── llm.call <model>
    └── tool.execute task
        └── agent.run             （子 Agent）
            └── llm.call <model>
```

父、子 Agent 共享同一个 `traceId`，而不是为子 Agent 创建自定义关联字段。子 Agent 不打印 `[Trace ID]`，以避免污染父终端；这只影响显示，不影响 Trace 结构。

#### MCP 工具

MCP 工具沿用注册名 `mcp__<namespace>__<tool>`，因此业务 Span 名称例如 `tool.execute mcp__git__git_status`。项目不额外创建 `mcp.started` / `mcp.finished` 等平行事件；如果 SDK 或 HTTP 自动埋点生成更底层 Span，可以保留为子节点。

#### 同一响应内的前台并发工具

完整工具调用到达后会进入 `ToolCallDispatcher`。默认前台工具由 `ToolExecutionScheduler` 在虚拟线程中执行：

- 连续的 `concurrencySafe` 工具可以并发启动；
- 独占工具等待此前安全批次完成，后续安全工具也等待该独占工具；
- 同时进入公共工具管线的任务最多为 10 个；
- `collectToolResults()` 仍按模型提出 `tool_use` 的顺序 `join()` 并回填结果。

因此，在 Jaeger 中同一 `llm.call` 下可以出现多个时间范围重叠的兄弟 `tool.execute` Span；它们的显示次序和模型最终收到 `tool_result` 的顺序不应被混为一谈。工具很快或模型事件间隔较大时，实际时间范围也可能不重叠，这不违反调度契约。

### 4.5 后台工具的特殊边界

目前只有 `BashTool` 在参数 `run_in_background=true` 时进入 `BACKGROUND` 路径。此时 `tool.execute bash` 覆盖的是审批、登记和“后台任务已启动”的返回过程；真正的命令在 `BackgroundTaskScheduler` 的另一个虚拟线程中持续运行，并在完成后等待 Hook 收集结果。

当前没有用于表示“真实后台命令开始—结束—结果被下一轮模型消费”的业务 Span，也没有后台任务 ID 到 Trace 的持久化映射。排查这类任务应结合终端输出、后台任务状态和 SLF4J 日志，不能把启动工具 Span 的结束时间当作命令真实结束时间。

### 4.6 上下文传播约束

前台工具在真实运行验收中已证明能够继承发起它们的 `llm.call` / `agent.run` 上下文，因此当前未在 `ToolExecutionScheduler` 中显式包裹 `Context.taskWrapping(...)`。这一结论依赖 OpenTelemetry Java Agent 已对所用 Java 执行器和虚拟线程路径提供上下文传播。

如果未来升级 JDK、Java Agent 或替换执行器后观察到 `tool.execute` 变成独立 Trace，应先以真实 Jaeger 树复现，再在调度器提交边界使用 OpenTelemetry 提供的上下文包装能力修复；不得引入自定义 `ThreadLocal`、`parentId` 或自行重建 Trace 树。

## 5. Trace 数据最小化与安全边界

### 5.1 Jaeger 中允许出现的数据

当前业务代码只会人为影响三类信息：

- Span 名称：`agent.run`、`llm.call <model>`、`tool.execute <toolName>`；
- Span 的开始/结束时间与父子关系；
- OpenTelemetry 生成的 `traceId`、`spanId`、服务名等运行时元数据。

底层 HTTP 自动埋点可能额外记录目标地址、HTTP 方法、状态等传输元数据。这属于 Agent/SDK 的自动埋点行为；业务代码没有把请求或响应正文写入 Span。

### 5.2 Jaeger 中禁止保存的数据

下列数据必须继续留在本地展示、模型协议内存或按需本地文件中，不得为了“方便查询”加入 Span 名称、属性、事件或异常文本：

- 用户原始任务、System Prompt、记忆召回文本、Hook 注入上下文；
- 模型正文和 thinking；
- 工具 JSON 参数、工具原始结果、文件内容、命令内容与 MCP 负载；
- API Key、GitHub Token、任何凭据；
- Provider 原始错误 body 和完整异常栈。

这是数据最小化要求，而不是性能优化。Trace 通常会离开本机进入 Jaeger / OTLP 后端，其读取权限和保留周期未必等同于工作区本地文件。

### 5.3 终端 transcript 的敏感性

交互 transcript 会接收 stdout 的副本，因此 thinking 和正文会原样写入，工具调用会带格式化 JSON 参数。工具结果虽然只显示前 2,000 个 Java 字符，仍可能含有敏感内容。该文件不能被当作可安全分享的日志；分享前必须人工审查并脱敏。

用户通过键盘输入的原文不是 stdout，当前不会自动写入终端 transcript。不要据此认为 transcript 可以完整重放一次会话：它记录的是应用输出，不是所有输入/输出协议消息。

## 6. 终端展示与本地转录

### 6.1 交互模式的输出链路

仅 `interactive` 模式启动时，`ManualAgentApplication` 会：

1. 创建 `agentHome/.task_outputs/transcripts`；
2. 使用 `manual-agent-yyyyMMdd-HHmmss-SSS.log` 创建新文件；
3. 以 `TeeOutputStream` 把 `System.out` 同时写向原终端和该文件；
4. 注册 JVM shutdown hook 关闭会话输出流；
5. 在终端第一行打印 `[Terminal transcript] <绝对路径>`。

当前启动配置把 `agentHome` 暂时设为 `cwd`，所以实际目录通常位于 manual-agent 工作目录下；该路径的语义仍是 Agent 自身运行记录，未来 `agentHome` 与 `workspace` 分离时不应把它迁回 workspace。`exec` 模式不创建 Scanner 或终端 transcript，因为其 stdout 由 Harbor 隔离环境捕获。

### 6.2 输出协议

`StreamOutputPrinter` 只负责显示，既不负责 Trace 生命周期，也不保存原始 SSE 事件。父 Agent 以当前 `System.out` 为输出目标，子 Agent 使用空输出流。

| 事件 | 显示形式 | 是否写入交互 transcript |
| --- | --- | --- |
| 有效 Agent Span 开始 | `[Trace ID] <32 位十六进制 ID>` | 是（父 Agent） |
| thinking 块开始与增量 | `[thinking]` 后原样实时写入 | 是（父 Agent） |
| 正文块开始与增量 | `[Agent]` 后原样实时写入 | 是（父 Agent） |
| 完整工具调用 | `[工具调用] <name>` 与格式化 JSON | 是 |
| 工具结果 | 名称、成功/失败、原始字符数、至多 2,000 字符预览 | 是 |
| 本地恢复/错误提示 | `printLocalMessage()` 的文本 | 是（父 Agent） |
| 子 Agent 过程 | 静默 | 否；但 `[Subagent spawned]` / `[Subagent done]` 由 `TaskTool` 的 stdout 写入 |

终端工具结果截断只影响展示和 `.log` 文件，不改变返回给模型的原始 `ToolExecutionResult`，也不改变 `ContextManager` 后续做上下文预算时处理的原始内容。

### 6.3 Trace 与终端的关联流程

当 Java Agent 已建立有效上下文时，按下列路径定位一次交互调用：

1. 在终端 transcript 中搜索 `[Trace ID]`；
2. 复制该 32 位十六进制 ID；
3. 在 Jaeger 的 `manual-agent` 服务中按 Trace ID 查询；
4. 用 Span 树确定慢点、失败前后关系、模型回合和工具触发点；
5. 回到同一 transcript 读取需要人工理解的显示文本。

一个交互会话可处理多条用户消息，故同一个 `.log` 可能包含多个父 `agent.run` 的 Trace ID。一个 `task` 子 Agent 与父 Agent 共享其 Trace ID，但不会额外写子 Agent 的 ID 行。

## 7. 上下文治理产生的持久化记录

### 7.1 大工具结果文件

每个 `ContextManager` 实例会为当前进程生成独立的目录：

```text
workspace/.task_outputs/tool-results/<session-uuid>/<result-uuid>.txt
```

当同一轮 tool result 的总字符数超过 200,000 字符预算时，ContextManager 仅将具有足够替换收益的完整结果写入该目录；随后让模型看到文件路径、原始字符数和最多 2,000 字符预览。文件以 `CREATE_NEW` 写入，失败会直接中断而不是假装引用可用。

这是一项模型上下文控制机制：文件是完整结果的恢复入口，不是面向用户的终端记录，也不会自动反映到 Jaeger。终端仍按照它自己的 2,000 字符展示规则输出当时结果。

### 7.2 会话 JSONL 存档

在中段裁剪或模型摘要等有损压缩之前，`ContextManager` 先将完整 `MessageParam` 历史逐行保存到：

```text
workspace/.transcripts/context-<uuid>.jsonl
```

只有完整存档成功后才允许继续摘要；摘要后的模型上下文会包含相对路径，模型必要时可通过 `read_file` 读取该存档。该 JSONL 包含协议级消息，可能包含用户输入、thinking、完整工具参数和结果，敏感性通常高于终端 transcript。

这类文件的触发条件是上下文压缩，不是“每一个 Agent Turn”。因此其缺失只代表当前尚未发生需要持久化的压缩，不能作为 Trace 丢失的判断依据。

### 7.3 存储隔离现状

| 数据 | 当前逻辑位置 | 所属语义 | 是否由 `.gitignore` 排除 |
| --- | --- | --- | --- |
| 交互终端 transcript | `agentHome/.task_outputs/transcripts/` | Agent 运行记录 | 是（`.task_outputs/`） |
| 大工具结果 | `workspace/.task_outputs/tool-results/` | 上下文恢复资源 | 是（`.task_outputs/`） |
| 会话 JSONL | `workspace/.transcripts/` | 压缩前协议历史 | 是（`.transcripts/`） |
| Jaeger Trace | 配置的 OTLP 后端 | 调用拓扑和耗时 | 不受仓库控制 |

现阶段 `agentHome == cwd`，而 `workspace` 也来自启动 `cwd`，三处文件可能物理上位于同一项目目录；这是当前配置结果，不改变它们的职责边界。

## 8. SLF4J 日志与错误可观测性

SLF4J 不进入 Trace 导出链路，承担的是本地开发诊断职责。当前重要日志包括：

- Git 根目录未发现时跳过 Git MCP 注册；
- BeforeModelCall Hook 追加了多少段上下文；
- 输出达到上限时的续写次数；
- SSE 流中断时保留的完整内容块/工具数量和异常栈；
- Provider 输出被内容检查拒绝后的恢复次数；
- 工具公共管线的未处理异常（工具名、tool use ID 与完整异常）。

另外，`ToolLoggingHook` 在 debug 级别记录工具名与最多 120 个字符的参数预览；虽然有长度限制，仍可能暴露文件路径或内容片段。日志收集/分享策略应以敏感数据处理，而不能因它不是 Jaeger 数据就降低要求。

面向用户的 Provider 错误则由 `ManualAgent` 打印 HTTP 状态、错误类型、消息、请求 ID 与原始 body。该文本进入交互 transcript，但当前不会同步为 Span 属性或日志 Trace 事件。

## 9. 运行与排障操作手册

### 9.1 进入 Trace 模式

1. 启动 Jaeger，使 OTLP/HTTP 可接收 `http://localhost:4318`；
2. 为 Java 进程附加 OpenTelemetry Java Agent；
3. 配置第 4.1 节的六项 `OTEL_*` 环境变量；
4. 启动 `ManualAgentApplication` 的交互模式；
5. 发送一条无需工具的简单指令，确认终端有 `[Trace ID]`；
6. 在 Jaeger 查询对应 Trace，至少应看到 `agent.run → llm.call <model>`，底层 HTTP Span 的出现由自动 instrumentation 决定。

### 9.2 最小验收矩阵

| 场景 | Jaeger 中的关键结构 | 终端 / 本地记录关键点 |
| --- | --- | --- |
| 纯模型回答 | `agent.run → llm.call <model>` | `[Trace ID]`、thinking/正文（若模型返回） |
| 本地 `read_file` | 首轮 `llm.call` 下的 `tool.execute read_file` | 工具调用 JSON、工具结果状态和预览 |
| `task` 子 Agent | `tool.execute task → agent.run → llm.call` | `[Subagent spawned]`、`[Subagent done]`，子过程保持静默 |
| Git MCP | `tool.execute mcp__git__<tool>` | MCP 调用名和结果预览 |
| 两个并发安全工具 | 同一 `llm.call` 下两个同级工具 Span，可时间重叠 | 结果按模型调用顺序显示/回填 |
| 后台 Bash | 工具启动 Span | 后台任务 ID 与后续状态；不能期待命令完成时间被该 Span 覆盖 |

### 9.3 常见现象与判读

| 现象 | 正确判读 | 首选处理 |
| --- | --- | --- |
| 没有 `[Trace ID]`，但 Agent 正常回复 | Java Agent 未启用或当前 Span 无效 | 检查 VM options 与 `OTEL_*` 环境变量 |
| 有 Trace ID 但 Jaeger 无记录 | exporter/接收端不可用、查询服务名不匹配或导出尚未到达 | 检查 Jaeger、OTLP endpoint 和服务名；不要修改业务 Span |
| 工具 Span 位于 `llm.call` 下 | 当前实现的正确父子关系 | 通过该关系定位触发它的模型回合 |
| 工具 Span 变成独立 Trace | 跨虚拟线程上下文传播可能退化 | 用最小工具用例复现，检查 Java Agent/JDK，再评估上下文包装 |
| 两个工具没有时间重叠 | 工具过快或流事件到达间隔导致 | 以调度器并发测试和提交模式判断，不只看一次时间轴 |
| 终端没有完整工具结果 | 终端设计上限为 2,000 字符 | 查看工作区 `.task_outputs/tool-results`（若发生持久化），或重跑读取工具 |
| 找不到会话 JSONL | 本次没有触发有损上下文压缩 | 不把它视为终端或 Trace 故障 |

## 10. 设计不变量与演进约束

后续修改可观测性时，必须保持以下不变量：

1. 业务 Trace 继续使用 OpenTelemetry 的 Trace ID、上下文传播和 OTLP Exporter；不重新实现这些能力。
2. `llm.call` 必须覆盖完整 SSE 消费，而不能只包住 `createStreaming(...)` 建连的一行代码。
3. `tool.execute` 必须覆盖统一的 Hook → 审批 → 工具注册表 → After Hook 管线，不能只记录 `toolRegistry.execute()`。
4. 子 Agent 的可见性策略与 Trace 策略分离：子 Agent 可以静默显示，但必须保持正常上下文继承。
5. 工具结果显示截断不能影响模型收到的原始结果，更不能修改 Trace 数据以“补全”终端内容。
6. 敏感业务内容默认不进入 Span；若确有新增属性的需求，必须先明确数据分级、查询价值、访问范围和保留策略。
7. 新增 Metrics、日志关联、后台任务全生命周期 Trace 或 Trace 查询页都属于独立需求，需单独设计，不应作为现有 Trace 的隐式扩张。

## 11. 现状验证依据

当前实现和既有验收已确认：

- 业务代码已经具备 `agent.run`、`llm.call <model>` 和 `tool.execute <toolName>` 三个 Span 边界；
- 纯模型、本地 `read_file`、同步 `task` 子 Agent、Git MCP 与同一响应两个工具调用均已进行真实 Trace 验收；
- 前台工具的虚拟线程上下文能够保持与发起模型回合的父子关系，当前无需显式 `Context.taskWrapping(...)`；
- 交互启动会创建终端 transcript；有效 Trace 时 transcript 中的 Trace ID 可与 Jaeger 查询结果互相定位；
- 普通 Maven 测试以及附加 OpenTelemetry Java Agent 的测试均已通过既有验收。

真实并发工具在一次验收中未必产生重叠时间区间，但调度器单元测试通过闩锁验证了并发安全工具可以同时进入执行阶段；这是当前“允许并发”的行为契约。
