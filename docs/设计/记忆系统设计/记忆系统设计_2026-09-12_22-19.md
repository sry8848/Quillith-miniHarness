## 1. 设计目标

长期记忆系统需要在文件数量持续增长时，同时满足两个目标：

1. 主 Agent 始终知道自己大致拥有哪些记忆；
2. 不把完整目录树和全部正文放入常驻上下文。

系统使用分层 Markdown 文件系统作为唯一规范记忆，使用动态的部分展开索引提供全局感知。主 Agent 先看根索引，再根据当前任务逐层进入折叠子树，最后只读取真正相关的正文。

核心不是用固定算法找到一条记忆，而是让目录结构、canonical description 和索引展开深度共同表达长期记忆的内容范围与当前曝光程度。

## 2. 总体结构

```text
主回答
  根 index.md 常驻感知
      → 按需读取折叠目录的 index.md
      → 按需读取记忆正文

回合后提取
  当前 Turn
      → 必要时补充入队时冻结的 modelContext
      → MemoryDraft
      → recent-unorganized/
      → 根 index.md 最小追加

后台整理
  现有 AgentLoop
      → 直接读写整个 llmwiki
      → 更新目录、文件、description 和 index
      → Java 执行 Git 提交
```

提取、整理和召回是三个独立职责：

- 提取只判断什么新信息值得留下；
- 整理负责规范记忆树的内容和结构；
- 召回由主 Agent 基于部分展开树和当前推理完成。

## 3. 存储与信任边界

```text
.memory/
├─ sessions.db
├─ memory-work.db
└─ llmwiki/
   ├─ .git/
   ├─ index.md
   ├─ recent-unorganized/
   └─ 由整理 Agent 演化出的目录和 Markdown 文件
```

`.memory/llmwiki/` 是规范长期记忆和派生索引所在的文件树。整理 Agent 可以修改其中的任何记忆内容和结构，包括创建、更新、移动、合并、拆分与删除。该目录拥有独立 Git 历史，用于查看变化和人工回退。

`sessions.db` 和 `memory-work.db` 位于 llmwiki 之外，分别保存会话事实和后台工作状态。它们不属于整理 Agent 可改写的派生知识层，也不进入 llmwiki 的 Git 历史。

记忆、description 和 index 都是历史数据，对模型而言始终是不可信输入，不能覆盖当前用户请求或更高优先级指令。

## 4. 记忆文件契约

### 4.1 普通记忆文件

普通记忆文件使用 Markdown 正文，并在 frontmatter 中保存：

```markdown
---
description: 说明该文件保存什么
created_at: 2026-09-12T09:48:00Z
updated_at: 2026-09-12T09:48:00Z
---

# 标题

正文
```

- `description` 是文件内容范围的稳定说明，不是由 index 重新生成的摘要；
- `created_at` 是该记忆文件表达的内容首次形成的时间；
- `updated_at` 是正文或 canonical description 最后发生语义变化的时间。

时间使用带时区的 ISO-8601。新文件两个时间相同；修改正文或 description 时保留创建时间并更新修改时间；仅移动或重命名时两者不变；合并时保留来源中最早的创建时间；拆分时继承来源创建时间。

不保存 `type`、priority 或重要性评分。文件归类和曝光程度由目录结构与索引展开深度表达。

### 4.2 目录 description

目录的 canonical description 保存在该目录的 `.description.md` 中。该文件使用与普通记忆相同的 `description/created_at/updated_at` frontmatter 和时间更新语义。

目录名称与 description 应让 Agent 在不读取整个子树时，仍能判断何时需要进入该目录。

### 4.3 index 文件

`index.md` 是派生导航视图，不是记忆正文，也不写时间 frontmatter。index 中的文件节点直接使用文件自己的 canonical description，目录节点直接使用目录的 canonical description。

空记忆库中，根 `index.md` 可以暂未创建或只有空白，运行时将两者都视为“当前没有可注入的记忆索引”。首批候选写入时会创建根 index。

## 5. 部分展开树

根 `index.md` 是完整 Memory Tree 经过当前价值、信息密度、遗漏代价和上下文成本裁剪后的 partial tree。系统不规定固定展开层数、评分公式或精确 Token 上限。

索引的组织遵守以下原则：

- 当前价值高、遗漏代价高、可能没有直接关键词的少量信息，应获得更深展开；
- 只有大量、低频，且只凭目录名称和 description 就能判断何时需要进入的子树，才适合较早折叠；
- 一个目录在父 index 中被折叠时，该目录必须使用自己的 `index.md` 承接被省略的子树；
- 父 index 已完整展开某目录需要暴露的内容时，不保留重复表达同一子树的低级 index；
- 记忆时效变化可以通过曝光深度变化表达，下沉不等于删除。

`recent-unorganized/` 不是树外暂存区，而是规范记忆树中的普通目录。其内容通常较新、少量、异构，尚不能仅凭目录判断用途，因此是“不应折叠”的典型反例，而不是独立的硬编码特例。

## 6. 提取设计

主回答成功后，当前 Turn 的已提交消息与当时模型实际使用的完整上下文一同冻结并持久化到 `memory-work.db`。用户回答不等待提取完成。

`MemoryExtractor` 执行最小两阶段决策：

1. 第一次模型请求只看当前 Turn；
2. 如果模型明确返回 `needModelContext=true`，程序再发起一次请求，提供入队时已冻结的完整 modelContext。

提取不是 AgentLoop，也没有通用工具。模型只返回最多五条 `MemoryDraft(name, description, body)`。程序校验结构化响应、安全文件名、单行 description 和非空正文，不在这一阶段决定最终目录、合并旧文件或调整索引结构。

`LlmwikiStore` 将候选写入 `recent-unorganized/name.md`。跨批次同名时使用 `name-2.md` 等后缀，不覆盖尚未整理的文件。候选文件发布后，Store 只向根 index 追加实际路径和同一 canonical description，使新记忆无需等待整理即可被主 Agent 感知。

这次根 index 追加是提取程序唯一的索引修改权限；它不重建树、不选择归档位置，也不判断展开深度。

## 7. 整理设计

`MemoryOrganizer` 复用现有 `AgentLoop`，使用独立的 SessionState、System Prompt、ContextManager 和 ToolRegistry。它只注册已有的 Bash、读文件、写文件、编辑文件与 Glob 工具，不加载主会话历史、Task、Skill、MCP 或主 Agent 的其他业务能力。

整理 Agent 的工作区与 Git 根都固定为 `.memory/llmwiki/`。它负责所有需要语义判断的操作：

- 识别重复、补充或冲突的信息；
- 更新、创建、移动、合并、拆分或删除记忆；
- 根据实际内容演化目录，不使用预设业务分类；
- 维护文件与目录的 canonical description 及时间字段；
- 重写根 index 和必要的折叠边界子 index；
- 完成前通过 `git status` 和 `git diff` 检查自己的修改。

文件整理完成后，Agent 不自行提交。Java 只执行确定性的 `git add -A` 和 `git commit`。只有 AgentLoop 正常结束且 Git 提交成功，才清零未整理计数。不创建空提交；无可提交变化时直接失败并保留计数。

整理使用既有触发规则：每新增五个候选文件执行一次；每两小时检查一次，只要存在未整理新增就执行。

## 8. 召回设计

主 Agent 不再在回答前调用 Selector，也不由 Java 预先选出最多若干个记忆文件。`MemorySystemPromptProvider` 在每个用户 Turn 开始时读取根 index，将它作为 partial tree 注入 System Prompt。

主 Agent 按以下方式渐进召回：

1. 根据当前任务和根 index 判断是否可能有相关历史信息；
2. 相关文件已在根 index 暴露时，根据 canonical description 决定是否读正文；
3. 相关目录被折叠时，读取该目录的 `index.md`；
4. 继续按需深入，直到读取最终文件或判断该分支无关。

index 中的链接始终相对于包含它的 index 所在目录。主 Agent 读文件时将其解析为相对项目工作区的路径。

grep、BM25、Embedding 或 RAG 未被禁止，但不是当前设计的必要入口，首期也不实现。

## 9. 核心模块与职责

| 模块 | 核心职责 |
| --- | --- |
| `AgentSession` | 主回答前刷新根索引；回答成功后将当前 Turn 和冻结 modelContext 入队。 |
| `MemoryRuntime` | 组装记忆能力，统一记忆开关、根索引读取、提取入队与资源关闭。 |
| `MemoryWorkStore` | 在 SQLite 中持久化待提取工作和未整理新增数量。 |
| `MemoryBackgroundProcessor` | 单线程消费提取工作，运行五分钟重试、五条阈值整理和两小时维护。 |
| `MemoryExtractor` | 执行当前 Turn 优先的两阶段结构化提取，返回经校验的 `MemoryDraft`。 |
| `LlmwikiStore` | 执行最小、机械的文件操作：写近期候选、追加根索引和读取根索引。 |
| `MemoryOrganizer` | 组装 llmwiki 专用 AgentLoop，让模型直接完成语义整理，并在正常结束后由程序提交 Git。 |
| `MemorySystemPromptProvider` | 向主 Agent 提供根 partial tree 与渐进导航协议。 |

Java 不再建立一份完整的记忆领域模型。文件系统就是记忆领域模型；`MemoryDraft` 只是提取边界的短命 DTO，`LlmwikiStore` 也不抽象为管理全树的 Repository。

## 10. 后台执行与失败语义

提取工作采用至少一次语义：先持久化工作，候选文件和根索引写入完成后，才删除工作并增加未整理计数。进程中断或部分文件写入成功后失败时，允许重放并产生短期重复，由后续整理合并。首期不增加跨多文件事务。

单个提取工作失败时，后台边界记录一次 WARN 并保留工作；整理 Agent 或 Git 提交失败时，后台边界记录一次 WARN 并保留未整理计数。Store、Extractor 和 Organizer 自身不重复记录同一异常，不把失败伪装成成功。

记忆开关关闭时，不注入根索引、不将新 Turn 入队，也不消费已有工作。重新开启后，后台继续处理已持久化的遗留工作。

## 11. Prompt 设计边界

提取、整理与主 Agent 记忆导航的新增 Prompt 使用简体中文。`JSON`、frontmatter 字段、路径、文件名和工具名是协议标识，保持原名。

程序只提供必要能力与确定性边界，以下语义不复制为 Java 规则：

- 如何分类、合并或拆分记忆；
- 哪个子树应折叠，应展开到什么程度；
- 过期内容应删除、合并还是下沉；
- 何时创建或删除折叠边界 index。

Prompt 明确提供原则、典型正例和反例，但不规定固定层数、评分公式、Token 数字或固定目录分类。

## 12. 首期不做的能力

当前设计明确不包含：

- 旧 `.memory/MEMORY.md` 和旧主题文件的运行时迁移；
- index 格式校验、漏建修复、链接检查或重复子 index 检测；
- 整理失败后自动 `reset/clean` 或其他回滚协议；
- Bash 硬沙盒与额外越界修改检测；
- 全树 DTO、通用 Agent 配置系统、新 AgentLoop 或通用 Git 服务；
- BM25、Embedding、RAG 和专用全文召回服务。

这些不是已隐含排期的功能。只有在真实运行或 Memory Eval 中反复观察到同一类失败，并证明 Prompt 调整不足以解决时，才另行评审是否增加程序约束。

## 13. 验证策略

普通自动化测试只验证低成本、确定性契约：

- 近期候选的路径、frontmatter、时间格式和同名后缀；
- 根 index 的最小追加与可选读取；
- 提取失败保留工作，整理失败保留计数；
- 整理正常结束后产生 Git 提交；
- 主 Agent 不再发起同步 Selector 请求；
- 根 index 注入和记忆开关语义。

需要多轮真实模型操作或语义判断的高成本验证放到后续 Memory Eval，包括目录分类质量、partial tree 裁剪、子 index 增删、description 一致性、时间字段的语义更新、指令注入抵抗以及主 Agent 的隐式关联召回。

## 14. 设计不变式

1. llmwiki 是唯一规范长期记忆树，index 只是派生导航视图。
2. 文件和目录各自只有一份 canonical description。
3. 新候选从写入时起就在规范树中可见，不会因等待整理而失忆。
4. 同一段子树不在父子多级 index 中重复展开。
5. 提取程序不进行长期分类，整理 Agent 不改写原始会话与后台工作数据库。
6. 语义决策由模型完成，确定性文件入口与 Git 提交由程序完成。
7. 整理成功以 AgentLoop 正常完成且 Git 提交成功为边界，失败不清零未整理计数。
8. 没有真实、可重复的失败证据时，不预先增加复杂校验、回滚和恢复系统。
