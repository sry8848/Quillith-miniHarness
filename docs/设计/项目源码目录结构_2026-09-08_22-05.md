# Quillith-miniHarness 项目源码目录结构与文件职责

## 文档说明

本文档描述当前工作树中的源码。职责判断以代码现在的实际行为为准，不把目标架构或历史设计当成当前实现。

文档范围只纳入源码相关内容：

- 根目录的 Harbor 适配器和启动脚本；
- src/main/java 下的 Java 生产源码；
- src/main/resources 下被程序加载的运行资源；
- src/test/java 和 src/test/python 下当前存在的测试源码。

文档不纳入：

- docs/、skills/ 中的 Markdown 文档；
- pom.xml 等构建配置；
- target/、__pycache__/、.task_outputs/ 等构建产物、缓存和运行记录；
- 当前工作树中已经删除的旧源码文件。

这里的“职责”不是只写模块名，而是说明文件真正拥有的状态、边界和流程位置。相邻文件职责相似时，会明确它们之间的区别。

### 核心调用边界

| 层次 | 当前实际职责 | 不负责的内容 |
| --- | --- | --- |
| ManualAgentApplication | 解析入口、确定工作区、创建进程级输入输出、选择 Runner、关闭 Runtime | 不实现模型循环和工具业务 |
| AgentRuntime | 装配父 Agent、子 Agent、工具、Hook、Memory、MCP、Session Store 和客户端，并统一释放资源 | 不处理某一条用户 Turn |
| AgentSession | 处理父 Session 的一条完整 Turn：接受输入、刷新 Prompt、召回 Memory、提交持久化事实、在主回答完成后把记忆提取工作入队、恢复或新建 Session | 不消费模型 SSE，不等待后台记忆提取，也不决定单次工具调度顺序 |
| AgentLoop | 执行模型请求、消费流式响应、调度工具、提交 tool result、处理恢复和停止条件 | 不解析终端命令、不决定父/子 Runtime 的装配 |
| SessionStore / TurnJournal | 负责 SQLite 中的 canonical history、checkpoint、in-flight 工具事实，以及按 Turn 读取记忆提取所需的 canonical 消息快照 | 不决定模型应该如何继续推理 |
| ConversationState | 保存完整历史和模型活动上下文的双视图 | 不负责写 SQLite |
| 具体 Tool | 把一个模型工具调用转换为实际文件、Shell、任务、技能或 Session 查询操作 | 不负责模型循环、审批策略和统一重试 |

## 二、根目录源码与启动脚本

| 文件 | 当前职责与边界 |
| --- | --- |
| harbor_adapter.py | Harbor 侧的 Python Agent 适配层。QuillithHarborAgent 校验宿主机传入的 Quillith JAR、OpenTelemetry Agent、模型连接和 GitHub Token，在 Trial 中上传已构建制品，创建 FIFO，并启动长期运行的 Java Harbor 进程；随后用 Base64 单行协议提交 TURN、RECORDED_TURN、NEW_SESSION 和 ANSWER。QuillithMemoryAgent 在此基础上增加对话记忆 Case 的校验、固定 user/assistant 历史回放、跨 Session 切换和最终答案落盘。它只负责 Harbor 生命周期与跨进程协议，不接触 Java 内部消息历史或 Memory 实现。 |
| quillith-harbor-run.ps1 | 宿主机 launcher。每次调用先执行一次 Maven package，再严格定位本次构建产生的 target/quillith.jar，校验 OpenTelemetry Java Agent，临时设置 PYTHONPATH，并把 JAR 路径、Trace Agent 路径和其余参数交给 harbor run。它负责构建和启动边界，不实现 Harbor Trial 内的 FIFO 协议，也不实现 Agent 行为。 |

## 三、Java 生产源码

### 3.1 manual 根包：应用入口、Runtime、Session 和主循环

| 文件 | 当前职责与边界 |
| --- | --- |
| src/main/java/dev/learn/agent/manual/ManualAgentApplication.java | Java 进程入口。解析 ApplicationOptions，确定当前工作目录和 Agent Home，发现 Git 根目录，创建唯一 SessionState，并根据模式进入 InteractiveRunner、ExecRunner 或 HarborRunner；交互模式还负责 Tee transcript 和共享 Scanner。它只拥有进程级输入输出和 Runtime 生命周期，不承载 Agent Turn 的模型/工具逻辑。 |
| src/main/java/dev/learn/agent/manual/AgentRuntime.java | 应用装配根。读取模型、API、Base URL 和 Bash 配置，创建 WorkspacePathResolver、SessionStore、MemoryRuntime、Prompt Manager、父/子 ToolRegistry、Hook、MCP Client、AgentLoop 和 AgentSession，并定义父 Agent 与子 Agent 的工具白名单及关闭顺序。MemoryRuntime 在这里启动并持有后台记忆处理器，关闭 Runtime 时先停止它。它是依赖组合和资源所有权中心，不是一个业务服务。 |
| src/main/java/dev/learn/agent/manual/AgentSession.java | 父 Agent 的 Turn 外层编排器。它负责分配 Turn 序号、触发用户输入 Hook、刷新 Session Prompt、召回 Memory、在 Provider 调用前提交 user 事实、调用 AgentLoop，并在主回答成功后读取本 Turn 的 canonical 消息和模型上下文，将记忆提取工作持久化入队；它还负责 startNewSession、listSessions、resume 和记忆开关。它不消费 SSE、直接执行 Tool 或等待后台提取/整理完成。 |
| src/main/java/dev/learn/agent/manual/AgentLoop.java | 实际的 Agent 核心循环。它构造模型请求并消费流式事件，重建完整文本和 tool_use，按前台/后台及并发安全级别调度 Tool，应用 Hook 和审批，限制模型轮次，处理输出续写、流中断、Provider 错误、请求级恢复、工具结果上下文预算、Session Journal 和 ConversationCompactor。它是“模型如何继续运行”的唯一主实现；Runner 和 AgentSession 都只调用它。 |
| src/main/java/dev/learn/agent/manual/SessionState.java | 父 Agent、子 Agent 及其组件共享的 Session 事实容器。它保存 Session ID、当前 Turn 序号、Memory 开关、审批模式、Agent Home、Workspace、allowedRoots 和 Git 根目录；其中运行期开关可变，路径上下文在 Session 创建时固定。它不保存消息历史，也不执行持久化。 |

### 3.2 background：后台命令的生命周期

| 文件 | 当前职责与边界 |
| --- | --- |
| src/main/java/dev/learn/agent/manual/background/BackgroundTaskScheduler.java | 维护一个 AgentLoop 的后台任务生命周期：启动动作返回后台任务 ID，真实命令继续在虚拟线程执行，完成结果进入队列，随后由 Hook 在模型请求前取走。它区分 runningTasks 和“已完成但尚未交付”的 completedTasks，并在关闭时等待已登记任务；它不负责把结果写入消息历史，结果通知由 BackgroundTaskHook 完成。 |

### 3.3 cli：三种输入协议的薄适配层

| 文件 | 当前职责与边界 |
| --- | --- |
| src/main/java/dev/learn/agent/manual/cli/ApplicationOptions.java | 把命令行参数转换为不可变的 mode、memoryEnabled 和 instruction。它只识别 interactive、exec、harbor 三种入口及现有 Memory 开关，负责参数合法性，不启动 Runtime。 |
| src/main/java/dev/learn/agent/manual/cli/ExecRunner.java | 单次执行入口。把一条 instruction 交给 AgentSession，完成后把已经诊断过的 Provider 最终失败映射为进程退出码 1；它不维护消息历史，也不负责模型请求。 |
| src/main/java/dev/learn/agent/manual/cli/InteractiveRunner.java | 终端交互循环。读取用户行，处理 /memory、/sessions、/resume、/new 等本地命令，其余文本交给同一个 AgentSession，并在会话间保持 Scanner。它负责终端命令语义，不负责模型或 SQLite 细节。 |
| src/main/java/dev/learn/agent/manual/cli/HarborRunner.java | Java 侧 Harbor FIFO 协议实现。它从 request.pipe 读取单行消息，解码 Base64 UTF-8，区分普通 Turn、固定历史 Turn、新 Session 和返回答案的 Turn，按顺序调用 AgentSession，再把 OK 或 RESULT 写入 response.pipe。它是 Java 与 Python Adapter 之间的协议边界，不是 Harbor 环境安装逻辑。 |

### 3.4 context：上下文体积控制和会话压缩

| 文件 | 当前职责与边界 |
| --- | --- |
| src/main/java/dev/learn/agent/manual/context/ContextManager.java | 只处理一批 tool_result 的活跃上下文预算。超过字符预算时，按结果大小选择候选，将完整输出写入工作区会话目录，再用安全路径、原始长度和短预览替换模型看到的正文；只有整体替换计划可行后才产生文件副作用。它不负责终端显示，也不负责压缩普通会话历史。 |
| src/main/java/dev/learn/agent/manual/context/ConversationCompactor.java | 父 Session 的唯一会话压缩实现。它从 SQLite canonical message 和 turn_seq 确定完整 Turn 边界，保留头部和尾部，递归把中间历史交给无工具摘要请求，验证摘要的 session_id/coverage，成功后保存 Context Checkpoint 并替换 ConversationState 的 modelContext。它不改写 canonical history，也不处理单次工具输出预算。 |

### 3.7 memory：长期记忆的领域对象、模型服务和文件仓库

| 文件 | 当前职责与边界 |
| --- | --- |
| src/main/java/dev/learn/agent/manual/memory/MemoryBatch.java | 结构化模型输出的外层 DTO，用于承载 MemoryDraft 列表，解决 SDK 需要具体 Class 才能做结构化输出的问题。它不做领域校验，也不写文件。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryDraft.java | 模型返回的单条原始记忆 DTO，保存 name、type、description 和 body。它故意不承担业务校验，外部结果进入系统前由 MemoryEntry 统一校验。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryExtractionDecision.java | 记忆提取首轮模型判断的 DTO，携带是否需要读取完整 modelContext，以及在当前 Turn 已足够时直接返回的 MemoryDraft 列表。它只承载模型协议结果，不执行第二次请求或领域校验。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryExtractionTask.java | 一项可持久化、可重复执行的记忆提取工作。它冻结 task_id、当前 Turn 的完整 canonical 消息和入队时的 modelContext，并在构造时复制列表，避免后台线程读取后续 Turn 的实时状态；它不调用模型，也不写记忆文件。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryEntry.java | 可信的长期记忆领域对象。它统一校验稳定名称、类型和非空文本，并成为 MemoryRepository 保存、MemorySelector 目录选择和 MemoryExtractor/Consolidator 输出之间的共同数据边界。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryType.java | 长期记忆类型及其稳定 wireValue，负责在 Java 枚举和文件/模型协议值之间转换；未知协议值直接失败，不做默认归类。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryFileParser.java | 单个 Markdown 记忆文件的格式解析器。它拆分 YAML frontmatter、校验字段类型、校验文件名与 name 一致，并构造 MemoryEntry；不扫描目录、不写文件、不重建索引。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryRepository.java | 当前 Workspace 的 .memory 持久化边界。它负责保存、列举、读取、删除主题文件，以及供后台提取使用的 createNew：提取结果不覆盖旧主题，重名候选会追加后缀；它还从主题文件重建 MEMORY.md 索引，统一执行路径边界和原子文件发布。主题文件是事实来源，索引是派生视图。 |
| src/main/java/dev/learn/agent/manual/memory/MemorySelector.java | 轻量 side-query 服务。它只向模型发送记忆名称和描述目录及当前问题，解析并校验最多五个目录索引，返回稳定记忆名称；它不读取正文，也不修改消息历史。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryRecallService.java | 召回流程协调器：读取候选 MemoryEntry，调用 MemorySelector 选择主题，再由 Repository 读取正文并格式化为本轮临时上下文。它不修改 System Prompt 或 Session history。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryExtractor.java | 后台记忆提取服务。它先只把 MemoryExtractionTask 的当前 Turn 交给模型判断；只有信息不足时，才在第二次请求中加入同一任务冻结的完整 modelContext。它校验截断、拒绝、结构化块数量、最多五条、领域字段和重复名称，返回 MemoryEntry 候选但不读取或写入记忆文件。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryConsolidator.java | 对当前全部主题记忆执行一次全量模型整理，合并重复、处理冲突和淘汰过期信息，并校验结果不能凭空扩张、清空或超过输入集合。它先保存全部新版本，再删除不保留的旧主题；整理的触发时机由 MemoryBackgroundProcessor 决定，它不负责后台调度、并发锁或多文件事务。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryWorkStore.java | 记忆后台工作的 SQLite 持久化边界，保存待处理的 task_id、Turn 消息快照和 modelContext，并记录尚未整理的新文件数量。只有后台确认新主题文件写入成功后才删除工作并增加整理计数；它不调用模型、不操作主题文件，也不决定何时整理。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryBackgroundProcessor.java | 记忆后台处理器。它用单一守护线程在启动时恢复待处理工作，收到唤醒后按入队顺序提取并通过 MemoryRepository.createNew 写入，成功确认后累计整理计数；新文件达到五条或两小时维护时调用 MemoryConsolidator。提取/整理失败时保留工作或计数等待再次处理，关闭时不删除 SQLite 中的未完成工作。 |
| src/main/java/dev/learn/agent/manual/memory/MemoryRuntime.java | 记忆能力的 Session 级门面和开关边界。它根据 SessionState 判断是否读取索引、召回和入队，统一组装 Repository、Selector、Recall、Extractor、Consolidator、MemoryWorkStore 和后台处理器；主回答完成后由它持久化冻结快照并唤醒后台线程，重新启用记忆时恢复队列消费，关闭时停止后台执行器。它不执行主模型循环，也不等待提取/整理完成。 |

### 3.9 recovery：模型请求失败的识别、状态和恢复分派

## 五、从当前源码可以确认的架构事实

1. 父 Agent 和子 Agent 共用同一个 AgentRuntime 装配出来的部分能力，但通过不同 AgentLoop、ToolRegistry、HookRegistry、BashTool 和输出目标隔离运行边界；子 Agent 使用 NoOpTurnJournal，不把中间过程写入父 Session。
2. 父 Session 的完整历史和模型活动上下文已经是两份不同视图：SessionStore 保存 canonical history，ConversationCompactor 只替换 modelContext，并通过 checkpoint 记录覆盖位置；后台记忆提取从 SessionStore 按 Turn 读取完整 canonical 消息，同时使用入队时冻结的 modelContext。
3. 工具失败被分成三层语义：具体 Tool 通过 RetryableToolException/NonRetryableToolException 表达重试意图，ToolRegistry 消费重试预算，AgentLoop 再把最终 ToolExecutionResult 配回模型；审批 Gate 和调度器不承担重试判断。
4. 记忆系统分成几个有明确边界的部分：MemoryRuntime 负责开关、召回、提取工作入队和生命周期；MemoryWorkStore 持久化未完成工作与整理计数，MemoryBackgroundProcessor 串行恢复、重试和触发整理；MemoryExtractor/Selector/Consolidator 负责模型侧决策；MemoryRepository/MemoryFileParser/MemoryEntry 负责可信文件领域边界。
5. ContextManager 的“工具结果过大”与 StreamOutputPrinter 的“终端预览过长”是两条不同路径：前者改变模型上下文并保存完整文件，后者只改变用户看到的终端文本。
6. Harbor 有两层适配：Python 负责 Trial 环境、制品上传、长期 Java 进程和子进程外部协议；Java HarborRunner 负责 FIFO 消息解码和 AgentSession 调用。两者都不应直接复制 AgentLoop 逻辑。

## 六、当前职责混合点

下面不是理想架构建议，而是从当前代码职责可以直接观察到的混合点，后续若继续拆分应以这些边界为依据：

- AgentSession 同时负责父 Turn 编排、Session 恢复、Provider 错误展示和 Memory 后台工作的入队；
- AgentLoop 同时负责流式协议解析、工具执行管线、恢复、压缩入口和实时输出；
- AgentRuntime 同时负责配置读取、父/子对象图组装、MCP 可选注册以及 Memory 后台线程和其他资源的关闭；
- ToolRegistry 同时承担工具注册表、执行入口和统一重试；
- SessionStore 同时保存 canonical history、checkpoint、in-flight 工具恢复事实，并提供后台记忆提取所需的按 Turn 消息读取；
- harbor_adapter.py 同时包含普通 Harbor Agent 和 Memory Case 专用 Agent。

这些文件的职责描述应以“当前行为”为准，不能据此推断某个拆分已经存在。
