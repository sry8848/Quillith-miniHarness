## 2. 背景与设计目标

manual-agent 已经不再是“模型返回工具名，然后直接调用 Java 方法”的简单结构。当前一次工具调用可能同时涉及：

- 模型协议中的 tool_use 和 tool_result 配对；
- 本地文件、Bash、任务系统、Skill 等内置工具；
- 父 Agent 和 SubAgent 的不同工具集合；
- 前台工具之间的并发和顺序依赖；
- 可以立即返回、稍后交付结果的后台任务；
- MCP Server 的工具发现、Schema 转换和远程调用；
- Hook 对调用的拦截、修改和结果追加；
- 工具执行前的用户审批；
- Provider 拒绝请求、流式错误和用户轮次回滚。

因此设计目标不是单独实现某个工具，而是建立一条可追踪、可控制、可恢复的公共执行链路。

### 2.1 目标

1. 所有模型工具调用都经过统一的 ToolCall、Hook、审批、注册表和结果包装流程。
2. 只读且明确声明安全的工具可以在同一模型响应内并发执行；有副作用或未声明的工具默认独占执行。
3. 后台任务只在“启动登记”阶段立即返回，真实结果必须通过 Agent 生命周期重新交付给模型。
4. 本地工具和 MCP 工具使用相同的 AgentTool、审批和结果协议，不为 MCP 建立平行的执行通道。
5. 审批策略、审批模式和工具执行解耦：工具是否需要审批、当前是否询问用户、工具是否真的执行，是三个不同问题。
6. 错误恢复只在能够证明协议状态仍然安全时进行，并且设置明确上限；不因为模型请求失败而重复执行可能有副作用的工具。
7. 保留工具 ID、错误状态和执行事实，使模型、终端日志和 Trace 能够对同一次调用进行关联。

### 2.2 非目标与边界

当前设计不包含以下能力：

- 操作系统级文件系统沙盒或 Bash 命令沙盒；
- 跨进程、跨机器的持久化任务队列；
- 后台任务在 Agent 重启后的恢复；
- 对任意工具进行通用自动重试；
- 对已经执行的文件写入、Git 操作或远程调用进行事务回滚；
- 运行期间自动刷新 MCP 工具列表；
- 基于命令文本推断 Bash 的细粒度风险并自动放行；
- 将所有工具的审批规则都提前扩展成复杂的 RBAC 或策略语言。

这些能力可以作为后续方向，但不能从当前“工具调用治理”需求中隐式扩展出来。

## 3. 总体模型：五个彼此独立的执行维度

一次工具调用应同时拥有以下维度。它们不能互相替代。

| 维度   | 取值                        | 解决的问题            |
| ---- | ------------------------- | ---------------- |
| 工具来源 | 内置工具、任务/SubAgent、MCP      | 工具实现和资源边界在哪里     |
| 执行路径 | FOREGROUND、BACKGROUND     | 当前模型是否等待真实操作完成   |
| 并发属性 | 并发安全、独占                   | 是否可以和同批其他工具重叠执行  |
| 审批要求 | NOT_REQUIRED、REQUIRED     | 这次调用是否需要用户授权判断   |
| 审批模式 | BYPASS、ASK                | 需要审批时是直接放行还是询问用户 |
| 结果状态 | 成功、工具失败、Hook 阻止、审批拒绝、管线异常 | 模型应如何理解这次调用结果    |

例如：

- read_file 是内置、前台、并发安全、通常无需审批的工具；
- bash 默认是内置、前台、独占、需要审批的工具，但当 run_in_background=true 时执行路径变为后台；
- 一个 MCP 查询工具虽然看起来可能是只读的，当前仍属于 MCP、前台、独占、需要审批；
- write_file 在 Workspace 内通常无需审批，但仍然是独占工具，因为“不需要审批”不等于“可以并发”。

这种拆分避免了几个常见错误：把“只读”误当作“无需审批”，把“后台”误当作“没有副作用”，或者把“远程查询”误当作“可以安全重试”。

## 4. 运行时组件和状态所有权

### 4.1 组件职责

| 组件                          | 职责                           | 不负责的事情                         |
| --------------------------- | ---------------------------- | ------------------------------ |
| AgentState                  | 保存 Session 级语义状态、审批模式和路径上下文  | 不保存线程池、后台队列、消息历史或单次工具结果        |
| AgentRuntime                | 创建和关闭一组 Session 运行资源         | 不代替 AgentState 保存可变 Session 状态 |
| ManualAgent                 | 编排用户 Turn、记忆、历史提交和失败回滚       | 不直接决定单个工具如何调度                  |
| AgentLoop                   | 驱动模型请求、解析工具调用、提交结果并继续循环      | 不实现具体本地工具或 MCP 传输              |
| AgentTool                   | 暴露模型定义、并发属性、执行模式和执行动作        | 不自行绕过公共审批管线                    |
| ToolRegistry                | 注册工具、生成模型定义、按名称执行工具          | 不负责用户询问和调度等待                   |
| ToolCallDispatcher          | 根据工具声明分流到前台或后台调度器            | 不复制 Hook、审批和工具执行逻辑             |
| ToolExecutionScheduler      | 管理同一模型响应内前台调用的并发和顺序屏障        | 不管理后台任务的跨轮次结果                  |
| BackgroundTaskScheduler     | 管理后台真实执行、完成队列和完成屏障           | 不决定用户审批规则                      |
| HookRegistry                | 执行工具前、工具后、模型前和停止前 Hook       | 不取代工具注册表执行工具                   |
| ToolApprovalPolicy          | 根据完整调用分类审批要求                 | 不询问用户，也不执行工具                   |
| ToolApprovalGate            | 组合策略和当前 Session 审批模式，必要时询问用户 | 不执行工具，也不提供 OS 沙盒               |
| McpAgentTool                | 把一个 MCP 远程工具适配成本地 AgentTool  | 不管理 MCP Server 生命周期            |
| McpToolClient               | 抽象初始化、工具发现、远程调用和关闭           | 不参与模型工具并发决策                    |
| ModelRequestRecoveryManager | 按优先级分派模型请求错误恢复 Handler       | 不重放工具调用                        |

### 4.2 Session 共享关系

当前一个 CLI Session 创建一份 AgentState。父 Agent 和 SubAgent 共享：

- 同一个 AgentState，因此读取到同一份 memoryEnabled、approvalMode 和路径上下文；
- 同一个 ToolApprovalGate，因此审批模式切换对后续父子调用都生效，且共享终端输入时不会并发读取同一个 Scanner。

父 Agent 和 SubAgent 不共享：

- 工具注册表。父 Agent 注册 MCP、任务和 Todo 工具，SubAgent 当前只注册 Bash、文件和 Glob 工具；
- 后台任务调度器。这样一个 Agent 的后台任务不会被另一个 Agent 的停止 Hook 误收集；
- 输出打印器。父 Agent 输出到终端，SubAgent 使用静默输出。

父子 Agent 可以共享同一个模型 Client、ContextManager 和恢复管理器，但这些共享资源不改变各自的 AgentLoop 生命周期。

## 5. 工具调用公共生命周期

当前完整调用链可以概括为：

```text
模型返回完整 tool_use
        |
        v
AgentLoop 解析为 ToolCall
        |
        v
ToolCallDispatcher 根据原始 ToolCall 选择执行路径
        |
        +--> 前台调度器：建立并发/独占顺序屏障
        |
        +--> 后台调度器：提交启动动作，等待“启动登记”
                         |
                         v
                 公共 executeTool 管线
                         |
                         v
                BeforeToolUse Hook
                         |
                         v
                 应用 Hook 输入修改
                         |
                         v
                ToolApprovalPolicy/Gate
                         |
                         v
                    ToolRegistry
                         |
              +----------+----------+
              |                     |
          内置 AgentTool        McpAgentTool
              |                     |
              v                     v
          本地执行动作          McpToolClient -> MCP Server
              |                     |
              +----------+----------+
                         |
                         v
                AfterToolUse Hook
                         |
                         v
                 ToolExecutionResult
                         |
                         v
       按原始模型顺序包装成 tool_result，并继续请求模型
```

### 5.1 具体顺序

1. 模型流收到完整的工具块。只有在工具块已经接收完毕后，AgentLoop 才把它视为可执行的调用。
2. SDK 工具块转换为内部 ToolCall，校验工具 ID、名称和 JSON 对象输入。
3. ToolCallDispatcher 从注册表读取执行模式。未知工具固定进入前台路径；只有工具自身明确声明后台能力，才可以进入后台路径。
4. 前台调用进入 ToolExecutionScheduler，根据并发安全属性等待相应屏障；后台调用进入 BackgroundTaskScheduler，但等待的只是启动动作。
5. 调度器执行公共 executeTool 管线：先触发 BeforeToolUse Hook，再应用输入修改，然后对最终有效输入执行审批，再进入 ToolRegistry。
6. 工具注册表找到本地工具或 MCP 适配工具并执行。未知工具、参数错误、远程失败和本地异常都转换为失败结果，而不是让同批结果失去配对关系。
7. 成功进入注册表的工具调用触发 AfterToolUse Hook。审批拒绝或 BeforeToolUse Hook 阻止的调用不会触发 AfterToolUse，因为工具并未真实执行。
8. AgentLoop 按模型原始调用顺序等待结果，保留每个 tool_use_id 和 isError，构造对应的 tool_result。
9. 工具结果提交到消息历史后，AgentLoop 再请求模型，直到模型不再请求工具、停止 Hook 允许结束，或达到模型轮次边界。

### 5.2 Hook 修改输入的边界

当前实现有一个需要明确记录的顺序：

- 执行路径和前台并发属性由调度分流阶段读取原始 ToolCall；
- 审批和实际执行使用 BeforeToolUse Hook 修改后的有效 ToolCall。

因此 Hook 可以修改工具参数，但当前不会重新计算调用已经进入前台还是后台，也不会重新计算它是否属于并发安全批次。现有设计假设 Hook 修改的是参数内容，不改变工具的执行类别。如果未来允许 Hook 把一个调用改造成不同风险或不同生命周期的操作，需要单独设计“修改后重新路由”规则。

## 6. 当前工具分类

当前注册表中的工具可按下表理解。表中的“无需审批”是默认审批策略分类，不代表工具没有副作用。

| 工具或工具组                               | 执行路径                            | 并发属性 | 默认审批                        | 说明                          |
| ------------------------------------ | ------------------------------- | ---- | --------------------------- | --------------------------- |
| read_file、glob                       | 前台                              | 并发安全 | 无需审批                        | 只读文件或目录查询                   |
| list_tasks、get_task                  | 前台                              | 并发安全 | 无需审批                        | 只读任务状态                      |
| load_skill                           | 前台                              | 并发安全 | 无需审批                        | 启动后只读 Skill 注册表             |
| write_file、edit_file                 | 前台                              | 独占   | Workspace 内无需；Workspace 外需要 | 路径边界由路径解析器和具体工具处理           |
| todo_write                           | 前台                              | 独占   | 当前无需审批                      | 修改当前 Todo 状态                |
| create_task、claim_task、complete_task | 前台                              | 独占   | 当前无需审批                      | 修改任务存储或任务所有权                |
| task                                 | 前台                              | 独占   | 当前无需审批                      | 启动 SubAgent，并等待其任务结果        |
| bash                                 | 默认前台；run_in_background=true 时后台 | 独占   | 需要审批                        | 通过 Git Bash 启动本地进程；不是文件系统沙盒 |
| mcp__git__*                          | 前台                              | 默认独占 | 需要审批                        | 本地 Git MCP 工具               |
| mcp__github__*                       | 前台                              | 默认独占 | 需要审批                        | GitHub MCP 工具               |
| 未知工具                                 | 前台                              | 独占   | 由公共管线处理                     | 注册表返回未知工具失败，不允许借名称绕过调度边界    |

新增工具默认是前台、独占。只有实现类明确证明其只读、可重入、不会修改共享状态，并主动覆盖 isConcurrencySafe()，才能加入并发安全集合。只有明确支持“先启动、后交付”的工具，才能覆盖 executionMode() 返回后台。

## 7. 后台工具设计

### 7.1 三阶段语义

后台工具必须把一次调用拆成三个阶段：

| 阶段   | 含义                     | 模型看到的结果                         |
| ---- | ---------------------- | ------------------------------- |
| 启动登记 | 校验、审批、创建后台任务 ID、提交异步动作 | Background task bg_XXXX started |
| 真实执行 | 在独立虚拟线程中运行命令或其他后台动作    | 模型暂时看不到最终结果                     |
| 结果交付 | 将完成结果写入通知上下文并交给模型      | <task_notification>             |

“启动成功”不是“任务成功”。后台工具的第一次 tool_result 只证明后台任务已登记，最终状态必须等完成通知。

### 7.2 当前实现

当前只有 Bash 工具暴露后台语义。模型通过 run_in_background=true 请求后台执行：

1. ToolCallDispatcher 发现 Bash 的执行模式为 BACKGROUND。
2. 后台调度器提交完整公共工具管线作为启动动作。
3. 公共管线仍然执行 BeforeToolUse Hook、输入修改和审批；审批通过后，Bash 创建真实进程并返回后台任务 ID。
4. submitLaunch 的 Future 只等待启动动作，不等待 Bash 进程结束。
5. 真实命令结束后，后台调度器把结果放入完成队列，再移除运行中任务并完成该任务的完成 Future。

### 7.3 后台状态

后台调度器维护两个核心集合：

- runningTasks：真实命令仍在运行；
- completedTasks：真实命令已经结束，但结果还没有被 Hook 交付给模型。

只有两个集合都为空，后台生命周期才算完全清空。完成顺序有两个重要保证：

1. 任务先登记到 runningTasks，再提交异步执行，避免极快任务在登记前完成而丢失状态。
2. 任务完成时先写入 completedTasks，再从 runningTasks 删除，避免两个集合在中间瞬间同时为空。

结果队列按任务完成顺序收集，不承诺按 bg_0001、bg_0002 的编号顺序交付。

### 7.4 结果交付和最终停止

BackgroundTaskHook 接入两个生命周期点：

- beforeModelCall：收集已经完成但尚未消费的结果，拼成 <task_notification>，作为隐藏上下文交给模型；
- onStop：如果仍有运行中任务或未交付结果，则等待真实任务结束、收集结果并阻止当前停止，要求模型继续处理通知。

因此 Agent 不会在后台任务仍未完成时直接给出最终答案。后台结果既可能在下一次模型请求前到达，也可能由停止 Hook 强制等待后再交付。

### 7.5 后台与审批的结合

审批发生在公共执行管线中，而公共管线作为后台启动动作运行。因此在 ASK 模式下，后台调用的审批询问可能发生在后台调度线程，而不是模型流所在的调用线程。

父 Agent、SubAgent 共享一个 ToolApprovalGate，Gate 对实际 Scanner 读取部分加锁，保证多个并发调用不会同时消费同一个控制台输入。这个锁只保护询问过程，不会把所有无需审批的工具人为串行化。

### 7.6 当前边界

当前后台设计不提供：

- 用户主动取消单个后台任务的接口；
- 后台任务状态查询工具；
- 任务结果持久化和进程重启恢复；
- 后台任务的通用重试；
- 跨 AgentLoop 的后台任务共享。

关闭 Runtime 时，调度器会中断 Java 虚拟线程，Bash 工具还负责清理其跟踪的操作系统进程。两者不是同一层生命周期，不能把关闭线程池等同于已经可靠终止所有子进程。

## 8. 并发与顺序设计

### 8.1 前台调度器

每次模型响应创建一个前台 ToolExecutionScheduler。它使用 Java 虚拟线程执行任务，并通过公平 Semaphore 设置最多 10 个并发工具任务的资源上限。这个数字是并发上限，不是已经测得的吞吐或性能指标。

前台调度器维护两类顺序屏障：

- 并发安全调用只等待最近的独占屏障，因此连续多个只读调用可以重叠执行；
- 独占调用等待此前所有当前并发安全调用和此前独占链完成；后续并发安全调用等待该独占调用完成。

例如调用顺序为：

```text
read_A   read_B   write_C   read_D
  \_______并发_______/

read_D 等待 write_C 完成后再执行
```

实际效果是：

- read_A 和 read_B 可以同时执行；
- write_C 不会和前面的读取重叠；
- read_D 不会在 write_C 完成前读取旧状态；
- 工具结果仍然按模型产生调用的原始顺序提交，而不是按完成速度乱序提交。

### 8.2 失败不破坏同批结果配对

每个调度 Future 都会被转换为不抛异常的完成屏障。工具执行异常转成 ToolExecutionResult.failure，因而某一个调用失败不会让同批其他调用没有机会形成 tool_result。

这同时满足两件事：

- 调度层允许并发执行；
- Anthropic 工具协议仍然要求每个 tool_use_id 有对应的结果。

### 8.3 前台和后台的区别

前台调度器解决的是“同一模型响应内，工具彼此如何等待”。后台调度器解决的是“真实任务跨模型轮次如何继续运行和交付”。后台调用不加入前台独占屏障，而是进入独立生命周期。

因此工具作者不能仅仅因为某个工具耗时较长，就把它改成后台工具。只有当工具可以接受“模型先收到启动结果，最终结果稍后通过通知返回”的语义时，才适合后台化。

### 8.4 并发安全的判定原则

并发安全是工具实现的显式承诺，而不是调度器通过工具名称猜测的结果。默认值为不安全，原因是新增工具更可能遗漏并发语义，而不是主动声明错误。

当前 MCP 适配器没有覆盖 isConcurrencySafe()，因此默认独占。这是保守选择：远程 Server 的副作用、SDK Client 的线程安全和服务端限流边界不能从“查询名称”可靠推断。

## 9. 审批机制设计

### 9.1 三层职责

审批链路分为三层：

```text
BeforeToolUse Hook
    -> 可以阻止调用或修改输入

ToolApprovalPolicy
    -> 判断这次有效调用是否 REQUIRED

ToolApprovalGate
    -> 读取当前 AgentState.approvalMode
    -> ASK 时询问用户，BYPASS 时直接放行

ToolRegistry
    -> 只有允许继续时才真正执行工具
```

这样设计有两个原因：

1. 风险分类不应和控制台交互代码绑定，便于以后增加非交互执行入口或其他审批来源。
2. BYPASS 只跳过询问，不改变 Policy 的分类结果。系统仍然知道某类操作本来需要审批。

### 9.2 当前执行顺序

对一个工具调用，实际顺序是：

1. 从模型请求解析原始 ToolCall。
2. 触发 BeforeToolUse Hook。
3. 如果 Hook 返回 BLOCK，直接形成失败结果，不进入审批和工具实现。
4. 如果 Hook 修改了输入，生成有效 ToolCall。
5. Policy 根据有效调用分类审批要求。
6. NOT_REQUIRED 直接放行；REQUIRED + BYPASS 直接放行；REQUIRED + ASK 询问用户。
7. 用户输入 y 或 yes 才允许执行，其余输入视为拒绝。
8. 审批通过后进入 ToolRegistry，执行成功或失败都触发 AfterToolUse Hook。
9. 审批拒绝返回 Permission denied by user，不进入注册表，也不触发 AfterToolUse Hook。

审批放在 Hook 输入修改之后，是为了审批用户最终会允许执行的参数，而不是审批已经被 Hook 改写前的参数。

### 9.3 当前策略矩阵

| 调用                               | ASK 模式 | BYPASS 模式                    |
| -------------------------------- | ------ | ---------------------------- |
| mcp__*                           | 询问     | 直接放行，但仍被 Policy 分类为 REQUIRED |
| bash                             | 询问     | 直接放行，但仍被 Policy 分类为 REQUIRED |
| Workspace 内 write_file/edit_file | 直接放行   | 直接放行                         |
| Workspace 外、仍在允许范围内的文件写入         | 询问     | 直接放行                         |
| read_file、glob                   | 直接放行   | 直接放行                         |
| 当前未配置专门规则的其他工具                   | 直接放行   | 直接放行                         |

当前所有以 mcp__ 开头的工具统一需要审批，包括 Git 和 GitHub 的查询工具。即使 GitHub Client 配置了只读请求头，也不能将远程工具的只读意图当作宿主授权的替代品。

### 9.4 审批不是沙盒

审批只回答“用户是否允许这次工具调用继续”，不回答“工具在操作系统层面能访问什么”。

当前安全边界由多个层次共同构成：

- 文件工具通过路径解析器处理工作区和允许目录；
- Bash 明确不是文件系统沙盒，审批针对整个 Bash 调用，不解析命令文本；
- MCP Server 自身的权限、凭证和传输配置决定远程能力；
- ToolApprovalGate 只控制是否进入 ToolRegistry。

因此不能把“用户点了允许”描述成“操作已被沙盒限制”，也不能把 BYPASS 描述成不存在风险。BYPASS 是当前运行模式的授权选择，不会自动增加隔离能力。

## 10. MCP 集成设计

### 10.1 设计目标

MCP 的作用是把外部工具能力接入 Agent，但接入后不应破坏 Agent 已有的调度、审批、结果和 Trace 语义。当前选择的模型是：

```text
MCP Server
    -> McpToolClient
    -> McpAgentTool
    -> ToolRegistry
    -> AgentLoop 公共工具管线
```

MCP 不建立第二套“模型直接调用远程工具”的链路。

### 10.2 最小客户端契约

McpToolClient 只抽象四个动作：

1. initialize()：完成 MCP 初始化握手；
2. listTools()：读取 Server 当前暴露的工具定义；
3. callTool(remoteToolName, arguments)：使用 Server 原始工具名调用；
4. close()：关闭客户端和底层连接。

当前不额外引入连接管理器，是因为本地 Git MCP 和远程 GitHub MCP 虽然传输不同，但 Agent 需要的生命周期相同。保持最小契约可以减少一层没有实际职责的抽象。

### 10.3 当前两类 MCP Client

#### 本地 Git MCP

- 只有在启动目录能够发现 gitRoot 时才创建；
- 使用 MCP 官方 SDK 的同步 Client；
- 通过标准输入输出启动 uvx mcp-server-git --repository <gitRoot>；
- 初始化和请求超时统一设置为 30 秒；
- Server 固定绑定启动时发现的仓库根目录，运行期间不自动切换。

#### GitHub MCP

- 使用官方 GitHub MCP HTTP Endpoint；
- 通过 GITHUB_PERSONAL_ACCESS_TOKEN 提供 Bearer Token；
- 当前请求配置 X-MCP-Readonly: true；
- 当前启用 repos、issues、pull_requests 工具集；
- 使用官方 Streamable HTTP 同步 Client；
- 初始化和请求超时统一设置为 30 秒。

凭证属于运行时配置，不能写入工具定义、普通日志、Trace 属性或模型上下文。

### 10.4 工具发现与命名

Runtime 启动时依次执行：

1. 初始化 MCP Client；
2. 调用 tools/list；
3. 对每个远程工具创建一个 McpAgentTool；
4. 将适配器注册到父 Agent 的 ToolRegistry；
5. 将转换后的工具定义发送给模型。

模型侧使用命名空间避免不同 Server 的同名工具冲突：

```text
mcp__git__git_status
mcp__github__search_repositories
```

调用时，模型侧名称和 MCP Server 原始名称分离：

- 模型看到带命名空间的名称；
- McpAgentTool 根据注册时保存的原始名称调用远程 Server；
- 远程 Server 不需要理解 mcp__git__ 或 mcp__github__ 前缀。

### 10.5 Schema 和结果转换

McpAgentTool 在构造阶段将 MCP 的 inputSchema 转换为 Anthropic 工具定义：

- 保留对象类型、属性、嵌套结构和 required 字段；
- 当前 AgentTool 契约要求对象输入，非 object Schema 在注册阶段报错；
- 模型产生的 JsonNode 转成 MCP Client 需要的 Map<String,Object>；
- MCP 返回的文本内容直接作为工具结果；其他内容块保留结构化字符串表示；
- MCP isError=true 转换为 ToolExecutionResult.failure，确保上游能够生成 is_error=true 的 tool_result。

MCP 远程错误不会绕过 AgentLoop，而是沿用本地工具失败结果的协议路径。

### 10.6 MCP 与审批、并发、恢复的关系

- 审批：所有带 mcp__ 前缀的工具统一进入 REQUIRED 分类；
- 并发：当前 McpAgentTool 使用默认独占策略；
- 执行路径：当前没有 MCP 后台能力，统一走前台；
- 工具失败：转为失败 ToolExecutionResult，不自动重新调用远程工具；
- Provider 请求失败：只恢复消息协议或可安全替换的结果正文，不重放 MCP 调用。

这条边界尤其重要：Provider 可能已经接受了 MCP 工具请求并导致远程副作用，即使随后拒绝了工具结果，也不能把“恢复模型请求”实现成“再次执行 MCP 工具”。

### 10.7 MCP 初始化失败边界

当前 MCP 工具是在 Runtime 创建阶段发现并注册的。如果初始化或工具列表获取失败，Runtime 关闭已经创建的 MCP Client 后向上抛出异常，不创建一个缺少部分工具的静默运行时。

这是一种启动失败策略，优点是模型看到的工具集合稳定，缺点是单个 MCP Server 故障可能影响整个 Runtime 启动。若未来需要“部分 MCP 可用”，应明确设计降级、提示和工具定义刷新，而不能只捕获异常后忽略。

## 11. 错误恢复设计

错误恢复必须先区分错误发生在哪一层。不同层的恢复动作和安全条件不同。

| 错误层                     | 当前处理                  | 是否重试模型         | 是否重试工具 |
| ----------------------- | --------------------- | -------------- | ------ |
| 工具返回业务失败                | 保留 error=true 的工具结果   | 会继续让模型看到失败结果   | 否      |
| 工具实现抛出 RuntimeException | 转为精简失败结果，完整堆栈写日志      | 会继续提交同批结果      | 否      |
| 工具公共管线异常                | 返回与原 tool_use 配对的失败结果 | 会继续提交同批结果      | 否      |
| HTTP Provider 请求错误      | 交给恢复 Handler          | 只有明确可恢复时有限重试   | 否      |
| SSE Provider 输出错误       | 根据方向和已完成内容决定          | 只在输出拒绝可安全提交时恢复 | 否      |
| 用户 Turn 最终失败            | ManualAgent 回滚失败 Turn | 不在本层自动重发       | 否      |

### 11.1 工具级错误

工具层使用 ToolExecutionResult(content, error) 表达结果，不把所有失败都变成 Java 异常向上冒泡。

当前有三道结果保护：

1. ToolRegistry.execute() 对未知工具和工具实现异常生成精简失败结果，并在本地日志保留完整异常。
2. AgentLoop.executeTool() 对 Hook、审批和工具公共管线中的未处理 RuntimeException 进行最后兜底，仍生成失败结果。
3. collectToolResults() 保留原始 tool_use_id 和 error 状态，形成协议要求的 tool_result。

这样某一个工具失败不会破坏同一批其他工具的结果配对，也不会让模型误以为工具成功。

工具级失败当前不会自动重试。原因是工具可能已经产生了外部副作用，调用失败不等于没有执行；通用重试会造成重复写入、重复提交或重复远程操作。

### 11.2 后台任务错误

后台真实执行线程会把未预期的 RuntimeException 转换为 failed 的 CompletedTask，然后仍然完成以下收尾动作：

- 放入完成队列；
- 从运行中集合移除；
- 完成等待 Future。

这样异常不会让后台任务永久处于 running 状态。模型最终收到的是失败通知，而不是一个永远等待的任务。

### 11.3 HTTP 请求级恢复

ModelRequestRecoveryManager 按注册顺序选择第一个支持当前异常的 Handler。当前唯一的专门 Handler 是 ContentRejectionRecoveryHandler，只识别错误 Body 根字段精确为 code=DataInspectionFailed 的 Provider 错误。

它只在以下条件全部满足时恢复：

1. 当前存在最近一批待确认的 Tool Result ID；
2. 这批 ID 能够在同一条 user 消息中完整定位；
3. 消息历史仍然保留 assistant 的原始 tool_use 和 tool result 配对关系；
4. 同一连续恢复链的次数没有达到上限。

恢复动作是原子替换整批工具结果正文：

- 保留 tool_use_id；
- 保留 assistant 的工具调用事实和参数；
- 将正文替换为说明 Provider 拒绝结果、要求缩小查询范围的安全文本；
- 将该工具结果标记为错误；
- 替换成功后才消耗一次恢复次数。

当前同一连续请求恢复链最多恢复 2 次。恢复 Handler 本身不调用模型，也不重新执行工具，只修改消息并把控制权交回 AgentLoop 重新发送请求。

如果错误无法精确识别、待恢复工具结果不完整、Body 不是可解析 JSON，或恢复次数耗尽，原始 Provider 异常继续向上抛出。

### 11.4 SSE 流式错误恢复

SSE Provider Error 可能发生在模型已经输出部分文本或完整工具调用之后，因此不能简单地丢弃整个流，也不能无条件重发原请求。

当前恢复规则是：

- 只有 Provider 明确表示内容检查失败时才进入专门判断；
- 如果是输出方向拒绝，且流中已经形成稳定的文本或完整工具调用，则先提交已完成事实和对应工具结果，再追加恢复说明；
- 保留已完成的工具 ID，不重复执行工具；
- 恢复请求只继续当前模型处理流程，不额外消耗普通业务轮次；
- 输入方向拒绝或方向无法判断时不自动恢复，直接抛出原异常；
- 连续恢复次数达到上限后停止恢复。

对于普通流中断，当前实现提交中断前已经完整关闭的协议块和工具事实，再回到外层请求前流程，不重发可能造成重复副作用的原始工具调用。

### 11.5 用户 Turn 回滚

ManualAgent 在一个用户 Turn 开始时保存必要的历史和记忆快照。只有 AgentLoop 成功完成，才完成记忆写入；如果模型请求最终失败，则：

- 回滚当前失败 Turn 对会话历史的影响；
- 不把失败的临时记忆写入长期存储；
- 将 Provider 错误交给上层运行模式处理。

这层回滚只针对 Agent 的会话状态，不是对工具副作用的数据库事务回滚。已经执行过的文件写入、进程启动或远程 MCP 操作不能仅靠消息历史回滚。

### 11.6 恢复设计的核心不变量

错误恢复必须满足以下不变量：

1. 不因为模型请求失败而重新执行已完成的工具。
2. 不删除 assistant 的 tool_use 事实来掩盖结果交付失败。
3. 需要替换工具结果时，整批替换，不提交半批协议。
4. 恢复次数必须有上限，并且只有实际修改消息后才计数。
5. 未识别错误保持原异常类型和上下文，不伪造“已经恢复”。
6. 工具失败状态必须在 tool_result.is_error 中保留。
7. 已经接受的新模型请求开始后，旧恢复链状态必须重置，避免错误次数跨请求泄漏。

## 12. 结果、日志和 Trace

### 12.1 模型协议结果

工具结果对模型至少包含：

- 原始 tool_use_id；
- 结果正文；
- 成功或失败标记。

终端展示可以受到大输出截断或格式化影响，但模型协议使用的结果和错误状态必须保持一致。这样用户看到的摘要不会改变模型实际收到的失败事实。

### 12.2 可观测性

当前工具调用使用 tool.execute Span，并在 Span 名称中加入真实工具名，例如：

```text
tool.execute read_file
tool.execute task
tool.execute mcp__git__git_status
```

当前不把完整工具输入、结果和错误详情写入 Span，避免把敏感内容和大文本扩散到 Trace 系统。完整异常由本地日志记录，模型只收到可继续推理的精简错误。

后台任务通知包含任务 ID、状态、命令和结果。命令内容可能包含敏感参数，后续若接入集中式日志或跨用户 Trace，需要重新评估脱敏策略。

## 13. 关闭和资源生命周期

Runtime 创建时初始化：

- 父 Agent 和 SubAgent 的后台调度器；
- 父 Agent 和 SubAgent 的 Bash 工具；
- 已配置的 Git、GitHub MCP Client；
- Anthropic 模型 Client。

Runtime 关闭时按资源依赖顺序关闭：

1. 父后台调度器；
2. SubAgent 后台调度器；
3. 父、子 Bash 工具及其进程；
4. GitHub MCP Client；
5. 可选的 Git MCP Client；
6. Anthropic Client。

工具定义在 Runtime 启动后作为注册快照使用。MCP Server 运行期间新增或删除工具不会自动反映到模型工具列表；若未来需要动态发现，必须同时解决模型上下文刷新、并发调用中的注册表一致性和旧工具调用的兼容问题。

## 14. 已落地能力与验证情况

当前代码和测试已经覆盖或验证了以下设计点：

- ToolRegistry 支持批量注册、重复工具名校验和稳定注册顺序；
- 新工具默认前台、独占，未知工具不能通过名称绕过安全边界；
- 前台调度器覆盖连续并发安全调用，以及独占工具前后的顺序屏障；
- 工具结果按模型调用顺序交付，并保留错误状态和工具 ID；
- 审批策略覆盖 Bash、MCP、路径相关文件写入和只读工具；
- 审批 Gate 读取当前 AgentState.approvalMode，而不是永久缓存启动时快照；
- 父 Agent 和 SubAgent 共用审批 Gate，但各自维护后台任务生命周期；
- 模型请求恢复有 Handler 分派单测、内容拒绝替换单测和 AgentLoop HTTP 集成测试；
- 已有 Trace 执行记录验证本地工具、SubAgent 和 Git MCP 工具可以关联到对应的 Agent Span。

当前仍建议补充或持续验证：

- BackgroundTaskScheduler 的独立并发竞态测试，特别是“先登记后执行”和“先入完成队列后移除运行任务”；
- McpAgentTool 的 Schema 转换、命名空间冲突、结构化内容和远程 isError 单测；
- MCP Server 不可用、初始化超时和关闭异常时的 Runtime 资源清理测试；
- 后台 Bash 在 ASK 模式下的审批交互测试；
- Hook 修改后台参数、Hook 阻止调用和审批拒绝之间的组合测试；
- 工具已经产生副作用后 Provider 错误的“不重复执行”集成测试；
- 大量并发安全工具叠加独占工具时的实际调度时间线和输出行为。

## 15. 后续演进优先级

按照对可靠性和简历项目含金量的综合价值，建议按以下顺序考虑后续工作：

### P0：补齐当前设计的证据链

- 为后台调度器补充竞态和生命周期测试；
- 为 MCP 适配器补齐纯单测和故障集成测试；
- 记录并发、审批、MCP、错误恢复的可重复验收脚本；
- 统一 Trace 字段和敏感数据脱敏规则。

### P1：提升单机 Agent 的可用性

- 增加后台任务查询、取消和明确的超时状态；
- 将控制台审批抽象为可替换的审批交互接口；
- 支持按工具或工具组配置审批策略；
- 对可证明幂等的 MCP 查询增加显式并发或有限重试声明；
- 对 MCP Client 的初始化失败提供可选降级，而不是只能整体启动失败。

### P2：面向生产环境的能力

- 持久化后台任务状态和结果；
- 跨进程任务恢复与进程生命周期监控；
- OS 级沙盒、网络出口控制和更细粒度的 Bash 权限；
- 分布式任务调度、租约、幂等键和重复提交保护；
- 统一指标：工具等待时间、审批等待时间、远程调用失败率、恢复次数和最终成功率。

后续新增能力仍应沿用本文的五个维度，先明确执行路径、并发属性、审批要求、结果状态和恢复边界，再决定是否新增代码抽象。

## 16. 结论

当前设计的核心不是“工具越来越多”，而是把工具调用纳入一个统一的执行治理模型：

```text
模型协议
  -> 调度分流
  -> Hook 管线
  -> 审批判断
  -> 本地/MCP 执行
  -> 结果配对
  -> 错误恢复或继续推理
```

前台并发解决效率，独占屏障解决顺序；后台任务解决长耗时操作，停止 Hook 解决最终交付；审批 Gate 解决用户授权，Policy 解决风险分类；MCP 扩展工具来源，适配器保证它仍遵守本地执行协议；错误恢复解决模型通信和结果交付失败，但不伪造事务回滚，也不重复执行有副作用的工具。

这套边界使系统能够在继续增加本地工具、SubAgent 和 MCP Server 的同时，保持执行顺序、权限判断、错误状态和可观测性的一致性。
