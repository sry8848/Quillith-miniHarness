# Skill 系统设计

## 1. 文档定位

### 1.1 适用范围

本文描述当前唯一进行中的 `manual-agent` 项目中的 Skill 系统：

```text
learn-claude-code/demo/manual-agent
```

本文记录当前系统应该是什么样、为什么采用这种结构，以及实现中的边界和不变量。它是设计文档，不是执行文档；不在本文中指定下一次修改必须编辑哪些代码行。

本文不把 `claude-code-cli` 中其他实验性实现当作本系统的运行时契约。除非另有说明，本文中的“Skill”都指 `manual-agent` 当前实现。

### 1.2 当前状态

- Skill 是一个本地 Markdown 指令包，不是 Java 插件，也不是一个自动执行脚本的插件容器。
- 一个 Skill 由 `skills/<skill-name>/SKILL.md` 表示。
- Runtime 启动时扫描并校验所有 Skill，建立本次 Session 的只读注册表。
- 模型只在 System Prompt 中看到名称和描述组成的轻量目录。
- 当目录中的某个 Skill 与任务匹配时，模型通过 `load_skill` 按名称加载完整正文。
- Skill 正文以工具结果进入会话历史，不会直接拼进 System Prompt。
- Skill 的脚本或资源不会因为 Skill 被加载而自动读取或执行。
- 当前父 Agent 可以使用 Skill；当前 SubAgent 没有 Skill 目录、Skill Provider 或 `load_skill` 工具。

### 1.3 一句话结论

Skill 系统把“发现能力”和“加载指令”分成两个阶段：

```text
本地文件系统
    │ 启动时扫描、解析、校验
    ▼
SkillRegistry（Session 内不可变快照）
    ├── catalog() ──> System Prompt 的轻量 Skill 目录
    └── find(name) ─> load_skill ─> 工具结果中的完整指令
                                      │
                                      ▼
                         模型根据指令自行调用普通工具
```

这种设计同时控制了模型上下文成本、运行时确定性和 Skill 文件路径的信任边界。

## 2. 背景与要解决的问题

Coding Agent 的通用工具只能表达“能做什么”，不能完整表达“在某一类任务中应该按照什么顺序、以什么标准、用什么输出格式做”。例如 Java 代码评审通常还需要规定：

- 先阅读哪些上下文；
- 如何区分确定问题和推测；
- 哪些风险优先级更高；
- 每个问题必须包含哪些证据；
- 没有问题时应该输出什么固定结论。

如果把所有领域指令在每次请求开始时全部注入 System Prompt，会产生三个问题：

1. 与当前任务无关的指令持续占用上下文。
2. Skill 数量增加时，System Prompt 会线性膨胀。
3. Skill 文件变化的读取时机不清晰，容易导致同一个 Session 中前后请求看到不同内容。

因此本系统需要同时满足以下要求：

1. Agent 能知道当前有哪些 Skill，并能依据描述判断是否相关。
2. 只有真正匹配任务的 Skill 才把完整指令放入模型上下文。
3. Skill 名称必须稳定、可验证，模型不能通过任意路径读取文件。
4. 一次 Runtime 生命周期内，Skill 集合和正文保持稳定。
5. Skill 的指令可以指导普通工具使用，但不能绕过普通工具已有的审批、Hook 和路径边界。
6. Skill 所属的 Agent 自身资源与用户工作区分离。

## 3. 设计目标与明确不做的事情

### 3.1 设计目标

#### 3.1.1 低成本发现

System Prompt 只保留 Skill 的 `name` 和 `description`。模型可以先完成能力选择，再决定是否支付完整正文的上下文成本。

#### 3.1.2 按需加载

完整指令只由 `load_skill` 返回。模型没有加载匹配 Skill 之前，不应按照该 Skill 的具体方法开始工作。

#### 3.1.3 启动期确定性

Skill 在 Runtime 创建阶段完成扫描、解析和校验。构造成功后，注册表不再修改，后续模型请求使用同一个内存快照。

#### 3.1.4 最小权限路径

模型传给 `load_skill` 的是逻辑名称，而不是文件路径。路径解析只发生在启动扫描阶段，并且必须位于 `agentHome/skills` 根目录内。

#### 3.1.5 与通用工具统一

Skill 只是给模型增加操作知识，不增加一套独立的执行通道。Skill 需要读文件、改文件、运行命令或调用 MCP 时，仍然必须使用已有工具管线。

### 3.2 当前版本明确不做

以下能力不属于当前设计，不应通过隐式兜底或预留抽象加入实现：

- 运行中的 Skill 热重载、目录监听或自动刷新；
- 从远程仓库下载、安装、升级或卸载 Skill；
- Skill 版本、依赖、参数 Schema、别名、模糊匹配或优先级配置；
- 自动执行 `SKILL.md` 中提到的脚本；
- 为每个 Skill 单独建立一套沙盒、审批策略或工具注册表；
- 自动把 `agentHome` 加入通用文件工具的 `allowedRoots`；
- 自动把 Skill 注入 SubAgent；
- 对 Markdown 正文进行语义安全审查、签名校验或恶意指令检测；
- 为损坏 Skill 静默使用默认描述、目录名或旧版本内容。

这些不是“系统已经支持但暂时没有文档化”的能力，而是当前边界之外的事项。若将来需要，必须单独讨论生命周期、权限和兼容策略。

## 4. 核心概念模型

### 4.1 概念定义

| 概念 | 含义 | 当前实现 | 是否进入模型上下文 |
| --- | --- | --- | --- |
| Skill 根目录 | 所有 Skill 子目录的容器 | `agentState.agentHome()/skills` | 否 |
| Skill 目录 | 一个 Skill 的一级子目录 | `skills/<name>` | 通过 Base directory 间接告知 |
| `SKILL.md` | Skill 的唯一清单和指令文件 | `skills/<name>/SKILL.md` | 完整正文按需进入 |
| frontmatter | `SKILL.md` 开头的 YAML 元数据 | `name`、`description` | 名称和描述进入目录 |
| SkillDefinition | 已解析、已校验的内存对象 | `SkillDefinition` record | 不直接发送 |
| Skill catalog | 所有 Skill 的名称/描述索引 | `SkillRegistry.catalog()` | 是，放入 `<skills>` section |
| SkillRegistry | 名称到定义的只读映射 | `SkillRegistry` | 通过 Provider 提供目录 |
| `load_skill` | 按准确名称返回正文的 AgentTool | `LoadSkillTool` | 工具结果进入历史 |
| Skill 指令 | `SKILL.md` frontmatter 后的 Markdown 正文 | `SkillDefinition.instructions()` | 只有加载后进入 |
| Skill 资源 | Skill 目录中除 `SKILL.md` 外的文件 | 当前不自动处理 | 不自动进入 |

### 4.2 Skill 不是工具

工具是可被模型调用并产生外部效果的执行单元；Skill 是供模型阅读的领域操作规范。两者关系如下：

```text
Skill ──提供方法、顺序、判断标准──> 模型
模型 ──调用已有工具──────────────> 文件系统、终端、MCP 或任务系统
```

Skill 本身不拥有 `execute()`，也不直接修改工作区。它不能绕开 `ToolApprovalGate`、通用 Hook、`ToolRegistry` 或 `ToolExecutionScheduler`。

### 4.3 Skill 的身份由名称和目录共同组成

Skill 的逻辑名称不是任意标签，而是一个目录契约：

```text
skills/java-code-review/SKILL.md
       └────────────┘
       name 必须等于 java-code-review
```

这样可以使目录结构、人类维护者看到的名称、System Prompt 中的名称以及模型调用参数保持一致。系统不做大小写转换、自动 Trim、别名匹配或模糊匹配。

## 5. 总体架构

### 5.1 组件关系

```text
ManualAgentApplication
    │
    ├── 确定 cwd / agentHome / workspace / allowedRoots
    └── 创建 AgentState
            │
            ▼
      AgentRuntime.create(agentState)
            │
            ├── SkillRegistry(agentHome/skills)
            │       ├── SkillFileParser
            │       └── SkillDefinition
            │
            ├── 父 ToolRegistry
            │       └── LoadSkillTool ──> SkillRegistry.find(name)
            │
            └── 父 SystemPromptManager
                    ├── identity Provider
                    ├── workspace Provider
                    ├── memory Provider
                    └── SkillRegistry Provider ──> catalog()
                                                        │
                                                        ▼
                                                  AgentLoop
                                                        │
                                                        ├── 每次请求刷新 System Prompt
                                                        ├── 发送 catalog + tool schema
                                                        └── 执行模型生成的 load_skill
```

### 5.2 组件职责

| 组件 | 职责 | 不负责的事情 |
| --- | --- | --- |
| `ManualAgentApplication` | 建立本次进程的 `agentHome` 和 `workspace` 语义，装配 `AgentState` | 不解析 Skill，不处理模型回合 |
| `AgentState` | 保存 Session 共享的路径上下文和策略状态 | 不扫描目录，不持有 Skill 映射 |
| `AgentRuntime` | 按依赖顺序创建 registry、Tool 和 Prompt Provider | 不决定单个 Skill 的内容 |
| `SkillFileParser` | 解析一个 `SKILL.md` 的 frontmatter 和正文 | 不扫描目录，不检查名称重复 |
| `SkillDefinition` | 对解析结果执行字段规范化和数据契约校验 | 不执行正文，不访问其他文件 |
| `SkillRegistry` | 扫描根目录，检查路径/名称/重复项，提供 catalog 和精确查找 | 不动态监听文件，不执行脚本 |
| `SystemPromptManager` | 按生命周期管理 `<skills>` section 并组装完整 System Prompt | 不加载 Skill 正文 |
| `LoadSkillTool` | 校验模型参数，按名称查找并返回完整正文 | 不接受路径，不执行正文中的操作 |
| `AgentLoop` | 发送带 catalog 和工具定义的请求，提交工具结果到历史 | 不理解 Skill 业务语义 |
| `ToolApprovalGate` / Hook | 对模型后续的普通工具操作执行统一安全治理 | 不给 Skill 额外权限 |

### 5.3 父 Agent 与 SubAgent 的边界

当前 `AgentRuntime` 创建两套工具和提示词上下文：

| 能力 | 父 Agent | SubAgent |
| --- | --- | --- |
| `SkillRegistry` | 有 | 无 |
| `<skills>` System Prompt section | 有 | 无 |
| `load_skill` | 有 | 无 |
| 普通文件/终端工具 | 有 | 有限共享 |
| 共享 `AgentState` | 是 | 是 |

因此当前系统的约定是：Skill 发现和加载由父 Agent 完成。父 Agent 可以把已经理解后的具体任务要求交给 SubAgent，但 SubAgent 不会自动获得 Skill 目录，也不能自行调用 `load_skill`。这一区别是实际注册表装配结果，不是仅由身份提示词文字决定的权限。

## 6. 目录结构与文件格式

### 6.1 目录布局

逻辑布局为：

```text
agentHome/
└── skills/
    ├── java-code-review/
    │   ├── SKILL.md
    │   ├── references/        # 当前不自动扫描
    │   └── scripts/           # 当前不自动执行
    └── another-skill/
        └── SKILL.md
```

扫描规则只有一层：`skills/` 下的直接子目录是候选 Skill。`skills/` 下的普通文件会被忽略；没有 `SKILL.md` 的直接子目录会导致注册失败；更深层目录不会被当作独立 Skill 扫描。

### 6.2 `SKILL.md` 结构

文件必须以完整 YAML frontmatter 开始，并在 frontmatter 后提供非空 Markdown 正文：

```markdown
---
name: java-code-review
description: Review Java code for correctness, trust-boundary violations, resource leaks, and unnecessary complexity. Use when the user asks to review Java source code, a Java diff, or a Java implementation.
---

# Java Code Review

对 Java 代码进行基于证据的评审。

## 评审顺序

1. 先阅读用户指定的代码和直接相关调用链。
2. 区分已经确定的问题与仍需验证的推测。
```

frontmatter 必须位于文件开头。解析器使用完整字符串匹配，不能在任意 Markdown 中段找到一段 `---` 就把它误当作清单头部。

### 6.3 元数据契约

| 字段 | 类型 | 约束 | 运行时用途 |
| --- | --- | --- | --- |
| `name` | 字符串 | 必填；去除首尾空白后不能为空；最多 64 个字符；匹配 `[a-z0-9]+(?:-[a-z0-9]+)*`；必须等于父目录名 | catalog 展示和 `load_skill` 精确查找键 |
| `description` | 字符串 | 必填；去除首尾空白后不能为空；最多 1,024 个字符 | catalog 中帮助模型判断适用时机 |
| 正文 | Markdown 字符串 | 去除首尾空白后不能为空 | `load_skill` 成功时返回模型 |
| 其他 frontmatter 字段 | 任意 | 当前解析器不读取、不解释 | 不产生当前运行时行为 |

`name`、`description` 和正文在进入 `SkillDefinition` 时都会进行首尾空白规范化。YAML 字段必须是字符串；例如数字、数组、对象不能代替 `name` 或 `description`。

### 6.4 正文和资源的语义

正文是模型可读的 Markdown 指令，当前不会进一步解析为步骤 AST、工具白名单或执行计划。正文可以说明：

- 什么时候适用；
- 应该先读取什么；
- 判断问题的优先级；
- 应该调用哪些已有工具；
- 输出必须遵守什么格式。

但正文中的“执行脚本”“读取参考资料”等文字只是模型指令。`load_skill` 只返回正文和 Skill 根目录，不会自动：

- 执行脚本；
- 读取 `references/` 文件；
- 把资源文件内容拼进结果；
- 修改工作区；
- 给模型新增工具。

返回的 `Base directory` 只是帮助模型理解正文中相对路径的上下文，不等同于权限授予。当前默认 `allowedRoots` 只有 `workspace`，`agentHome` 不会因为存在 Skill 就被自动加入通用文件工具边界。

## 7. 启动扫描与注册流程

### 7.1 路径语义

Skill 属于 Agent 自身资源，不属于用户当前工作区。当前路径角色如下：

| 路径角色 | 来源 | Skill 相关含义 |
| --- | --- | --- |
| `agentHome` | `AgentState.agentHome()` | Skill 根目录的上一级 |
| `workspace` | `AgentState.workspace()` | 默认文件和终端工作目录 |
| `allowedRoots` | `AgentState.allowedRoots()` | 通用文件工具的可操作目录集合，默认只有 workspace |
| Skill 根目录 | `agentHome.resolve("skills")` | 只由 Runtime 内部注册表读取 |

当前应用为了保持旧运行行为，`ManualAgentApplication` 中的 `configuredAgentHome` 暂时取当前 `cwd`。这只是当前配置值与工作区恰好相同，不改变概念上的归属：Skill 的路径来源仍然必须是 `agentState.agentHome()`，不能在其他代码中重新从 `workspace` 偶然派生。

### 7.2 注册阶段顺序

Runtime 创建时，`AgentRuntime` 使用以下路径装配：

```java
new SkillRegistry(
        agentState.agentHome().resolve("skills")
)
```

`SkillRegistry` 的构造流程如下：

1. 对 Skill 根目录执行 `toRealPath()`，因此根目录必须已经存在且可访问。
2. 确认真实根路径是目录。
3. 使用 `Files.list()` 获取根目录的直接子项。
4. 只保留目录，并按稳定顺序排序。
5. 对每一个候选目录执行真实路径解析和边界检查。
6. 要求候选目录下存在普通文件 `SKILL.md`。
7. 使用 `SkillFileParser` 解析 `SKILL.md`。
8. 再次检查解析后 `SKILL.md` 的真实父目录位于 Skill 根目录内。
9. 检查真实候选目录名等于 frontmatter 中的 `name`。
10. 以 `name` 为键放入临时 `LinkedHashMap`，重复名称立即失败。
11. 复制到新的 `LinkedHashMap` 并包装为不可修改 Map。

所有候选项都成功后，注册表才对外可用；任意一个 Skill 不符合契约，整个 `SkillRegistry` 构造失败，Runtime 不会带着一个不完整的 Skill 集合继续运行。

### 7.3 路径和符号链接检查

Skill 文件来自文件系统，不能只使用字符串路径判断安全性。当前实现采用真实路径检查：

- Skill 根目录先转换为真实绝对路径。
- 候选 Skill 目录转换为真实路径后，必须位于 Skill 根目录内。
- `SKILL.md` 解析时再次转换为真实路径。
- 如果 `SKILL.md` 是指向外部目录的符号链接，解析后的父目录检查会拒绝它。
- 名称与真实候选目录名不一致时拒绝注册。

这里的“位于目录内”使用 `Path.startsWith(Path)` 的路径组件语义，而不是字符串前缀比较，避免把类似 `skills-other` 的路径误判为 `skills` 的子目录。

### 7.4 解析器的安全边界

`SkillFileParser` 使用 Jackson YAML 的树形读取方式：

- 只把 frontmatter 解析为 `JsonNode` 数据树；
- 开启严格重复字段检测；
- 不启用多态对象反序列化；
- 只读取 `name` 和 `description` 两个字段；
- Markdown 正文原样作为文本交给 `SkillDefinition` 做非空校验。

因此 YAML 内容只能影响 SkillDefinition 的文本字段，不能通过 frontmatter 指示系统实例化任意 Java 类型或调用任意代码。

## 8. System Prompt 集成

### 8.1 Skill catalog 的内容

`SkillRegistry` 同时实现 `SystemPromptProvider`，其固定属性为：

| 属性 | 值 | 目的 |
| --- | --- | --- |
| `id()` | `skills` | 作为 Prompt Item 身份和外层标签 |
| `scope()` | `APPLICATION` | 一个 Runtime 内只建立一次 Skill 快照 |
| `order()` | `300` | 排在身份、工作区和记忆说明之后 |

当注册表非空时，Provider 返回的内容逻辑上是：

```text
当前可用技能：
- java-code-review: Review Java code ...
- another-skill: ...
当某个技能与用户任务匹配时，必须首先调用 load_skill 加载完整指令；在此之前不要调用 todo_write、其他工具或输出文本。
```

每个目录条目只占一行。`description` 中允许存在多行 YAML 文本，但进入 catalog 前会把连续空白折叠为单个空格，防止多行描述被模型误认为多个 Skill 条目。

当没有 Skill 时，catalog 返回 `(no skills available)`，但 Provider 仍然可以提供 `<skills>` section，让模型明确知道当前没有可用 Skill。

### 8.2 父 Agent 的 Provider 顺序

父 Agent 的 `SystemPromptManager` 按以下顺序装配 Provider：

```text
identity  order=100  scope=APPLICATION
workspace order=200  scope=SESSION
memory    order=250  scope=SESSION
skills    order=300  scope=APPLICATION
```

最终 System Prompt 会被组装成带 section 边界的内容，Skill 部分的外层形式为：

```text
<skills>
当前可用技能：
...
</skills>
```

这些标签只用于组织 Prompt，不作为 XML 被程序解析。Skill catalog 的具体文本来源仍然是 `SkillRegistry.catalog()`。

### 8.3 刷新时机

`RefreshScope` 按以下顺序表示生命周期从长到短：

```text
APPLICATION → USER → SESSION → TURN → MODEL_CALL
```

刷新某一级时，`SystemPromptManager` 会刷新该级及其之后更短生命周期的 Provider。Skill 是 `APPLICATION` 级，因此当前行为是：

| 事件 | 是否重新扫描 Skill 文件 | 说明 |
| --- | --- | --- |
| Runtime 创建 | 是 | `SkillRegistry` 读取所有 Skill 并保存正文 |
| `refreshFrom(APPLICATION)` | 使用已创建的 Skill Provider | 不会再次扫描目录 |
| 新用户 Session/回合 | 否 | Skill catalog 仍使用同一快照 |
| 每次真实模型请求 | 否 | `MODEL_CALL` 刷新不会触发 APPLICATION Provider |
| 新建 Runtime | 是 | 新 Runtime 才会重新读取文件 |

`ManualAgent` 在 Session 边界刷新 Session Provider，`AgentLoop` 在一次任务开始时刷新 Turn Provider，并在每个真实模型请求中通过统一入口刷新 Model Call Provider。Skill 在首次 Application 刷新后保持不变。

### 8.4 为什么 catalog 不直接放完整正文

这是当前设计中最重要的上下文取舍：

- catalog 让模型有足够信息做“是否适用”的判断；
- 完整正文只在匹配时加载，避免无关指令占用每个请求；
- Skill 数量增加时，System Prompt 的增量主要是短描述，而不是全部正文；
- 同一个正文只在被使用的会话历史中出现，而不是在所有请求的系统区域重复出现。

代价是模型需要多执行一次工具调用，且 Skill 正文会作为工具结果受上下文压缩策略影响。这是当前以可控上下文成本换取一次调用延迟的明确取舍。

## 9. `load_skill` 工具设计

### 9.1 工具协议

模型可见的工具名称为 `load_skill`，参数只有一个：

```json
{
  "name": "java-code-review"
}
```

工具 Schema 要求 `name` 为字符串，但 Schema 只是模型生成约束，执行时仍由 `LoadSkillTool` 对实际 JSON 做运行时校验。

### 9.2 执行步骤

`LoadSkillTool.execute(input)` 的语义为：

1. 从 JSON 对象读取 `name`。
2. 要求该字段存在、是字符串且不是空白字符串。
3. 不 Trim、不转小写、不做别名或模糊匹配。
4. 调用 `skillRegistry.find(name)` 做精确查找。
5. 找不到时返回失败结果 `Error: unknown skill: <name>`。
6. 找到时返回 Skill 名称、真实 Base directory 和完整正文。

成功结果的逻辑结构为：

```text
Loaded skill: java-code-review
Base directory: <real skill directory>

<完整 SKILL.md 正文>
```

工具不接受 `path` 参数，因此模型不能借助该工具指定 `../`、任意绝对路径或未注册目录。

### 9.3 工具执行管线

虽然 `load_skill` 只进行内存查询，但它仍然作为普通 `AgentTool` 注册到父 Agent 的 `ToolRegistry`，并经过 AgentLoop 的公共调用流程：

```text
模型生成 tool_use
    → ToolCallDispatcher 判断执行模式
    → BeforeToolUse Hook
    → ToolApprovalGate
    → ToolRegistry.execute
    → AfterToolUse Hook
    → tool_result 写入消息历史
```

当前 `LoadSkillTool` 声明 `isConcurrencySafe() == true`，原因是注册表在构造完成后只读，查询不会造成共享状态冲突。默认审批策略对未列入特殊审批规则的工具返回 `NOT_REQUIRED`，所以当前默认行为不会为 `load_skill` 单独询问用户；这不改变它必须经过统一 Gate 的结构。

### 9.4 正文进入历史后的行为

AgentLoop 收到完整工具调用后，会把模型的 `assistant tool_use` 与 `user tool_result` 成对追加到会话消息历史。于是：

- 当前模型请求可以继续依据完整 Skill 正文工作；
- 后续模型请求仍可能看到该工具结果，直到上下文治理压缩或裁剪它；
- Skill 正文不会修改 `SkillRegistry`；
- Skill 正文不会改变工具 Schema 或审批策略。

如果 `load_skill` 失败，失败结果也会和原 `tool_use_id` 配对返回模型。模型可以据此修正名称或继续处理错误，而不会留下未配对的工具调用消息。

## 10. 一次完整调用的时序

下面按父 Agent 的一次用户任务描述完整路径：

```text
1. 进程启动
   Application → AgentState(agentHome, workspace, allowedRoots)
   AgentRuntime → SkillRegistry(agentHome/skills)

2. 建立模型上下文
   SkillRegistry.catalog()
       → SystemPromptManager 的 <skills> section
   ToolRegistry
       → load_skill 工具定义

3. 用户提交任务
   ManualAgent → SESSION Prompt refresh → 记忆召回
   AgentLoop   → TURN Prompt refresh

4. 发送第一次模型请求
   system = identity + workspace + memory + skills catalog
   tools  = 普通工具 + load_skill + MCP 工具

5. 模型判断 Skill 匹配
   若匹配 → tool_use(load_skill, {name: exactName})
   若不匹配 → 继续使用普通能力

6. 加载正文
   LoadSkillTool → SkillRegistry.find(exactName)
   成功 → 返回正文和 Base directory
   失败 → 返回成对的错误 tool_result

7. 模型继续工作
   Skill 只提供方法和标准
   文件读写、命令、MCP 等仍由普通工具执行

8. 任务结束
   工具结果和最终文本进入既有 AgentLoop / ManualAgent 生命周期
```

一个关键点是：Skill 加载发生在模型已经收到 catalog 之后，但不改变当前模型请求的 System Prompt；完整正文通过工具结果在下一次模型请求中可见。

## 11. 信任边界与安全设计

### 11.1 本地文件到注册表

这是 Skill 系统的第一个信任边界。只有通过以下检查的文件才能进入内存注册表：

- 根目录真实路径可解析且是目录；
- 候选项是 Skill 根目录的直接子目录；
- 候选目录真实路径没有离开根目录；
- `SKILL.md` 存在且是普通文件；
- frontmatter 结构可解析；
- `name` 和 `description` 是非空字符串；
- 名称格式和长度合法；
- `SKILL.md` 的真实父目录仍在根目录内；
- frontmatter 的名称等于候选目录名；
- 全部 Skill 名称不重复。

检查失败时直接失败，不使用默认值，不将错误内容注册成可见 Skill。

### 11.2 注册表到模型

这是第二个边界。模型只能看到：

- catalog 中的名称和描述；
- `load_skill` 工具的名称参数契约；
- 成功加载后返回的正文和 Base directory。

模型不能通过 `load_skill` 传入路径，也不能通过名称查找未在启动快照中注册的文件。

但结构校验不等于语义可信。`SKILL.md` 正文仍然是外部文件内容，当前系统不会判断其中是否存在提示注入、错误流程或危险建议。正文以工具结果进入模型上下文，不获得高于系统级指令的特殊执行权限；模型依据正文发起的真实操作仍要走普通工具管线。

### 11.3 模型到外部操作

Skill 本身不扩大外部操作权限：

- 读写文件仍由现有文件工具和 `WorkspacePathResolver` 处理；
- 命令执行仍由 `BashTool` 处理；
- MCP 调用仍由已有 MCP 工具处理；
- 审批仍由 `ToolApprovalPolicy`、`AgentState.approvalMode()` 和 `ToolApprovalGate` 决定；
- Hook 仍可以阻止、修改或记录真实工具调用。

需要特别区分两个事实：

1. Skill 根目录由 Runtime 内部读取，不通过 `allowedRoots` 交给模型文件工具。
2. `load_skill` 返回 Base directory 不会自动把该目录加入 `allowedRoots`。

因此当前设计没有把“能读 Skill 正文”扩大为“能任意操作整个 agentHome”。

## 12. 一致性不变量

以下不变量是当前设计必须保持的行为：

1. **名称唯一**：一个注册表中一个 Skill 名称最多对应一个定义。
2. **目录一致**：Skill 定义的 `name` 必须等于其父目录名称。
3. **快照稳定**：SkillRegistry 构造完成后不再修改；同一 Runtime 的所有模型请求看到同一 Skill 集合和正文。
4. **索引可加载**：catalog 中出现的名称必须可以被 `find(name)` 找到。
5. **精确查找**：名称匹配是大小写敏感的字符串相等比较。
6. **正文非空**：注册表中不存在正文为空白的 Skill。
7. **路径封闭**：Skill 目录和 `SKILL.md` 的真实路径不能离开 Skill 根目录。
8. **执行分离**：加载正文不会自动执行正文中提到的脚本或工具操作。
9. **权限不扩张**：Skill 不会改变 `allowedRoots`、审批模式或工具集合。
10. **生命周期明确**：Skill 变更只有在新建 Runtime 时才会生效；运行期间修改磁盘文件不会改变当前快照。
11. **父子边界明确**：当前只有父 Agent 暴露 Skill 能力，SubAgent 不应假设自己拥有 `load_skill`。

## 13. 失败语义

| 失败位置 | 典型原因 | 当前行为 | 设计理由 |
| --- | --- | --- | --- |
| Skill 根目录 | 不存在、不可访问、不是目录 | `SkillRegistry` 构造失败，Runtime 启动失败 | 防止带着未知能力集合运行 |
| 候选目录 | 缺少 `SKILL.md` | 注册失败 | 直接子目录的含义必须明确 |
| frontmatter | 缺少边界、YAML 无法解析、重复字段 | 注册失败 | 不把不确定元数据暴露给模型 |
| 字段校验 | 名称非法、描述过长、正文为空 | 注册失败 | 统一维护数据契约 |
| 路径校验 | 符号链接指向根目录外 | 注册失败 | 防止通过 Skill 目录间接读取任意文件 |
| 名称校验 | 目录名与 `name` 不一致 | 注册失败 | 防止路径身份和模型身份分裂 |
| 重复名称 | 多个目录声明相同名称 | 注册失败 | 避免“哪个 Skill 被加载”依赖扫描细节 |
| 工具参数 | `name` 缺失、非字符串或空白 | 返回失败 `ToolExecutionResult` | 保证 tool_use 有配对结果 |
| 运行时查找 | 名称不在启动快照中 | 返回 `Error: unknown skill` | 让模型看到明确、可修正的错误 |
| 文件运行中修改 | 磁盘内容与启动时不同 | 当前 Runtime 不受影响，新 Runtime 才重新读取 | 保持 Session 内确定性 |

系统选择“启动失败”而不是“跳过坏 Skill”，因为当前 Skill 根目录是 Agent 能力集合的一部分。静默跳过会让模型看到一个与维护者预期不同的 catalog，而且错误可能直到任务执行中才暴露。

## 14. 并发与生命周期

### 14.1 注册表并发模型

`SkillRegistry` 的可变状态只存在于构造阶段：

- 扫描过程使用局部 `LinkedHashMap`；
- 构造结束后保存不可修改 Map；
- `find()` 只读；
- `catalog()` 只读；
- `LoadSkillTool` 因此声明可并发执行。

这允许同一模型响应中的多个只读 Skill 查询进入安全并发批次，同时仍由 AgentLoop 按模型原始顺序交付工具结果。

### 14.2 Runtime 生命周期

SkillRegistry 隶属于一次 `AgentRuntime`，不是全局静态目录服务：

```text
创建 Runtime → 扫描并校验 → 父 Agent 使用快照 → Runtime 关闭
```

当前没有独立的 SkillRegistry 关闭动作，因为它不持有目录流、线程、文件监听器或外部连接；扫描阶段的 `Files.list()` 会在 try-with-resources 中关闭。

## 15. 示例：`java-code-review`

当前示例 Skill 的 frontmatter 为：

```yaml
name: java-code-review
description: Review Java code for correctness, trust-boundary violations, resource leaks, and unnecessary complexity. Use when the user asks to review Java source code, a Java diff, or a Java implementation.
```

用户输入“请评审这段 Java 代码”时，模型第一次请求只会看到类似目录项：

```text
- java-code-review: Review Java code for correctness, trust-boundary violations, resource leaks, and unnecessary complexity. Use when the user asks to review Java source code, a Java diff, or a Java implementation.
```

模型判断匹配后调用：

```json
{
  "name": "java-code-review"
}
```

加载结果包含完整评审顺序和输出要求。模型随后读取用户指定文件、相关调用链，必要时调用 `read_file` 或 `glob`，最后依照 Skill 中的 P0-P3、证据和最小修复方向要求输出。读取代码和其他实际操作不由 Skill 直接完成。

## 16. 测试与验收

### 16.1 当前已有验证

`AgentHomeResourcePathTest` 已覆盖当前路径归属中的关键行为：

- `agentHome/skills` 中的 Skill 可以被注册并通过 `load_skill` 加载；
- 仅存在于 `workspace/skills` 的 Skill 不会进入注册表；

该测试使用 `@TempDir` 创建相互独立的 `workspace` 和 `agentHome`，不依赖真实用户目录。

### 16.2 Skill 系统应持续验证的场景

后续维护或修改 Skill 系统时，至少应覆盖：

1. 正常 frontmatter 可以解析，正文完整保留。
2. 缺少 frontmatter、缺少 `name`、缺少 `description`、正文为空时启动失败。

9. catalog 顺序稳定，描述中的换行不会制造额外条目。
10. `load_skill` 的空参数、错误类型、未知名称都返回失败结果。
11. `load_skill` 成功结果包含正确名称、Base directory 和完整正文。
12. Runtime 创建后修改磁盘上的 `SKILL.md` 不影响当前注册表。
13. 父 Agent 有 Skill 能力，SubAgent 不会意外出现 `load_skill`。
14. 加载 Skill 不会直接执行脚本、修改文件或改变 `allowedRoots`。

### 16.3 验收判断

可以用以下问题判断实现是否仍符合本设计：

- 模型是否先看到轻量 catalog，再按需加载正文？
- 是否只能用注册名称加载，而不能传文件路径？
- 一个 Runtime 内 Skill 集合是否稳定？
- 是否每个 Skill 都必须满足目录、文件、YAML、字段和重复名称契约？
- Skill 正文是否仍然只是模型上下文，不是可执行代码？
- Skill 触发的实际文件、终端和 MCP 操作是否仍走原有工具管线？
- `agentHome` 与 `workspace` 的职责是否仍然分离？
- SubAgent 是否没有被无意中授予父 Agent 的 Skill 工具？

## 17. 设计决策与取舍

### 17.1 为什么使用 `SKILL.md` 而不是 Java 类

Skill 的主要产物是给模型阅读的自然语言流程和输出规范。使用 Markdown 可以让维护者直接修改说明，不需要重新编译 Runtime，也不把每一种领域流程都变成 Java 扩展点。执行能力仍由稳定的 Java 工具提供，职责清晰。

### 17.2 为什么启动时一次性扫描

一次性扫描让以下事实在 Session 内保持稳定：

- catalog 不会突然新增或消失；
- 已加载正文不会在同一任务中被磁盘修改悄悄替换；
- 目录、名称、重复项错误在启动阶段暴露；
- Registry 可以简单地使用不可修改 Map，不需要同步、缓存失效和监听器。

代价是编辑 `SKILL.md` 后必须创建新的 Runtime 才能生效。当前项目优先选择可解释性和实现简单性。

### 17.3 为什么名称查找优于路径查找

名称查找把模型可控输入限制在已经注册的能力集合内。路径查找虽然看起来更直接，但会把符号链接、相对路径、绝对路径、目录越界和任意文件读取问题带入模型调用协议。路径解析集中放在启动扫描阶段，工具运行时只做内存键查找，边界更小。

### 17.4 为什么不在失败时跳过单个 Skill

当前 catalog 代表“本次 Agent 实际拥有的能力”。如果某个维护者写坏了 Skill，系统继续启动但悄悄少一项能力，会把配置错误伪装成模型选择问题。失败即停止更符合当前简单、确定的启动模型。

### 17.5 为什么 Skill 不拥有自己的权限系统

Skill 只是方法说明，真正产生效果的是已有工具。再给 Skill 增加独立权限系统会产生两套安全语义：一套在 Skill 层，一套在工具层，容易出现“Skill 允许但工具拒绝”或相反的理解。当前把权限集中在普通工具管线，Skill 只描述应该做什么。

### 17.6 为什么不把 `agentHome` 自动放入 `allowedRoots`

Skill 由 Runtime 内部注册表读取，并不需要通过模型文件工具暴露整个 Agent 自身目录。将 `agentHome` 自动加入 `allowedRoots` 会把内部资源、日志、缓存和其他未来内容一并扩大为模型可操作范围。当前只把 Skill 的读取能力留在内部，保持 Agent 自身资源与工作区权限边界分离。
