# Subagent 设计

## 1. 文档定位

本文档记录 `manual-agent` 当前已经确定并落地的 Subagent 设计。它描述系统“现在应该是什么样”、各组件之间的职责边界、关键生命周期和必须保持的不变量。

本文档不是执行文档，不规定某一次修改需要删除哪几行代码或新增哪一个方法。后续如果设计发生变化，应新增带时间戳的完整设计版本，并在设计主题形成目录后维护对应的变更记录。

当前设计基线：

- 项目：`learn-claude-code/demo/manual-agent`；
- 设计版本：2026-09-02；
- Subagent 入口：父 Agent 暴露的 `task` 工具；
- 当前执行语义：同步委派、独立上下文、单次返回最终文本；
- 当前实现边界：Subagent 是一个隔离的子 `AgentLoop`，不是独立 CLI 会话，也不是持久化任务调度器。

## 2. 设计结论摘要

当前 Subagent 采用“父 Agent 通过工具同步调用子 AgentLoop”的最小实现：

```text
用户
  │
  ▼
ManualAgent
  │ 持有父会话历史
  ▼
父 AgentLoop
  │ 模型生成 task(description)
  ▼
TaskTool
  │ 只转发 description，不复制父历史
  ▼
子 AgentLoop
  │ 使用全新的消息历史完成子任务
  ▼
子 Agent 最终文本
  │
  ▼
TaskTool tool_result
  │
  ▼
父 AgentLoop 继续推理
  │
  ▼
父 Agent 最终回答
```

核心原则如下：

1. 子 Agent 的上下文与父 Agent 隔离；父历史不自动进入子 Agent，子历史也不回写父历史。
2. 父子 Agent 共享同一次 Session 的工作区、路径上下文、审批状态、模型客户端和上下文治理组件。
3. 子 Agent 使用独立的工具注册表，只暴露完成子任务所需的文件和 Bash 工具，不暴露 `task`、长期记忆、持久化任务、Todo、Skill 或 MCP 工具。
4. `task` 当前是同步工具。父 Agent 必须等待子 Agent 完成，才能得到对应的 `tool_result` 并继续自己的模型轮次。
5. 子 Agent 的中间输出保持终端静默，只有 `TaskTool` 的启动/结束标记和子 Agent 的最终结论对父流程可见。
6. 子 Agent 可以对共享工作区产生真实副作用；当前没有为子 Agent 创建独立 worktree、临时文件系统或事务回滚层。
7. Subagent、持久化项目任务和后台 Bash 命令是三个不同概念，不能通过名称相似而互相替代。

## 3. 需要解决的问题

父 Agent 适合理解用户目标、拆解工作、综合多个结果，但一个复杂任务中的某些局部工作具有以下特点：

- 需要单独阅读较多代码或资料；
- 目标边界相对清晰，可以独立完成；
- 中间推理和工具结果没有必要长期占用父 Agent 的上下文窗口；
- 结果只需要以结论、检查报告或局部实现结果的形式返回；
- 父 Agent 仍然需要掌握最终控制权，决定是否采纳子 Agent 的结果。

如果把所有局部工作都放进父历史，会带来三个直接问题：

1. 父上下文会混入大量与当前综合决策无关的中间过程。
2. 父 Agent 很难区分“自己已经确认的事实”和“某个局部探索过程中的临时结论”。
3. 一个子任务失败或输出过长时，错误影响范围会扩大到整个父会话。

Subagent 的目标不是让多个 Agent 自由协商，而是提供一个受父 Agent 控制的、边界清晰的局部执行单元。

## 4. 概念定义

### 4.1 父 Agent

父 Agent 是面向用户的主执行者，由两个层次组成：

- `ManualAgent`：持有跨用户回合持续存在的父会话历史，负责用户回合外层编排、记忆召回和回合结束后的记忆处理；
- 父 `AgentLoop`：负责模型调用、流式响应解析、工具调度、工具结果提交、上下文治理和停止判断。

父 Agent 拥有完整的模型能力，是唯一直接承接用户输入并生成最终用户可见结论的 Agent。

### 4.2 子 Agent / Subagent

Subagent 是由父 Agent 调用 `task` 工具后进入的一个子 `AgentLoop` 实例。它具有以下特征：

- 有独立的一次性消息历史；
- 有独立的子 Agent 身份提示；
- 有独立的工具注册表和 Hook 注册表；
- 没有 `ManualAgent` 外层，不持有跨回合会话历史；
- 不直接接收用户回合，不触发父级 `UserPromptSubmit` 流程；
- 完成后只返回一段最终文本给 `TaskTool`；
- 不能继续通过 `task` 工具递归委派。

这里的“独立”指执行上下文和能力边界独立，不代表进程、工作区、API 客户端或 Session 状态独立。

### 4.3 `task` 工具

`task` 是父 Agent 暴露给模型的同步委派工具。它的输入只有一个必填字段：

```json
{
  "description": "A complete description of the subtask. Include all context the subagent needs."
}
```

它负责：

1. 校验委派描述；
2. 为当前调用创建一份新的子消息历史；
3. 调用预先装配好的子 `AgentLoop`；
4. 等待子 Agent 返回最终文本；
5. 将该文本包装成父 Agent 可以消费的工具结果。

它不负责：

- 分析任务依赖；
- 为子任务创建持久化记录；
- 分配独立工作区；
- 解析子 Agent 的文本并重新判断成功或失败；
- 把子 Agent 的中间消息复制到父历史；
- 创建异步通知或后台回调。

### 4.4 持久化任务系统

`create_task`、`list_tasks`、`get_task`、`claim_task`、`complete_task` 组成的是项目任务状态系统。它们把任务保存为工作区 `.tasks/*.json`，支持依赖、认领和完成状态。

这个系统和 Subagent 的关系是“可以由父 Agent 分别使用”，但二者不是同一个对象：

| 项目 | Subagent `task` | 持久化任务系统 |
| --- | --- | --- |
| 目的 | 立即委派一段局部工作 | 记录跨会话项目任务 |
| 生命周期 | 一次工具调用内完成 | 保存在 `.tasks/*.json` 中 |
| 结果 | 子 Agent 最终文本 | 任务状态和依赖状态 |
| 执行者 | 预先装配的子 `AgentLoop` | 由主 Agent 按 owner 认领完成 |
| 是否进入子 Agent 工具表 | 不适用，子 Agent 不暴露 `task` | 不暴露给子 Agent |
| 是否自动创建 | 不创建持久化任务 | 只有模型明确调用任务工具才创建 |

子 Agent 不应通过 `task` 代替项目任务记录，也不应自行伪造持久化任务状态。

### 4.5 后台 Bash 任务

`bash` 的 `run_in_background=true` 是工具内部的异步命令执行语义。它表示 Bash 命令先返回后台任务 ID，真实进程继续执行，完成结果稍后由所属 `AgentLoop` 的后台任务 Hook 交付给该 Agent。

它不是 Subagent：

- 后台 Bash 没有自己的模型推理循环；
- 后台 Bash 不拥有独立提示词或消息历史；
- 后台 Bash 结果只回到发起它的 AgentLoop；
- 子 Agent 发起的后台 Bash 只进入子 Agent 的后台队列，不会直接进入父 Agent 的后台队列。

## 5. 总体架构

### 5.1 运行时对象关系

一次 CLI Session 的核心对象关系如下：

```text
AgentRuntime
├── AgentState                         Session 唯一状态
├── AnthropicClient                    父子共享
├── ContextManager                     父子共享，实现上下文治理
├── ToolApprovalGate                   父子共享，读取 AgentState 当前审批模式
├── ModelRequestRecoveryManager        父子共享恢复规则
│
├── 父侧
│   ├── ManualAgent
│   │   └── parentHistory
│   ├── parent AgentLoop
│   ├── parent ToolRegistry
│   ├── parent HookRegistry
│   ├── parent SystemPromptManager
│   ├── parent StreamOutputPrinter
│   └── parent BackgroundTaskScheduler
│
└── 子侧
    ├── TaskTool ────────────────┐
    ├── subagent AgentLoop       │
    ├── subagent ToolRegistry    │
    ├── subagent HookRegistry    │
    ├── subagent SystemPromptManager
    ├── subagent StreamOutputPrinter
    └── subagent BackgroundTaskScheduler
                                  │
                                  └── TaskTool 持有子 AgentLoop 引用
```

`TaskTool` 注册在父 `ToolRegistry` 中。子 `ToolRegistry` 不注册 `TaskTool`，因此依赖对象图本身就阻断了子 Agent 继续委派的路径。

### 5.2 组件职责分层

| 组件 | 在 Subagent 设计中的职责 |
| --- | --- |
| `AgentRuntime` | 一次性装配父子 Agent 所需的共享对象和独立对象，并负责关闭资源 |
| `ManualAgent` | 只负责父用户会话；子 Agent 不经过此层 |
| `AgentLoop` | 父子共用的模型/工具执行循环，具体行为由注入的注册表、Hook 和 Prompt 决定 |
| `TaskTool` | 把父模型的委派描述转换为一次子 `AgentLoop.run()` 调用 |
| `ToolRegistry` | 通过父子不同实例实施能力白名单 |
| `HookRegistry` | 通过父子不同实例实施生命周期行为差异 |
| `SystemPromptManager` | 通过父子不同 Provider 集合实施身份和能力说明差异 |
| `AgentState` | 保存父子共享的 Session 语义、审批策略和路径上下文 |
| `ToolApprovalGate` | 在父子工具真正执行前使用同一份动态审批策略 |
| `StreamOutputPrinter` | 父侧显示实时过程，子侧丢弃中间输出 |
| `BackgroundTaskScheduler` | 为每个 AgentLoop 保存独立后台任务状态和完成通知 |
| `ContextManager` | 对传入的当前消息列表执行上下文治理；不持有父子 history |

## 6. 父子能力矩阵

### 6.1 工具能力

当前父子工具能力如下：

| 能力 | 父 Agent | 子 Agent | 设计理由 |
| --- | --- | --- | --- |
| `bash` | 有 | 有 | 子任务可能需要运行测试、检查命令或构建命令 |
| `read_file` | 有 | 有 | 子任务需要自行读取工作区事实 |
| `write_file` | 有 | 有 | 子任务可以直接完成被委派的文件修改 |
| `edit_file` | 有 | 有 | 子任务可以进行精确文件编辑 |
| `glob` | 有 | 有 | 子任务可以搜索工作区文件 |
| `todo_write` | 有 | 无 | Todo 属于父 Agent 的用户任务进度，不让子任务污染父进度 |
| `create_task` | 有 | 无 | 持久化项目任务由父 Agent 统一编排 |
| `list_tasks` | 有 | 无 | 避免子 Agent 把持久化任务系统当成自己的协作协议 |
| `get_task` | 有 | 无 | 同上 |
| `claim_task` | 有 | 无 | owner 语义只绑定父 Agent |
| `complete_task` | 有 | 无 | 子 Agent 不拥有父级持久化任务 |
| `load_skill` | 有 | 无 | Skill 选择由父 Agent 控制，避免子任务任意扩大提示上下文 |
| `task` | 有 | 无 | 阻止递归委派和任务树无限增长 |
| Git MCP | 按当前仓库配置有 | 无 | 当前子任务使用 Bash 或文件工具完成，不直接开放 MCP 能力 |
| GitHub MCP | 有 | 无 | 外部服务能力和用户级协作动作保留在父 Agent |

子 Agent 的能力不是“父 Agent 的权限复制品”，而是面向局部工作所需的最小当前白名单。

### 6.2 共享对象与独立对象

| 对象 | 共享/独立 | 说明 |
| --- | --- | --- |
| `AgentState` | 共享 | 父子读取同一份 Session 状态，审批模式修改可以立即影响后续子工具调用 |
| `AnthropicClient` | 共享 | 使用同一个 Provider 客户端和模型配置 |
| 模型标识 | 共享配置 | 当前为 `qwen3.5-flash` |
| `ContextManager` | 共享实例 | 组件本身不持有 history，实际处理的列表仍由各 Agent 独立提供 |
| `ToolApprovalGate` | 共享实例 | ASK 模式共享 Scanner，实际读取部分由 Gate 串行化 |
| `ModelRequestRecoveryManager` | 共享实例 | 恢复 Handler 是无会话历史的规则集合，每次 `run()` 有自己的恢复状态 |
| 文件工具 | 当前共享实例 | 父子使用相同工作区和路径边界；调用输入仍在各自工具管线中处理 |
| `BashTool` | 独立实例 | 每个实例绑定自己的后台调度器和运行进程集合 |
| `BackgroundTaskScheduler` | 独立实例 | 父子不能直接消费对方的后台完成队列 |
| `ToolRegistry` | 独立实例 | 子侧通过白名单阻止访问父级能力 |
| `HookRegistry` | 独立实例 | 父子生命周期行为不同 |
| `SystemPromptManager` | 独立实例 | 父子身份和能力说明不同 |
| `StreamOutputPrinter` | 独立实例 | 父侧写入终端，子侧使用静默输出流 |
| `ManualAgent` | 仅父侧 | 维护面向用户的跨回合 history、Memory 和用户 Hook |
| `MemoryRuntime` | 仅父侧 | 子 Agent 不召回或保存长期记忆 |
| `TodoState` | 仅父侧 | 子 Agent 不写父级 Todo |
| `TaskStore` | 仅父侧工具使用 | 子 Agent 不直接读写 `.tasks/` 任务状态 |

## 7. 子 Agent 的装配设计

### 7.1 装配顺序

父子 Agent 的装配必须先建立子循环，再把子循环包装进父侧 `TaskTool`。逻辑顺序为：

```text
1. 建立一次 Session 的 AgentState
2. 建立共享路径解析器、客户端、上下文治理和审批 Gate
3. 建立父侧与子侧各自的 BackgroundTaskScheduler
4. 建立父 BashTool 与子 BashTool
5. 建立共享文件工具
6. 建立父 ToolRegistry，注册父侧完整能力
7. 建立子 ToolRegistry，只注册 bash/read/write/edit/glob
8. 建立父子 HookRegistry
9. 建立父子 StreamOutputPrinter
10. 建立父子 SystemPromptManager
11. 创建 subagent AgentLoop
12. 创建 TaskTool(subagentLoop)，注册到父 ToolRegistry
13. 创建 parent AgentLoop
14. 创建只面向用户的 ManualAgent
```

这个顺序体现了一个重要依赖关系：

```text
subagentLoop
    ↓
TaskTool
    ↓
parent ToolRegistry
    ↓
parent AgentLoop
```

子循环不能依赖父 `TaskTool`，否则会形成递归委派路径。

### 7.2 预先装配而不是每次动态装配

当前 `TaskTool` 持有一个预先创建好的子 `AgentLoop`，调用时只创建新的消息列表。这种安排有三个目的：

1. 保持 Runtime 的资源所有权清晰。客户端、工具、Hook 和调度器在 Session 创建时完成装配，并在 Runtime 关闭时统一释放。
2. 让父子能力白名单在启动时固定，避免模型通过输入改变子 Agent 的工具集合。
3. 复用已经验证过的 `AgentLoop` 逻辑，父子只通过注入的组件不同来形成行为差异。

预先装配不等于复用子会话历史。子 `AgentLoop` 本身不持有会话历史；每次 `TaskTool.execute()` 都会构造新的 `subagentMessages`。

### 7.3 子循环配置

当前子 Agent 的核心配置为：

- 使用共享 `AnthropicClient`；
- 使用与父 Agent 相同的模型标识；
- 使用子 Agent 专用 `SystemPromptManager`；
- 使用子 Agent 专用 `ToolRegistry` 和 `HookRegistry`；
- 使用共享 `ToolApprovalGate`；
- 使用共享 `ContextManager`；
- 使用静默 `StreamOutputPrinter`；
- 使用子 Agent 专用 `BackgroundTaskScheduler`；
- 最大业务模型轮次为 30；
- 不创建 `ManualAgent`。

父 Agent 当前最大业务模型轮次为 100。父子轮次上限分别属于各自的 `AgentLoop`，子循环耗尽不会直接改变父循环的轮次计数。

## 8. 调用生命周期

### 8.1 父模型生成委派

父 Agent 在一次模型响应中生成类似下面的完整工具调用：

```json
{
  "name": "task",
  "input": {
    "description": "检查认证模块的异常处理，运行相关测试，并返回发现的问题和修改建议。"
  }
}
```

模型不传入 `owner`、工作区路径、审批模式或工具列表。这些内容由应用装配和运行时状态决定，避免模型通过参数伪造执行身份或扩大能力边界。

### 8.2 工具调用进入父执行管线

父 `AgentLoop` 只在模型流收到完整工具块后执行工具。`TaskTool` 与其他工具一样经过父 Agent 的公共工具管线：

```text
完整 tool_use
  ↓
父 BeforeToolUse Hook
  ↓
共享 ToolApprovalGate
  ↓
父 ToolRegistry.execute(task)
  ↓
父 AfterToolUse Hook
  ↓
父 tool_result
```

当前默认审批策略中，`task` 本身不需要用户审批；但子 Agent 真实执行的 `bash`、外部文件写入或 MCP 工具如果存在于其工具白名单中，仍然必须在执行前经过同一个审批 Gate。当前子 Agent 没有 MCP 工具，因此子流程不会产生 MCP 审批调用。

### 8.3 `TaskTool` 输入校验

`TaskTool` 在进入子 Agent 可信执行边界前校验 `description`：

- 字段必须存在；
- 字段必须是字符串；
- 字符串不能是空白内容。

校验失败时不创建子消息、不调用模型，直接返回失败的 `ToolExecutionResult`，让父 Agent 得到与原始 `tool_use` 配对的错误结果。

委派描述是子 Agent 唯一自动接收的父侧业务上下文。因此父模型必须在描述中明确提供：

- 子任务目标；
- 必要的文件、模块或范围；
- 已知约束和验收标准；
- 需要返回给父 Agent 的结论格式；
- 哪些动作属于允许范围，哪些动作不应执行。

系统不会自动把父历史、父模型上一轮思考或父侧工具结果拼接进去。

### 8.4 创建子历史

输入校验通过后，`TaskTool` 创建新的 `ArrayList<MessageParam>`，并只加入一条 user 消息：

```text
subagentMessages = [
    user(description)
]
```

这一步是上下文隔离的实际边界：

- 不复制父 `ManualAgent.history`；
- 不复制父模型的 assistant 消息；
- 不复制父工具调用和工具结果；
- 不复制父侧长期记忆召回文本；
- 不复制父侧 Todo、持久化任务列表或 Skill 内容。

子 Agent 需要的背景信息必须由父模型写入 `description`，或由子 Agent 自己通过当前工具读取工作区事实。

### 8.5 子 Agent 运行

`TaskTool` 调用：

```java
subagentLoop.run(subagentMessages, "")
```

第二个参数是空的临时回合上下文，表示当前没有额外的父级记忆召回内容。子 Agent 之后按照普通 `AgentLoop` 流程运行：

```text
子 AgentLoop.run()
  ↓
刷新 TURN 级 System Prompt
  ↓
BeforeModelCall Hook
  ↓
上下文裁剪/工具结果治理
  ↓
模型流式请求
  ↓
解析文本和完整工具调用
  ↓
执行子侧白名单工具
  ↓
提交 tool_use/tool_result 历史
  ↓
继续模型轮次
  ↓
没有工具调用时触发 Stop Hook
  ↓
结束并返回最终文本
```

子 Agent 的中间消息保留在 `subagentMessages` 中，只用于当前子循环的后续模型请求。`run()` 返回后，这份列表不被父 Agent 保存，也不进入父 `ManualAgent.history`。

### 8.6 子结果返回父侧

子 Agent 正常结束后，`TaskTool` 把返回的 `String conclusion` 包装成成功的 `ToolExecutionResult`。父 Agent 随后把它作为 `task` 对应的 `tool_result` 加入自己的消息历史：

```text
父 assistant: tool_use(task, description)
父 user:      tool_result(task, conclusion)
```

父 Agent 会再次请求模型，由父模型决定如何使用结论。子 Agent 的文字不是最终用户回答，除非父模型在后续综合中选择直接采用它。

### 8.7 父流程继续

父 Agent 收到子工具结果后可以：

- 继续调用其他工具；
- 验证子 Agent 修改的文件；
- 要求另一个独立子任务；
- 综合子 Agent 的结论回答用户；
- 在子结果包含问题时修正或拒绝该结果。

子 Agent 不拥有父流程控制权。它不能直接结束父 Agent，也不能直接把文本发送给用户。

## 9. 上下文隔离设计

### 9.1 隔离的内容

以下内容不从父 Agent 自动复制到子 Agent：

| 内容 | 是否复制 | 说明 |
| --- | --- | --- |
| 用户原始历史 | 否 | 子 Agent 只看到委派描述 |
| 父 assistant 思考和正文 | 否 | 避免把父推理当成子任务事实 |
| 父工具调用 | 否 | 子 Agent 需要时自行检查工作区 |
| 父工具结果 | 否 | 防止历史和大结果直接占用子上下文 |
| 父长期记忆召回 | 否 | 子 Agent 不使用 MemoryRuntime |
| 父 Todo 状态 | 否 | 子 Agent 不注册 Todo 工具 |
| 父持久化任务列表 | 否 | 子 Agent 不注册任务工具 |
| 父 Skill 内容 | 否 | 子 Agent 不注册 LoadSkillTool |
| 父 MCP 工具结果 | 否 | 子 Agent 没有 MCP 工具 |
| `description` | 是 | 唯一的显式父到子业务上下文 |
| `AgentState` 路径和审批状态 | 是，共享引用 | 它们是 Session 环境，不是会话历史 |

### 9.2 共享工作区不等于共享历史

父子 Agent 在同一个 workspace 中运行，子 Agent 的文件修改、Bash 命令和构建结果是真实的共享副作用。父 Agent 可以在子 Agent 返回后通过工具读取这些变化。

但是，工作区共享不代表消息历史共享：

```text
共享：文件、Bash 工作目录、路径策略、Git 根目录、审批模式
隔离：父/子消息列表、身份 Prompt、工具白名单、Hook 集合、终端输出、后台任务队列
```

这个选择把“协作媒介”放在工作区和最终文本中，而不是放在彼此的完整上下文中。

### 9.3 ContextManager 的位置

父子 `AgentLoop` 共享同一个 `ContextManager`，但 `ContextManager` 不持有会话历史。每次调用时，它只接收当前 Agent 提供的消息列表并返回治理后的列表。

因此：

- 父侧上下文裁剪只作用于父消息列表；
- 子侧上下文裁剪只作用于子消息列表；
- 共享 Manager 不会自动把父消息带入子 Agent；
- 大工具结果的落盘目录属于共享 Session 资源，子 Agent 产生的结果文件可能被父 Agent 后续读取。

共享 Manager 的价值是维持父子一致的上下文预算、工具结果压缩和异常语义；历史隔离仍由调用方持有的消息列表保证。

### 9.4 结果隔离与事实边界

子 Agent 返回的是文本结论，不是父历史的增量补丁。父 Agent 必须把该结论视为“委派结果”，而不是自动可信的系统事实。父 Agent 仍负责：

- 结合任务目标检查结论是否完整；
- 对重要修改重新读取文件或运行验证命令；
- 识别子 Agent 是否误解了委派描述；
- 处理子 Agent 返回的失败提示或不确定结论。

当前实现没有额外的结构化事实协议，也没有自动对结论做语义验证。

## 10. System Prompt 设计

### 10.1 父 Agent 身份

父 Agent 的身份 Provider 当前表达通用职责：

```text
你是一个编程智能体。请使用当前可用的能力完成用户任务。
```

父 Prompt 还可以包含 workspace、Memory 和 Skill 等父侧能力说明。

### 10.2 子 Agent 身份

子 Agent 的身份 Provider 当前表达三层约束：

```text
你是一个编程子智能体。
只完成交给你的子任务，必要时使用当前可用的工具，返回简洁且基于事实的结论。
不要尝试继续委派任务。
```

这段身份说明与工具白名单共同构成子 Agent 的行为边界：

- Prompt 层告诉模型不要继续委派；
- Registry 层让 `task` 不存在，形成执行层硬边界；
- 结果层只把最终文本交回父 Agent。

Prompt 不能替代工具白名单。即使模型忽略“不要继续委派”，没有注册 `task` 仍然不能执行递归委派。

### 10.3 子 Agent 的 workspace 说明

子 Agent 使用 workspace Provider，能够知道当前工作目录和 Git 仓库根目录。这使子 Agent 可以在不复制父历史的情况下，通过工具定位当前项目。

但 workspace 说明不等于 MCP 能力授权：子 Agent 当前看得到 Git 根目录文本，却没有 Git/GitHub MCP 工具。

### 10.4 子 Agent 不使用 Memory

长期记忆只挂在父 `ManualAgent` 的外层流程中：

```text
父用户输入
  ↓
MemoryRuntime.recall()
  ↓
父 AgentLoop.run()
  ↓
MemoryRuntime.completeTurn()
```

子 Agent 直接进入 `AgentLoop.run()`，没有 `MemoryRuntime.recall()` 和 `completeTurn()`。这样做是为了避免：

- 子任务读取与用户长期目标无关的记忆；
- 子任务中间结论被误保存为用户长期记忆；
- 同一次父回合因多个子任务重复触发记忆提取；
- 子任务之间通过长期记忆产生隐式耦合。

## 11. 权限与安全边界

### 11.1 共享审批 Gate

父 Agent 和子 Agent 使用同一个 `ToolApprovalGate`。Gate 每次审批都从共享 `AgentState` 读取当前 `approvalMode`，而不是在创建时保存一个不可变快照。

因此，Session 运行期间如果审批模式发生变化，后续父子工具调用都读取新模式：

```text
AgentState.approvalMode
       ▲
       │ 每次 approve() 读取
       │
ToolApprovalGate
       ├── 父 Agent 工具
       └── 子 Agent 工具
```

在 `ASK` 模式下，父子共享同一个 Scanner。Gate 只对实际读取用户输入的 `askUser()` 部分加锁，防止并发工具同时消费同一行终端输入。

### 11.2 `task` 自身与子工具的审批不同

当前默认策略中，`task` 不属于需要审批的工具，因此父 Agent 委派本身不会弹出二次确认。

但子 Agent 执行工具时仍逐个经过共享 Gate：

```text
父 task 调用
  └── TaskTool（当前不需要单独审批）
       └── 子 bash/write/edit 等真实工具
            └── 共享审批 Gate
```

因此“允许父 Agent 委派”不等于“预先批准子 Agent 的所有副作用”。每一个需要审批的子工具仍遵循当前 Session 的审批规则。

### 11.3 文件工具与 Bash 的边界

父子文件工具共享 `WorkspacePathResolver` 和 `AgentState.allowedRoots`，Java 文件工具的路径边界由解析器负责。

当前 Bash 工具执行的是工作区中的真实 `bash.exe` 命令。`allowedRoots` 不是 Bash 的操作系统沙盒，也不通过解析命令文本实现完整的 shell 隔离。实际环境安全边界来自应用当前的宿主环境、审批策略以及在非交互执行时使用的隔离运行环境。

设计文档不能把“子 Agent 工具列表较小”表述成“子 Agent 已拥有操作系统级沙盒”。当前 Subagent 设计只解决应用层能力白名单和会话上下文隔离。

### 11.4 共享工作区的副作用

子 Agent 可以修改父 Agent 之后要使用的同一份代码。当前不提供：

- 子 Agent 专用 worktree；
- 文件锁或路径级冲突协调；
- 修改事务；
- 自动 diff 审核；
- 子任务失败时的自动回滚。

因此父模型在委派描述中必须明确子任务的写入范围，并在收到结果后负责验证。

## 12. 输出与可见性

### 12.1 终端输出策略

父 Agent 使用写入 `System.out` 的 `StreamOutputPrinter`，用于显示：

- 父模型 thinking；
- 父模型正文；
- 父工具调用；
- 父工具结果；
- 父侧本地诊断。

子 Agent 使用 `StreamOutputPrinter.silentTerminal()`，因此以下内容不会直接进入父终端：

- 子模型 thinking；
- 子模型正文增量；
- 子 Agent 的工具调用展示；
- 子 Agent 的工具结果展示；
- 子 Agent 的 Trace ID 本地输出。

这不是把子 Agent 的输出丢弃：这些内容仍参与子模型的消息历史和子 Agent 的 Trace，只是没有直接写入用户终端。

### 12.2 委派边界标记

`TaskTool` 当前会在同步调用前后直接输出：

```text
[Subagent spawned]
[Subagent done]
```

这两个标记用于让用户知道父 Agent 正在进入和离开一个子任务边界。它们属于本地 stdout 输出，不是模型消息，也不是 `StreamOutputPrinter` 的工具结果协议。

在交互模式下，父终端和这些标记会进入同一次 terminal transcript；子 Agent 的静默中间流不会制造额外终端噪声。

### 12.3 父侧工具结果

子 Agent 的最终结论会作为父侧 `task` 工具结果进入正常工具结果展示和模型上下文。父终端看到的是父侧工具结果，而不是子 Agent 的完整中间历史。

终端展示的工具结果预览限制只影响展示，不修改传给父模型的完整工具结果。上下文预算治理仍由 `ContextManager` 单独处理。

## 13. 同步、并发与顺序

### 13.1 为什么当前是同步委派

同步语义使 `task` 具有简单且可推理的契约：

```text
task 工具调用开始
  ↓
父 Agent 等待
  ↓
子 Agent 完成全部模型/工具轮次
  ↓
返回一个 task tool_result
  ↓
父 Agent 继续模型请求
```

它避免当前版本必须同时解决以下问题：

- 子 Agent 结果如何异步通知父 Agent；
- 父 Agent 是否可以在子结果到达前最终回答；
- 子 Agent 生命周期由谁持有；
- 用户如何取消子 Agent；
- 子 Agent 结果是否需要持久化；
- 父会话重启后如何恢复未完成子任务。

同步是当前设计的明确选择，不是遗漏了异步接口。

### 13.2 `TaskTool` 的前台独占属性

`TaskTool` 沿用 `AgentTool.isConcurrencySafe()` 的默认值 `false`，因此在一个模型响应内，它被前台 `ToolExecutionScheduler` 视为独占工具。

这意味着：

- 它不会与同一前台安全批次的工具并行进入执行管线；
- 它会建立前台独占顺序边界；
- 同一响应中的多个 `task` 调用不会并行执行；
- 父 Agent 不会同时复用同一个子 `AgentLoop` 处理多个并行 `task` 调用。

典型顺序如下：

```text
父模型响应中的工具调用：A、task-1、task-2、B

A          ──前台安全批次──┐
                            ├─ task-1 完成
task-1     ──独占边界───────┘
                            ├─ task-2 完成
task-2     ──独占边界───────┘
B          ──后续工具───────┘
```

模型输出顺序与工具结果收集顺序仍保持一致。即使某些前台安全工具并发执行，父消息中的 `tool_result` 也按原始 `tool_use` 顺序配对。

### 13.3 与后台 Bash 的关系

后台 Bash 不进入前台 `ToolExecutionScheduler`。因此父模型同一响应中如果同时生成一个 `run_in_background=true` 的 Bash 和一个 `task`：

- 后台 Bash 进入父侧后台调度器；
- `task` 进入父侧前台独占调度器；
- 二者的真实执行生命周期可以重叠；
- 子 Agent 不会自动收到父后台 Bash 的完成通知。

如果子 Agent 自己启动后台 Bash，后台任务只归属于子侧 `BackgroundTaskScheduler`。子 Agent 在准备结束前会由自己的 `BackgroundTaskHook` 等待并读取结果，因此父 Agent 最终只看到子 Agent 综合后的文本。

### 13.4 当前并发不变量

当前设计依赖以下不变量：

1. 正常父流程不会并发调用同一个 `TaskTool` 绑定的子 `AgentLoop`。
2. 一个 `TaskTool.execute()` 在子 `AgentLoop.run()` 返回前不会返回。
3. 父 Agent 只有在收到子 `task` 结果后才能基于该结果继续下一次模型请求。
4. 父子后台任务队列分别由各自 Hook 消费。
5. 共享审批 Scanner 的读取由 Gate 串行化。

如果未来要允许多个并行 Subagent，不能只把 `TaskTool` 标记为并发安全；还需要重新设计子循环实例复用、结果关联、审批交互、资源限额和并发写入冲突。

## 14. 错误与终止语义

### 14.1 输入错误

委派描述不合法时，错误在 `TaskTool` 边界转换为失败工具结果：

```text
父 tool_use(task)
  ↓
TaskTool 校验失败
  ↓
ToolExecutionResult(error=true)
  ↓
父 tool_result(is_error=true)
```

子 Agent 不会被创建一次模型请求。

### 14.2 子 Agent 正常返回

当子 Agent 得到没有工具调用的最终模型响应，并且 Stop Hook 允许停止时，`AgentLoop.run()` 返回累积的最终文本。`TaskTool` 将该文本作为成功工具结果返回。

### 14.3 子 Agent 达到轮次或续写限制

当前 `AgentLoop.run()` 的正常接口返回类型仍是 `String`。当子 Agent 达到最大模型轮次，或输出续写次数耗尽时，循环会返回包含错误信息的文本。

当前 `TaskTool` 不解析这个字符串来重新构造结构化失败状态，而是把 `run()` 返回值作为成功工具结果传回父 Agent。这个行为属于当前协议限制：父模型可以从文本中的错误信息判断异常，但应用层没有得到可靠的结构化 `AgentResult`。

### 14.4 子 Agent 抛出 Provider 异常

如果子 Agent 的模型请求最终抛出不可恢复的 Provider 异常，异常沿子 `AgentLoop`、`TaskTool` 和父工具执行管线向外传播。父 `AgentLoop.executeTool()` 的统一异常边界会记录完整异常，并返回一个可与父 `tool_use` 配对的失败工具结果。

当前子 Agent 不经过父 `ManualAgent`，因此不会执行父用户回合的 Provider 诊断和 history rollback 流程。

### 14.5 子 Agent 工具失败

子 Agent 的单个工具失败通常以 `ToolExecutionResult(error=true)` 进入子消息历史。子模型可以根据失败结果调整策略、重试或在最终结论中说明失败。

工具失败本身不必然终止子循环；是否继续由子模型和 `AgentLoop` 的正常工具循环决定。

### 14.6 子 Agent 背景任务未完成

如果子 Agent 在没有工具调用时准备停止，而其后台 Bash 仍在运行，子侧 `BackgroundTaskHook.onStop()` 会：

1. 阻止本次停止；
2. 等待子侧后台命令结束；
3. 收集完成结果；
4. 把任务通知加入子消息上下文；
5. 让子 Agent 再请求模型；
6. 等子模型根据结果形成最终结论。

父 Agent 只等待整个 `TaskTool` 返回，不直接消费这批子后台通知。

### 14.7 没有自动取消

当前 Subagent 设计没有独立的取消 API、超时配置或用户级子任务控制面板。父 Agent 的同步等待会持续到：

- 子 Agent 正常结束；
- 子 Agent 达到已有轮次/续写边界；
- Provider 或工具错误被现有管线转换或抛出；
- Runtime 被关闭，触发已有资源关闭行为。

Bash 本身沿用既有命令超时和进程关闭逻辑，但这不等价于整个子 Agent 有统一的端到端超时。

## 15. Hook 设计

### 15.1 父 Hook 集合

父 `HookRegistry` 当前包含：

1. `WorkspaceLoggingHook`；
2. `ToolLoggingHook`；
3. `LargeOutputHook`；
4. `TodoReminderHook`；
5. `SessionSummaryHook`；
6. `BackgroundTaskHook(parentBackgroundScheduler)`。

父 Hook 负责面向用户会话的工作区日志、Todo 提醒、会话摘要和父侧后台任务交付。

### 15.2 子 Hook 集合

子 `HookRegistry` 当前包含：

1. `ToolLoggingHook`；
2. `LargeOutputHook`；
3. `BackgroundTaskHook(subagentBackgroundScheduler)`。

子侧不注册父级工作区日志、Todo 提醒或 Session Summary Hook。这样子任务不会触发父会话专属的回合行为。

### 15.3 为什么 HookRegistry 必须独立

父子共用同一个 `AgentLoop` 类，但不能共用同一个 Hook 集合：

- 父 `UserPromptSubmit` 只属于真实用户回合；
- 父 Todo 只描述用户任务整体进度；
- 父 Session Summary 不应把子任务中间历史当作父会话内容；
- 父后台任务 Hook 不能消费子后台队列；
- 子 Agent 需要保持简洁的局部执行行为。

共享 Hook 实例本身是可以的，例如当前日志 Hook 和大输出 Hook 被父子两个 Registry 注册；真正需要隔离的是 Registry 的组成和触发范围。

## 16. 可观测性设计

### 16.1 Trace 层级

父子 Agent 使用同一套 `AgentLoop` 埋点边界：

```text
agent.run                       父 Agent
└── llm.call <model>
    └── tool.execute task
        └── agent.run            子 Agent
            └── llm.call <model>
                └── tool.execute <child-tool>
```

如果子 Agent 继续调用 Bash 或文件工具，对应的 `tool.execute` 出现在子 `agent.run` 下。子 Agent 的终端静默不影响 Trace 产生。

### 16.2 Span 职责

| Span | 覆盖范围 |
| --- | --- |
| `agent.run` | 一次父或子 AgentLoop 从进入到最终返回的完整生命周期 |
| `llm.call <model>` | 一次模型请求以及完整流消费过程 |
| `tool.execute <name>` | 一个完整工具调用的 Hook、审批、执行和结果构造管线 |

`task` 的 `tool.execute task` Span 覆盖同步等待子 Agent 的时间，因此可以直接观察父侧委派成本和子侧 `agent.run` 的嵌套关系。

### 16.3 日志与终端记录

工具日志通过日志框架记录，父终端 transcript 记录父侧 stdout。子 Agent 的模型流由静默打印器接收，但子 Agent 的工具执行仍可能产生日志记录；日志可见性和终端可见性是两个不同层次。

诊断时应使用 Trace、日志和父侧工具结果共同判断，不能因为终端看不到子中间过程就认为子 Agent 没有执行工具。

## 17. 关键设计决策与取舍

### 17.1 复用 `AgentLoop`，不另建 `SubagentLoop`

父子模型请求、流式解析、工具调用协议、上下文治理和恢复机制本质相同。复用 `AgentLoop` 可以让父子保持同一协议生命周期，并通过注入对象差异实现能力隔离。

代价是 `AgentLoop` 的职责仍然较宽，父子差异需要通过 Runtime 装配和白名单表达，而不是通过两个类名直观表达。当前这个代价低于复制一套模型循环并承担行为漂移。

### 17.2 每次调用新建消息列表，不复制父历史

这样可以用最少的状态表达清晰的上下文隔离。它也降低子任务输出过长对父上下文的直接影响。

代价是父模型必须主动把所需背景写入 `description`，且父 Agent 需要在结果返回后自行验证，不会自动得到子 Agent 的全部证据链。

### 17.3 共享 Session 状态，不复制路径和审批配置

父子属于同一次 CLI Session，应在同一个工作区和审批政策下行动。共享 `AgentState` 可以保证审批模式更新、workspace、allowed roots 和 Git 根目录语义一致。

代价是子 Agent 可以对父工作区产生真实副作用，且父子不能天然拥有两套互不影响的权限策略。当前通过工具白名单和共享 Gate 控制，而不是引入第二份 Session。

### 17.4 子侧最小工具白名单

只开放文件工具和 Bash，足以支持多数代码检查与局部修改，同时阻断：

- 递归 Subagent；
- 父级 Todo 污染；
- 持久化任务 owner 伪造；
- Skill 和 MCP 的额外能力扩张。

代价是部分需要父级专用能力的工作不能直接交给子 Agent，必须由父 Agent 自己执行或先在委派前完成必要准备。

### 17.5 同步结果而不是异步消息

同步结果让父 Agent 的历史协议保持标准的 `tool_use/tool_result` 配对，不需要为异步通知增加新的消息类型。

代价是父 Agent 会被子任务耗时阻塞，无法在子任务运行期间独立完成最终回答。异步化需要单独定义任务生命周期、取消、恢复和通知关联，不应仅通过线程池改造实现。

### 17.6 子 Agent 静默中间输出

用户通常只需要看到父 Agent 的主流程和最终的委派结果。静默可以避免父终端被多个模型流、工具详情和思考过程交错占满。

代价是调试时不能只看终端，需要通过 Trace、日志或额外诊断方式查看子执行过程。

### 17.7 不在当前设计中引入结构化 `AgentResult`

当前 `AgentLoop.run()` 返回 `String`，`TaskTool` 也继续返回文本工具结果。保持这一点可以避免在 Subagent 设计之外同时引入新的成功、失败、部分完成和取消协议。

代价是轮次耗尽等错误可能以文本形式返回，应用层无法稳定区分正常结论和错误结论。这是已知限制，后续如要解决，应单独设计结构化结果协议。

## 18. 必须保持的不变量

以下不变量是 Subagent 设计的核心验收标准：

### 18.1 上下文不变量

1. 每一次 `task` 调用都从一份新的子消息列表开始。
2. 子消息列表初始只包含一条由 `description` 构成的 user 消息。
3. 父 history 不因子 Agent 执行而增加子 Agent 的中间消息。
4. 子 Agent 返回后，子 history 不进入父 `ManualAgent.history`。
5. 子 Agent 不使用父 Memory 召回内容，也不写入长期记忆。

### 18.2 能力不变量

1. 父 `ToolRegistry` 注册 `TaskTool`。
2. 子 `ToolRegistry` 不注册 `TaskTool`。
3. 子 Agent 只能看到当前子侧白名单工具定义。
4. 子 Agent 不拥有父级持久化任务、Todo、Skill 和 MCP 工具。
5. 工具能力由 Runtime 装配确定，不能通过 `description` 动态扩大。

### 18.3 Session 不变量

1. 父子使用同一个 `AgentState`。
2. 父子使用同一个工作区和路径上下文。
3. 父子工具审批都进入同一个 `ToolApprovalGate`。
4. 审批模式在每次工具调用时从当前状态读取。
5. 子 Agent 的共享工作区副作用对父 Agent 后续工具可见。

### 18.4 生命周期不变量

1. `TaskTool` 在子 Agent 返回前不返回。
2. 子 Agent 的后台任务只由子侧调度器和 Hook 管理。
3. 父 Agent 不直接消费子 Agent 的后台完成队列。
4. 子 Agent 返回的最终文本只能通过父 `task` 工具结果进入父模型。
5. 父子 Agent 都使用统一的 `AgentLoop` 模型/工具协议边界。

### 18.5 可见性不变量

1. 子模型的 thinking、正文、工具调用和工具结果默认不写入父终端。
2. `Subagent spawned/done` 标记属于本地诊断，不属于模型历史。
3. 子 Agent 的静默输出不应破坏 Trace 和日志。
4. 父模型仍能在工具结果中得到子 Agent 最终结论。

## 19. 典型场景

### 19.1 只读代码审查

父模型委派：

```text
请检查 src/auth 下的异常处理，找出可能吞掉错误的路径。
只读分析，不修改文件。返回文件、行号、原因和建议。
```

执行结果：

```text
父模型 → task(description)
       → 子 Agent 使用 glob/read_file
       → 子 Agent 返回审查报告
       → 父模型收到 task tool_result
       → 父模型决定是否向用户报告或继续验证
```

父历史中不会出现子 Agent 读取每个文件的完整中间过程，只保留最终工具结果文本。

### 19.2 局部实现并验证

父模型委派：

```text
为 UserValidator 增加邮箱格式校验，运行相关测试。
只修改 validator 及对应测试，不要修改公共接口。
返回修改文件、测试命令和测试结果。
```

子 Agent 可以读取代码、编辑文件并运行 Bash 测试。修改直接发生在共享 workspace 中。子 Agent 返回后，父 Agent 应再次读取 diff 或运行验证，不能只依据一句“已完成”结束用户任务。

### 19.3 子 Agent 使用后台 Bash

子 Agent 委派期间启动一个后台测试命令：

```text
父 task
  └── 子 Agent
       ├── bash(run_in_background=true) → child bg_0001
       ├── 继续处理其他子侧步骤
       ├── Stop Hook 发现 bg_0001 未交付
       ├── 等待并注入 child bg_0001 结果
       └── 返回综合后的最终结论
```

父侧不会看到 `child bg_0001` 的后台通知，也不会把它当成父侧 `bg_0001`。

### 19.4 委派描述不足

如果父模型只传：

```text
帮我处理一下。
```

子 Agent 只能根据当前 workspace 和这句描述猜测目标，结果质量不可保证。系统当前不会自动补齐父历史，因此清晰、完整的 description 是委派协议的重要组成部分。

### 19.5 子 Agent 试图继续委派

子 Prompt 明确要求不要继续委派，且子工具表没有 `task`。即使模型输出未知的 `task` 工具调用，`ToolRegistry` 也不会找到对应实现，最终只能返回 unknown tool 错误，不能形成递归子 Agent。

## 21. 验收标准

### 21.1 基础委派

- 父模型调用 `task` 后出现 `[Subagent spawned]` 和 `[Subagent done]`；
- 子 Agent 能够完成一个无需工具的简单问题；
- 父 Agent 收到子 Agent 的最终文本并继续请求模型；
- 父终端不显示子 Agent 的 thinking 和中间工具过程。

### 21.2 上下文隔离

- 子 Agent 初始只收到委派 description；
- 父历史不出现子 Agent 的中间消息；
- 子 Agent 不读取父 Memory 召回内容；
- 多次 `task` 调用之间不共享上一调用的子 history；
- 子 Agent 返回后不会留下可供下一次调用复用的对话历史。

### 21.3 工具白名单

- 父 Agent 可以看到 `task`、Todo、持久化任务、Skill 和当前 MCP 工具；
- 子 Agent 只能看到 Bash、文件读取、文件写入、文件编辑和 glob；
- 子 Agent 无法调用 `task` 形成递归；
- 子 Agent 不会直接修改父 Todo 或持久化任务状态。

### 21.4 权限和工作区

- 父子工具都读取同一个 `AgentState`；
- 审批模式改变后，父子后续工具调用使用新模式；
- ASK 模式下父子共享 Scanner 时不会同时消费输入；
- 子 Agent 的文件修改发生在当前共享 workspace；
- 文档和测试不把 Bash 错误描述为已获得 OS 级沙盒。

### 21.5 后台任务隔离

- 子 Agent 的后台 Bash 由子侧调度器登记；
- 子 Agent 结束前会等待并接收自己的后台结果；
- 父侧后台完成队列不出现子 Agent 的任务通知；
- 父 Agent 最终只收到子 Agent 综合后的结论。

### 21.6 可观测性

- Trace 中能看到父 `agent.run`；
- `task` 出现为父侧 `tool.execute task`；
- 子 Agent 作为嵌套的 `agent.run` 出现；
- 子 Agent 内部模型请求和工具调用归属于子 `agent.run`；
- 子侧静默输出不影响 Span 层级和 Trace ID 关联。

## 22. 已知限制与暂不处理范围

### 22.1 没有结构化子 Agent 结果

当前只返回 `String`。正常完成、轮次耗尽和部分错误可能都通过文本体现，父工具层没有统一的结构化状态、错误码或部分完成字段。

### 22.2 没有独立子任务取消

父 Agent 在同步等待子 Agent。当前没有单独取消某个子任务、查看子任务进度或向运行中的子 Agent 追加消息的接口。

### 22.3 没有异步 Subagent

后台 Bash 的异步能力不应被误认为异步 Subagent。若将来需要异步委派，需要另行定义持久化身份、通知关联、父历史注入、重启恢复、超时和取消协议。

### 22.4 没有并行 Subagent

当前 `TaskTool` 作为前台独占工具执行。同一父模型响应中的多个 `task` 不并行。未来并行化前需要先解决共享文件写冲突、审批交互、客户端并发额度和子循环复用问题。

### 22.5 没有 worktree 隔离或自动回滚

子 Agent 和父 Agent 共享工作区。子 Agent 修改文件后，即使其最终文本返回失败，修改也不会自动撤销。

### 22.6 没有自动事实验证

父 Agent 收到子结论后负责验证。系统不会自动读取 diff、重跑测试或判断子 Agent 的文本是否准确。

### 22.7 子 Agent 没有 MCP、Skill 和父级任务能力

这是当前最小白名单的有意限制，不应在未明确需求的情况下通过“复用父 ToolRegistry”放开。

## 23. 后续演进的前置条件

以下方向可以作为未来独立设计，但不属于当前 Subagent 设计的既定内容：

- 结构化 `AgentResult`：区分 completed、failed、cancelled、partial 等状态；
- 异步 Subagent：定义任务 ID、通知和父会话恢复；
- 并行 Subagent：定义资源、审批和工作区冲突模型；
- 独立 worktree：定义子任务交付、diff 合并和失败清理；
- 子 Agent 可选工具能力：定义能力模板和审批继承规则；
- 可恢复子任务：定义持久化上下文、重启恢复和生命周期归属；
- 受控的父子结果协议：区分事实、建议、修改摘要和验证证据。

这些方向会改变当前同步、共享 workspace、字符串结果和单一子循环的设计边界，进入实现前必须形成新的需求和技术评审文档。

## 24. 结论

当前 Subagent 的本质是：

> 在同一个 Session 和工作区内，由父 Agent 通过 `task` 工具同步调用一个拥有独立消息历史和最小工具白名单的子 `AgentLoop`，子 Agent 完成局部工作后只返回最终文本，父 Agent 保留最终控制权。

这个设计用较少的新增状态获得了三个直接收益：

1. 子任务中间上下文不会污染父会话；
2. 父子 Agent 仍共享真实项目环境和当前 Session 政策；
3. 父子使用同一套模型/工具循环和可观测性边界，不需要维护两套执行协议。

同时，它明确承认当前系统仍然是同步、共享工作区、字符串结果的轻量委派模型，而不是具备异步调度、沙盒、事务回滚和多 Agent 协作协议的完整平台。后续扩展应围绕这些边界单独设计，避免把未实现的能力提前当成现状。
