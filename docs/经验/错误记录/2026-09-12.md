# 2026-09-12 错误记录

## 12:58 Memory 结构化提取请求被百炼返回 400

### 尝试了什么

使用 `QuillithMemoryAgent` 正式运行 LongMemEval Case `edced276`。Runtime 成功启动并回放 2 个 Session、9 个 Turn，但每次后台记忆提取都收到：

```text
com.anthropic.errors.BadRequestException: 400: Unknown
```

最终显式 Memory 收尾仍有 9 个 pending task，Trial 在最终问题和 Judge 执行前结束。归档中只有 `memory-work.db` 和 `sessions.db`，没有生成 Memory 文件。

### 为什么不行

`MemoryExtractor` 使用 Anthropic Java SDK 的 `outputConfig(responseType)` 请求结构化输出。当前模型 `qwen3.5-flash` 在百炼 Anthropic 兼容接口中使用普通 JSON 模式，该模式要求 system 或 messages 显式包含不区分大小写的 `JSON` 关键词。

现有提取提示词描述了字段结构，但没有出现 `JSON`，因此请求不满足服务端约束。SDK 将响应包装成 `400: Unknown`，隐藏了服务端原始错误正文，使问题最初看起来像网络、密钥或地址异常。

使用同一个 `DASHSCOPE_API_KEY`、Base URL 和模型执行最小对照请求后得到：

```text
普通消息请求                              200
结构化请求，提示词不含 JSON              400
相同结构化请求，提示词包含 JSON          200
```

400 的原始响应明确指出：

```text
'messages' must contain the word 'json' in some form
```

因此根因是 Quillith 请求构造不符合目标模型的兼容接口约束，不是 API Key、网络或 Base URL 错误，也不是服务商临时故障。

### 最终采用什么方式

在 `MemoryExtractor` 的 system prompt 中明确要求返回符合指定结构的 JSON 对象，不改变模型、密钥、Base URL、重试策略或 Memory 协议。

同时在 `MemoryBackgroundProcessorTest` 中复用现有本地 Provider，检查 Anthropic SDK 最终发送的请求体确实包含 `JSON`，避免以后修改提示词时再次破坏服务端前置条件。

定向测试结果：

```text
Tests run: 5, Failures: 0, Errors: 0, Skipped: 0
```

没有用重复正式评测验证确定性的请求格式错误。
