# 2026-09-05 错误记录

## 19:23 Harbor 0.21.0 在 Windows 上无法读取官方 UTF-8 task.toml

### 尝试了什么

将 Harbor Cookbook 固定提交 `e093c9a860b988d9d74901010ddddb9c7f124f92` 中的完整 `multi-step` recipe 复制到本地，仅为 Dockerfile 增加 Quillith 必需的 Git 和 Java 21 Runtime，然后通过现有 launcher 使用 `--resume-trajectory` 启动验证。

### 为什么不行

Harbor 0.21.0 在创建 Job 前校验任务目录时，通过 `Path.read_text()` 读取 `task.toml`，没有显式指定 UTF-8。在当前 Windows 环境中默认编码为 GBK，而官方文件包含 U+2014 EM DASH，因此抛出：

```text
UnicodeDecodeError: 'gbk' codec can't decode byte 0x94 in position 1064: illegal multibyte sequence
```

失败发生在 `Task.is_valid_dir()`，早于环境构建、Agent 安装和第一个 step。它不是 Quillith Session、Dockerfile、模型调用或 verifier 失败。

### 最终采用什么方式

没有修改官方任务或设置进程级 `PYTHONUTF8`。在当前实际生效的 Harbor 0.21.0 中，将任务运行链读取 `task.toml` 和 instruction 的 `Path.read_text()` 调用明确改为 `read_text(encoding="utf-8")`。

修复后 `Task.is_valid_dir()`、`Task()` 和三个 `step_instruction()` 均能读取官方任务，后续 Job 成功创建。该修改位于 uv 安装的 `site-packages`，重新安装或升级 Harbor 会覆盖它。

## 22:36 Ubuntu 包仓库返回 502 导致环境构建失败

### 尝试了什么

修复 Harbor UTF-8 读取后，原样重新运行官方 multi-step task。

### 为什么不行

Docker 构建已经成功完成 `apt-get update` 并下载大部分依赖，但 Ubuntu 仓库获取 `libkrb5support0_1.20.1-6ubuntu2.8_amd64.deb` 时返回 `502 Bad Gateway`，最终 `apt-get install` 以 exit code 100 退出。

失败发生在环境构建阶段，尚未安装或执行 Quillith，与 Dockerfile 依赖声明无关。

### 最终采用什么方式

保留失败 Job `jobs/2026-09-05__22-30-32`，没有修改镜像源、增加 `--fix-missing` 或改写 Dockerfile。使用完全相同的命令重新运行，下一次构建成功。

## 22:43 Windows Git checkout 将官方 LF 改成 CRLF

### 尝试了什么

从 Harbor Cookbook 固定提交的 Windows Git 工作树复制完整 recipe，并与该工作树进行逐文件 SHA-256 比较。Job `jobs/2026-09-05__22-36-58` 中 scaffold 通过，但 implement verifier 返回 0。

### 为什么不行

Agent 生成的脚本能够正确输出 `Hello, Harbor!` 和动态读取其他名字。真正差异在官方 fixture：Windows Git `core.autocrlf` 已将 `steps/implement/tests/expected.txt` 的结尾从 LF 改为 CRLF，shell 命令替换留下 `\r`，导致 verifier 比较失败。

与同一个已被转换的工作树比较哈希，只能证明复制一致，不能证明本地字节与提交 blob 一致。

### 最终采用什么方式

使用 `core.autocrlf=false` checkout 固定提交，重新复制完整 recipe；再通过 `git hash-object --no-filters` 将每个本地文件与固定提交 blob 对比。除已确认修改的 Dockerfile 外，其余 15 个文件全部匹配，`expected.txt` 以单个 LF 结尾。

## 22:49 同步记忆提取使第三轮超过官方 60 秒 timeout

### 尝试了什么

用已恢复原始字节的官方任务运行 Job `jobs/2026-09-05__22-46-20`。三个 verifier 均为 1，三轮 PID 相同，但 document step 仍记录 `AgentTimeoutError`。

### 为什么不行

第三轮主任务和文件写入约 15 秒完成。`AgentSession.submit()` 在主循环返回后还会同步执行 `memoryRuntime.completeTurn()`，只有记忆提取完成后 `HarborRunner` 才向 FIFO 写入 `OK`。本轮完整 submit 超过官方 document step 的 60 秒 timeout，Harbor 先取消了等待响应的进程。

Verifier 仍能看到已写完的 README 并给出 1，但 reward 通过不能抵消 Agent timeout，因此该 Job 不能作为无异常验收结果。

### 最终采用什么方式

保持 Memory 开启并保持官方 task 不变。运行时增加 Harbor 原生参数 `--agent-timeout-multiplier 2`。最终 Job `jobs/2026-09-05__22-52-38` 在 2 分 53 秒内完成，三个 step reward 均为 1、异常数为 0，三轮 PID 均为 67。
