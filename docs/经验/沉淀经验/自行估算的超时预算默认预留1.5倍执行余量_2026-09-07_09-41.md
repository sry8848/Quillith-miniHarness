# 自行估算的超时预算默认预留 1.5 倍执行余量

## 规则

如果超时时间由执行者自行估算，并且没有用户要求、官方用例或外部协议规定固定值，首次运行就使用估算耗时的 1.5 倍作为超时预算。

```text
执行超时 = 估算耗时 × 1.5
```

用户明确指定、官方用例固定或协议约定的超时不能擅自放大。实际触发这类超时时，应记录证据并由需求方决定是否修改。

## 原因

自行估算超时时，容易只计算理想路径或最近一次可见耗时，却遗漏正常波动：

- Windows 进程调度和文件系统开销。
- Docker 镜像、容器及 JVM 的冷启动开销。
- 首次构建、依赖缓存和磁盘 I/O 波动。
- 模型响应时间和外部服务延迟的自然变化。
- 日志收集、verifier 以及进程退出清理所需的尾部时间。

“预计需要 60 秒”通常只是中心值附近的判断，并不适合作为 60 秒的失败边界。超时是异常判定边界，不是期望性能指标；把二者设为同一个数，会把正常的慢执行误判为失败。

实际执行中已经反复出现第一次因预算不足而失败、提高到约 1.5 倍后正常完成的情况。继续使用较小预算会制造一次可预见的无效失败，并增加重复构建、重复调用和人工等待成本。

## 做法

1. 先判断超时是外部规定，还是由我们自行估算。
2. 自行估算时，默认使用估算值的 1.5 倍。
3. 预算覆盖冷启动、核心执行、验证和退出清理的完整链路。
4. 记录实际耗时和超时发生阶段，用真实数据修正后续预算。
5. 有稳定历史数据后，使用历史高分位耗时校准预算，不再长期依赖主观估算。

1.5 倍是根据当前实际偏差得到的默认起点，不是假装精确的永久常数。不能使用无限超时掩盖死锁、阻塞或进程退出检测缺失；超过合理余量仍未完成时，应调查真实根因。

## 验证

- 确认自行估算的超时已经包含 1.5 倍默认余量。
- 确认预算覆盖完整执行链路，而不只是核心步骤。
- 记录实际耗时及超时发生位置。
- 确认放大预算没有掩盖已知的死锁、阻塞或协议错误。
