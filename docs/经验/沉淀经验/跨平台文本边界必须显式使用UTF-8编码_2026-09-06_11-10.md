# 跨平台文本边界必须显式使用 UTF-8 编码

## 规则

文本跨越文件、Git、Python、Shell、Docker、Java 或进程标准流时，必须在我们控制的边界上显式声明 UTF-8，不能依赖操作系统、locale 或运行时默认值。

## 原因

文本每跨过一次边界，都会发生一次“字节与字符如何转换”的选择。Python、Java、Shell 和容器采用的默认值可能不同，因此同一段代码可能在开发机正常，进入 Windows、Linux 或精简容器后产生乱码或直接失败。

本次 Harbor 验证出现了两个典型问题：

- Python 使用 `Path.read_text()` 等接口但没有指定 `encoding`，在 Windows 上可能按本地代码页读取本应为 UTF-8 的任务文件。
- Java 进程的 `file.encoding` 虽然是 UTF-8，但精简容器使用 POSIX locale，`stdout.encoding` 和 `stderr.encoding` 实际为 `ANSI_X3.4-1968`。中文在写入日志前就被替换为 ASCII 问号。日志里的 `?` 是真实的 `0x3F` 字节，不是查看工具的显示问题。

## 做法

Python 在具体文件入口直接声明编码：

```python
task_text = task_path.read_text(encoding="utf-8")
```

Java 进程显式声明标准输出和标准错误编码：

```text
-Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8
```

容器环境同时明确 UTF-8 locale：

```text
LANG=C.UTF-8
LC_ALL=C.UTF-8
```

不要用 `errors="ignore"` 或 `errors="replace"` 掩盖问题，因为它们会静默丢失信息。全局设置 `PYTHONUTF8` 可以作为运行环境约束，但不能代替明确文件协议入口上的 `encoding="utf-8"`。

## 验证

- 对文件执行严格 UTF-8 解码，不允许自动替换非法字节。
- 检查日志原始字节，区分真实的 `?` 与显示工具生成的替换字符。
- 检查进程实际编码；Java 除了 `file.encoding`，还要检查 `native.encoding`、`stdout.encoding` 和 `stderr.encoding`。
- 在 Windows 宿主机和 Linux 容器之间执行一次真实的端到端验证。
