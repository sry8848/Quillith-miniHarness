# 验证官方文件原样引入时必须比较 Git 提交 Blob 而不是工作树

## 规则

验证“官方文件原样引入”时，必须以指定提交中的 Git blob 为基准，并比较目标文件的真实字节；不能将任意一次本地检出的源工作树作为真实性基准。

## 原因

Git 提交中的 blob 保存仓库对象的内容，检出的工作树文件则可能被 `.gitattributes`、`core.autocrlf` 等规则转换。二者看起来可能完全相同，实际字节却不同。

本次官方任务的 `expected.txt` 在提交 blob 中使用 LF，Windows 检出后被转换为 CRLF。Shell 命令替换只移除了结尾的 LF，残留的 `\r` 导致 verifier 比较失败。Agent 生成的业务结果正确，但测试仍返回 0 分。

调查初期曾将目标副本与已经经过 Windows 检出转换的源工作树比较。两边哈希一致，只能证明它们经历了相同转换，不能证明目标文件与官方提交中的 blob 一致。

## 做法

处理“原样引入”、精确复现或对换行敏感的测试夹具时，应明确区分：

1. 仓库声明的逻辑文本规则。
2. Git 提交中 blob 的原始字节。
3. 当前操作系统上的工作树表示。

导入官方任务时，使用关闭自动换行转换的检出，或者直接从 Git blob 提取文件。

校验时比较固定提交的 blob 与目标文件的真实字节：

```powershell
git rev-parse "<commit>:<path>"
git hash-object --no-filters "<copied-file>"
```

不能省略 `--no-filters`。普通 `git hash-object` 可能应用 clean 过滤或换行归一化，使 CRLF 文件得到与 LF blob 相同的对象哈希，从而隐藏真实差异。

对于自己维护的跨平台仓库，使用 `.gitattributes` 明确关键文件的换行协议，例如：

```gitattributes
*.sh text eol=lf
```

只有语义确实依赖精确 LF 的测试夹具才增加相应规则，不无依据扩大配置范围。

## 验证

- “原样引入”的验收基准使用固定提交的 blob，不使用源工作树。
- 对换行敏感文件检查原始字节，明确区分 LF 与 CRLF。
- 哈希目标文件时禁用 Git 过滤器，防止归一化掩盖差异。
- verifier 异常时同时检查被测输出和期望文件，避免把夹具字节问题误判为 Agent 行为错误。
