# 使用兼容接口的新能力前必须验证最终请求和服务端约束

## 规则

通过兼容接口使用结构化输出、工具调用、流式响应等能力前，必须针对实际的服务商、端点和模型验证最终 HTTP 请求与服务端约束。

SDK 能够构建某个参数，只证明客户端支持生成该请求，不证明目标兼容接口或目标模型完整支持相同语义。

## 原因

兼容接口通常只兼容主协议，并可能按模型系列对扩展能力采用不同实现。同一个参数可能在某些模型上严格执行 JSON Schema，在另一些模型上退化为普通 JSON 模式并增加额外的提示词约束。

类型安全和编译成功无法发现这类差异。SDK 还可能在异常映射时丢失服务商的原始错误正文，使明确的参数错误表现为笼统的 `400: Unknown`。如果只看异常类型，很容易误判为密钥、地址、网络或服务商故障，并通过无效重试制造更多请求。

本次问题中，Anthropic Java SDK 正常生成了 `output_config`，但 `qwen3.5-flash` 对应的百炼普通 JSON 模式要求提示词包含 `JSON`。请求缺少该关键词，因此所有 Memory extraction 都被确定性拒绝。

## 做法

1. 固定诊断对象：记录实际服务商、Base URL、模型和 SDK 版本，不用其他模型的成功结果代替验证。
2. 查阅服务商官方文档，确认目标模型对该能力的支持层级、必填参数和提示词约束。
3. 检查 SDK 最终序列化的 HTTP 请求，而不只检查本地 builder 调用或对象类型。
4. 使用相同密钥、端点和模型执行最小对照：普通请求、当前能力请求、满足文档约束后的能力请求。
5. 捕获状态码和脱敏后的原始错误正文；不要只保留 SDK 转换后的异常消息。
6. 修复服务端要求的最小前置条件，不通过换网络、增加重试或更换密钥掩盖确定性的 4xx 参数错误。
7. 为最终请求体增加契约测试，确保后续重构或提示词修改不会移除服务端必需字段或关键词。

## 验证

- 相同密钥、端点和模型的普通请求成功，证明基础连接和鉴权可用。
- 不满足约束的能力请求稳定失败，错误正文与官方文档一致。
- 只补齐目标约束后请求成功，期间不改变密钥、端点、模型或网络。
- 自动测试检查最终发送请求，而不是只检查某个本地常量。
- 对确定性 4xx 不执行盲目重试；失败原因能够在日志中直接定位到请求约束。
