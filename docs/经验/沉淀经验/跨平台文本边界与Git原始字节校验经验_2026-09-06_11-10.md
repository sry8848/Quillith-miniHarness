# 跨平台文本边界与 Git 原始字节校验经验

## 背景

在 Windows 宿主机、Git、Python、Shell、Docker 和 Java 共同参与的执行链路中，文本会跨越多个进程与文件系统边界。此次 Harbor 多轮任务验证暴露出的编码乱码和校验失败，并不是孤立的环境偶发现象，而是两个可以复用的工程问题：把平台默认值误当成协议，以及把 Git 工作树误当成提交中的原始内容。

## 1. 文本边界必须显式声明编码

### 根因

文本每跨过一次边界，都会发生一次“字节与字符如何转换”的选择。如果代码没有明确指定，Python、Java、Shell 和容器会各自采用当前平台或区域设置的默认值。这些默认值在 Windows、Linux 和精简容器中并不一致，因此同一段代码可能在开发机正常、进入容器后产生乱码或直接失败。

本次问题中有两个典型表现：

- Python 使用 `Path.read_text()` 等接口但未指定 `encoding`，在 Windows 上可能按本地代码页读取本应为 UTF-8 的任务文件。
- Java 进程虽然 `file.encoding` 是 UTF-8，但精简容器的区域设置是 POSIX，`stdout.encoding` 和 `stderr.encoding` 实际为 `ANSI_X3.4-1968`。中文在写入日志之前就被不可逆地替换成了 ASCII 问号。日志中的 `?` 是真实的 `0x3F` 字节，并不是查看工具显示错误。

### 经验规则

编码是跨边界协议的一部分，不能依赖机器默认值。凡是由我们控制的边界，都应明确约定：

- 文本文件统一使用 UTF-8 读写。
- Linux 脚本和依赖精确字节的测试夹具使用 LF。
- 子进程标准输出和标准错误明确使用 UTF-8。
- 容器明确设置 UTF-8 locale；Java 启动参数明确设置 `stdout.encoding` 和 `stderr.encoding`。

Python 应在具体文件入口直接写明编码，例如：

```python
task_text = task_path.read_text(encoding="utf-8")
```

Java 进程应显式声明输出编码，例如：

```text
-Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8
```

容器环境宜同时明确：

```text
LANG=C.UTF-8
LC_ALL=C.UTF-8
```

不应使用 `errors="ignore"`、`errors="replace"` 等方式掩盖问题。它们虽然能让流程继续运行，却会静默丢失信息，使后续日志和验证结果不再可信。全局设置 `PYTHONUTF8` 也只能作为运行环境约束，不能替代在明确的文件协议边界上写出 `encoding="utf-8"`。

### 验证方法

- 对文件执行严格 UTF-8 解码，不允许自动替换非法字节。
- 检查日志原始字节，区分真实的 `?` 与显示器产生的替换字符。
- 检查进程实际使用的输入、输出编码；Java 不能只看 `file.encoding`，还要看 `native.encoding`、`stdout.encoding` 和 `stderr.encoding`。
- 在 Windows 宿主机和 Linux 容器之间做一次真实端到端验证，不能只验证单个平台。

## 2. Git blob 与工作树不是同一个字节来源

### 根因

Git 提交中的 blob 保存仓库对象的内容，检出的工作树文件则可能被 `.gitattributes`、`core.autocrlf` 等规则转换。二者在视觉上可能完全相同，实际字节却不同。

本次官方任务的 `expected.txt` 在提交 blob 中使用 LF。Windows 检出后被转换为 CRLF；Shell 命令替换只移除了结尾的 LF，残留的 `\r` 导致 verifier 比较失败。Agent 生成的业务结果是正确的，但测试仍返回 0 分。

调查初期还出现了一个误判：将目标副本与已经经过 Windows 检出转换的源工作树比较，哈希一致便认为“官方文件保持原样”。实际上两边都可能已经被同一种规则转换，这种比较无法证明它们与官方提交中的 blob 一致。

### 经验规则

处理“原样引入”“精确复现”或对换行敏感的测试夹具时，必须区分三层内容：

1. 仓库声明的逻辑文本规则。
2. Git 提交中 blob 的原始字节。
3. 当前操作系统上的工作树表示。

官方任务的真实性应以指定提交中的 blob 为基准，而不是以任意一次本地检出的文件为基准。导入时应使用关闭自动换行转换的检出，或直接从 Git blob 提取文件。

校验时应比较目标文件的真实字节与提交 blob，避免 Git 过滤器再次归一化内容。例如：

```powershell
git rev-parse "<commit>:<path>"
git hash-object --no-filters "<copied-file>"
```

不能省略 `--no-filters`。普通 `git hash-object` 可能应用 clean 过滤或换行归一化，使 CRLF 文件得到与 LF blob 相同的对象哈希，从而隐藏真实差异。

对于我们自己维护的跨平台仓库，应使用 `.gitattributes` 明确关键文件的换行协议，例如：

```gitattributes
*.sh text eol=lf
```

只有语义确实依赖精确 LF 的测试夹具才应增加相应规则，不应无依据地扩大配置范围。

### 验证方法

- “原样复制”的验收基准使用固定提交的 blob，不使用源工作树。
- 对换行敏感文件检查原始字节，明确区分 LF 与 CRLF。
- 哈希目标文件时禁用过滤器，防止归一化掩盖差异。
- verifier 异常时同时检查被测输出和期望文件，避免把夹具字节问题误判成 Agent 行为错误。

## 最小检查清单

- 所有明确的文本入口是否指定 UTF-8？
- 容器 locale 和进程标准输出编码是否明确？
- Linux 脚本及字节敏感夹具是否为 LF？
- “官方原样”是否以固定提交 blob 为基准？
- 文件哈希是否使用了不经过 Git 过滤的真实字节？
